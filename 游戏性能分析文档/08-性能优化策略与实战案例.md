# 游戏性能分析 — 性能优化策略与实战案例

> 本文档是「游戏性能分析」系列文档的第 **8** 篇（终篇），系统梳理 CPU/GPU/内存三大维度的常见优化模式，通过典型实战案例串联前 7 篇文档的分析方法论，并提供可落地的最佳实践清单。

## 1. 优化策略框架

### 1.1 优化优先级原则

性能优化不是"什么快做什么"，而是有明确的优先级排序：

```
优化优先级金字塔 (从下到上):

                    ┌───────────┐
                    │ 微观优化   │ ← 最后: 位运算/内联/寄存器
                    │ (指令级)  │   收益小, 可读性差
                    ┌───────────┐
                    │ 算法优化   │ ← 其次: 换数据结构/算法
                    │ (复杂度)  │   O(n²)→O(n log n) 收益大
                    ┌───────────┐
                    │ 架构优化   │ ← 优先: 数据布局/并行/批处理
                    │ (系统级)  │   AoS→SoA, 串行→并行
                    ┌───────────┐
                    │ 减少工作   │ ← 首要: 少做不必要的事
                    │ (需求级)  │   剔除/LOD/降分辨率 收益最大
                    └───────────┘

核心原则:
├─ 先减少工作量, 再优化执行效率
├─ 先解决最大瓶颈, 再处理次要瓶颈
├─ 先测量, 后优化 (永远不要猜测)
├─ 先验证, 后提交 (A/B 对比)
└→ 80/20 法则: 20% 的优化解决 80% 的性能问题
```

### 1.2 优化决策矩阵

| 瓶颈类型 | 减少工作 | 架构优化 | 算法优化 | 微观优化 |
|---------|---------|---------|---------|---------|
| **CPU 热点** | 降低更新频率 | SoA/Job System | 换算法/空间分区 | SIMD/内联/分支消除 |
| **GPU 像素** | 降分辨率/LOD | Z-Pre-Pass | 合并 Shader Pass | 减少纹理采样/寄存器 |
| **GPU 几何** | 剔除/LOD | 合批/Instancing | 空间分区 | 顶点缓存优化 |
| **GPU 带宽** | 纹理压缩/减少 RT | 资源别名 | 带宽排序 | ASTC/BCn |
| **内存** | 减少资源量 | 对象池/分配器 | 换数据结构 | 缓存行对齐 |
| **功耗** | 降帧率/降负载 | 异步计算 | — | — |

## 2. CPU 优化模式

### 2.1 减少更新频率

```
模式: 分级更新 (Variable Tick Rate)

问题: 1000 个 AI 实体每帧 Tick → CPU 10ms
优化: 分级 Tick, 近处高频, 远处低频

┌──────────────────────────────────────────────────┐
│  距离玩家         │ Tick 频率    │ 实体数 │ 总开销 │
├──────────────────┼─────────────┼────────┼────────┤
│  < 50m (近)      │ 每帧 (60Hz) │ 50     │ 高     │
│  50-200m (中)    │ 每3帧 (20Hz)│ 200    │ 中     │
│  200-500m (远)   │ 每6帧 (10Hz)│ 400    │ 低     │
│  > 500m (极远)   │ 每30帧 (2Hz)│ 350    │ 极低   │
└──────────────────────────────────────────────────┘

// 实现
class AIEntity {
    float tickInterval;  // 根据距离设置
    float timeAccumulator;
    
    void Update(float dt) {
        timeAccumulator += dt;
        if (timeAccumulator >= tickInterval) {
            UpdateAI(timeAccumulator);  // 用累积时间更新
            timeAccumulator = 0;
        }
    }
};

→ 1000 实体从全量 60Hz → 加权约 15Hz 等效
→ CPU 开销从 10ms 降至 ~3ms
```

### 2.2 数据导向设计

```
模式: AoS → SoA 重构

问题: 遍历 10000 实体更新位置, 缓存利用率 27%
优化: 分离热数据, 连续排列

// 改造前 (AoS):
struct Entity {
    Transform transform;   // 64B  热
    Mesh* mesh;           // 8B   冷
    Material* material;   // 8B   冷
    Health health;         // 12B  温
    AIState aiState;       // 32B  温
    // 124B/entity, 但遍历时只需要 transform
};
Entity entities[10000]; // 1.24MB, 缓存命中率低

// 改造后 (SoA):
struct EntityData {
    Transform* transforms;  // 640KB 连续, 热数据
    Mesh** meshes;           // 冷数据
    Material** materials;    // 冷数据
    Health* healths;         // 温数据
    AIState* aiStates;       // 温数据
};
EntityData entities;

// 只遍历 transforms:
for (int i = 0; i < 10000; i++) {
    entities.transforms[i].position += velocity * dt;
}
// 640KB 全部热数据, L2 缓存命中率高
// 同时可 SIMD 向量化

// 更进一步: 分组更新 (只更新活跃实体)
struct EntitySystem {
    // 连续存储活跃实体
    std::vector<Transform> activeTransforms;
    int activeCount;
    
    void Update(float dt) {
        // 只遍历活跃的
        for (int i = 0; i < activeCount; i++) {
            activeTransforms[i].position += velocity * dt;
        }
    }
};
```

### 2.3 并行化

```
模式: Job System / Task Graph

问题: 单线程逐实体更新 → 10ms
优化: 多线程并行处理

// 串行:
void UpdateAll(float dt) {
    for (int i = 0; i < count; i++) {
        UpdateEntity(entities[i], dt);
    }
}
// 1 线程, 10ms

// 并行 (Job System):
void UpdateAll(float dt) {
    JobSystem::Dispatch(count, 64, [&](int start, int end) {
        for (int i = start; i < end; i++) {
            UpdateEntity(entities[i], dt);
        }
    });
    JobSystem::Wait();  // 等待所有 Job 完成
}
// 8 线程, ~1.5ms (理论上 1.25ms, 有调度开销)

注意事项:
├─ 数据竞争: 多线程修改同一数据 → 需要分区/无锁
├─ 伪共享: 线程修改同一缓存行 → 缓存行对齐
├─ 负载均衡: 任务大小不均 → 动态分配
├─ 同步开销: 过多同步点抵消并行收益
└→ SIMD: 单条指令处理多个数据 (最后的并行化)
```

### 2.4 渲染提交优化

```
模式: 渲染命令批处理

问题: 逐物体提交 → API 调用过多

// 优化前:
for (auto& obj : objects) {
    SetPipeline(obj.pipeline);
    SetDescriptorSets(obj.material);
    SetVertexBuffers(obj.mesh);
    DrawIndexed(obj.indexCount);
}
// 5000 物体 = 20000 次 API 调用

// 优化1: 排序减少状态切换
SortByPipeline(objects);
SortByMaterial(objects);
// → Pipeline 切换从 5000 次降至 ~50 次

// 优化2: 实例化渲染
// 相同网格+材质的物体一次绘制
DrawIndexedInstanced(indexCount, instanceCount);
// 5000 物体 → 50 批次 = 200 次 API 调用

// 优化3: GPU-Driven (Multi-Draw Indirect)
vkCmdDrawIndexedIndirect(cmd, indirectBuffer, 1);
// CPU 仅 1 次 API 调用, GPU 读取所有绘制命令
// → 2 次 API 调用

优化收益:
┌──────────────────┬──────────┬──────────┬────────┐
│ 方式              │ API调用   │ CPU时间   │ 瓶颈转移│
├──────────────────┼──────────┼──────────┼────────┤
│ 逐物体提交        │ 20000    │ 10ms     │ CPU提交 │
│ 排序+实例化       │ 200      │ 2ms      │ CPU提交 │
│ GPU-Driven (MDI) │ 2        │ 0.5ms    │ GPU执行 │
└──────────────────┴──────────┴──────────┴────────┘
→ 从 CPU 提交瓶颈 → GPU 执行瓶颈
```

## 3. GPU 优化模式

### 3.1 分辨率自适应

```
模式: 动态分辨率缩放

原理: 根据帧时间动态调整渲染分辨率

┌───────────────────────────────────────────────┐
│  帧时间 > 18ms (60fps 目标 16.67ms)           │
│  → 降低渲染分辨率: 1080p → 900p               │
│  → 通过升采样(TAAU/FSR/DLSS)恢复到 1080p      │
│                                               │
│  帧时间 < 14ms                                │
│  → 提高渲染分辨率: 900p → 1080p               │
│                                               │
│  滞回控制 (避免抖动):                          │
│  ├─ 降级阈值: 18ms                            │
│  └─ 升级阈值: 14ms (留 2.67ms 余量)            │
└───────────────────────────────────────────────┘

// 实现
class DynamicResolution {
    float targetFrameTime = 16.67f;  // 60fps
    float resolutionScale = 1.0f;
    float minScale = 0.5f;  // 最低 50%
    float maxScale = 1.0f;
    
    void Update(float frameTime) {
        if (frameTime > targetFrameTime * 1.1f) {
            // 帧时间超标 → 降分辨率
            resolutionScale = max(minScale, resolutionScale - 0.05f);
        } else if (frameTime < targetFrameTime * 0.85f) {
            // 帧时间充裕 → 升分辨率
            resolutionScale = min(maxScale, resolutionScale + 0.02f);
        }
    }
};

收益:
├─ 帧时间稳定 (避免卡顿尖峰)
├─ 画质自适应 (设备能力匹配)
├─ 功耗降低 (移动端降负载)
└→ 推荐所有平台默认开启
```

### 3.2 LOD 系统

```
模式: 细节层次 (Level of Detail)

┌───────────────────────────────────────────────┐
│  距离        │ LOD级别  │ 三角形数  │ 纹理分辨率│
├─────────────┼─────────┼──────────┼──────────┤
│  < 20m      │ LOD0    │ 50,000   │ 2048     │
│  20-50m     │ LOD1    │ 20,000   │ 1024     │
│  50-100m    │ LOD2    │ 8,000    │ 512      │
│  100-200m   │ LOD3    │ 2,000    │ 256      │
│  > 200m     │ Billbd  │ 2(四边形)│ 128      │
└───────────────────────────────────────────────┘

进阶: 屏幕空间 LOD (基于像素大小)
├─ 根据物体在屏幕上的投影面积决定 LOD
├─ 比距离 LOD 更准确 (不受 FOV/分辨率影响)
├─ 屏幕面积 < 阈值 → 降级 LOD
└→ UE5 Nanite: 自动像素级 LOD, 无需手动

LOD 过渡:
├─ 硬切换 (Pop): 最简单, 但有跳变
├─ 淡入淡出 (Cross-fade): 过渡平滑, 但多渲染一次
├─ 形变过渡 (Morph): 最平滑, 但需预计算
└→ 移动端: 硬切换 (省 GPU), 高端: 淡入淡出
```

### 3.3 遮挡剔除

```
模式: Hi-Z 遮挡剔除

原理: 使用上一帧的深度金字塔剔除被遮挡物体

┌───────────────────────────────────────────────┐
│  Step 1: 上一帧深度 → 生成 Hi-Z 金字塔         │
│  ┌─────────────────────────┐                  │
│  │ Level 0: 1920×1080      │ 原始深度           │
│  │ Level 1: 960×540        │ 每级取最大值       │
│  │ Level 2: 480×270        │                   │
│  │ ...                     │                   │
│  │ Level N: 1×1            │ 最远深度            │
│  └─────────────────────────┘                  │
│                                               │
│  Step 2: GPU Compute 剔除                     │
│  for each object:                             │
│    1. 计算 AABB 在屏幕空间的投影                │
│    2. 选择 Hi-Z 金字塔对应级别                  │
│       (投影面积匹配的 Mip 级别)                 │
│    3. 采样 Hi-Z → 比较物体最远深度与遮挡深度     │
│    4. 被遮挡 → 写入剔除列表                    │
│    5. 未被遮挡 → 写入可见列表                   │
│                                               │
│  Step 3: 仅渲染可见物体                         │
└───────────────────────────────────────────────┘

收益:
├─ 室内场景: 剔除率 60-80%
├─ 城市场景: 剔除率 40-60%
├─ 开放世界: 剔除率 20-40%
├→ GPU Compute 开销 <1ms, 节省渲染 5-15ms
```

```
模式: 纹理格式与流式加载

┌──────────────────────────────────────────────────┐
│  优化项              │ 收益            │ 优先级   │
├──────────────────────┼────────────────┼─────────┤
│  未压缩→BC7/ASTC     │ 显存省 75-90%  │ ★★★    │
```

### 3.5 Shader 优化

```
模式: Shader 性能优化

┌───────────────────────────────────────────────┐
│  优化项                │ 效果                  │
├───────────────────────┼──────────────────────┤
│  消除分支发散          │ Warp 占用率↑ 20-50%  │
│  减少纹理采样          │ 带宽↓, 延迟↓         │

└───────────────────────────────────────────────┘

分支消除示例:
// 差: if/else 分支发散
if (materialType == METAL) {
    color = specular * albedo;
} else {
    color = diffuse + specular;
}
// Warp 内不同像素走不同分支 → 两分支都执行

// 好: 数据驱动, 无分支
float metalness = material.metalness;
color = lerp(diffuse + specular, specular * albedo, metalness);

半精度优化 (移动端):
// 差: 高精度计算
float3 normal = normalize(cross(edge1, edge2));  // float32

// 好: 移动端用 mediump
mediump float3 normal = normalize(cross(edge1, edge2));
// Mali/Adreno: mediump 快 2x, 寄存器减半
// 但: 精度降低, 法线/UV 用 mediump 可接受
//     位置/深度用 highp
```

### 4.2 内存池化

```
模式: 对象池 + 帧分配器

// 对象池 (固定类型复用)
template<typename T>
class ObjectPool {
    std::vector<T*> freeList;
    std::vector<std::unique_ptr<T[]>> chunks;
    size_t chunkSize;
    
public:
    T* Acquire() {
        if (freeList.empty()) {
            // 分配新块
            auto chunk = std::make_unique<T[]>(chunkSize);
            for (size_t i = 0; i < chunkSize; i++)
                freeList.push_back(&chunk[i]);
            chunks.push_back(std::move(chunk));
        }
        T* obj = freeList.back();
        freeList.pop_back();
        return new (obj) T();  // placement new
    }
    
    void Release(T* obj) {
        obj->~T();  // 析构但不释放内存
        freeList.push_back(obj);
    }
};

// 帧分配器 (每帧临时数据)
class FrameAllocator {
    char* buffer;
    size_t capacity;
    size_t offset;
    
public:
    void Reset() { offset = 0; }
    
    void* Allocate(size_t size, size_t alignment = 16) {
        size_t aligned = AlignUp(offset, alignment);
        offset = aligned + size;
        return buffer + aligned;
    }
};

// 使用:
void RenderFrame() {
    frameAlloc.Reset();  // 回收上帧临时数据
    
    // 临时数据, 帧结束自动回收
    auto* tempData = frameAlloc.Allocate(sizeof(Matrix4) * 1000);
    // ... 使用 ...
    // 无需手动释放, 下一帧 Reset 时回收
}
```

### 4.3 GPU 资源别名

```
模式: 渲染目标资源别名 (Aliasing)

问题: GBuffer + 后处理 RT + 阴影 RT = 300MB VRAM
优化: 不同 Pass 的 RT 分时复用同一块显存

┌──────────────────────────────────────────────┐
│  传统方式 (每个 RT 独立分配):                  │
│                                              │
│  Pass 1: GBuffer (4 RT)  ── 80MB ── 常驻     │
│  Pass 2: Bloom RT         ── 16MB ── 常驻     │
│  Pass 3: SSR RT           ── 16MB ── 常驻     │
│  Pass 4: TAA History      ── 16MB ── 常驻     │
│  Pass 5: Motion Vector    ── 8MB  ── 常驻     │
│  → 总计: 136MB 常驻                           │
│                                              │
│  别名方式 (分时复用):                         │
│                                              │
│  时间轴:                                      │
│  GBuffer ──写入──→ 光照读取 ──→ 释放           │
│                      │                        │
│                      ▼                        │
│  Bloom RT ←──── 复用 GBuffer 的显存            │
│  SSR RT  ←──── 复用 Bloom RT (Bloom完成后)    │
│                                              │
│  → 峰值显存: 80MB (仅 GBuffer 大小)           │
│  → 节省: 56MB (41%)                           │
└──────────────────────────────────────────────┘

Vulkan 实现:
├─ vkAllocateMemory: 大块显存
├─ vkBindImageMemory2: 多个 Image 绑定到同一块
├─ 需要正确的屏障同步 (确保前一个使用完成)
└→ FrameGraph 系统自动管理别名 (推荐)
```

## 5. 实战案例

### 5.1 案例：开放世界帧率优化

```
初始状态:
├─ 场景: 开放世界城市, 5km × 5km
├─ 设备: RTX 3060 (中端 PC)
├─ 帧时间: 28ms (35fps)
├─ 目标: 16.67ms (60fps)

分析过程:

Step 1: stat unit / 引擎 Profiler
├─ Game Thread: 10ms
├─ Render Thread: 8ms
├─ GPU: 22ms ← 最大瓶颈
└→ GPU-bound

Step 2: stat gpu / GPU Visualizer
├─ BasePass: 6ms (27%)
├─ DeferredShading: 5ms (23%)
├─ ShadowDepths: 4ms (18%)
├─ PostProcessing: 3ms (14%)
├─ Translucency: 2ms (9%)
└→ BasePass + DeferredShading 是最大开销

Step 3: RenderDoc 帧检视
├─ Draw Calls: 3,500 (过多)
├─ 三角形: 8.5M (过多)
├─ 纹理: 未压缩 RGBA8 占 4.5GB
├─ Overdraw: 城市区域 8-15x
└→ 多个问题: Draw Call/三角形/纹理/Overdraw

Step 4: NSight Graphics Range Profiler
├─ BasePass: 像素着色器 65% (瓶颈)
│   ├─ 纹理采样: 8 次/像素
│   ├─ 寄存器: 56 GPR (占用率 62%)
│   └→ 纹理采样和寄存器是问题
├─ ShadowDepths: 顶点处理 70% (瓶颈)
│   └→ 阴影投射物过多
└→ 确认: BasePass 像素瓶颈 + 阴影几何瓶颈

优化措施:

┌───────────────────────────────────────────────┐
│ 优化项               │ 帧时间变化  │ 累计    │
├──────────────────────┼────────────┼─────────┤
│ 纹理压缩 BC7        │ 28→25ms    │ 25ms    │
│ (带宽↓, 显存↓)      │ -3ms       │         │
├──────────────────────┼────────────┼─────────┤
│ LOD 系统             │ 25→22ms    │ 22ms    │
│ (三角形 8.5M→3M)    │ -3ms       │         │
├──────────────────────┼────────────┼─────────┤
│ 遮挡剔除 (Hi-Z)      │ 22→19ms    │ 19ms    │
│ (Draw Call 3500→1800)│ -3ms      │         │
├──────────────────────┼────────────┼─────────┤
│ Z-Pre-Pass + 前向排序 │ 19→17ms    │ 17ms    │
│ (Overdraw↓)          │ -2ms       │         │
├──────────────────────┼────────────┼─────────┤
│ 阴影 LOD             │ 17→15.5ms  │ 15.5ms  │
│ (阴影距离/LOD)      │ -1.5ms     │         │
├──────────────────────┼────────────┼─────────┤
│ 后处理合并 Pass      │ 15.5→15ms  │ 15ms    │
│ (5 Pass→3 Pass)     │ -0.5ms     │         │
└──────────────────────┴────────────┴─────────┘

最终: 28ms → 15ms (60+fps) ✓
```

### 5.2 案例：移动端发热降频

```
初始状态:
├─ 场景: 3D 动作游戏, 城市场景
├─ 设备: Snapdragon 8 Gen3 (Android)
├─ 冷机帧时间: 16ms (60fps)
├─ 热机 10 分钟后: 28ms (35fps)
├─ 温度: 52°C
├─ 功耗: 4.2W

分析过程:

Step 1: Snapdragon Profiler 热机分析
├─ GPU 频率: 850MHz → 450MHz (降频 47%)
├─ CPU 频率: 3.2GHz → 2.0GHz (降频 37%)
├─ GPU 时间: 10ms → 18ms (降频导致)
├─ 功耗分布:
│   ├─ GPU: 45%
│   ├─ DDR: 25% ← 带宽功耗高
│   ├─ CPU: 20%
│   └─ 其他: 10%
└→ 降频是帧时间恶化的直接原因

Step 2: 带宽分析
├─ 帧带宽: 3.2 GB/帧
├─ DDR 功耗占比 25%
├─ RenderDoc: GBuffer 4 个 RT (未压缩格式)
├─ 纹理: 部分未压缩
└→ 带宽是功耗的主要来源

Step 3: GPU 计数器分析
├─ 像素着色器: 60% (复杂 PBR Shader)
├─ 带宽: 3.2 GB/帧 (接近峰值 4 GB/帧)
└→ 两个瓶颈: Shader 算力 + 带宽

优化措施:

┌───────────────────────────────────────────────┐
│ 优化项               │ 效果                    │
├──────────────────────┼───────────────────────┤
│ 纹理压缩 ASTC 6×6   │ 带宽 3.2→2.1 GB/帧     │
│                      │ 功耗 4.2→3.5W          │
├──────────────────────┼───────────────────────┤
│ GBuffer 减为 2 个 RT │ 带宽 2.1→1.5 GB/帧     │
│ (合并通道)           │ 功耗 3.5→3.0W          │
├──────────────────────┼───────────────────────┤
│ TBDR 优化            │ 带宽 1.5→1.1 GB/帧     │
│ (正确 RenderPass)    │ 功耗 3.0→2.7W          │
├──────────────────────┼───────────────────────┤
│ Shader 简化          │ GPU 时间 10→7ms (冷机) │
│ (减少采样/分支)      │ 功耗 2.7→2.4W          │
├──────────────────────┼───────────────────────┤
│ 动态分辨率           │ 热机时降分辨率         │
│ (85%→100% 自适应)    │ 帧时间稳定在 16ms      │
├──────────────────────┼───────────────────────┤
│ 动态帧率             │ 非战斗时 30fps         │
│ (场景切换时降频)     │ 功耗 2.4→2.0W          │
└──────────────────────┴───────────────────────┘

最终:
├─ 冷机帧时间: 12ms (60fps, 有余量)
├─ 热机 10 分钟后: 17ms (稳定 55fps+)
├─ 温度: 44°C (降低 8°C)
├─ 功耗: 2.0W (降低 52%)
├─ 降频延迟: 10 分钟 → 25 分钟
└→ 通过降低功耗和带宽, 显著改善热机性能
```

### 5.3 案例：内存泄漏排查

```
初始状态:
├─ 场景: RPG 游戏, 多场景切换
├─ 现象: 每次切换场景内存增长 ~50MB
├─ 运行 1 小时后: 4GB → 6.5GB → OOM 崩溃

分析过程:

Step 1: 确认泄漏
├─ VS Memory Usage 快照:
│   ├─ 场景A加载: 4.0 GB
│   ├─ 场景A卸载: 4.3 GB (应为 3.8, 增长 500MB!)
│   ├─ 场景B加载: 4.8 GB
│   ├─ 场景B卸载: 5.1 GB (增长 300MB!)
│   └→ 每次切换泄漏 300-500MB
└→ 确认: 内存泄漏

Step 2: 快照对比定位
├─ 快照1 (场景A加载) vs 快照2 (场景A卸载)
├─ 差异最大的类型:
│   ├─ Texture2D: +320MB (未释放!)
│   ├─ Mesh: +80MB (未释放!)
│   └→ ParticleSystem: +45MB (未释放!)
└→ 纹理是主要泄漏源

Step 3: 引用链分析
├─ 选中未释放的 Texture2D
├─ 查看引用链:
│   Texture2D ← Material ← Renderer ← GameObject ← ???
│   ↑ GameObject 不在场景中但仍被引用
├─ 回溯到根引用:
│   静态缓存: static Dictionary<string, Texture2D> textureCache
│   ↑ 永不清理的静态缓存!
└→ 定位到: ResourceManager 的静态缓存未清理

修复:
// 修复前 (泄漏):
class ResourceManager {
    static Dictionary<string, Texture2D> cache;
    // 场景卸载时未清理 cache
}

// 修复后:
class ResourceManager {
    Dictionary<string, Texture2D> cache;
    
    void OnSceneUnloaded(Scene scene) {
        // 场景卸载时清理非持久资源
        foreach (var kv in cache) {
            if (!persistentResources.Contains(kv.Key)) {
                Resources.UnloadAsset(kv.Value);
                cache.Remove(kv.Key);
            }
        }
    }
}

验证:
├─ 修复后场景切换: 内存稳定在 4.0-4.1 GB
├─ 运行 2 小时: 无增长
└→ 泄漏修复 ✓
```

## 6. 性能优化最佳实践清单

### 6.1 CPU 最佳实践

```
□ 每帧零堆分配 (GC Alloc = 0)
  ├─ 预分配所有容器, Clear() 复用
  ├─ 避免 foreach (旧 Unity) / LINQ / 闭包
  ├─ 缓存所有 GetComponent / Transform 引用
  └─ 使用帧分配器管理临时数据

□ 热点数据 SoA 布局
  ├─ 高频遍历的数据分离为连续数组
  ├─ 冷数据分离到独立结构
  └─ 缓存行对齐 (alignas(64))

□ 分级更新
  ├─ 远处降低 Tick 频率
  ├─ 不可见物体暂停更新
  └─ 使用 Timer 替代不必要的 Tick

□ 并行化
  ├─ 独立任务用 Job System 并行
  ├─ 避免 Lock, 使用无锁结构
  └─ 检查伪共享 (缓存行填充)

□ 渲染提交优化
  ├─ 按 Pipeline/Material 排序 Draw Call
  ├─ 使用实例化渲染
  └─ GPU-Driven (MDI) 消除逐物体提交
```

### 6.2 GPU 最佳实践

```
□ 纹理压缩
  ├─ PC: BC7 (色彩) / BC5 (法线) / BC4 (单通道)
  ├─ 移动: ASTC 6×6 (平衡) / 4×4 (高质量)
  └─ 所有纹理必须有 Mipmap

□ LOD 系统
  ├─ 至少 3 级 LOD + BillBoard
  ├─ 屏幕空间 LOD (比距离更准确)
  └─ Nanite (UE5) 自动处理

□ 剔除
  ├─ 视锥剔除 (必须)
  ├─ 遮挡剔除 (Hi-Z, 室内/城市必备)
  └─ 距离剔除 (远处不渲染)

□ Overdraw 控制
  ├─ Z-Pre-Pass + 前向排序 (PC)
  ├─ PowerVR HSR (移动, 利用硬件遮挡)
  └─ 透明物体 LOD / 合并

□ 分辨率自适应
  ├─ 动态分辨率 (帧时间驱动)
  ├─ 升采样 (TAAU / FSR / DLSS)
  └─ 移动端: 渲染分辨率 < 显示分辨率

□ Shader 优化
  ├─ 消除分支发散 (数据驱动)
  ├─ 减少纹理采样 (通道合并)
  ├─ 减少寄存器 (简化临时变量)
  ├─ 移动端: mediump (法线/UV)
  └─ 阴影: PCF 3×3 足够, 避免 5×5+

□ 移动端 TBDR
  ├─ 正确的 RenderPass 结构 (Subpass)
  ├─ 临时 RT: STORE_OP_DONT_CARE
  ├─ 减少 Pass 切换
  └─ 利用 Tile Memory
```

### 6.3 内存最佳实践

```
□ 内存分配策略
  ├─ 每帧零堆分配 (帧分配器)
  ├─ 同类型对象用池分配器
  ├─ 资源用块分配器 (减少碎片)
  └─ 避免 malloc/free 在热路径

□ 资源管理
  ├─ 场景卸载时释放资源
  ├─ 纹理流式加载 (Mipmap Streaming)
  ├─ 远距离资源延迟加载
  └─ 预加载下一场景 (预测性加载)

□ GPU 显存
  ├─ 纹理压缩 (最大收益)
  ├─ RT 资源别名 (减少峰值)
  ├─ GBuffer 精简 (合并通道)
  ├─ VMA 统计监控碎片
  └─ 移动端: 统一内存预算

□ 泄漏预防
  ├─ 内存快照定期对比
  ├─ ASan 覆盖测试
  ├─ 引用链分析工具
  └─ CI/CD 内存回归检测
```

### 6.4 流程最佳实践

```
□ 测量驱动
  ├─ 优化前先建立基线
  ├─ 优化后 A/B 对比验证
  ├─ 使用 P99 而非平均帧时间
  └─ 热机状态测试 (移动端)

□ 持续监控
  ├─ CI/CD 性能回归
  ├─ 自动化基准测试
  ├─ 多设备覆盖
  └─ 性能趋势追踪

□ 目标硬件优先
  ├─ 在目标最低配置上测试
  ├─ 不要只在高配上优化
  ├─ 移动端关注功耗/发热
  └─ 跨 GPU 厂商测试

□ 工具组合
  ├─ 自建 Profiler → 快速定位方向
  ├─ VTune → CPU 深度分析
  ├─ NSight Graphics → GPU 深度分析
  ├─ RenderDoc → 帧调试
  └─ ASan → 内存安全
```
