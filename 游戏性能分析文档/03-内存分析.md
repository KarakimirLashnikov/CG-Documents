# 游戏性能分析 — 内存分析

> 本文档是「游戏性能分析」系列文档的第 **3** 篇，详细阐述游戏内存分析的完整方法论，涵盖 CPU 内存泄漏与碎片化、GPU 显存管理分析、缓存友好的数据布局、各平台内存分析工具链以及常见内存瓶颈模式。

## 1. 内存分析概述

### 1.1 内存分析为何独立成篇

内存问题在游戏中具有**隐性**和**延迟性**特征——它不总是直接表现为帧率下降，而是通过缓存未命中间接拖慢 CPU/GPU、通过碎片化导致运行时间增长后崩溃、通过显存溢出导致纹理流式加载卡顿：

```
内存问题的三种表现形态:
┌───────────────────────────────────────────────────────────┐
│                                                           │
│  形态1: 崩溃型 (显性)                                     │
│  ┌────────────────────────────────────┐                   │
│  │ OOM 崩溃 / 访问违规 / 内存耗尽       │ ← 容易发现       │
│  └────────────────────────────────────┘                   │
│                                                           │
│  形态2: 增长型 (半隐性)                                   │
│  ┌────────────────────────────────────┐                   │
│  │ 内存随时间持续增长, 最终崩溃或卡顿  │ ← 需监控曲线      │
│  └────────────────────────────────────┘                   │
│                                                           │
│  形态3: 性能型 (隐性)                                     │
│  ┌────────────────────────────────────┐                   │
│  │ 缓存未命中/碎片化/频繁分配 → 帧时间  │ ← 最难发现       │
│  │ 增加但内存总量正常                  │   需微架构分析    │
│  └────────────────────────────────────┘                   │
│                                                           │
└───────────────────────────────────────────────────────────┘
```

### 1.3 关键指标速查

内存分析不像 CPU/GPU 那样有单一的"耗时"指标，它的指标分散在**容量、分配行为、缓存效率、带宽**四个维度上。下表按维度整理了核心指标。

#### 1.3.1 CPU 内存容量类指标 — "用了多少内存"

| 指标 | 含义 | 异常信号 | 告诉你什么 | 查看工具 |
|------|------|---------|-----------|---------|
| **RSS (Resident Set Size)** | 进程实际占用的物理内存 | 持续增长 → 泄漏 | 整体内存占用基线 | Task Manager / VS Memory Usage / `ps` |
| **Working Set** | 当前被映射到物理内存的虚拟页集合 | 远小于 RSS → 大量内存被换出 | 热数据是否驻留物理内存 | Process Explorer / VTune |
| **Virtual Address Space** | 进程虚拟地址空间使用量 | 接近上限 → 地址空间耗尽（32 位常见） | 是否需要切 64 位 / 减少虚拟映射 | VMMap / `pmap` |
| **Committed Memory** | 已提交（分配了物理存储后备）的虚拟内存 | > 物理内存 → 系统开始换页 | 是否会触发缺页风暴 | Task Manager / Resource Monitor |
| **Managed Heap (托管堆)** | C#/Lua 等托管运行时的堆大小 | 持续增长 → GC 压力 | Unity 中需要关注 GC Heap | Unity Profiler (GC Alloc) / Memory Profiler |

#### 1.3.2 CPU 内存分配行为类指标 — "分配模式健康吗"

| 指标 | 含义 | 异常信号 | 告诉你什么 | 查看工具 |
|------|------|---------|-----------|---------|
| **Allocation Rate** | 每秒堆分配次数 | > 10K/s → GC 压力 / 碎片化 | 对象池化 / 减少临时分配 | VS Profiler / Unity Profiler |
| **Allocation Size Distribution** | 按大小分桶的分配次数分布 | 大量小分配 → 分配器开销高 | 合并小分配 / 用 Arena/Pool | malloc hook / Heap Profiler |
| **Fragmentation Ratio** | 碎片化率 = 空闲块总量 / 最大连续空闲块 | > 2.0 → 严重碎片化 | 碎片导致无法满足大块请求 | jemalloc stats / Unity Memory Profiler |
| **Peak Allocation** | 单帧内峰值分配量 | 尖峰 > 1MB → 加载/生成导致的帧卡顿 | 分散到多帧 / 预分配 | Unity Profiler (GC Alloc) / Unreal Insights |
| **Leak Count / Leak Size** | 疑似泄漏的分配次数/总大小 | 持续增长 → 确认泄漏 | ASan LeakSanitizer / VS Memory Snapshot 对比 | ASan / VS Memory Usage / mimalloc |

```
碎片化的直观理解:

  ┌── 堆布局 ──────────────────────────────────┐
  │  ██ ░░ ██ ░░░░ ██ ░░ ██ ░░░░░░ ██ ░░ ██    │
  │  ██ 已用  ░░ 空闲                            │
  └────────────────────────────────────────────┘
  
  空闲总量 = 12 格, 但最大连续空闲块 = 4 格
  Fragmentation Ratio = 12 / 4 = 3.0 → 碎片化严重
  → 申请 5 格的请求会失败, 尽管总空闲足够
  
  游戏常见原因:
  ├─ 频繁分配/释放不同大小的对象 (如特效/弹幕)
  ├─ 资源加载/卸载交替 (Asset Bundle / Texture Streaming)
  └─ 第三方库内部 malloc (如 PhysX / JSON 解析)
```

#### 1.3.3 CPU 缓存效率类指标 — "内存访问是否缓存友好"

这些指标本质上是"CPU 性能"指标，但根因在内存访问模式，所以放在内存分析中。

| 指标 | 含义 | 正常范围 | 异常信号 | 告诉你什么 |
|------|------|---------|---------|-----------|
| **L1 Data Cache Miss Rate** | L1 D-Cache 未命中率 | < 5% | > 15% → 数据布局差 | AoS → SoA / 预取 / 减小热数据 |
| **L2 Cache Miss Rate** | L2 未命中率 | < 10% | > 30% → 工作集超 L1 | 分块处理 / 压缩数据 |
| **LLC (L3) Miss Rate** | 末级缓存未命中率 | < 20% | > 50% → 频繁访问主存 | 数据重排 / 内存池 / 减少随机访问 |
| **DTLB Miss Rate** | 数据 TLB 未命中 | < 1% | > 5% → 大量页表遍历 | 大页 (Huge Pages) / 减少地址空间分散 |
| **False Sharing 指标** | 多核修改同一缓存行的不同变量 | — | VTune 显示高 MESI 协议流量 | 对齐到缓存行 / Pad 结构体 |

> **CS 视角理解**：缓存未命中是"隐性内存瓶颈"——内存总量正常，但访问模式导致 CPU 大量时间在等内存返回数据。VTune Microarchitecture Exploration 是发现这类问题的核心工具。详见 [01-CPU 性能分析](01-CPU性能分析.md) §3.5。

#### 1.3.4 GPU 显存类指标 — "显存够不够、带宽够不够"

| 指标 | 含义 | 异常信号 | 告诉你什么 | 查看工具 |
|------|------|---------|-----------|---------|
| **VRAM Usage** | GPU 显存总占用 | > 90% 容量 → OOM 风险 | 纹理/网格/RT 总量是否超标 | NSight Graphics / RenderDoc / DXUT |
| **VRAM by Resource Type** | 按资源类型分类的显存占用 | 纹理占比 > 70% → 纹理是显存主因 | 压缩纹理 / 减少分辨率 / 流式加载 | NSight Graphics Resource View |
| **Allocation Count** | 显存分配次数 | > 10000 → 分配碎片化 | VMA (Vulkan Memory Allocator) 池化 | NSight Graphics / RenderDoc |
| **Memory Bandwidth Utilization** | 显存带宽使用率 | > 90% → Bandwidth-bound | 与 GPU 指标交叉看（见 02-GPU §1.4.4） | NSight Graphics / Snapdragon Profiler |
| **Texture Memory** | 纹理总显存占用 | — | 降 Mipmap / 压缩格式 (ASTC/BCn) | Unity Memory Profiler / UE stat texture |
| **RT Memory** | Render Target 总显存占用 | — | 降 RT 分辨率 / 减 GBuffer 通道数 | NSight Graphics |
| **Tile Memory Spill (移动端)** | TBDR Tile Memory 溢出导致回退 VRAM 往返 | 出现 spill → 移动端带宽激增 | 减 GBuffer 通道 / 减 RT 数量 / 降 MSAA | Snapdragon Profiler / Mali Streamline |

```
VRAM 预算示例 (移动端 4GB 设备, 可用显存 ~2.5GB):

  ┌──────────────────────────────────────────────────┐
  │  纹理:        1.2 GB  (48%)  ← 最大项            │
  │  网格:        0.3 GB  (12%)                      │
  │  Render Target: 0.4 GB (16%)                     │
  │  Shader:      0.2 GB  ( 8%)                      │
  │  Buffer:      0.1 GB  ( 4%)                      │
  │  系统保留:    0.3 GB  (12%)                      │
  │  合计:        2.5 GB  (100%)  ← 接近上限!        │
  └──────────────────────────────────────────────────┘
  → 纹理是显存主因, 优先压缩纹理 + 纹理流送
```

#### 1.3.5 移动端 UMA 特有指标

移动端 CPU 和 GPU 共享同一块物理内存（UMA 架构），有额外指标需要关注：

| 指标 | 含义 | 异常信号 | 查看工具 |
|------|------|---------|---------|
| **Shared Memory Pressure** | CPU+GPU 共享内存的总压力 | 接近设备物理内存上限 | Android Profiler / Xcode Instruments |
| **GPU Memory Bandwidth (移动端)** | 移动 GPU 的实际带宽使用 | > 80% → 移动端首要瓶颈 | Snapdragon Profiler / Mali Streamline |
| **System Memory Backed Textures** | 纹理数据驻留在系统内存而非 GPU 可访问区域 | 大量此类纹理 → 访问延迟高 | Xcode Metal debugger / Mali |

#### 1.3.6 指标 → 问题类型速查

```
你看到的指标异常                        →   可能的内存问题

RSS 持续增长, 不回落                    →   内存泄漏 (ASan / 对比快照)
Fragmentation Ratio > 2.0              →   堆碎片化 (改用池/Arena 分配器)
Allocation Rate > 10K/s                →   GC 压力 (对象池 / 减少临时分配)
L1/L2/LLC Miss Rate 高                 →   缓存不友好 (SoA / 预取 / 分块)
VRAM Usage > 90%                       →   显存不足 (压缩纹理 / 流送 / 减 RT)
Bandwidth Utilization > 90%            →   带宽瓶颈 (见 02-GPU §1.4.4)
Tile Memory Spill (移动端)             →   TBDR 效率丧失 (减 GBuffer / 减 RT)
Peak Allocation 尖峰                    →   单帧大分配 (分散到多帧 / 预分配)
```

## 2. CPU 内存分析

### 2.1 堆分配追踪

游戏中的动态内存分配是性能杀手，每次 malloc/free 都有固定开销：

```
分配开销构成:
┌───────────────────────────────────────────────┐
│  一次 malloc(64) 的开销:                      │
│                                               │
│  1. 分配器查找空闲块:     ~100-500 ns         │
│  2. 可能触发系统调用:     ~1-10 μs (brk/mmap) │
│  3. 可能触发页面缺失:     ~1-10 μs            │
│  4. 缓存污染:             新分配数据不在缓存   │
│                                               │
│  → 如果每帧 10000 次小分配:                   │
│    10000 × 300ns = 3ms (纯分配开销!)          │
│    + 页面缺失/缓存未命中 → 实际可能 5-10ms    │
└───────────────────────────────────────────────┘

优化策略: 减少分配次数 → 内存池化
┌───────────────────────────────────────────────┐
│  传统方式 (每帧大量分配):                      │
│  Frame N:                                     │
│    malloc(64) × 5000次 → 3ms分配开销          │
│    ... 游戏逻辑 ...                           │
│    free() × 5000次 → 1ms释放开销               │
│                                               │
│  内存池方式 (预分配, 复用):                    │
│  初始化:                                      │
│    pool = PoolAllocator<Particle>(10000)      │
│    // 预分配 10000 个 Particle, 一次性         │
│                                               │
│  Frame N:                                     │
│    pool.Alloc() × 5000次 → ~0ns (指针移动)    │
│    ... 游戏逻辑 ...                           │
│    pool.Reset() → ~0ns (重置指针)             │
│    // 0ms 分配开销                             │
└───────────────────────────────────────────────┘
```

### 2.2 常见分配器类型与适用场景

| 分配器 | 原理 | 分配 | 释放 | 碎片 | 适用场景 |
|--------|------|------|------|------|---------|
| **系统 malloc** | OS 堆管理 | 慢 | 慢 | 高 | 通用，不建议热路径使用 |
| **线性分配器** | 指针前移 | O(1) 极快 | 不支持单次释放 | 无 | 每帧临时数据 |
| **栈分配器** | 指针前移+回退 | O(1) | LIFO 顺序释放 | 无 | 嵌套作用域 |
| **池分配器** | 固定大小块链表 | O(1) | O(1) | 无 | 同类型对象（粒子、实体） |
| **块分配器** | 分页+slab | O(1) | O(1) | 低 | 混合大小分配 |
| **自由链表** | 空闲块链表 | O(n) | O(1) | 中 | 通用替代 malloc |

```
游戏引擎典型分配器架构:
┌───────────────────────────────────────────────────────┐
│  系统堆 (malloc/new)                                  │
│  └─ 仅用于: 启动初始化、资源加载、长生命周期对象       │
│                                                       │
│  帧分配器 (Linear/Stack Allocator)                   │
│  └─ 每帧临时数据: 临时数组、字符串、中间计算结果       │
│     Frame begin: allocator.Reset()                   │
│     ... 整帧使用 ...                                   │
│     Frame end: 自动全部回收                            │
│                                                       │
│  对象池 (Pool Allocator)                              │
│  └─ 同类型对象: 粒子、子弹、UI 元素、临时矩阵         │
│     预分配 N 个, Alloc/Free O(1)                      │
│                                                       │
│  资源分配器 (Block/Buddy Allocator)                   │
│  └─ 纹理/网格/音频: 加载时分配, 卸载时释放            │
│     按 Block 分页管理, 减少碎片                       │
└───────────────────────────────────────────────────────┘
```

### 2.3 内存泄漏检测

#### Visual Studio Diagnostics（Windows）

```
工作流:
1. Debug → Performance Profiler → Memory Usage
2. 运行游戏
3. 时间点1: 场景A加载后 → Take Snapshot
4. 时间点2: 场景A卸载后 → Take Snapshot
5. 时间点3: 再次加载场景A → Take Snapshot
6. 对比快照1和快照2

分析:
├─ 快照1 → 快照2 差异:
│   ├─ 如果有对象残留 → 泄漏
│   ├─ 双击残留类型 → 查看分配调用栈
│   └─ 定位到未释放的代码位置
│
├─ 快照1 → 快照3 对比:
│   ├─ 如果内存增长 → 每次加载泄漏
│   └─ 定位资源未正确卸载
```

#### AddressSanitizer (ASan)

ASan 是最强大的编译期内存检测工具，支持 GCC/Clang/MSVC：

```cmake
# CMake 中启用 ASan
if(ENABLE_ASAN)
    add_compile_options(-fsanitize=address -fno-omit-frame-pointer)
    add_link_options(-fsanitize=address)
endif()

# MSVC 中启用 ASan (需 VS 2019 16.9+)
# cl.exe /fsanitize=address /Zi ...
```

```
ASan 检测能力:
├─ 堆缓冲区溢出 (Heap Buffer Overflow)
│   char* buf = new char[64];
│   buf[64] = 'x';  ← ASan 立即报错
│
├─ 栈缓冲区溢出 (Stack Buffer Overflow)
│   int arr[10];
│   arr[10] = 0;    ← ASan 立即报错
│
├─ 释放后使用 (Use-After-Free)
│   delete obj;
│   obj->method();  ← ASan 立即报错
│
├─ 双重释放 (Double Free)
│   free(p); free(p); ← ASan 立即报错
│
├─ 内存泄漏 (Leak)
│   func() {
│       char* p = new char[100];
│       return;  // p 未释放 → ASan 退出时报泄漏
│   }
│
└─ 初始化顺序问题 (部分)

ASan 开销: ~2x 慢, ~3x 内存
→ 仅用于测试构建, 不用于 Release/性能分析
```

### 2.4 内存碎片化分析

```
内存碎片化示意:

初始状态 (连续空闲):
┌─────────────────────────────────────────┐
│ ████████████░░░░░░░░░░░░░░░░░░░░░░░░  │
│ ← 已分配 →   ←────── 空闲 ──────────→   │
│ 总空闲: 240 KB (连续)                   │
└─────────────────────────────────────────┘

运行一段时间后 (碎片化):
┌─────────────────────────────────────────┐
│ ██░░░██░░░░██░░░██░░░██░░░░██░░░░░██░  │
│ ←碎片→←碎片→←碎片→←碎片→←碎片→←碎片→  │
│ 总空闲: 240 KB (分散在 40-60KB 的块中)  │
│ → 需要 200KB 连续块时分配失败!          │
└─────────────────────────────────────────┘

碎片化指标:
├─ 外部碎片: 空闲块总量足够, 但无足够大连续块
├─ 内部碎片: 分配器对齐填充导致浪费
├─ 碎片率 = 1 - (最大空闲块 / 总空闲)
│   → >50% 表示碎片化严重
└─ 长时间运行的游戏(MMO/开放世界)碎片化是崩溃主因

缓解策略:
├─ 固定大小池分配器: 同类对象集中分配, 零碎片
├─ 块分配器: 按页分配, 减少小碎片
├─ 压缩式GC: 定期整理内存 (需移动对象, 暂停)
├─ 资源预加载: 减少运行时动态分配
└─ 分级分配: 按生命周期分组管理
```

### 2.5 缓存命中率分析

缓存未命中是 CPU 性能的**隐性杀手**——代码没有 bug，逻辑正确，但就是慢：

```
缓存层次与延迟:
┌──────────────────────────────────────────────────┐
│  L1 Cache:   4 cycles     ~1ns     32-64 KB     │
│  L2 Cache:   12 cycles    ~4ns     256KB-1MB    │
│  L3 Cache:   40 cycles    ~14ns    4-32 MB      │
│  主内存:      200+ cycles  ~80ns    全部          │
│                                                  │
│  → L1 命中 vs 主内存: 80 倍速度差异!             │
│  → 一次 L3 miss 的时间可以做 40 次 L1 命中运算   │
└──────────────────────────────────────────────────┘

数据布局对缓存的影响:

AoS (Array of Structures) - 缓存不友好:
struct Entity {
    Vector3 position;     // 12 bytes
    Quaternion rotation; // 16 bytes
    Vector3 scale;       // 12 bytes
    int entityId;        // 4 bytes
    // 44 bytes per entity
};
Entity entities[1000];  // 遍历位置时, 旋转/缩放也被加载到缓存

更新所有位置:
for (int i = 0; i < 1000; i++) {
    entities[i].position += velocity * dt;
}
// 每个 Entity 44 bytes, 缓存行 64 bytes
// → 64/44 ≈ 1.45 个 Entity/缓存行
// → 实际只用了 12/44 ≈ 27% 的缓存数据
// → 缓存利用率: 27%

SoA (Structure of Arrays) - 缓存友好:
struct EntityData {
    Vector3* positions;    // 1000 × 12 = 12KB 连续
    Quaternion* rotations;
    Vector3* scales;
    int* entityIds;
};
EntityData entities;

更新所有位置:
for (int i = 0; i < 1000; i++) {
    entities.positions[i] += velocity * dt;
}
// positions 连续排列, 缓存行 64 bytes / 12 bytes ≈ 5.3 个/行
// → 缓存利用率: 100%
// → 同时可 SIMD 向量化处理连续内存
```

**VTune Microarchitecture 分析缓存**：

```
VTune → Microarchitecture Exploration → 关注:

Backend Bound → Memory Bound:
├─ L1 Bound:   L1 缓存未命中导致的停顿
│   → 高 = 数据局部性差, 需改 SoA
├─ L2 Bound:   L2 缓存未命中
│   → 高 = 数据集超过 L1 大小
├─ L3 Bound:   L3 缓存未命中
│   → 高 = 数据集超过 L3, 需分块处理
└─ DRAM Bound: 主内存访问延迟
    → 高 = 严重的数据访问瓶颈

关键计数器:
├─ L1-dcache-load-misses:  L1 数据缓存未命中
├─ LLC-load-misses:         末级缓存未命中
├─ dTLB-load-misses:        数据 TLB 未命中 (大数组遍历)
└─ cache-references:        缓存访问次数
```

```
GPU 显存占用构成:

│  │  └─ 管线对象     │  │  │  └─ 临时RT            │    │
│  └─────────────────┘  │  ├─ Uniform Buffer       │    │
│                       │  ├─ Storage Buffer       │    │
│  典型占比: 40-60%      │  └─ Staging Buffer       │    │
│                       │  典型占比: 30-50%         │    │
│                       └─────────────────────────┘    │

│  │  典型占比: 5-15%                                  │ │
│  └─────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘

显存预算示例 (8GB 显卡):
├─ 纹理:          2.5 GB (31%)
├─ 网格:          0.8 GB (10%)
├─ GBuffer:       0.5 GB (6%)
├─ ShadowMap:     0.3 GB (4%)
├─ 后处理RT:      0.4 GB (5%)
├─ 着色器/管线:   0.5 GB (6%)
├─ Uniform/Storage: 0.3 GB (4%)
├─ 交换链/深度:    0.1 GB (1%)
├─ 系统预留:      0.6 GB (8%)
└─ 可用余量:      2.0 GB (25%) ← 安全余量
```

### 3.2 纹理显存优化

纹理是显存占用大户，压缩是首要优化手段：

| 压缩格式 | 压缩比 | 质量 | 平台 | 每像素位 |
|---------|--------|------|------|---------|
| **未压缩 (RGBA8)** | 1× | 最高 | 全平台 | 32 bit |
| **BC1 (DXT1)** | 6:1 | 中 | PC (DX) | 4 bit (无alpha) |
| **BC3 (DXT5)** | 4:1 | 中高 | PC (DX) | 8 bit (有alpha) |
| **BC5 (ATI2)** | 4:1 | 高(法线) | PC (DX) | 8 bit (双通道) |
| **BC6H** | 6:1 | 高(HDR) | PC (DX) | 8 bit (HDR) |
| **BC7** | 3:1 | 最高 | PC (DX) | 8 bit |
| **ASTC 4×4** | 8:1 | 高 | 移动/Vulkan | 8 bit |
| **ASTC 6×6** | 18:1 | 中高 | 移动/Vulkan | 3.56 bit |
| **ASTC 12×12** | 72:1 | 低 | 移动/Vulkan | 0.89 bit |

```
纹理显存计算:
未压缩 4096×4096 RGBA8:
  4096 × 4096 × 4 = 67,108,864 bytes = 64 MB

BC7 压缩 4096×4096:
  4096 × 4096 × 1 = 16,777,216 bytes = 16 MB (省 75%)

ASTC 6×6 压缩 4096×4096:
  4096 × 4096 × 0.445 = 7,466,839 bytes ≈ 7.1 MB (省 89%)

→ 一个场景 500 张纹理:
  未压缩: 500 × 64MB = 32 GB (超出 8GB 显存!)
  BC7:    500 × 16MB = 8 GB (刚好)
  ASTC:   500 × 7MB  = 3.5 GB (安全)

Mipmap 额外开销:
  Mipmap 链 = 原始大小 × 1.33 (等比级数和)
  → 64MB + Mipmap = 64 × 1.33 = 85 MB
  → 压缩后同样 ×1.33
```

### 3.4 VMA (Vulkan Memory Allocator) 分析

Vulkan 中显存分配通过 VMA 管理，分析 VMA 分配状态是显存优化的核心：

```
VMA 内存堆类型:
┌──────────────────────────────────────────────────────────┐
│  VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT                     │
│  → GPU 专用显存 (最快), 纹理/网格/RT 首选                │
│  → 容量 = 显卡 VRAM                                      │
├──────────────────────────────────────────────────────────┤
│  VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT                    │
│  → CPU 可见 (映射), 用于 CPU→GPU 数据传输               │
│  → 速度较慢 (PCIe 带宽), Uniform/Staging Buffer         │
├──────────────────────────────────────────────────────────┤
│  DEVICE_LOCAL | HOST_VISIBLE                            │
│  → 统一内存架构 (UMA) 设备特有                          │
│  → 移动端 GPU (Adreno/Mali/PowerVR) 默认此类型           │
│  → CPU 和 GPU 共享同一物理内存                           │
├──────────────────────────────────────────────────────────┤
│  HOST_COHERENT | HOST_CACHED                            │
│  → CPU 端缓存, 适合频繁 CPU 读写                        │
│  → 需配合 vkFlushMappedMemoryRange 使用                 │
└──────────────────────────────────────────────────────────┘

VMA 分配策略分析:
┌──────────────────────────────────────────────────┐
│  VMA_CREATE_FAST_DEVICE_ADDRESS_BIT              │
│  → 使用大型虚拟分配 + 子分配                       │
│  → 减少 vkAllocateMemory 调用 (有 4096 限制)     │
│  → Bindless 资源需要此标志                       │
│                                                  │
│  分析 VMA 状态:                                   │
│  vmaCalculateStatistics(allocator, &stats)       │
│  ├─ stats.total.blocks: 分配的内存块数             │
│  ├─ stats.total.allocationCount: 子分配数          │
│  ├─ stats.total.usedBytes: 已使用字节              │
│  ├─ stats.total.unusedBytes: 内部碎片              │
│  └─ unusedRangeSizeMax: 最大空闲块                 │
│                                                  │
│  关键指标:                                        │
│  ├─ unusedBytes/totalBytes > 20% → 分配粒度过大   │
│  ├─ blocks > 100 → 过多 vkAllocateMemory 调用     │
│  └─ unusedRangeSizeMax < 需求 → 碎片化             │
└──────────────────────────────────────────────────┘
```

## 4. 移动端统一内存架构 (UMA)

### 4.1 UMA 与离散 GPU 的差异

```
PC 离散 GPU 架构:
┌──────────────┐         ┌──────────────┐
│   CPU        │ ←PCIe→  │   GPU        │
│  Host RAM    │  32GB/s │  VRAM        │
│  16-32 GB    │         │  8-24 GB    │
│              │         │  400+ GB/s  │
└──────────────┘         └──────────────┘
→ CPU 和 GPU 内存独立, 数据需通过 PCIe 传输
→ GPU 访问 Host RAM 很慢 (PCIe 带宽限制)
→ VRAM 带宽远高于 Host RAM

移动端 UMA 架构:
┌──────────────────────────────────────┐
│            共享物理内存 (LPDDR)       │
│  ┌──────────┐    ┌──────────────┐   │
│  │   CPU    │    │     GPU      │   │
│  │  逻辑    │    │   渲染/计算   │   │
│  └──────────┘    └──────────────┘   │
│                                      │
│  统一内存: 4-12 GB LPDDR5            │
│  带宽: 25-68 GB/s (远低于 PC VRAM)   │
└──────────────────────────────────────┘
→ CPU 和 GPU 共享同一块物理内存
→ 无需 PCIe 传输, CPU 可直接写 GPU 可读数据
→ 但带宽远低于 PC, 带宽是首要约束
→ 总容量有限, 内存预算紧张
```

### 4.2 UMA 对内存分析的影响

| 分析维度 | 离散 GPU (PC) | UMA (移动端) |
|---------|-------------|-------------|
| **数据传输** | 需 Staging Buffer 通过 PCIe | 可直接 HOST_VISIBLE + DEVICE_LOCAL |
| **映射内存** | 需 vkFlushMappedMemoryRange | COHERENT 内存自动可见 |
| **带宽约束** | VRAM 带宽充足 | 共享带宽是首要瓶颈 |
| **容量约束** | VRAM 独立, 较充裕 | 与 CPU 争用, 紧张 |
| **内存碎片** | VRAM 独立管理 | CPU/GPU 分配互相影响 |
| **功耗** | 不受内存影响 | 内存访问是功耗大头 |

## 5. 内存分析实战工作流

### 5.1 内存泄漏排查流程

```
Step 1: 确认泄漏
├─ 运行游戏 30 分钟
├─ 每 5 分钟记录内存占用
├─ 如果持续增长不回落 → 确认泄漏
└─ 记录增长速率 (如 +2MB/分钟)

Step 2: 定位泄漏类型
├─ CPU 内存增长? → 堆分配泄漏
│   ├─ VS Memory Usage 快照对比
│   ├─ 或 ASan 运行检测
│   └─ 定位到分配调用栈
│
├─ GPU 显存增长? → 资源未释放
│   ├─ NSight Graphics 资源列表对比
│   ├─ 或 VMA 统计对比
│   └─ 定位到纹理/Buffer/RT 未释放
│
└─ Unity/UE 引擎内存? → 引擎资源泄漏
    ├─ 引擎 Memory Profiler 对比
    └─ 定位到资产未卸载

Step 3: 修复验证
├─ 修复后重新运行 30 分钟
├─ 确认内存稳定不再增长
└─ 在多场景切换中验证
```

### 5.2 缓存性能优化流程

```
Step 1: VTune Microarchitecture 分析
├─ 关注 Backend Bound → Memory Bound
├─ 查看 L1/L2/L3 Bound 占比
├─ 高 L3 Bound → 数据集超过缓存 → 分块处理
└─ 高 L1 Bound → 数据局部性差 → SoA 重构

Step 2: 数据布局重构
├─ 热点数据从 AoS 改为 SoA
├─ 确保热数据连续排列
├─ 冷数据分离到独立数组
└─ 添加缓存行对齐填充 (alignas(64))

Step 3: 验证改善
├─ VTune 重新分析, 确认 Cache Miss 下降
├─ CPI 下降
├─ 帧时间下降
└─ 确认无其他回归
```

## 6. 常见内存问题模式

### 6.1 每帧大量小分配

```cpp
// 问题: 每帧创建临时对象
void Update() {
    for (auto& entity : entities) {
        auto temp = std::vector<int>();  // ← 每帧每对象 malloc!
        temp.resize(100);
        // ...
    }  // ← 每帧每对象 free!
}
// 1000 实体 × 2次分配 = 2000 次 malloc/free 每帧

// 修复: 预分配复用
class System {
    std::vector<int> tempBuffer;  // 成员变量, 一次性分配
    void Update() {
        for (auto& entity : entities) {
            tempBuffer.clear();
            tempBuffer.resize(100);
            // ... 复用同一块内存
        }
    }
};
```

### 6.2 字符串分配

```cpp
// 问题: 字符串拼接产生临时分配
std::string GetName(int id) {
    return "Entity_" + std::to_string(id);  // ← 每次调用分配!
}
// 每帧调用 1000 次 = 1000 次堆分配

// 修复1: 预格式化 / string_view
std::string_view GetNamePrefix() { return "Entity_"; }

// 修复2: 静态缓存
const std::string& GetCachedName(int id) {
    static std::unordered_map<int, std::string> cache;
    auto it = cache.find(id);
    if (it == cache.end()) {
        cache[id] = "Entity_" + std::to_string(id);
    }
    return cache[id];
}

// 修复3: 帧分配器
std::string GetName(FrameAllocator& alloc, int id) {
    // 使用帧分配器, 帧结束自动回收
    return alloc.Format("Entity_%d", id);
}
```

### 6.3 显存泄漏（RT 未释放）

```cpp
// 问题: 每帧创建新 RT
void RenderFrame() {
    auto rt = CreateRenderTarget(1920, 1080, RGBA8);
    RenderScene(rt);
    Present(rt);
    // ← 忘记销毁 rt!
}
// 每帧泄漏 8.3MB → 60fps → 500MB/秒

// 修复: RT 池化复用
class RTPool {
    std::unordered_map<RTDesc, RenderTarget*> pool;
    RenderTarget* Acquire(const RTDesc& desc) {
        auto it = pool.find(desc);
        if (it != pool.end()) return it->second;
        auto rt = CreateRenderTarget(desc);
        pool[desc] = rt;
        return rt;
    }
};
// 或使用 FrameGraph 自动管理 RT 生命周期
```
