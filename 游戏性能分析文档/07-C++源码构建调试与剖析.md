## 2. 构建系统：CMake + Visual Studio

### 2.1 CMake 工程结构

```cmake
# 典型游戏引擎 CMake 结构
cmake_minimum_required(VERSION 3.20)
project(GameEngine CXX)

# C++ 标准
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# === 构建类型配置 ===
if(NOT CMAKE_BUILD_TYPE)
    set(CMAKE_BUILD_TYPE RelWithDebInfo CACHE STRING "Build type" FORCE)
endif()

# === 编译选项 (按平台) ===
if(MSVC)
    # MSVC (Windows)
    add_compile_options(
        /W4              # 高警告级别
        /WX              # 警告视为错误
        /permissive-     # 严格标准合规
        /Zc:__cplusplus  # 正确的 __cplusplus 值
        /utf-8           # UTF-8 源码编码
    )
    
    # 按构建类型配置
    if(CMAKE_BUILD_TYPE STREQUAL "Debug")
        add_compile_options(/Od /Zi /Ob0)
        # 注意: Debug 仅用于逻辑调试, 不用于性能分析
    elseif(CMAKE_BUILD_TYPE STREQUAL "RelWithDebInfo")
        add_compile_options(/O2 /Zi /Ob1)
        # 性能分析推荐: 优化开启 + 调试符号
    elseif(CMAKE_BUILD_TYPE STREQUAL "Release")
        add_compile_options(/O2 /Ob2)
        # Release for production: 无符号
    endif()
    
    # 关闭增量链接 (提高 Release 构建速度)
    add_link_options(/INCREMENTAL:NO)
    
else()
    # GCC / Clang
    add_compile_options(
        -Wall -Wextra -Werror
        -fno-omit-frame-pointer    # 保留帧指针 (采样需要)
    )
    
    if(CMAKE_BUILD_TYPE STREQUAL "RelWithDebInfo")
        add_compile_options(-O2 -g)
    elseif(CMAKE_BUILD_TYPE STREQUAL "Debug")
        add_compile_options(-O0 -g3)
    endif()
endif()

# === PDB 配置 (Windows) ===
if(MSVC)
    # 生成完整调试信息
    add_link_options(/DEBUG:FULL)
    # PDB 文件路径
    set(CMAKE_PDB_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/pdb)
endif()

# === AddressSanitizer 支持 ===
option(ENABLE_ASAN "Enable AddressSanitizer" OFF)
if(ENABLE_ASAN)
    if(MSVC)
        add_compile_options(/fsanitize=address)
        add_link_options(/fsanitize=address)
    else()
        add_compile_options(-fsanitize=address -fno-omit-frame-pointer)
        add_link_options(-fsanitize=address)
    endif()
endif()

# === Tracy / Optick 集成 ===
option(ENABLE_TRACY "Enable Tracy Profiler" OFF)
if(ENABLE_TRACY)
    add_compile_definitions(TRACY_ENABLE)
    add_subdirectory(third_party/tracy)
endif()

# === 主目标 ===
add_executable(GameEngine
    src/main.cpp
    src/Engine.cpp
    src/Renderer.cpp
    # ...
)

target_include_directories(GameEngine PRIVATE src)
target_link_libraries(GameEngine PRIVATE Vulkan::Vulkan)
```

### 2.2 构建类型与性能分析的关系

```
构建类型对性能分析的影响:

┌─────────────────┬────────┬────────┬──────────┬─────────────────────┐
│ 构建类型         │ 优化   │ 符号   │ 性能代表 │ 适用分析             │
├─────────────────┼────────┼────────┼──────────┼─────────────────────┤
│ Debug           │ /Od    │ /Zi    │ ❌ 不代表 │ 逻辑调试, 内存安全   │
│ (无优化)         │ 全关   │ 有     │          │ 不能用于性能分析!     │
├─────────────────┼────────┼────────┼──────────┼─────────────────────┤
│ RelWithDebInfo  │ /O2    │ /Zi    │ ✅ 代表  │ ★性能分析首选★       │
│ (带符号优化)     │ /Ob1   │ 有     │          │ VTune/RenderDoc/     │
│                  │        │        │          │ NSight 均适用       │
├─────────────────┼────────┼────────┼──────────┼─────────────────────┤
│ Release         │ /O2    │ 无     │ ✅ 代表  │ 最终性能验证         │
│ (无符号优化)     │ /Ob2   │ 无     │          │ 无符号无法定位函数   │
├─────────────────┼────────┼────────┼──────────┼─────────────────────┤
│ Debug + ASan    │ /Od    │ /Zi    │ ❌ 不代表 │ 内存安全检测         │
│ (ASan)           │ +ASan  │ 有     │          │ 开销大, 不用于性能   │
└─────────────────┴────────┴────────┴──────────┴─────────────────────┘

关键规则:
├─ 性能分析: 必须用 RelWithDebInfo (/O2 + /Zi)
├─ 逻辑调试: 可以用 Debug
├─ 内存安全: 用 Debug + ASan 或 RelWithDebInfo + ASan
├─ 生产发布: Release (/O2, 无符号)
└→ 绝对不要在 Debug 构建下分析性能!
   Debug 的 /Od 会: 关闭内联、关闭循环展开、关闭向量化
   → 热点函数完全失真

内联对分析的影响:
├─ /Ob0 (Debug): 所有函数调用保留 → 调用栈清晰但性能失真
├─ /Ob1 (RelWithDebInfo): 仅内联标记函数 → 平衡 (推荐)
├─ /Ob2 (Release): 内联所有适合函数 → 性能最优但调用栈合并
└→ VTune 在 /Ob1 下能保留更好的函数级调用关系
```

## 3. PDB 符号管理

### 3.1 PDB 的重要性

PDB（Program Database）是性能分析工具**定位函数和代码行**的基础：

```
没有 PDB 时 (VTune 视角):
┌──────────────────────────────────────────┐
│ Function              │ CPU Time │       │
├───────────────────────┼──────────┤       │
│ 0x7FF6A8231000        │ 4230ms   │       │ ← 无法识别
│ 0x7FF6A8231200        │ 2100ms   │       │ ← 无法识别
│ 0x7FF6A8231500        │ 1560ms   │       │ ← 无法识别
└──────────────────────────────────────────┘
→ 只有地址, 无法定位到函数和源码
→ 性能分析几乎无法进行

有 PDB 时:
┌──────────────────────────────────────────┐
│ Function              │ CPU Time │ Source │
├───────────────────────┼──────────┼───────┤
│ Renderer::SubmitDraw()│ 4230ms   │Rend.cpp│
│ Physics::StepSim()    │ 2100ms   │Phys.cpp│
│ Scene::CullVisible()  │ 1560ms   │Scn.cpp │
└──────────────────────────────────────────┘
→ 清晰定位到函数和源码行
→ 可以直接跳转到代码
```

### 3.2 PDB 配置最佳实践

```cmake
# CMake 中 PDB 最佳配置
if(MSVC)
    # 1. 生成完整调试信息 (而非 FastLink)
    target_link_options(GameEngine PRIVATE /DEBUG:FULL)
    
    # 2. PDB 输出到统一目录
    set_target_properties(GameEngine PROPERTIES
        PDB_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/symbols
        PDB_NAME GameEngine
    )
    
    # 3. 也为 DLL/静态库生成 PDB
    foreach(target ${ENGINE_LIBRARIES})
        set_target_properties(${target} PROPERTIES
            COMPILE_PDB_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/symbols
            COMPILE_PDB_NAME ${target}
        )
    endforeach()
    
    # 4. Release 也生成 PDB (可选, 用于生产调试)
    if(CMAKE_BUILD_TYPE STREQUAL "Release")
        target_compile_options(GameEngine PRIVATE /Zi)
        target_link_options(GameEngine PRIVATE /DEBUG:FULL /OPT:REF /OPT:ICF)
    endif()
endif()
```

```
PDB 配置选项对比:
┌──────────────┬──────────────┬────────────┬───────────────────┐
│ 选项          │ 速度         │ 完整性      │ 适用              │
├──────────────┼──────────────┼────────────┼──────────────────┤
│ /DEBUG:FAST  │ 最快         │ 部分(无行号)│ 快速迭代开发       │
│ /DEBUG:FULL  │ 较慢         │ 完整(含行号)│ ★性能分析首选★    │
│ /DEBUG:NONE  │ N/A          │ 无          │ Release 无符号     │
└──────────────┴──────────────┴────────────┴───────────────────┘

关键: VTune 需要行级符号 → 必须 /DEBUG:FULL
```

### 3.3 符号路径配置

```
Visual Studio 符号路径:
1. Tools → Options → Debugging → Symbols
2. 添加符号路径:
   ├─ 本工程: $(SolutionDir)symbols
   ├─ 微软符号服务器: https://msdl.microsoft.com/download/symbols
   └─ 引擎依赖: C:\Symbols\ThirdParty
3. 缓存路径: C:\Symbols\Cache

VTune 符号路径:
1. VTune → Configure Analysis → Binary/Symbol Search
2. 添加:
   ├─ 工程二进制目录: D:\Engine\build\RelWithDebInfo
   ├─ PDB 目录: D:\Engine\build\symbols
   └─ 源码目录: D:\Engine\src

RenderDoc 符号路径:
1. Tools → Settings → Source Paths
2. 添加源码路径

NSight Graphics 符号路径:
1. Nsight Graphics → Options → Symbol Path
2. 添加 PDB 目录
```

### 3.4 第三方库符号

```
第三方库符号管理:
├─ Windows SDK: 自动从微软符号服务器获取
├─ Vulkan Loader: 通常无 PDB, 忽略
├─ GPU 驱动: 无公开 PDB, 忽略
├─ 自研库: 确保 CMake 生成 PDB
├─ 开源库 (如 glm, stb): 源码编译, 有符号
└─ 商业中间件: 向供应商索取 PDB

符号缺失的影响:
├─ 系统库无符号 → VTune 显示为 "Unknown" 或地址
│   → 不影响自研代码的分析
├─ 自研代码无符号 → 严重, 必须解决
└─ 符号版本不匹配 → VTune 可能显示错误函数名
   → 确保 PDB 与 EXE/DLL 的时间戳匹配
```

### 4.2 条件断点与数据断点

```
条件断点 (Conditional Breakpoint):
├─ 在断点上右键 → Conditions
├─ 条件表达式: entityId == 42 && frameCount > 1000
├─ 仅当条件为 true 时中断
├→ 适合: 只在特定对象/帧上中断

数据断点 (Data Breakpoint):
├─ Debug → New Breakpoint → Data Breakpoint
├─ 地址: &m_renderTarget 或 ptr 指向的地址
├─ 当该内存被修改时中断
├→ 适合: 追踪"谁修改了这个变量"

断点操作:
├─ Hit Count: 只在第 N 次命中时中断
├─ Filter: 只在指定线程/进程中断
├─ Action: 命中时输出日志而非中断 (日志断点)
├─ Label: 标记断点用途
└→ 日志断点: 不暂停程序, 输出信息, 适合性能调试
```

## 5. 自建 Profiler 系统

### 5.1 为什么需要自建 Profiler

外部工具（VTune/NSight）虽然强大，但有局限：

```
外部工具的局限:
├─ 无法在 Release 构建中持续运行 (开销)
├─ 无法自定义语义标记 (只有函数名)
├─ 难以与游戏逻辑关联 (如"技能释放阶段")
├─ 无法实时显示给玩家/QA
└→ 自建 Profiler 补充这些能力

自建 Profiler 的定位:
├─ 轻量级: 可在 Release 持续运行 (开销 <0.1ms)
├─ 语义化: 用游戏术语标记 (如 "Physics", "AI", "Render")
├─ 实时显示: 画面叠加/控制台输出
├─ 远程查看: 通过网络传到开发机
└→ 与外部工具互补, 不是替代
```

### 5.2 基础 Profiler 实现

```cpp
// 基础性能计时器 (使用高精度时钟)
class Profiler {
public:
    static Profiler& Get() {
        static Profiler instance;
        return instance;
    }

    void BeginFrame() {
        frameStart_ = Now();
    }

    void EndFrame() {
        auto frameEnd = Now();
        float frameMs = DurationMs(frameStart_, frameEnd);
        frameHistory_.push_back(frameMs);
        if (frameHistory_.size() > 300) {
            frameHistory_.pop_front();
        }
    }

    void BeginZone(const char* name) {
        zones_[name].start = Now();
    }

    void EndZone(const char* name) {
        auto end = Now();
        auto& zone = zones_[name];
        zone.lastMs = DurationMs(zone.start, end);
        zone.totalMs += zone.lastMs;
        zone.callCount++;
    }

    // 打印到控制台/叠加层
    void Dump() const {
        printf("=== Frame Time: %.2fms ===\n", frameHistory_.back());
        for (auto& [name, zone] : zones_) {
            printf("  %-30s %8.2fms  calls=%d\n",
                   name, zone.lastMs, zone.callCount);
        }
    }

private:
    using TimePoint = std::chrono::high_resolution_clock::time_point;

    TimePoint Now() const {
        return std::chrono::high_resolution_clock::now();
    }

    float DurationMs(TimePoint start, TimePoint end) const {
        return std::chrono::duration<float, std::milli>(end - start).count();
    }

    struct Zone {
        TimePoint start;
        float lastMs = 0;
        float totalMs = 0;
        uint64_t callCount = 0;
    };

    TimePoint frameStart_;
    std::unordered_map<std::string, Zone> zones_;
    std::deque<float> frameHistory_;
};

// RAII 包装
class ScopedZone {
public:
    ScopedZone(const char* name) : name_(name) {
        Profiler::Get().BeginZone(name);
    }
    ~ScopedZone() {
        Profiler::Get().EndZone(name_);
    }
private:
    const char* name_;
};

// 使用宏
#define PROFILE_SCOPE(name) ScopedZone _zone_##name(#name)
#define PROFILE_FUNCTION()  ScopedZone _zone_(__FUNCTION__)
```

```cpp
// 使用示例
void GameLoop() {
    Profiler::Get().BeginFrame();
    {
        PROFILE_SCOPE(Update);
        UpdateWorld();
    }
    {
        PROFILE_SCOPE(Physics);
        StepPhysics();
    }
    {
        PROFILE_SCOPE(Render);
        RenderFrame();
    }
    Profiler::Get().EndFrame();

    if (frameCount % 60 == 0) {
        Profiler::Get().Dump();
    }
}
```

### 5.3 集成 Tracy / Optick

对于需要更专业功能（火焰图、远程查看、线程可视化）的场景，推荐集成开源 Profiler：

```
Tracy Profiler:
├─ 开源, 跨平台, 实时
├─ 集成方式:
│   ├─ CMake 添加 tracy 子目录
│   ├─ 编译定义: TRACY_ENABLE
│   └─ 头文件: #include <tracy/Tracy.hpp>
│
├─ 使用:
│   ZoneScoped;                    // 当前作用域计时
│   ZoneScopedN("Custom Name");    // 自定义名称
│   FrameMark;                     // 帧标记
│   TracyPlot("Memory", memMB);    // 自定义计数器曲线
│   TracyMessage("Event logged");  // 消息标记
│
├─ 优势:
│   ├─ 实时远程查看 (网络连接)
│   ├─ 火焰图 + 时间线
│   ├─ GPU Zone 支持 (vkZone)
│   ├─ 内存分配追踪
│   └─ 极低开销 (<0.01ms)
│
└→ 推荐: 自研引擎首选集成

Optick:
├─ 开源, 跨平台, 类似 Tracy
├─ API: OPTICK_EVENT(), OPTICK_FRAME()
├─ 优势: C++ API 更简洁, 内置 GPU 支持
└→ 可作为 Tracy 替代

Remotery:
├─ 轻量级, Web 界面查看
├─ 适合简单需求
└→ 不如 Tracy/Optick 功能丰富
```

## 6. 与外部剖析工具联动

### 6.1 VTune 联动

```
VTune 分析原生 C++ 引擎工作流:

Step 1: 构建准备
├─ CMake RelWithDebInfo 构建
├─ 确认 PDB 生成 (symbols/*.pdb)
├─ 确认源码路径

Step 2: VTune 配置
├─ Target: GameEngine.exe
├─ Working Dir: 资产目录
├─ Arguments: 测试场景参数
├─ Symbol Search: 添加 PDB 目录
├─ Source Search: 添加源码目录

Step 3: 采集
├─ Hotspots Analysis:
│   ├─ Start → 游戏启动
│   ├─ 进入目标场景, 等稳定
│   ├─ 采集 10 秒 → Stop
│   └→ 查看 Top-Down / Bottom-Up
│
├─ Microarchitecture Exploration:
│   ├─ 选择热点函数所在区域
│   ├─ 采集 → 分析 Backend/Frontend Bound
│   └→ 判断: 缓存/分支/端口 瓶颈
│
└─ Threading Analysis:
    ├─ 分析锁竞争
    ├─ 分析负载均衡
    └→ 分析 CPU 核心利用率

Step 4: 结果解读
├─ 双击热点函数 → 源码级标注 (行号耗时)
├─ 右键 → View Call Stack → 调用链
├─ 过滤: Thread / Module / CPU Core
└→ 导出报告: CSV / HTML
```

### 6.2 RenderDoc 联动

```
RenderDoc 捕获原生引擎:

Step 1: 配置注入
├─ 方式1: RenderDoc 启动引擎
│   ├─ RenderDoc → File → Inject into Process
│   ├─ 或: 直接配置可执行文件路径 + 启动
│   ├─ 适用: 容易注入的进程
│   └→ 推荐
│
├─ 方式2: 环境变量注入
│   ├─ 设置: ENABLE_API_LAYER_RENDERDOC=1 (Vulkan)
│   ├─ 设置: RENDERDOC_CAPTURE=1 (通用)
│   ├─ 引擎启动时自动加载 RenderDoc 层
│   └→ 适合: 难以直接注入的场景
│
└─ 方式3: API 集成 (代码内触发)
    // 引擎中调用 RenderDoc API
    RENDERDOC_StartFrameCapture(device, windowHandle);
    // ... 渲染一帧 ...
    RENDERDOC_EndFrameCapture(device, windowHandle);
    → 精确控制捕获时机

Step 2: Debug Marker 集成
├─ 引擎中使用 vkCmdBeginDebugUtilsLabelEXT
├─ RenderDoc Event Browser 中显示标记名称
├─ 大大提高可读性:
│   "Scene.OpaquePass"
│   "Character.ShadowPass"
│   "PostProcess.Bloom"
└→ 建议在引擎中全面集成 Debug Marker

Step 3: 捕获与分析
├─ F12 捕获帧
├─ 逐 Draw Call 检视 (参考 02-GPU分析)
├─ 纹理/Buffer 查看
├─ Pipeline State 查看
└→ 重点关注: Draw Call 数/状态切换/Overdraw/纹理格式
```

### 6.3 NSight Graphics 联动

```
NSight Graphics 分析原生引擎:

Step 1: 配置
├─ NSight Graphics → New Activity
├─ Target: GameEngine.exe
├─ Working Dir: 资产目录
├─ Args: 测试场景参数
├─ Symbol Path: PDB 目录
└→ Frame Debugger / Range Profiler 模式

Step 2: 捕获
├─ 触发方式:
│   ├─ NSight 热键捕获 (默认 Ctrl+Z)
│   ├─ 或设置自动捕获帧 (如第 1000 帧)
│   └─ 或代码内 Nsight API 触发
│
├─ Frame Debugger:
│   ├─ 逐 Draw Call 检视 (类似 RenderDoc)
│   ├─ 每个 Draw Call 的 GPU 耗时
│   └→ 适合: 找最慢的 Draw Call
│
└─ Range Profiler:
    ├─ 选择 Draw Call 范围
    ├─ 深度 GPU 性能剖析
    ├─ 瓶颈分类 (像素/几何/带宽)
    ├─ GPU 计数器
    └→ 适合: GPU 瓶颈深度定位 (参考 02-GPU分析)

Step 3: 与 VTune 交叉验证
├─ VTune: CPU 侧分析
├─ NSight: GPU 侧分析
├─ Nsight Systems: CPU+GPU 时间线
└→ 三工具配合, 全栈覆盖
```

## 7. 完整分析工作流

```
原生 C++ 引擎性能分析全流程:

Phase 1: 自建 Profiler 快速定位
├─ 引擎内嵌 Profiler (自建或 Tracy/Optick)
├─ 实时查看帧时间分布
├─ 定位热点 Zone (如 "Render" vs "Physics")
├─ 判断 CPU-bound 还是 GPU-bound
└→ 快速初筛, 缩小范围

Phase 2: 精确工具深入分析
├─ CPU 深入 → VTune
│   ├─ Hotspots: 定位热点函数
│   ├─ Microarchitecture: 分析微架构瓶颈
│   ├─ Threading: 分析线程效率
│   └→ 参考本文档第 6.1 节 + 01-CPU分析
│
├─ GPU 深入 → NSight Graphics
│   ├─ Range Profiler: 瓶颈分类
│   ├─ GPU 计数器: 吞吐量/缓存/占用率
│   ├─ Shader 分析: 指令/寄存器/采样
│   └→ 参考 02-GPU分析
│
├─ GPU 帧调试 → RenderDoc
│   ├─ Draw Call 检视
│   ├─ 资源/纹理查看
│   ├─ Overdraw 分析
│   └→ 参考 02-GPU分析
│
└─ 内存分析 → VS Memory / ASan / VMA
    ├─ CPU 内存: ASan + VS Memory Usage
    ├─ GPU 显存: NSight Graphics + VMA Stats
    └→ 参考 03-内存分析

Phase 3: 优化与验证
├─ 针对性优化 (参考 08-优化策略)
├─ 自建 Profiler 确认改善
├─ VTune/NSight 精确验证
├─ A/B 对比
└→ 多平台验证
```

## 8. 本章小结

| 环节 | 关键配置/工具 | 核心要点 |
|------|-------------|---------|
| **构建** | CMake RelWithDebInfo | /O2 + /Zi, 绝不用 Debug 分析性能 |

| **内存分析** | ASan + VS Memory + VMA | 越界/泄漏/碎片 三维度 |
| **Debug Marker** | vkCmdBeginDebugUtilsLabelEXT | 提高工具可读性 |
