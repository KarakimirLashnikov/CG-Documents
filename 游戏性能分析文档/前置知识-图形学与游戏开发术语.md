## 1. "前端"与"后端"——最容易混淆的术语

这两个词在 Web 开发中含义非常明确（前端 = 浏览器端、后端 = 服务器），但在游戏/图形学中**完全不同**，且有**三层含义**。

### 1.1 含义一：图形管线的前端与后端 (Graphics Pipeline Frontend/Backend)

这是本系列中最常出现的含义。

```
图形渲染管线 (Graphics Pipeline)

┌─────────────────────────────────────────────┐
│              「前端」Frontend                │
│                                              │
│  输入装配 (IA)                               │
│     │  从顶点缓冲区读取顶点数据、索引数据      │
│     ▼                                        │
│  顶点着色器 (VS)                              │
│     │  逐顶点变换：模型空间 → 世界 → 裁剪空间 │
│     ▼                                        │
│  曲面细分 (Tessellation) — 可选               │
│     │  将粗网格细分为更多三角形               │
│     ▼                                        │
│  几何着色器 (GS) — 可选                       │
│     │  逐图元操作：生成/销毁/修改三角形        │
│     ▼                                        │
│  裁剪 (Clipping) & 视口变换                   │
│                                               │
├─────────────────────────────────────────────┤
│              「后端」Backend                  │
│                                              │
│  光栅化 (Rasterization)                       │
│     │  三角形 → 屏幕像素（生成片元 Fragment） │
│     ▼                                        │
│  提前深度测试 (Early-Z) — 可选                │
│     │  在片元着色器之前丢弃被遮挡的像素         │
│     ▼                                        │
│  片元着色器 (PS/FS)                           │
│     │  逐像素计算颜色、采样纹理、光照计算      │
│     ▼                                        │
│  输出合并 (OM)                                │
│     │  深度测试、模板测试、Alpha 混合          │
│     │  写入 Render Target                     │
│                                               │
└─────────────────────────────────────────────┘
```

**一句话总结**：前端 = 顶点处理（几何变换），后端 = 像素处理（光栅化+着色），分水岭是光栅化。

**为什么区分前/后端？** 因为瓶颈完全不同：

- **前端瓶颈**（Geometry Bound）：三角形太多、顶点着色器太重 → 对应名词：Triangle Throughput, Vertex Bound
- **后端瓶颈**（Pixel Bound / Fill Rate Bound）：像素太多、片元着色器太重 → 对应名词：Fill Rate, Bandwidth, Overdraw

### 1.2 含义二：引擎线程架构的前端与后端 (Engine Threading Model)

在 Unity/UE 等多线程引擎中，线程也有"前/后"之分：

```
┌──────────────────────────────────────────────────────────┐
│                      引擎线程模型                          │
│                                                          │
│   「前端线程」 (Frontend Thread)                          │
│   ┌─────────────────────────────────────────────────┐    │
│   │  Game Thread (主线程)                             │    │
│   │  ├─ 脚本逻辑 (C#/Blueprint/Lua)                  │    │
│   │  ├─ 物理模拟 (PhysX/Chaos)                       │    │
│   │  ├─ 动画更新                                      │    │
│   │  ├─ AI 行为树                                     │    │
│   │  └─ 场景遍历 / Culling                            │    │
│   └─────────────────────────────────────────────────┘    │
│                         │                                 │
│                         ▼ 提交渲染命令                    │
│   ┌─────────────────────────────────────────────────┐    │
│   │  Render Thread (在 Unity 中是单独的线程)           │    │
│   │  ├─ 可见性剔除结果                               │    │
│   │  ├─ 生成 Draw Call 列表                          │    │
│   │  ├─ 执行 State Sorting (减少状态切换)            │    │
│   │  └─ 调用底层图形 API                             │    │
│   └─────────────────────────────────────────────────┘    │
│                         │                                 │
│   「后端」 (Backend)       ▼                              │
│   ┌─────────────────────────────────────────────────┐    │
│   │  RHI Thread / Graphics Driver / GPU              │    │
│   │  ├─ 图形 API 命令记录                            │    │
│   │  ├─ 驱动层处理 (状态校验/命令缓冲)               │    │
│   │  └─ GPU 硬件执行                                 │    │
│   └─────────────────────────────────────────────────┘    │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**与本系列的关联**：

- Unity 中可以通过 `PlayerLoop` 看到 Game Thread → Render Thread 的移交
- UE 中 GameThread 和 RenderThread 是独立存在的，Unreal Insights 可以将它们的时间线对齐比较
- **前端瓶颈**（这里 = GameThread 慢）：脚本太多、物理重、Culling 效率低
- **后端瓶颈**（这里 = RenderThread + GPU 慢）：Draw Call 过多、State Change 开销大

### 1.3 含义三：图形 API 的前端与后端 (API Frontend/Backend)

这是最底层的一层含义，涉及图形 API 封装：

| 层次 | 含义 | 举例 |
|------|------|------|
| **API 前端** | 面向应用层的高级 API 抽象 | Direct3D 11 的 Device Context、OpenGL 的 Context；Unity 的 `Graphics.DrawMesh` |
| **API 后端** | 对应具体硬件的驱动实现 | Direct3D/AMD 驱动、Vulkan/Mali 驱动；Unity 的 D3D11/Vulkan/Metal Backend |

这一层通常只在引擎开发或 API 选型时才需要关心。在本系列中，当你看到某个平台工具"支持 X 前端、Y 后端"时，就是这个意思。

### 1.4 快速判断口诀

| 看到什么 | 一般指的是 | 关注点 |
|---------|-----------|--------|
| "前端瓶颈" / "Frontend bound" | 管线前端：顶点/几何处理慢 | 三角形数量、顶点着色器复杂度 |
| "后端瓶颈" / "Backend bound" | 管线后端：像素/光栅化慢 | 分辨率、片元着色器、显存带宽 |
| "主线程" / "Game Thread" 慢 | 线程前端：逻辑更新慢 | 脚本、AI、物理、Culling |
| "Render Thread" 慢 | 线程中端：渲染命令提交慢 | Draw Call 数量、状态切换 |
| "GPU 慢" | 线程后端：GPU 硬件执行慢 | Shader、带宽、填充率 |
| "图形 API 后端" | 驱动/硬件实现 | 平台兼容性、驱动 Bug |

> **本系列约定**：若无特别说明，"前端/后端"指图形管线的前端/后端（含义一）。线程相关讨论中会明确写 "Game Thread / Render Thread"。

## 2. 渲染管线核心概念

本节覆盖渲染管线中的基础名词。你无需记住每个细节，但应能在读文档时认出这些词并知道它们在管线中的位置。

### 2.1 Draw Call

```
本质：一次"CPU 命令 GPU 画东西"的 API 调用。

类比：CPU 是项目经经理，GPU 是施工队。
Draw Call = 经理给施工队开的"施工单"。

一张施工单 = 一包工作：
   "用这套工具（Shader），
    处理这堆材料（Mesh+Texture），
    画到那块画板上（Render Target）"

如果经理一次只开很小的施工单（比如每个物体一张单），
    经理大部分时间都在填写单据，施工队大量时间在等单 → CPU 瓶颈
```

**关键理解**：

| 说法 | 正确含义 |
|------|---------|
| ❌ "这个场景有 100 个物体" | 物体数量不等于 Draw Call 数量 |
| ❌ "Draw Call 过多会 GPU 慢" | Draw Call 多 → CPU Render Thread 慢（CPU 在发号施令），不是 GPU 慢 |
| ✅ "Draw Call 开销在 CPU 侧的 API 调用和状态验证" | 每次 glDraw/VkCmdDraw 驱动要做状态校验、命令缓冲编码 |
| ✅ "减少 Draw Call = Batch / GPU Instancing / SRP Batcher" | 把多个施工单合并成一张大单，降低 CPU 调度开销 |

**SetPass Call (Unity/Shader 概念)**：Draw Call 中真正开销大的子类——每次切换 Shader/材质时 CPU 要做完整的状态刷新（设置 Blend 模式、深度测试模式、填充模式等）。在性能分析中，SetPass Call 数量比原始 Draw Call 数量更能反映 CPU 负载。

> 从 CS 视角理解：Think of Draw Call as a remote procedure call (RPC) from CPU to GPU with non-trivial serialization overhead (command buffer encoding) and driver-side validation.

### 2.2 Pass (渲染 Pass / 渲染通道)

```
一个 Pass = 一次完整的"渲染一遍"。

类比：一张照片不是一次拍成的，而是多张底片叠加出来的。

第一次 Pass：拍底色（不透明物体 → 得到深度+颜色）
第二次 Pass：拍半透明层（玻璃、粒子 → 叠加上去）
第三次 Pass：拍特效（后处理 → Bloom、Tone Mapping）
第四次 Pass：拍 UI（在一切之上）

每个 Pass 都伴随着：
  - 切换 Render Target（换底片）
  - 清除/保留之前的像素数据
  - 执行一批 Draw Call
```

常见 Pass 类型：

| Pass | 做什么 | 性能特点 |
|------|--------|---------|
| **Depth Pre-pass (Z-Prepass)** | 只写深度，不写颜色 | 靠 Early-Z 让后续 Base Pass 避免 Overdraw |
| **Base Pass** | 画所有不透明物体 | 主要时间消耗者 |
| **Shadow Pass** | 从光源视角渲染深度图 | 多个光源 = 多个 Shadow Pass（昂贵） |
| **Transparent Pass** | 画半透明物体（从远到近排序） | 无法 Early-Z，Overdraw 严重 |
| **Post-process Pass** | 后处理特效（Bloom/DOF/Color Grading） | 全屏像素处理，带宽密集 |

### 2.3 Shader（着色器）

```
运行在 GPU 上的函数。每类 Shader 执行在管线不同阶段：

┌──────────────────────────────────────────────────┐
│ Shader 类型        │ 执行的时机     │ 输入        │
├────────────────────┼───────────────┼─────────────┤
│ Vertex Shader (VS) │ 逐顶点         │ 顶点属性    │
│                    │ (前端)         │ (位置/法线/  │
│                    │                │  UV等)      │
│ Fragment/Pixel     │ 逐片元(像素)   │ 插值后的    │
│ Shader (PS/FS)     │ (后端)         │ 顶点数据    │
│ Compute Shader (CS)│ 通用计算       │ 任意 Buffer │
│                    │ (不在管线中)   │ + 纹理      │
│ Geometry/Hull/     │ 逐图元/补丁    │ 顶点列表    │
│ Domain Shader      │ (前端, 少见)   │             │
└──────────────────────────────────────────────────┘
```

**关键误解纠正**：

- "Shader 就是让画面好看的程序" → Shader 可以纯粹做 GPU 计算（Compute Shader），跟画面完全无关（如粒子物理、AI 寻路）
- "Shader 加载卡是因为文件大" → Shader 文件一般不大，卡的是 **Shader 编译**，特别在移动端（Vulkan/Metal 提前编译 vs OpenGL 运行时编译）

**Shader Variant（变体）** 是本系列的关键概念：

```
一个 Shader 源文件，通过 #pragma multi_compile 宏编译出多个版本：

// Unity 示例
#pragma multi_compile _ SHADOW_ON SHADOW_OFF
#pragma multi_compile _ FOG_LINEAR FOG_EXP

组合起来 = 4 个变体：
  (SHADOW_ON,  FOG_LINEAR)
  (SHADOW_ON,  FOG_EXP)
  (SHADOW_OFF, FOG_LINEAR)
  (SHADOW_OFF, FOG_EXP)

5 个 pragma × 3 种选项 = 3^5 = 243 个变体 → "变体爆炸"
→ 编译时间长、运行时内存占用巨大
```

### 2.4 Material（材质）与 Texture（纹理）与 Mesh（网格）

这是游戏资源最基本的三个概念，但很容易混淆：

```
Material (材质)
  │
  ├─ Shader (着色器程序) —— "用哪种算法画"
  │   
  ├─ Texture (纹理) —— "贴上什么图案"
  │   └─ 可以有多张: Albedo(颜色) + Normal(法线) + Roughness(粗糙度)...
  │
  └─ Parameters (参数) —— "算法参数是多少"
      └─ 如: 金属度 = 0.8, 光滑度 = 0.3

Mesh (网格 / 模型)
  └─ 定义的形状: 顶点位置 + 三角形索引 + UV坐标（纹理映射坐标）+ 法线方向
     └─ "画一个什么形状的东西出来"
     └─ 同一个 Mesh 可以搭配不同 Material（石像 vs 金像）
```

**与性能分析的关联**：

- Material 数量多 → SetPass Call 多 → **CPU Render Thread 瓶颈**
- Texture 分辨率过高 → 占用 VRAM 大 + 纹理采样带宽高 → **GPU 显存瓶颈**
- Mesh 三角形过多 → 顶点着色器压力大 → **GPU 前端瓶颈**（Geometry Bound）
- Material 参数变化频繁 → 破坏合批（Batching） → **Draw Call 增加**

### 2.5 Render Target（渲染目标）与 Frame Buffer（帧缓冲）与 Swap Chain（交换链）

```
这三者描述的是"画到哪里"的递进关系：

GPU 作画不是在屏幕上直接画的，而是在内存中的"画板"上画。

Render Target (单张画板)
  └─ GPU 写入像素数据的缓冲区（通常就是一张纹理）
     └─ 可以是颜色 + 深度/模板的组合

Frame Buffer (一组画板的集合)
  └─ 一个 Frame Buffer = 多个 Render Target 的绑定
     └─ 例如: Color RT (RGBA 颜色) + Depth RT (深度值) + Stencil RT (模板标记)

Swap Chain (双缓冲/多缓冲机制)
  └─ 至少 2 张"最终 Frame Buffer"交替使用
     └─ GPU 写入 Back Buffer → 完成后与 Front Buffer 交换 → 显示器显示
     └─ 这是避免"画面撕裂"的机制
```

**帧同步的 CS 视角**：Swap Chain 就是一个**生产者-消费者模型**——GPU 是生产者（渲染帧到 Back Buffer），显示器是消费者（读取 Front Buffer 刷新屏幕）。VSync 是当 Back Buffer 没准备好时**阻塞生产者**的同步机制。

### 2.6 深度/模板缓冲与 Early-Z

```
Depth Buffer (深度缓冲区, Z-Buffer)
  └─ 每个像素记录自己离摄像机的距离（深度值）
     └─ 深度测试：新像素的深度 ≥ 已存深度 → 丢弃（被遮挡）
     └─ 深度写入：新像素的深度 < 已存深度 → 写入并更新深度值

Early-Z (提前深度测试)
  └─ 管线优化：在片元着色器执行之前就做深度测试
     └─ 如果一个像素会被遮挡，连着色器都不用跑 → 节省大量 GPU 时间
     └─ 前提条件：片元着色器不能修改深度值、不能使用 discard
     └─ 这就是 Unity/UE 默认开启 Depth Prepass 的原因

Stencil Buffer (模板缓冲区)
  └─ 每个像素一个标记位（8bit 整数）
     └─ 用于区域遮罩、镜面反射、贴花等效果
     └─ 对应 Shader 中的 stencil 操作（增减/比较/替换）
```

### 2.7 透明度与 Overdraw

```
Opaque (不透明物体) 渲染策略：
  从近到远画 → Early-Z 把后面被遮挡的全丢弃 → 每个像素最多着色 1 次

Transparent (半透明物体) 渲染策略：
  从远到近画 → 每个透明层都要叠加到已有颜色上
  → 同一个像素可能被着色 5-10 次 → Overdraw

Overdraw = 同一像素被多次绘制的现象
  - 1x Overdraw = 正常（每个像素着色 1 次）
  - 4x Overdraw = 每个像素平均着色 4 次 → GPU 后端工作量 ×4
  
原因：
  1. 透明物体堆叠（最典型）
  2. 没有 Depth Prepass 时的不透明物体画序问题（先画的被后画的覆盖）
  3. UI 层级重叠
  4. 粒子特效叠加

衡量：RenderDoc 的 "Overdraw View" 可以可视化每像素被写了多少次
```

> Overdraw 直接放大**填充率（Fill Rate）** 需求。移动端 TBDR 架构对高 Overdraw 特别敏感。

### 2.8 渲染路径关键词

这个对比表格在系列文档中会反复被引用：

```
Forward Rendering (前向渲染)：
  每个物体在自己的 Draw Call 中直接完成所有光照计算
  ┌────────────────────────────────────────────┐
  │ 物体 A → VS → PS(光照 A) → 写到 Render Target │
  │ 物体 B → VS → PS(光照 B) → 写到 Render Target │
  │ 物体 C → VS → PS(光照 C) → 写到 Render Target │
  └────────────────────────────────────────────┘
  优点：支持 MSAA、内存友好、透明物体自然
  缺点：多光源时 PS 复杂度爆炸（每个物体算所有光源）

Deferred Rendering (延迟渲染)：
  先把场景的"几何信息"（法线、颜色、粗糙度等）写入多张 RT（G-Buffer），
  再逐像素计算光照
  ┌────────────────────────────────────────────┐
  │ GBuffer Pass: 所有物体 → 写 GBuffer        │
  │   ├─ RT0: Albedo(颜色)                     │
  │   ├─ RT1: Normal(法线) + Roughness         │
  │   └─ RT2: Depth                            │
  │ Light Pass: 逐像素遍历 G-Buffer 算光照      │
  └────────────────────────────────────────────┘
  优点：多光源支持好、SSAO/SSR 等后处理效果自然
  缺点：不支持 MSAA、G-Buffer 占用大量显存带宽、不透明/透明物体需要分开处理
```

## 3. GPU 硬件基础

即使你只做 CPU 端开发，了解 GPU 的硬件模型也能极大帮助你理解 GPU 性能分析。

### 3.1 CPU 并行 vs GPU 并行

```
CPU 核心模型 (你熟悉的)：
  8 个核心 × 1 个线程 = 8 个并行线程
  每个线程可以做完全不同的事 (MIMD)
  每个线程有自己的分支、自己的内存访问模式
  
GPU 核心模型 (SIMT)：
  一个 SM (Streaming Multiprocessor) 有 64-128 个 CUDA Core
  但同一时刻，32 个 Core 必须执行相同的指令！
  (NVIDIA: 32 = 1 Warp, AMD: 32 = 1 Wavefront)

  类比：32 个人排成一排齐步走
  - 能并排走 → 快
  - if-else 分支 → 一半人原地踏步等另一半走完 → "Warp Divergence" 性能损失
  - 有人绊倒（内存访问未命中）→ 所有人都等他回来 → "Memory Stall"

这解释了为什么 GPU 上：
  - 简单的、数据并行的计算很快（比如把 100 万个像素各加 0.1）
  - 复杂分支很慢（Warp Divergence）
  - 内存访问模式很重要（Coalesced Access 可以让一次读服务 32 个线程）
```

### 3.2 GPU 核心术语

| 术语 | 含义 | CS 对应类比 |
|------|------|------------|
| **SM (Streaming Multiprocessor)** | NVIDIA GPU 的基本计算单元，包含 CUDA Core + 寄存器 + 缓存 + 调度器 | 一个多核 CPU 核心（但内部 SIMT，不是 MIMD） |
| **Warp** (NVIDIA) / **Wavefront** (AMD) | 32 个线程一组，同一时刻执行相同指令 | SIMD 向量宽度 32 的向量处理器 |
| **CUDA Core** (NVIDIA) / **Stream Processor** (AMD) | GPU 上最基础的 ALU 单元 | CPU 上的一个 ALU（但一个 SM 里有几十上百个） |
| **TMU (Texture Mapping Unit)** | 专门处理纹理采样（读取纹理、过滤、寻址） | 专用的纹理数据访问协处理器 |
| **ROP (Render Output Unit)** | 处理像素输出：深度测试、混合、写入 Frame Buffer | 显卡最后的"输出流水线" |
| **VRAM (Video RAM)** | GPU 专用的显存（GDDR6/GDDR6X/HBM） | 独立于系统内存的高速存储 |
| **Occupancy (占用率)** | 一个 SM 上同时活跃的 Warp 数量 / 理论最大 Warp 数量 | CPU 线程池中同时运行的任务数 / 核心数 |
| **Bandwidth (显存带宽)** | GPU 读写 VRAM 的最大速率 (GB/s) | 内存带宽 (GB/s)，但 GPU 对带宽更敏感 |

### 3.3 GPU 架构关键差异

```
IMR (Immediate Mode Rendering) — 桌面 GPU (NVIDIA/AMD):
  画一个物体 → 立刻写 VRAM → 画下一个 → 再写 VRAM → ...
  ┌─────────────────────────────────────┐
  │ GPU Core ←→ L2 Cache ←→ VRAM        │
  │ 每次读写都经过显存总线               │
  │ Bandwidth 需求高 (300-1000 GB/s)    │
  └─────────────────────────────────────┘
  特点：简单直接，带宽够大就能跑快
  问题：高分辨率 + 大量读写 = 带宽瓶颈

TBDR (Tile-Based Deferred Rendering) — 移动 GPU (Adreno/Mali/PowerVR/Apple):
  把屏幕切成 16×16 / 32×32 的 Tile，
  每个 Tile 先在片上超快 SRAM 里完成所有渲染，
  最后一次性写回 VRAM
  ┌───────────────────────────────────────────┐
  │ GPU Core ←→ Tile Memory (片上, ~100KB)     │
  │ (所有该 Tile 的 Draw Call 在这里做完)      │
  │ 完成 → 写回 VRAM (每个 Tile 只写一次)       │
  └───────────────────────────────────────────┘
  特点：极低的显存带宽需求（省电）
  问题：每个 Tile 结束时要做一次"Resolve"写回，
        多 Render Target 时可能溢出 Tile Memory
```

**与性能分析的关系**：

- RTX 4090 的 RT 瓶颈可能是 Shader 复杂度和带宽 → NSight Graphics 看 SM 利用率和带宽饱和
- 骁龙 8 Gen X 的瓶颈可能是 Tile Memory 溢出（GBuffer 太多） → Snapdragon Profiler 看 Memory Read/Write
- "移动端比 PC 更需要关掉 MSAA 和高分辨率 RT" → 因为 Tile Memory 宝贵，溢出就引起多次 VRAM 往返

## 4. 游戏引擎特有概念

以下是 Unity 和 UE 引擎中常用的专属名词。

### 4.1 Unity 特有

| 术语 | 含义 | 与本系列的关联 |
|------|------|--------------|
| **GameObject** | 场景中最基本的实体（等价于 UE 的 Actor） | Profiler 中按 GameObject 分类查看 CPU 开销 |
| **Component** | 附加在 GameObject 上的功能模块（Transform/MeshRenderer/Script 等） | 每个 Component 的 Update() 是 CPU 主要消耗者 |
| **MonoBehaviour** | Unity 脚本的基类，有自己的 Update/LateUpdate/FixedUpdate 生命周期 | Profiler 中按脚本方法查看耗时 |
| **Prefab** | 可复用的 GameObject 模板 | 大量同名 Prefab 适合 GPU Instancing 优化 |
| **Batching (Static/Dynamic)** | 把多个物体合并成一个 Draw Call 的优化技术 | 01-CPU 性能分析、05-Unity 平台 |
| **SRP Batcher** | URP/HDRP 中的高级合批方案，按 Shader 合批而非按 Mesh/材质 | 05-Unity 平台 |
| **GPU Instancing** | 同一 Mesh+Material 的多个实例在一次 Draw Call 中绘制 | "为什么 Draw Call 只减了 10 个？Instancing 效果不够" |
| **URP / HDRP / Built-in** | Unity 三种渲染管线：通用管线 / 高清管线 / 内置管线 | 不同管线的性能特征和工具支持不同 |
| **GC (Garbage Collection)** | C# 托管堆的垃圾回收，Boehm GC（非分代） | GC 触发时所有托管线程暂停 1-20ms |
| **IL2CPP** | Unity 将 C# IL 翻译为 C++ 再编译 → 减少 GC 压力 | 构建/构建时间和运行时性能的权衡 |
| **Job System** | Unity 的多线程任务系统（C# Job） | CPU 热点分析时关注 Job 调度 |
| **Burst Compiler** | Unity 的 C#→LLVM 编译器，用于 Job System | 可以与 C++ 性能接近 |
| **Player Loop** | Unity 每一帧的执行顺序（Input → Update → Animation → Physics → Render） | Profiler 中的帧时间分解就是按 Player Loop 展示 |
| **Coroutine (协程)** | 分帧执行的长耗时任务，在 yield 处让出控制权 | 用来分散加载/生成等重操作，避免单帧尖峰 |
| **Asset Bundle** | 可动态加载的资源包（纹理/模型/Shader） | 加载耗时会影响帧稳定性和内存 |
| **Addressables** | Unity 新的异步资源管理系统，替代 Asset Bundle | 同上，但更灵活 |

### 4.2 UE 特有

| 术语 | 含义 | 与本系列的关联 |
|------|------|--------------|
| **Actor** | 场景中的基本实体（等价于 Unity 的 GameObject） | Insights 中按 Actor 类型查看耗时 |
| **Component (UE)** | 附加在 Actor 上的功能模块 | 类似 Unity Component |
| **Blueprint** | UE 的可视化脚本系统 | 蓝图函数调用有虚函数开销，VTune 能看到 |
| **Level / World** | 关卡 / 世界（场景容器） | World Partition 用于开放世界流式加载 |
| **GameThread / RenderThread / RHIThread** | UE 的三线程渲染架构 | Insights 时间线可以看三线程的并行效率 |
| **Draw Call (UE 项目中的叫法)** | 通常叫 Draw Call / RHI Draw Call | stat rhi 命令查看 |
| **Nanite** | UE5 的虚拟化几何系统（自动 LOD） | Nanite culling/光栅化在 GPU 上，改变了瓶颈归属 |
| **Lumen** | UE5 的动态全局光照系统 | Lumen 大量依赖 Compute Shader 和 Trace，对 RTX GPU 有 RT core 加速 |
| **World Partition** | 开放世界关卡分割加载 | 流式加载的 IO 和内存是主要性能关注点 |
| **stat 命令** | 控制台命令，如 `stat fps` `stat gpu` `stat unit` | 06-UE平台 中有完整的命令参考 |
| **Console Variables (CVars)** | 运行时控制引擎行为的变量，如 `r.ScreenPercentage 70` | 用于快速验证渲染选项对性能的影响（如降分辨率测试 GPU-bound） |

### 4.3 跨引擎通用概念

| 术语 | Unity 侧 | UE 侧 | 说明 |
|------|---------|-------|------|
| **LOD (Level of Detail)** | LOD Group | LOD / Nanite 替代 | 远处物体用低模，减少三角形数量 |
| **Mipmap** | 自动生成 | 自动生成 | 纹理的多级分辨率链，远处用低分辨率版本 |
| **Culling (Frustum/Occlusion)** | 自动 + Occlusion Culling | 自动 + HZB + Nanite | 不渲染摄像机看不到的物体 |
| **Texture Streaming (纹理流送)** | Texture Streaming | Texture Streaming | 根据距离动态加载/卸载纹理的 Mipmap 级别 |
| **Occlusion Query** | GPU 硬件查询 | GPU 硬件查询 | 上帧渲染结果决定下帧是否可见 |
| **Z-Prepass / Depth Prepass** | 可选（URP 默认） | 默认开启 | 先渲染深度 → Early-Z 减少后续像素着色 |
| **HZB (Hierarchical Z-Buffer)** | N/A（不用） | 引擎内置 | 用低分辨率深度图的 Mipmap 链加速遮挡查询 |

## 5. 性能分析术语速查

### 5.1 分析领域名词

| 术语 | 含义 | 容易误解的地方 |
|------|------|--------------|
| **Profiling (剖析)** | 测量程序各部分的耗时/资源消耗 | ≠ Debugging（调试是找 Bug） |
| **Frame Capture (帧捕获)** | 把一帧所有的渲染命令录制下来，离线回放分析 | RenderDoc 的"捕捉一帧"就是做这个 |
| **Sampling (采样)** | 定时中断 CPU、记录当前调用栈，按统计推算函数耗时占比 | 开销低但无法捕获很短的函数 |
| **Instrumentation (插桩)** | 在函数入口/出口插入计时代码 | 精确但插入后改变了原本的执行特性（**观察者效应**） |
| **Hotspot (热点)** | 消耗 CPU/GPU 时间最多的函数或代码段 | 注意：占比高不等于"应该优化"（可能本来就应该那么耗时） |
| **Flame Graph (火焰图)** | 自底向上的调用栈可视化，越宽 = 耗时越多 | 宽度 = 占比，颜色无意义（工具默认配色） |
| **Call Tree (调用树)** | 按调用关系组织的函数耗时表格 | 关注 Self Time（函数自身耗时）vs Total Time（含子调用） |
| **Baseline (基线)** | 优化前的性能快照，用于 A/B 对比 | 必须相同场景、相同视角、相同硬件 |
| **PGO (Profile-Guided Optimization)** | 用真实运行数据指导编译器做更优的内联/分支预测 | C++ 构建可开启，见 07-C++源码构建 |
| **Micro-benchmark** | 隔离状态下测量单一操作（如一次 memcpy、一次 malloc） | vs Macro-benchmark 测量完整帧 |

### 5.2 GPU 性能计数器

在 NSight Graphics、PIX、Snapdragon Profiler 等工具中你会看到这些词：

| 计数器 | 含义 | 告诉你的信息 |
|--------|------|------------|
| **GPU Time** | GPU 执行该 Draw Call / Pass 的耗时 | 某个 Draw Call 是否特别慢 |
| **SM Utilization** | SM 中活跃 Warp 的占比 | 是否在等待内存（低）还是正在计算（高） |
| **Memory Bandwidth Utilization** | 显存带宽使用率 (%) | 是否被带宽限制（接近 100% = Bandwidth-bound） |
| **Texture L1/L2 Hit Rate** | GPU 纹理缓存的命中率 | 纹理采样模式是否缓存友好 |
| **Fill Rate** | 每秒写入像素数量 | 与分辨率 × Overdraw 直接相关 |
| **Triangle Throughput** | 每秒处理的三角形数量 | 几何复杂度是否超标 |
| **Primitive Culled** | 被裁剪（视锥/背面）掉的三角形占比 | Culling 是否工作正常 |
| **Shader ALU Utilization** | ALU 计算单元的利用率 | Shader 的算术运算是否饱和 |
| **Warp Occupancy** | SM 上同时存在的 Warp 数量 / 最大容量 | Block size / 寄存器使用是否合理 |

### 5.3 CPU 相关的性能术语

这些是本系列中反复出现的概念。其中很多你可能已经有 CS 基础来理解：

| 术语 | CS 视角的理解 | 游戏引擎中的额外含义 |
|------|-------------|-------------------|
| **Cache Miss** | L1/L2/L3 缓存未命中 → 访问内存延迟 | 游戏物体组件分散在不同内存区域 → AoS 布局 → 缓存命中率低 → 改用 SoA |
| **Branch Misprediction** | CPU 分支预测错误 → 流水线冲洗 | 引擎的虚函数调用（vtable dispatch）是不可预测的间接跳转 |
| **False Sharing** | 两个线程修改同一个缓存行中的不同变量 → 互相失效 | Job System 中常见（多个 Job 写入相邻的数组元素） |
| **Lock Contention** | 多线程争抢同一个锁 | Game Thread 和 Render Thread 之间的同步点 |
| **Memory Pool / Object Pool** | 预分配并复用以避免频繁 malloc/free | Unity 把 GameObject 放回 Pool 而不是 Destroy |
| **AoS vs SoA** | Array of Structs(每个元素紧邻) vs Struct of Arrays(同字段紧邻) | 物理、粒子系统触发频繁随机访问 → SoA 缓存友好 |
| **SIMD / Vectorization** | 指令级并行 (SSE/AVX/NEON) | 引擎中矩阵/向量运算大量使用，Burst Compiler 自动向量化 C# |

## 6. 常见概念速查表（按拼音排序）

适合在阅读系列文档时快速查阅：

> 表 A：游戏/图形特有术语

| 词   | 一句话解释 |
|------|-----------|
| Alpha Blending | 半透明混合：新像素颜色 = 新颜色 × alpha + 旧颜色 × (1-alpha) |
| Batch / Batching | 合并多个 Draw Call 为 1 个，降 CPU 负载 |
| Bloom | 后处理特效：亮区域向周围扩散光晕 |
| Compute Shader | 不参与渲染管线的 GPU 通用计算，做物理/AI/后处理 |
| Culling | 剔除看不见的物体（视锥/遮挡/背面），不提交给 GPU |
| Depth of Field (DOF) | 景深效果：焦点外模糊 |
| Dispatch | Compute Shader 的"Draw Call"（不是画图，是启动计算任务组） |
| Draw Call | CPU 通知 GPU 画一批图形的 API 调用 |
| Fill Rate | GPU 每秒能写入的像素数（硬件上限） |
| Frame Pacing | 帧间隔的均匀性（30fps 但间隔均匀 ≠ 30fps 但忽快忽慢） |
| Frustum Culling | 剔除摄像机视锥体外的物体（最基础的剔除） |
| G-Buffer (Geometry Buffer) | 延迟渲染中存储几何信息的 RT 集（法线/颜色/深度等） |
| HDR (High Dynamic Range) | 颜色值可以 >1.0，保留亮度信息直到 Tone Mapping |
| Instancing (GPU Instancing) | 同一 Mesh 的多次绘制在 GPU 端复制完成，只需 1 个 Draw Call |
| LOD (Level of Detail) | 根据距离切换不同精细度的模型 |
| Mip Level / Mipmap Chain | 纹理的多级分辨率链（1/1 → 1/2 → 1/4 → ...），提升缓存效率 |
| MSAA (Multi-Sample AA) | 硬件抗锯齿：每像素采样多个覆盖点，不增加 Shader 计算量 |
| Normal Map | 用纹理存储法线方向扰动信息 → 低模看起来像高模的细节 |
| Overdraw | 同像素被多次绘制（越靠后的层越浪费） |
| Post-Processing | 在最终画面上叠加的全屏效果（Bloom/Color Grading/Vignette 等） |
| Render Queue | 渲染顺序：Background < Geometry < AlphaTest < Transparent < Overlay |
| Render State | GPU 当前的一组设置（Blend 模式/深度测试/Cull 模式），切换就需要 State Change |
| SRP (Scriptable Render Pipeline) | Unity 的可编程渲染管线框架（URP 和 HDRP 都基于 SRP） |
| State Change | 改变渲染状态（如切换材质），需要验证/刷新 GPU 寄存器 → CPU 开销 |
| TAA (Temporal AA) | 利用前几帧的像素信息做抗锯齿（移动端几乎不用，因为消耗历史帧 buffer） |
| Tone Mapping | 将 HDR 颜色映射到显示器可显示的 LDR 范围 |
| UV Coordinates | 纹理坐标（每一顶点对应纹理中的(u,v)位置） |
| Vertical Sync (VSync) | 等待显示器刷新完成后再交换帧缓冲，消除画面撕裂 |
| Viewport | 渲染画面的像素区域（不一定等于窗口大小） |
| VRAM | GPU 专用的显存（GDDR6/HBM），独立于系统内存 |

> 表 B：CS 基础概念在游戏性能中的体现

| CS 概念 | 在游戏性能中的对应 |
|---------|------------------|
| 线程/并行 | Game Thread + Render Thread + Job Workers 并行执行 |
| 上下文切换 | 线程间同步点（Fence/Barrier）的等待开销，在时间线上表现为空白 |
| 堆分配/缺页 | GameObject 频繁 Instantiate/Destroy → 堆碎片化 → 缺页增多 |
| 缓存行 (64B) | AoS 布局 → 每读取一个物体要加载整条缓存行 → 浪费带宽 |
| 虚函数调用 | 虚函数 = 间接跳转 → 分支预测失败 + vtable 读 → VTune 中 ICache Miss |
| 锁竞争 | Game/Render Thread 交界的同步点（如 CommandBuffer 提交），FSight |
| SIMD | 引擎的矩阵/向量运算、粒子系统更新天然向量化友好 |
| 调用开销 | Draw Call = GPU 层面的"函数调用"，但驱动层有额外序列化开销 |
