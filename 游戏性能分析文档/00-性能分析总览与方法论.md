## 1. 文档目的与读者对象

### 1.1 文档目的

本系列文档旨在对游戏性能分析的**完整工具链与方法论体系**进行系统化阐述。内容涵盖从 CPU/GPU 性能剖析到内存分析、从引擎平台工具（Unity/UE）到原生 C++ 工程调试、从桌面端到移动设备的跨平台性能测量。

- **跨平台视角**：覆盖 Unity / UE / 原生 C++ 三大开发栈，以及 PC / 移动端 / 主机三类目标平台

## 2. 性能分析的核心定位

游戏性能分析不是"出问题后再查"的被动行为，而是贯穿开发全周期的**主动测量体系**。它回答三个核心问题：

```
┌─────────────────────────────────────────────────────────────┐
│                    游戏性能分析三大问题                        │
│                                                             │
│  Q1: 当前性能基线是什么？                                     │
│      → 帧时间分布、CPU/GPU 哪边是瓶颈、内存占用基线           │
│                                                             │
│  Q2: 瓶颈在哪里？                                            │
│      → 哪个函数/Draw Call/Shader/内存分配在消耗时间           │
│                                                             │
│  Q3: 优化是否有效？                                          │
│      → A/B 对比验证、回归监控、确保改动不引入新瓶颈            │
└─────────────────────────────────────────────────────────────┘
```

**关键边界**：

- **性能分析 ≠ 性能优化**：分析是"定位瓶颈"，优化是"消除瓶颈"。本系列以前者为核心，后者在实战篇中提供策略指引
- **测量优先于直觉**：游戏引擎是复杂系统，凭直觉优化常常南辕北辙
- **工具是手段不是目的**：理解每种工具能测量什么、不能测量什么，比记住操作步骤更重要

## 3. 性能瓶颈分层模型

游戏帧时间消耗分布在**四个维度**上，性能分析的首要任务是判断瓶颈落在哪一层：

```
┌──────────────────────────────────────────────────────┐
│                  一帧的耗时构成                        │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │  CPU 侧 (Game Thread + Render Thread)          │  │
│  │  ├─ 逻辑更新 (AI/物理/动画/脚本)                │  │
│  │  ├─ 场景遍历与可见性剔除                        │  │
│  │  ├─ 渲染命令录制与提交                          │  │
│  │  └─ 资源加载/卸载                              │  │
│  ├────────────────────────────────────────────────┤  │
│  │  GPU 侧 (Graphics/Compute Queue)               │  │
│  │  ├─ 顶点处理 (顶点着色器/曲面细分)              │  │
│  │  ├─ 光栅化与像素处理 (片元着色器)               │  │
│  │  ├─ 带宽受限操作 (GBuffer读写/纹理采样)         │  │
│  │  └─ 同步等待 (屏障/查询/帧间依赖)              │  │
│  ├────────────────────────────────────────────────┤  │
│  │  内存子系统                                     │  │
│  │  ├─ CPU 内存 (堆分配/缓存命中率/页面缺失)       │  │
│  │  └─ GPU 显存 (带宽/分配碎片/容量溢出)           │  │
│  ├────────────────────────────────────────────────┤  │
│  │  设备/平台约束                                   │  │
│  │  ├─ 发热降频 (移动端 thermal throttling)       │  │
│  │  ├─ 功耗预算 (电池续航/散热设计)                 │  │
│  │  └─ 硬件差异 (GPU 架构/驱动版本/核心数)         │  │
│  └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

### 瓶颈定位决策流

```
帧时间超标 (>16.67ms / 60fps)
     │
     ▼
 ┌───────────────────┐
 │ CPU-bound 还是     │
 │ GPU-bound?        │
 └───────┬───────────┘
         │
    ┌────┴────┐
    ▼         ▼
 CPU-bound  GPU-bound
    │         │
    ▼         ▼
 CPU 分析    GPU 分析
 (VTune/     (RenderDoc/
  Profiler)   NSight)
    │         │
    ▼         ▼
 定位热点    定位热点
 函数/Draw   Shader/带宽
    │         │
    ▼         ▼
 ┌───────────────────┐
 │ 内存是否是隐性瓶颈? │
 │ (缓存未命中/分配   │
 │  开销/显存带宽)     │
 └───────┬───────────┘
         │
         ▼
    ┌────┴────┐
    ▼         ▼
 CPU内存    GPU显存
 分析       分析
```

> **原则**：永远先判断瓶颈维度（CPU/GPU/内存/设备），再选择对应工具深入分析。跨维度猜测是性能分析中最常见的效率陷阱。

## 5. 性能分析方法论

### 5.1 测量驱动优化原则

性能分析遵循**测量 → 定位 → 优化 → 验证**的闭环：

```
    ┌──────────┐
    │ 1. 测量   │ ← 建立基线: 帧时间/CPU/GPU/内存 快照
    └────┬─────┘
         ▼
    ┌──────────┐
    │ 2. 定位   │ ← 瓶颈分层: CPU? GPU? 内存? 精确到函数/Draw/Shader
    └────┬─────┘
         ▼
    ┌──────────┐
    │ 3. 优化   │ ← 针对性修改: 合批/LOD/缓存/压缩/算法替换
    └────┬─────┘
         ▼
    ┌──────────┐
    │ 4. 验证   │ ← A/B对比: 同场景同视角重新测量, 确认改善且无回归
    └────┬─────┘
         │
         ▼
    改善达标? ──No──→ 回到 1
         │
        Yes
         ▼
    进入下一个瓶颈
```

### 5.2 分析环境要求

| 要求维度 | 说明 | 原因 |
|---------|------|------|
| **Release 构建** | 使用带调试符号的 Release/RelWithDebInfo | Debug 构建的优化关闭会严重失真 |
| **稳定场景** | 固定摄像机视角、固定输入序列 | 确保测量可比性 |
| **足够时长** | 至少采集 5-10 秒（300-600帧@60fps） | 统计平滑，滤除瞬时抖动 |
| **关闭垂直同步** | 或使用帧时间而非帧率 | vsync 会使帧时间钳制到 16.67ms 倍数，掩盖真实负载 |
| **代表性硬件** | 目标平台中位数或低端设备 | 高端设备无法暴露低端设备的瓶颈 |
| **独占运行** | 关闭后台无关程序 | 减少系统调度干扰 |

### 5.3 常见分析误区

| 误区 | 正确做法 |
|------|---------|
| ❌ "帧率低就是渲染慢" | 先判断 CPU-bound 还是 GPU-bound |
| ❌ 直接看某个函数耗时就优化 | 关注**占比**（占总帧时间百分比），而非绝对耗时 |
| ❌ 在 Debug 构建下分析性能 | 使用 RelWithDebInfo 或带符号的 Release |
| ❌ 只看单帧 | 采集多帧取统计分布，关注方差和尖峰 |
| ❌ 优化后不对比直接提交 | A/B 测量验证，确保改善且无其他回归 |
| ❌ 只在高端设备上测试 | 在目标最低配置上测试，暴露真实瓶颈 |
| ❌ 移动端只看帧率 | 移动端必须同时关注功耗和发热 |

## 6. 帧时间度量基础

### 6.1 帧时间 vs 帧率

帧时间（Frame Time / Frame Duration）是性能分析的**首选度量**，而非帧率（FPS）：

| 度量 | 单位 | 特点 | 问题 |
|------|------|------|------|
| **帧率 (FPS)** | 帧/秒 | 直观但非线性 | 60→30fps 感觉"降一半"，但 30→15fps 才是同等增量 |
| **帧时间 (ms)** | 毫秒 | 线性、可加性 | 16.67ms = 60fps，可直接拆分到各子系统 |

**帧时间可加性**是分析的核心优势：

```
单帧 25ms (40fps) 拆解:
┌─────────────────────────────────────┐
│ CPU 逻辑更新:     6ms                │
│ CPU 渲染提交:     4ms                │
│ GPU 执行:        12ms  ← 瓶颈        │
│ 同步等待:         3ms  ← 可压缩       │
│ 总计:           25ms                │
└─────────────────────────────────────┘
→ GPU 执行是最大占比 (48%)，优先优化
```

### 6.2 目标帧时间预算

| 目标帧率 | 帧时间预算 | 适用场景 |
|---------|-----------|---------|
| 30 fps | 33.33ms | 主机/大型开放世界 |
| 60 fps | 16.67ms | 竞技/动作/移动端标准 |
| 90 fps | 11.11ms | VR 标准最低 |
| 120 fps | 8.33ms | 高刷新率/VR 舒适 |
| 144 fps | 6.94ms | PC 竞技 |

### 6.3 CPU-bound 与 GPU-bound 判断

```
情况A: CPU 时间 > GPU 时间 → CPU-bound
┌──────────────────────────────┐
│ CPU: ████████████████ 18ms  │ ← 瓶颈
│ GPU: ████████ 12ms          │
│ 帧时间 = max(CPU, GPU) = 18ms│
└──────────────────────────────┘

情况B: GPU 时间 > CPU 时间 → GPU-bound
┌──────────────────────────────┐
│ CPU: ████████ 10ms          │
│ GPU: ████████████████ 20ms  │ ← 瓶颈
│ 帧时间 = max(CPU, GPU) = 20ms│
└──────────────────────────────┘

情况C: CPU 和 GPU 时间接近 → 双重瓶颈
┌──────────────────────────────┐
│ CPU: ████████████████ 17ms  │
│ GPU: █████████████████ 18ms │
│ 帧时间 = 18ms, 两侧都需要优化│
└──────────────────────────────┘
```

> **注意**：CPU 和 GPU 是**并行执行**的。帧时间不是 CPU 时间 + GPU 时间，而是两者的**较大值**加上同步等待。理解这一点是性能分析的基础。

## 8. 术语约定

| 术语 | 标准含义 | 常见误用 |
|------|---------|---------|
| **帧时间 (Frame Time)** | 单帧总耗时（毫秒），性能分析首选度量 | ❌ 与帧率混用（帧率非线性，不利于拆分分析） |
| **CPU-bound** | 帧时间由 CPU 侧耗时决定 | ❌ 认为"CPU 使用率高就是 CPU-bound"（需看帧时间瓶颈） |
| **GPU-bound** | 帧时间由 GPU 侧耗时决定 | ❌ 认为"画面复杂就是 GPU-bound"（需实际测量） |
| **采样 (Sampling)** | 周期性中断记录调用栈，低开销 | ❌ 等同于"不精确"（现代采样器精度足够） |
| **插桩 (Instrumentation)** | 在代码中注入计时代码，精确但有开销 | ❌ 适合所有场景（开销可能扭曲结果） |
| **Draw Call** | 单次绘制 API 调用（如 vkCmdDraw） | ❌ 等同于"渲染对象数量"（一个对象可能多次 Draw Call） |
| **Overdraw** | 同一像素被多次绘制 | ❌ 只影响移动端（PC 高分辨率同样受影响） |
| **Thermal Throttling** | 设备因发热降低 CPU/GPU 频率 | ❌ 仅影响帧率（实际同时影响帧时间稳定性） |
