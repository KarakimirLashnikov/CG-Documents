## 2. stat 命令体系

### 2.1 stat unit — 帧时间拆分

`stat unit` 是 UE 性能分析的**起点命令**，显示帧时间的多维度拆分：

```
stat unit 输出:
┌──────────────────────────────────────────────────┐
│                                                  │
│  Frame:  16.54   ← 总帧时间 (实际)               │
│  Game:    8.32   ← Game Thread 时间             │
│  Draw:    2.15   ← Render Thread 命令录制         │
│  GPU:    12.40   ← GPU 执行时间                  │
│  RHI:     1.80   ← RHI (Render Hardware Interface)│
│  Iris:    0.00   ← (保留)                        │
│  DynRes:  0.00   ← 动态分辨率                    │
│                                                  │
│  [Frame 1234]                                   │
│                                                  │
│  判断:                                           │
│  ├─ Frame = max(Game + Draw, GPU) + 同步        │
│  ├─ Game > GPU → CPU-bound (Game Thread)         │
│  ├─ GPU > Game → GPU-bound                      │
│  ├─ Draw 高 → 渲染命令录制瓶颈                   │
│  └─ RHI 高 → API 调用开销                       │
│                                                  │
│  本例: GPU 12.4ms > Game 8.3ms → GPU-bound      │
└──────────────────────────────────────────────────┘
```

**stat unit 的三线程模型**：

```
UE 渲染线程模型:
┌──────────────────────────────────────────────────────┐
│                                                      │
│  Game Thread (游戏线程)                              │
│  ├─ 逻辑更新 (AI/动画/物理/脚本)                     │
│  ├─ 场景可见性剔除                                    │
│  └─ 构建可见物体列表 → 传给 Render Thread            │
│  │                                                   │
│  Render Thread (渲染线程)                            │
│  ├─ 遍历可见物体                                     │
│  ├─ 执行渲染逻辑 (FPrimitiveSceneProxy)             │
│  ├─ 录制 RHI 命令                                    │
│  └─ 提交给 RHI Thread                               │
│  │                                                   │
│  RHI Thread (RHI 线程)                               │
│  ├─ 将引擎命令转换为图形 API 命令                    │
│  ├─ vkCmdDraw / glDrawElements / D3D12              │
│  └─ 提交到 GPU                                      │
│  │                                                   │
│  GPU                                                 │
│  └─ 执行渲染管线                                     │
│                                                      │
│  stat unit:                                          │
│  ├─ Game = Game Thread 耗时                          │
│  ├─ Draw = Render Thread 耗时 (命令录制)             │
│  ├─ RHI  = RHI Thread 耗时 (API 调用)               │
│  └─ GPU  = GPU 执行耗时                             │
└──────────────────────────────────────────────────────┘
```

## 3. Unreal Insights

### 3.1 Unreal Insights 定位

Unreal Insights 是 UE 的**专业级时间线追踪工具**，是 UE 性能分析的核心：

```
Unreal Insights 架构:
┌──────────────────────────────────────────────────────┐
│  数据采集                                             │
│  ├─ stat startfile → 采集到 .utrace 文件              │
│  ├─ trace.start [channel] → 实时流式追踪             │
│  └─ -trace=cpu,gpu,frame,... (命令行启动)             │
│                                                      │
│  数据通道 (Channels):                                 │
│  ├─ cpu:    CPU 函数级追踪                            │
│  ├─ gpu:    GPU Pass 追踪                             │
│  ├─ frame:  帧标记                                    │
│  ├─ render: 渲染系统追踪                              │
│  ├─ loading: 资源加载追踪                             │
│  ├─ asset:  资产管理追踪                              │
│  ├─ net:    网络追踪                                  │
│  └─ skeletal: 骨骼动画追踪                            │
│                                                      │
│  分析工具:                                            │
│  ├─ Timing Insights:  CPU/GPU 时间线                  │
│  ├─ Loading Insights: 异步加载分析                   │
│  └─ Networking Insights: 网络性能                    │
└──────────────────────────────────────────────────────┘
```

### 3.2 采集工作流

```
方法1: 离线采集 (推荐用于深度分析)
├─ 控制台输入: stat startfile
├─ 执行游戏操作 (进入目标场景, 游玩 30-60 秒)
├─ 控制台输入: stat stopfile
├─ 生成文件: Saved/Profiling/UnrealStats/<timestamp>.utrace
└─ 双击 .utrace → 自动打开 Unreal Insights

方法2: 实时流式追踪
├─ 控制台输入: trace.start cpu,gpu,frame,render,loading
├─ 或命令行启动: Game.exe -trace=cpu,gpu,frame
├─ Unreal Insights 自动连接, 实时显示
├─ 适合: 实时观察特定操作的影响
└─ 停止: trace.stop

方法3: 自动卡顿捕获
├─ stat dumphitches → 导出卡顿帧到日志
├─ 或配置: t.HitchFrameTimeThreshold=20 (20ms 以上为卡顿)
├─ 自动记录卡顿帧的详细调用栈
└→ 适合: 生产环境用户报告卡顿时分析

方法4: 命令行无人值守采集
├─ Game.exe -trace=cpu,gpu,frame,render -run=benchmark
├─ 配合自动化测试脚本
├─ CI/CD 集成
└→ 适合: 性能回归监控
```

### 3.4 关键分析技巧

**技巧1：帧间对比分析**

```
选中正常帧 (1231) 和卡顿帧 (1232):
├─ 对比两者 Timing Track
├─ 找到差异最大的 Track 段
├─ 正常帧 GPU: 11.5ms
│   └─ RenderBasePass: 0.7ms
├─ 卡顿帧 GPU: 22.5ms
│   └─ RenderBasePass: 8.5ms  ← 差异在此!
└→ BasePass 异常变慢, 排查原因 (可能是 LOD 切换/纹理流式)
```

**技巧2：Cycles (周期数) 而非毫秒**

```
Insights 显示 Cycles (CPU 周期) 而非 ms:
├─ 1 GHz = 10^9 cycles/sec → 1ms = 1,000,000 cycles
├─ 3.5 GHz → 1ms = 3,500,000 cycles
├─ 用 Cycles 的原因: 跨频率比较时更精确
│   (降频时同样 cycles 对应更多 ms)
└→ 但实际分析中可切换为 ms 显示
```

**技巧3：使用 Insight Filter**

```
过滤特定 Channel:
├─ 只看 CPU → 隐藏 GPU/RHI Track
├─ 只看指定线程 → 过滤 "Render Thread"
├─ 只看指定模块 → 过滤 "Physics"
└→ 减少视觉噪音, 聚焦分析目标
```

### 4.2 各 Pass 优化方向

| Pass | 含义 | 常见瓶颈 | 优化方向 |
|------|------|---------|---------|
| **PrePass** | 深度预通道 | 顶点数过多 | LOD/遮挡剔除 |
| **BasePass** | GBuffer 写入 | Overdraw/材质复杂度 | Z-Pre-Pass 合并/材质简化 |
| **DeferredShading** | 延迟光照计算 | 光源数量/体积光 | 光源合并/体积光优化 |
| **ShadowDepths** | 阴影深度渲染 | 阴影投射物多/级联 | 阴影 LOD/距离剔除 |
| **Translucency** | 透明物体渲染 | Overdraw/排序 | 透明物体 LOD/合并 |
| **PostProcessing** | 后处理 | Pass 数多/高分辨率 | 合并 Pass/降分辨率 |
| **AmbientOcclusion** | 环境光遮蔽 | 采样半径/层数 | 降低采样数/距离剔除 |
| **ScreenSpaceReflections** | SSR | 分辨率/粗糙度范围 | 降低 SSR 分辨率 |
| **VelocityFlat** | 运动矢量 | 不必要物体的运动矢量 | 排除静态物体 |

## 5. Session Frontend

### 5.1 Session Frontend 定位

Session Frontend 提供**实时远程性能监控**，可连接到运行中的设备：

```
Session Frontend 工作流:
1. Window → Developer Tools → Session Frontend
2. 连接到设备:
   ├─ 本机: 自动发现
   ├─ 远程设备: 输入 IP:Port (需开启 -SessionFrontEnd)
   └─ 移动设备: WiFi 连接 (设备与电脑同网段)
3. 选择运行中的实例 → 连接

实时监控面板:
┌──────────────────────────────────────────────────────┐
│  [Performance]                                       │
│                                                      │
```

## 7. UE 特有性能瓶颈

### 7.1 Blueprint 性能

```
Blueprint vs C++ 性能差异:
├─ Blueprint: 解释执行, 比原生 C++ 慢 10-100x
├─ Blueprint 调用有 VM 开销 (虚拟机进出)
├─ 每帧调用的逻辑 → 必须用 C++
├─ Blueprint 适合: 事件驱动/配置/不频繁逻辑
└→ 热点 Blueprint 应转为 C++ 或使用 Blueprint Nativize

Blueprint 性能检查:
├─ Insights 中查找 Blueprint 调用开销
├─ stat dumpTicks → 查看 Tick 函数列表
│  ├─ 标记为 "Blueprint" 的 Tick → 考虑转 C++
│  └→ 大量 Blueprint Tick = 性能瓶颈
├─ 控制台: p.EarlyOutRemoveTickDependencies=1
└→ 蓝图转 C++ 的标准路径: 使用 UFunction 标记
```

### 7.2 Tick 性能

```
stat dumpTicks 分析:
├─ 输出所有注册的 Tick 函数
├─ 按 Tick Group 分类:
│   ├─ TG_PrePhysics
│   ├─ TG_DuringPhysics
│   ├─ TG_PostPhysics
│   ├─ TG_PostUpdateWork
│   └─ TG_NewlySpawned
│
├─ 每个 Tick 显示:
│   ├─ Actor 名称
│   ├─ Tick 函数
│   ├─ 是否 Blueprint
│   ├─ Tick 间隔
│   └─ 总 Tick 时间
│
├─ 优化方向:
│   ├─ 减少 Tick 数量 (不需要每帧更新的 Actor)
│   │   → 设置 Tick 间隔 (PrimaryActorTick.TickInterval)
│   │   → 距离剔除 (远处降低 Tick 频率)
│   │   → 完全关闭不需要的 Tick
│   ├─ Blueprint Tick → C++ Tick
│   ├─ 使用 Timer 替代 Tick (低频更新)
│   └─ 使用 Mass Entity (UE5 ECS) 批量处理
│
└─ UE5 ECS (Mass Entity):
    └→ 大量同类实体用 Mass 替代 Actor+Tick
```

### 7.3 渲染线程瓶颈

```
UE 渲染线程模型导致的问题:
├─ Game Thread → 可见物体列表 → Render Thread
│   如果 Game Thread 慢 → Render Thread 等待
│   如果 Render Thread 慢 → Game Thread 等待
│
├─ 单线程渲染录制 → 无法利用多核
│   → UE5.3+ 支持部分多线程录制 (Nanite/MeshDrawPipeline)
│
├─ Render Thread 瓶颈表现:
│   ├─ stat unit: Draw 时间高
│   ├─ Insights: Render Thread Track 中耗时长
│   └→ 优化方向:
│       ├─ 减少 Draw Call (合批/LOD/剔除)
│       ├─ 使用 Nanite (自动 LOD + 高效渲染)
│       ├─ 使用 Instance Static Mesh
│       ├─ 减少材质变体
│       └→ 减少 Visible 物体 (CullDistance/遮挡)
│
└─ RHI Thread 瓶颈:
    ├─ stat unit: RHI 时间高
    ├→ 通常是 API 调用开销
    └→ 使用 Bindless / 减少 Descriptor 更新
```

### 7.4 Lumen 与 Nanite 分析

```
UE5 Lumen (全局光照):
├─ stat gpu 中查看 Lumen 相关 Pass:
│   ├─ LumenScreenProbeGather
│   ├─ LumenDiffuseIndirect
│   └─ LumenCardCapture
├─ Lumen 性能开销大, 移动端/低端机需降级
├─ 分析: Insights 中 Lumen Track
├─ 优化:
│   ├─ 降低 Lumen 质量 (Screen Probe 分辨率)
│   ├─ 限制 Lumen 更新频率
│   ├─ 使用 Lumen 性能预设
│   └→ 低端设备: 退回 SSAO + 烘焙光照

UE5 Nanite (虚拟几何):
├─ stat gpu 中查看 Nanite 相关 Pass:
│   ├─ NaniteCulling
│   ├─ NaniteRaster
│   └─ NaniteMaterial
├─ Nanite 优势: 无需手动 LOD, 自动处理
├─ 但: 像素着色器开销可能增加 (可见像素多)
├─ 分析: Insights 中 Nanite Track
├─ 优化:
│   ├─ Nanite 适合静态网格, 不适合动态变形
│   ├─ 控制最大像素误差 (Max Pixel Error)
│   └─ Nanite 不支持某些材质特性 (半透明/曲面细分)
│
└→ Nanite 改变了 GPU 瓶颈分布: 几何不再是瓶颈, 像素/带宽成为新瓶颈
```

## 8. UE 性能分析实战工作流

```
Step 1: 快速诊断
├─ stat unit → 判断 CPU-bound 还是 GPU-bound
├─ stat fps → 确认帧率目标
├─ stat gpu → 如果 GPU-bound, 定位哪个 Pass 慢
└→ 30 秒内确定瓶颈方向

Step 2: 深度追踪
├─ stat startfile → 采集 Insights trace
├─ 或: trace.start cpu,gpu,frame,render,loading
├─ 运行 30-60 秒覆盖目标场景
├─ stat stopfile → 生成 .utrace
└→ 打开 Unreal Insights 分析

Step 3: Insights 分析
├─ 选中目标帧 (高帧时间帧)
├─ Timing Insights → 定位热点 Track
│   ├─ Game Thread → UWorld::Tick 子调用
│   ├─ Render Thread → 渲染命令录制
│   └─ GPU → 各 Pass 耗时
├─ Counters → Draw Call/内存/三角形趋势
├─ 对比正常帧和卡顿帧
└→ 记录热点函数和 Pass

Step 4: 针对性优化
├─ CPU/Game Thread 瓶颈:
│   ├─ stat dumpTicks → Tick 开销分析
│   ├─ Blueprint → C++ 转换
│   ├─ 减少 Tick 数量 (间隔/距离剔除)
│   ├─ 物理: 减少碰撞体/简化场景
│   └─ AI: 减少 Tick 频率
│
├─ Render Thread 瓶颈:
│   ├─ 减少 Draw Call (合批/LOD/Nanite)
│   ├─ 减少材质变体
│   ├─ 优化可见性剔除
│   └→ 使用 Instance Static Mesh
│
├─ GPU 瓶颈:
│   ├─ stat gpu → 定位最慢 Pass
│   ├─ PostProcessing: 减少 Pass/降分辨率
│   ├─ DeferredShading: 减少光源
│   ├─ Translucency: 透明物体 LOD
│   ├─ Lumen: 降质量/降频更新
│   └─ Shadow: 阴影 LOD/距离剔除
│
└─ 内存瓶颈:
    ├─ stat memory → 内存分类
    ├─ memreport -full → 详细报告
    ├─ 纹理: 压缩/流式加载/虚拟纹理
    └─ 网格: Nanite/LOD/合批

Step 5: 验证
├─ 相同场景重新采集 Insights trace
├─ 对比优化前后帧时间
├─ 确认瓶颈 Pass 占比下降
├─ stat unit 确认 Game/GPU 时间改善
└→ 多设备验证
```
