# 游戏性能分析 — 设备与平台性能分析

> 本文档是「游戏性能分析」系列文档的第 **4** 篇，详细阐述跨设备、跨平台的性能分析方法论，涵盖移动端功耗与发热分析、PC 硬件分层测试、主机平台特性，以及移动端 GPU 架构（Adreno/Mali/PowerVR/Apple GPU）的差异分析。

---

## 1. 设备性能分析概述

### 1.1 为什么需要跨设备分析

同一份游戏代码在不同设备上的性能表现可能天差地别——不是代码有 bug，而是硬件架构差异导致：

```
同一场景在不同设备的帧时间:
┌───────────────────────────────────────────────────────┐
│ 设备              │ 帧时间   │ 瓶颈              │ 备注 │
├───────────────────┼──────────┼───────────────────┼─────┤
│ RTX 4090 (PC)    │ 5ms      │ CPU 提交          │ GPU空闲│
│ RTX 3060 (PC)    │ 12ms     │ 像素着色器        │ 中端 │
│ Steam Deck       │ 18ms     │ 带宽              │ 掌机 │
│ iPhone 15 Pro    │ 20ms     │ 带宽 + 功耗       │ 移动 │
│ Snapdragon 8 Gen3│ 28ms     │ 发热降频          │ 移动 │
│ Nintendo Switch  │ 33ms     │ GPU 算力          │ 主机 │
└───────────────────────────────────────────────────────┘

→ 同一代码, 五种不同瓶颈!
→ 仅在一种设备上优化是不够的
```

### 1.3 关键指标速查

设备级性能分析关注的是**硬件状态而非代码热点**——CPU/GPU 是否在降频、功耗是否超标、温度是否触发保护。这些指标是移动端性能分析的"生命体征"。

#### 1.3.1 热状态类指标 — "设备热不热、有没有在降频"

| 指标 | 含义 | 正常范围 | 异常信号 | 查看工具 |
|------|------|---------|---------|---------|
| **SoC Temperature** | 芯片温度 (℃) | < 45℃ | > 55℃ → 接近降频阈值 | Android Profiler / Snapdragon Profiler / Xcode |
| **Skin Temperature** | 设备表面温度 (℃) | < 38℃ | > 43℃ → 用户体感发烫 | 厂商 SDK / 手动测温 |
| **Thermal Throttling Status** | 是否触发降频及降频等级 | None | Light / Moderate / Severe | Android Thermal API / Snapdragon Profiler |
| **Frequency Reduction %** | CPU/GPU 频率相比最大值的降幅 | 0% | > 30% → 严重降频 | Snapdragon Profiler / Mali Streamline |
| **Thermal Headroom** | 距降频阈值的温度余量 (℃) | > 15℃ | < 5℃ → 即将降频 | Android Power API |

```
移动端降频曲线示意:

  GPU 频率
  100% ─────────────────────────
                            ╲
   80% ──────────────────────╲──────  Light Throttle
                               ╲
   60% ────────────────────────╲────  Moderate Throttle  
                                ╲
   40% ─────────────────────────╲───  Severe Throttle
                                 ╲___
   0%  ───────────────────────────────
        0min    5min    10min   15min   20min

  ┌───────────────────────────────────────────────────────┐
  │  典型场景:                                            │
  │  游戏开始 → GPU 满频运行 → 芯片温度上升               │
  │  → 触发 Light Throttle (GPU 降到 80%)                 │
  │  → 温度继续上升 → Moderate (降到 60%)                  │
  │  → 帧时间从 16ms 逐步恶化到 28ms                       │
  │  → 用户感受: "玩了几分钟就开始卡"                      │
  │                                                       │
  │  → 性能分析时如果不看温度曲线,                        │
  │    会误判为 "代码有 bug 导致帧率下降"                  │
  └───────────────────────────────────────────────────────┘
```

> **关键理解**：移动端性能分析中，"降频后的帧时间"和"满频下的帧时间"是完全不同的基线。如果你只看第 1 分钟的帧时间（满频），会得出"性能没问题"的错误结论。**必须在设备达到热稳态后（通常运行 10-15 分钟）再测量。**

#### 1.3.2 功耗类指标 — "设备在消耗多少电量"

| 指标 | 含义 | 正常范围 | 异常信号 | 查看工具 |
|------|------|---------|---------|---------|
| **Power Draw (整机功耗)** | 设备总功耗 (W 或 mW) | 移动端 2-5W | > 8W → 发热严重 / 电池快速消耗 | Android Battery Historian / Monsoon 功耗仪 |
| **GPU Power** | GPU 单独功耗 | — | 占总功耗 > 60% → GPU 是耗电主因 | Snapdragon Profiler / Mali Streamline |
| **CPU Power** | CPU 单独功耗 | — | 占总功耗 > 50% → CPU 是耗电主因 | 同上 |
| **Battery Drain Rate** | 电池消耗速率 (%/h 或 mA) | < 10%/h | > 25%/h → 功耗过高 | Android Battery Historian / Xcode Energy Log |
| **Energy per Frame** | 每帧消耗的能量 (mJ/帧) | — | 越低越好，是移动端优化的终极指标 | 计算式: Power(W) × Frame Time(s) |

```
Energy per Frame — 移动端优化的终极指标:

  场景A: 满频跑 60fps (16.7ms), 功耗 6W
    Energy/Frame = 6W × 0.0167s = 100mJ/帧

  场景B: 降频跑 30fps (33.3ms), 功耗 3W  
    Energy/Frame = 3W × 0.0333s = 100mJ/帧

  场景C: 中频跑 60fps (16.7ms), 功耗 4W
    Energy/Frame = 4W × 0.0167s = 67mJ/帧  ← 最优!

  → 降频不等于省电! 如果降频导致帧时间等比例增长,
    每帧能耗可能不变甚至更高
  → 真正省电的是: "用更少的计算量达到同样的帧率"
```

#### 1.3.3 频率与利用率类指标 — "核心在跑什么频率"

| 指标 | 含义 | 正常范围 | 异常信号 | 查看工具 |
|------|------|---------|---------|---------|
| **CPU Clock (各核)** | CPU 大核/中核/小核的实时频率 | 接近最大值 | 频率波动大 → DVFS 调度不稳 | Snapdragon Profiler / perf |
| **GPU Clock** | GPU 实时运行频率 | 接近最大值 | 持续低于最大值 → 降频 | Snapdragon Profiler / Mali Streamline |
| **CPU Core Usage (按核)** | 大核/中核/小核各自的利用率 | 大核为主 | 小核打满大核闲 → 任务被调度到小核 | Android Profiler / Snapdragon Profiler |
| **GPU Utilization** | GPU 整体利用率 | 60-90% | < 40% → GPU 没喂饱; > 95% → GPU-bound | Snapdragon Profiler / Mali / Xcode |
| **DVFS Governor** | 动态频率调度策略 | — | performance / powersave / schedutil | Android /sys/devices/system/cpu/ |

#### 1.3.4 帧稳定性类指标 — "帧稳不稳"

设备级分析中，帧时间的**稳定性**比平均值更重要：

| 指标 | 含义 | 正常范围 | 异常信号 | 查看工具 |
|------|------|---------|---------|---------|
| **Frame Time P99** | 99% 分位帧时间 | < 目标帧时间 × 1.2 | P99 >> P50 → 有突发尖峰 | Unreal Insights / Unity Profiler / 自定义 |
| **Frame Time Jitter** | 相邻帧帧时间差值的标准差 | < 2ms | > 5ms → 帧节奏不均，用户可感知卡顿 | Unreal Insights / Frame Pacing API |
| **Frame Pacing Consistency** | 帧提交到显示器的间隔均匀性 | CV < 5% | CV > 15% → 掉帧感明显 | Android Frame Pacing / Swappy |
| **Hitch (卡顿帧)** | 帧时间 > 目标 × 2 的帧 | 0 次/分钟 | > 3 次/分钟 → 用户可感知 | Unreal Insights (hitch detection) / Unity |
| **Dropped Frames** | 丢帧数（vsync 超时未提交） | < 1% | > 5% → 明显卡顿 | Android SurfaceFlinger / Xcode |

```
帧稳定性 vs 平均帧率:

  好的情况 (稳定 60fps):
  ││││││││││││││││││││  每帧 16.7ms ± 1ms
  → 用户感受: 流畅

  坏的情况 (平均 60fps 但不稳定):
  │││││  ││  ││││  │││  有 3 帧各花了 40ms
  → 平均帧率仍然是 60fps (60帧/秒)
  → 但用户明确感受到 "每隔一会卡一下"
  → 这就是为什么不能只看平均帧率

  ┌────────────────────────────────────────────────────┐
  │  性能分析黄金法则:                                  │
  │  1. 看 P99/P50 比值, 不只看平均值                  │
  │  2. 看帧时间分布, 不只看帧率                       │
  │  3. 看 hitch 次数, 不只看平均帧时间                │
  └────────────────────────────────────────────────────┘
```

#### 1.3.5 平台特有指标

| 平台 | 特有指标 | 含义 | 查看工具 |
|------|---------|------|---------|
| **Android (Adreno)** | GPU Frequency Bins | GPU 频率分档统计 | Snapdragon Profiler |
| **Android (Mali)** | Job Manager Slots | 顶点/片段 Job 槽位利用率 | Mali Streamline |
| **iOS (Apple GPU)** | GPU Cycle Count per Frame | GPU 总周期数 | Xcode Instruments (GPU) |
| **PC** | GPU Power Limit / Temperature Limit | 是否因功耗/温度墙降频 | NSight Graphics / GPU-Z |
| **PC** | PCIe Bandwidth** | CPU↔GPU 数据传输带宽 | NSight Systems |
| **主机** | Fixed Frame Budget | 固定 16.67ms/33.33ms 预算 | PIX / 平台 SDK |

#### 1.3.6 指标 → 设备级问题速查

```
你看到的指标异常                       →   可能的设备级问题

温度持续上升 + 帧时间逐步恶化          →   热降频 (优化功耗 / 降画质)
GPU Clock 持续低于最大值               →   GPU 降频中 (查温度 / 功耗墙)
Battery Drain > 25%/h                  →   功耗过高 (降帧率 / 简化渲染)
Frame Time P99 >> P50                  →   突发尖峰 (查加载/IO/GC)
Frame Time Jitter 大                   →   帧节奏不均 (查帧同步 / 调度)
大核闲 + 小核打满                       →   任务调度问题 (设 CPU Affinity)
GPU Utilization < 40%                  →   GPU 没喂饱 (Draw Call 少 / CPU-bound)
频繁 Hitch (数帧正常后突然一帧很慢)     →   资源加载 / GC / 内存分配尖峰
```

## 2. 移动端性能分析

### 2.1 移动端的核心约束

移动端与 PC/主机有根本性差异，性能分析必须考虑以下约束：

| 约束维度 | 移动端特性 | 对性能分析的影响 |
|---------|-----------|----------------|
| **功耗** | 电池容量有限 (4000-5000mAh) | 功耗比帧率更重要，必须同时监控 |
| **发热** | 无主动散热，被动散热 | 持续高负载导致降频，帧时间不稳定 |
| **内存** | 统一内存 4-12GB | CPU/GPU 共享，预算紧张 |
| **带宽** | LPDDR 25-68 GB/s | 远低于 PC VRAM (400+ GB/s) |
| **GPU 算力** | TFLOPS 远低于桌面 GPU | 计算密集型 Shader 瓶颈 |
| **散热** | 被动散热，热量积累 | 性能随时间衰减（持续性测试必需） |

### 2.2 发热降频 (Thermal Throttling)

```
移动端温度-性能曲线:
温度 (℃)
  │
45│ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  舒适区
  │
50│ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ╱──────  开始降频
  │                           ╱
55│ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ╱───────────  温和降频
  │                     ╱
60│ ─ ─ ─ ─ ─ ─ ─ ─ ╱─────────────────  中度降频
  │               ╱
65│ ─ ─ ─ ─ ─ ─ ╱─────────────────────  严重降频
  │           ╱
70│ ─ ─ ─ ─ ╱─────────────────────────  极限降频
  │       ╱
75│ ─ ─ ╱────────────────────────────  保护性关机区域
  │
  └──────────────────────────────────── 时间
     0     5     10    15    20    25 (分钟)

→ 游戏开始时 60fps, 运行 15 分钟后可能降至 30fps
→ 仅测试"冷机"性能是不够的, 必须测试持续运行性能
→ 优化目标: 在目标温度下维持稳定帧率, 而非峰值帧率

降频对分析的影响:
├─ 冷机帧时间: 16ms (稳定 60fps)
├─ 热机 10 分钟: 20ms (50fps)
├─ 热机 20 分钟: 28ms (35fps)
├─ → 冷机分析的"优化效果"在热机后可能无效
└─ → 必须在热机状态下进行性能基准测量
```

### 2.4 移动端 GPU 架构差异

不同移动端 GPU 架构对性能分析有重大影响：

```
移动端 GPU 架构对比:

┌──────────────────────────────────────────────────────────┐
│  Adreno (Qualcomm)                                       │
│  ├─ FlexRender: 可切换 Direct/TBDR 模式                   │
│  ├─ Tile 大小: 256×256 或动态                              │
│  ├─ 分析重点: Tile 模式是否正确启用                        │
│  │  → Vulkan: RenderPass 的 subpass 必须正确               │
│  │  → 错误的 loadOp/storeOp 会破坏 Tile 优化               │
│  └─ 工具: Snapdragon Profiler                             │
├──────────────────────────────────────────────────────────┤
│  Mali (ARM)                                              │
│  ├─ 固定 TBDR 架构                                        │
│  ├─ Tile 大小: 16×16 ~ 32×32 (取决于格式)                 │
│  ├─ 分析重点:                                             │
│  │  → Fragment 线程数 (Mali 是 warp-based)                │
│  │  → Tile Buffer 利用率                                  │
│  │  → FPK (Forward Pixel Kill) 是否启用                   │
│  └─ 工具: Mali Streamline + Offline Compiler             │
├──────────────────────────────────────────────────────────┤
│  PowerVR (Imagination)                                   │
│  ├─ TBDR + Hidden Surface Removal (HSR)                  │
│  ├─ HSR: 硬件遮挡剔除, 类似 Early-Z 但在光栅化前          │
│  ├─ 分析重点:                                             │
│  │  → HSR 效率 (不需要 Z-Pre-Pass!)                       │
│  │  → 不透明物体应使用不透明渲染目标 (非混合)               │
│  └─ 工具: PVRTune + PVRMonitor                          │
├──────────────────────────────────────────────────────────┤
│  Apple GPU (A/M 系列)                                     │
│  ├─ TBDR + Tile Shading                                  │
│  ├─ 可编程混合 (Programmable Blending)                    │
│  ├─ 分析重点:                                             │
│  │  → Metal 的 RenderCommandEncoder 结构                  │
│  │  → Tile Memory 利用 (Imageblock)                      │
│  │  → 可编程混合减少 Pass 数                              │
│  └─ 工具: Xcode GPU Frame Debugger + Instruments         │
└──────────────────────────────────────────────────────────┘
```

### 2.5 移动端 TBDR 分析要点

```
TBDR (Tile-Based Deferred Rendering) 核心原理:

传统即时渲染 (IMR - PC):
  Draw1 → 写GBuffer → 写回VRAM → Draw2 → 读GBuffer → 写回VRAM
  → 每次渲染都读写 VRAM → 带宽消耗大

TBDR (移动端):
  ┌──────────────────────────────────────────────────┐
  │  场景分块 (Tile)                                  │
  │  ┌────┬────┬────┬────┐                          │
  │  │ T00 │ T01 │ T02 │ T03 │                      │
  │  ├────┼────┼────┼────┤                          │
  │  │ T10 │ T11 │ T12 │ T13 │                      │
  │  └────┴────┴────┴────┘                          │
  │                                                  │
  │  每个 Tile 独立渲染:                              │
  │  1. 所有 Draw Call 的几何数据 → 分配到 Tile        │
  │  2. Tile 内所有 Draw → 在片上 Tile Buffer 渲染     │
  │  3. Tile 完成后 → 一次性写回 VRAM                 │
  │                                                  │
  │  → GBuffer 读写发生在 Tile Buffer (片上 SRAM)    │
  │  → 不经过主内存, 带宽消耗大幅降低                   │
  │  → 前提: RenderPass 结构正确                       │
  └──────────────────────────────────────────────────┘

TBDR 分析要点:
├─ RenderPass 合并: 多个 Draw Call 在同一 RenderPass
│  → Tile Buffer 中完成混合, 无需写回
│  → Subpass 是 TBDR 的最佳实践
│
├─ loadOp/storeOp 分析:
│  ├─ LOAD_OP_CLEAR:  清空 Tile Buffer (不需要读取)
│  ├─ LOAD_OP_LOAD:   从 VRAM 加载 (需要读取, 消耗带宽!)
│  ├─ STORE_OP_STORE: 写回 VRAM (需要保存结果)
│  └─ STORE_OP_DONT_CARE: 不保存 (临时RT, 省带宽!)
│  → 临时RT应用 DONT_CARE, 避免 Store 开销
│  → 深度缓冲如果后续不需要应用 DONT_CARE
│
├─ Pass 数量影响:
│  └─ 每个 RenderPass 结束都会 flush Tile Buffer → 写回VRAM
│     → 过多的 Pass 切换会破坏 TBDR 优化
│     → 移动端: 减少Pass > 减少Draw Call
│
└─ 带宽分析:
   → Snapdragon Profiler / Mali Streamline 测量实际带宽
   → 目标: 帧带宽 < 目标值 (如 2GB/帧)
```

### 2.6 功耗分析

```
移动端功耗优先级:

功耗构成 (典型移动游戏):
┌──────────────────────────────────┐
│  GPU 渲染:      35-45%           │
│  CPU 逻辑:      20-30%           │
│  DDR 带宽:      15-25%  ← 隐性! │
│  显示屏:        10-15%           │
│  网络:          5-10%            │
│  其他:          5%               │
└──────────────────────────────────┘

→ DDR 带宽是隐性功耗大户!
→ 减少带宽 = 减少功耗 = 延长续航

功耗优化策略:
├─ 降低渲染分辨率 (带宽↓ 功耗↓)
├─ 纹理压缩 (带宽↓ 功耗↓)
├─ 减少 Pass 数 (TBDR 友好, 带宽↓)
├─ 帧率自适应 (空闲时降至 30fps)
├─ 动态分辨率 (根据负载调整)
├─ 简化 Shader (GPU 计算↓ 功耗↓)
├─ CPU 负载均衡 (避免单核满载)
└─ 异步计算利用 (GPU 空闲时间填充)

功耗测量:
├─ Android: BatteryManager API / Snapdragon Profiler
├─ iOS: Xcode Energy Log / Instruments Energy
└─ 物理测量: Monsoon Power Monitor (外接功耗计, 最精确)
```

## 3. PC 硬件分层测试

### 3.1 硬件分层策略

```
PC 硬件分层测试矩阵:

┌───────────────────────────────────────────────────────────┐
│  Tier         │ GPU 代表          │ CPU 代表     │ 目标   │
├───────────────┼──────────────────┼──────────────┼────────┤
│  高端 (Tier S)│ RTX 4090/4080   │ i9/Ryzen 9  │ 基准   │
│               │                  │              │ (验证上限)│
├───────────────┼──────────────────┼──────────────┼────────┤
│  中高 (Tier A)│ RTX 4070/3080   │ i7/Ryzen 7  │ 目标   │
│               │                  │              │ (主优化) │
├───────────────┼──────────────────┼──────────────┼────────┤
│  中端 (Tier B)│ RTX 3060/2060   │ i5/Ryzen 5  │ 兼容   │
│               │                  │              │ (达标)   │
├───────────────┼──────────────────┼──────────────┼────────┤
│  低端 (Tier C)│ GTX 1060/1050Ti │ i3/Ryzen 3  │ 最低   │
│               │                  │              │ (可玩)   │
├───────────────┼──────────────────┼──────────────┼────────┤
│  集成显卡      │ Intel Iris/Xe   │ 各类          │ 流式   │
│               │ AMD APU          │              │ (降级)   │
└───────────────────────────────────────────────────────────┘

测试要求:
├─ 每层至少 2 种 GPU + 2 种 CPU 组合
├─ 覆盖 NVIDIA + AMD + Intel 三家
├─ 测试不同显存容量 (4GB/8GB/12GB/24GB)
├─ 测试不同内存配置 (8GB/16GB/32GB)
└─ 覆盖不同驱动版本 (至少测试 2 个版本)
```

### 3.2 显存容量适配

```
不同显存容量的适配策略:

4GB VRAM (低端):
├─ 纹理: 最高 2K, 最多 300 张同时驻留
├─ GBuffer: 减少RT数量 (2-3个)
├─ 后处理: 减少Pass数
├─ Mesh: 合批减少Buffer数
└→ 纹理流式加载必须, 动态管理

8GB VRAM (中端):
├─ 纹理: 最高 4K, 最多 600 张同时驻留
├─ GBuffer: 标准 4-5 个 RT
├─ 后处理: 完整后处理链
└→ 纹理流式加载推荐

12GB+ VRAM (高端):
├─ 纹理: 4K-8K, 大量预加载
├─ GBuffer: 完整, 可加自定义RT
├─ 后处理: 全部开启
└→ 可预加载所有纹理, 无需流式

显存溢出处理:
├─ 检测: VMA 统计 / GPU 查询可用显存
├─ 降级: 自动降低纹理质量
├─ 流式: 动态加载/卸载远处纹理
└─ 警告: 显存接近满时通知用户
```

### 3.3 CPU 核心数差异

```
多核适配分析:

4核 CPU:
├─ Game Thread: 核心0
├─ Render Thread: 核心1
├─ Worker Threads: 核心2-3
└→ 并行度有限, 容易 CPU-bound

8核 CPU:
├─ Game Thread: 核心0
├─ Render Thread: 核心1
├─ Worker Pool: 核心2-7
├→ 可充分利用 Job System
└→ 但需注意: 大小核架构 (ARM big.LITTLE)

16+核 CPU:
├─ 完全并行
├─ 但需注意: NUMA 架构跨节点访问慢
├→ 任务应尽量在本地 NUMA 节点执行
└→ 过多线程反而增加调度开销
```

### 3.4 GPU 驱动差异

```
NVIDIA vs AMD vs Intel 驱动差异:

NVIDIA 驱动:
├─ 成熟稳定, 工具链最完善 (NSight)
├─ Vulkan 扩展支持最全
├─ Bindless 性能优秀
├─ Shader 编译器优化好
└→ 作为主要开发与测试平台

AMD 驱动:
├─ 部分扩展行为与 NVIDIA 不同
├─ RenderDoc 兼容性好
├─ 需额外测试: RADV (开源) vs AMDVLK (官方)
├─ 某些 Shader 编译结果差异大
└→ 必须独立测试, 不能假设行为一致

Intel 集成显卡:
├─ 算力和显存有限
├─ 驱动行为可能不一致
├─ Mesh Shader / 光追可能不支持
├─ 需要降级渲染路径
└→ 作为最低配置测试基准
```

## 4. 主机平台分析

### 4.1 主机平台特性

| 平台 | GPU | 内存 | 特殊约束 | 分析工具 |
|------|-----|------|---------|---------|
| **PS5** | RDNA2 (36CU) | 16GB GDDR6 | 固定配置，API私有 | Razor (Sony) |
| **Xbox Series X** | RDNA2 (52CU) | 16GB GDDR6 | 固定配置，DX12 Ultimate | PIX |
| **Xbox Series S** | RDNA2 (20CU) | 10GB GDDR6 | 显存受限 | PIX |
| **Nintendo Switch** | Tegra X1 | 4GB | 移动架构 + Dock模式 | NVIDIA Graphics PerftHud |

```
主机分析特点:
├─ 固定硬件 → 无需跨设备测试, 一次优化全局受益
├─ 专属 API → 工具链与 PC 不同
│   ├─ PS5: GNM (低层) / PSSL (着色器)
│   ├─ Xbox: DX12 + 专属扩展
│   └─ Switch: NVN (NVIDIA 私有 API)
├─ 内存约束 → 必须精打细算
│   ├─ PS5/XSX: 16GB 共享, 但系统占用 3-4GB
│   └─ Switch: 仅 4GB, 极度紧张
├─ 认证要求 → 性能达标才能发布
│   ├─ PS5: 60fps 不掉帧 (或 30fps 稳定)
│   ├─ Xbox: 类似要求
│   └─ Switch: 帧率稳定性认证
└→ 主机优化优先级: 内存 > 带宽 > 算力
```

## 5. 跨设备基准测试方法论

### 5.1 基准测试场景设计

```
基准测试场景要求:
├─ 可重复性: 固定摄像机路径、固定输入序列
├─ 代表性: 覆盖典型游戏场景 (密集/开阔/室内/特效)
├─ 持续性: 足够长 (5-10分钟) 以触发热机效应
├─ 自动化: 脚本驱动, 无需人工操作
└─ 可比性: 所有设备运行相同场景

标准基准测试套件:
┌─────────────────────────────────────────────────┐
│ 场景1: CPU 密集 (大量 AI/物理/逻辑)               │
│  → 测试 CPU 瓶颈                                │
├─────────────────────────────────────────────────┤
│ 场景2: GPU 像素密集 (高分辨率+复杂Shader)         │
│  → 测试像素处理瓶颈                              │
├─────────────────────────────────────────────────┤
│ 场景3: GPU 几何密集 (大量三角形/LOD)             │
│  → 测试几何处理瓶颈                              │
├─────────────────────────────────────────────────┤
│ 场景4: 带宽密集 (大纹理+多RT+后处理)             │
│  → 测试带宽瓶颈                                  │
├─────────────────────────────────────────────────┤
│ 场景5: 内存密集 (场景切换+资源流式加载)          │
│  → 测试内存管理                                  │
├─────────────────────────────────────────────────┤
│ 场景6: 持续运行 (10分钟持续游戏)                 │
│  → 测试热机降频 (移动端)                         │
└─────────────────────────────────────────────────┘
```

### 5.2 基准数据采集

```
每帧采集数据:
├─ 帧时间 (ms)
├─ CPU 时间 (Game + Render Thread)
├─ GPU 时间
├─ Draw Call 数
├─ 三角形数
├─ 内存使用 (CPU + GPU)
├─ 温度 (移动端)
└─ 功耗 (移动端)

统计指标:
├─ 平均帧时间 (P50)
├─ 最差帧时间 (P99/P99.9)  ← 99分位更重要!
├─ 帧时间方差 (稳定性)
├─ 掉帧次数 (帧时间 > 目标的帧数)
├─ 冷机 vs 热机帧时间差异
└─ 功耗 (平均/峰值)

报告格式:
┌──────────────────────────────────────────────────┐
│ 设备: iPhone 15 Pro                              │
│ 场景: 场景3 (几何密集)                           │
│ 分辨率: 1170×2532 (原生)                         │
│ ────────────────────────────────────────────────│
│                  │ 冷机(0-2min)│ 热机(8-10min)  │
│ 平均帧时间        │ 14.2ms      │ 18.7ms         │
│ P50 帧时间        │ 14.0ms      │ 18.5ms         │
│ P99 帧时间        │ 22.1ms      │ 31.2ms         │
│ 帧时间方差        │ 2.1ms       │ 4.8ms          │
│ 掉帧率 (>16.67ms)│ 8%          │ 35%            │
│ 平均功耗          │ 2.8W        │ 3.1W           │
│ 温度              │ 38°C        │ 52°C           │
│ GPU 时间          │ 10ms        │ 14ms           │
│ CPU 时间          │ 12ms        │ 16ms           │
│ Draw Call 数      │ 1200        │ 1200           │
│ 三角形数          │ 1.2M        │ 1.2M           │
│ 内存 (CPU)        │ 1.2GB       │ 1.2GB          │
│ 内存 (GPU)        │ 0.8GB       │ 0.8GB          │
│ 瓶颈分析          │ GPU-bound   │ CPU+GPU        │
│                                                  │
│ 结论: 热机后 CPU 也成为瓶颈 (降频)               │
│ 建议: 降低 CPU 逻辑复杂度, 减少散热压力           │
└──────────────────────────────────────────────────┘
```

## 6. 实战工作流：移动端性能分析标准流程

```
Step 1: 冷机基线测量
├─ 设备冷却至室温 (等待 10 分钟)
├─ 运行标准基准场景
├─ 采集: 帧时间、CPU/GPU 时间、内存、功耗
├─ 时长: 2-3 分钟
└→ 建立"冷机基线"

Step 2: 热机持续测量
├─ 不间断运行游戏
├─ 每 2 分钟记录一次性能快照
├─ 时长: 10-15 分钟
├─ 关注: 降频起始时间、稳定后帧时间
└→ 建立"热机基线" (这是真实用户体验)

Step 3: 瓶颈定位
├─ 使用 Snapdragon Profiler / Mali Streamline
├─ 在热机状态下捕获帧
├─ 分析 GPU 计数器: 像素/几何/带宽占比
├─ 分析 CPU: Android Profiler 方法追踪
├─ 分析功耗: 哪些组件功耗最高
└→ 确定: 是算力瓶颈? 带宽瓶颈? 功耗瓶颈?

Step 4: 针对性优化
├─ 带宽瓶颈 (最常见):
│   ├─ 纹理压缩 (ASTC)
│   ├─ TBDR 优化 (正确 RenderPass 结构)
│   ├─ 减少后处理 Pass
│   └─ 降低渲染分辨率
│
├─ 算力瓶颈:
│   ├─ 简化 Shader
│   ├─ LOD 系统
│   └─ 减少特效
│
├─ 功耗瓶颈:
│   ├─ 动态帧率 (空闲 30fps, 操作 60fps)
│   ├─ 降低背景更新频率
│   └─ 异步计算填充 GPU 空闲
│
└─ 内存瓶颈:
    ├─ 资源流式加载
    ├─ 纹理池化
    └─ 场景分块加载

Step 5: 验证
├─ 相同条件 (冷机→热机) 重新测量
├─ 对比优化前后的冷机/热机曲线
├─ 确认降频延迟改善或帧时间稳定
└─ 多设备验证 (不同 SoC)
```
