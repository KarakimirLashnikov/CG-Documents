# 驱动问题定位 — 总览

> 本文档是「驱动问题定位」系列文档的第 **0** 篇。本系列面向渲染/引擎工程师，目标不是学会写驱动，而是建立**分层定位直觉**：看到什么现象 → 先怀疑哪一层 → 查什么日志/工具 → 怎么二分验证。以 Linux 图形栈（DRM/KMS + Mesa + amdgpu/i915/xe/NVRM）为主线，附 Windows（WDDM）对照。

---

## 1. 为什么渲染工程师要浅学驱动

### 1.1 一个真实场景

游戏在测试机上 `VK_ERROR_DEVICE_LOST` 崩溃。纯上层视角的排查路径是：查 RenderDoc → 查 Validation → 怀疑 Shader 越界 → 怀疑同步错误 → 改三天代码，问题依旧。

而有驱动直觉的人先看一眼 `dmesg`：

```
amdgpu 0000:03:00.0: [drm] *ERROR* ring gfx timeout, signaled seq=12345, emitted seq=12346
amdgpu 0000:03:00.0: [drm] GPU reset begin!
```

立刻换方向：**这是内核驱动报告 ring 超时后触发 GPU reset**，应用层的 DEVICE_LOST 只是 reset 的下游结果。下一步该查的是「什么命令把 ring 卡死」或「是否已知驱动 bug」，而不是继续在 Shader 里捞针。

### 1.2 本系列的核心命题

> 浅学驱动的目标不是会写驱动，而是能在关键时刻说出：
> **「这个 DEVICE_LOST 不是 Shader 问题，dmesg 里有 ring timeout，先查内核提交和 GPU reset。」**

分层定位直觉 = 一张**症状 → 层 → 证据**的映射表 + 一套**二分验证**流程。本系列就是这两样东西的完整展开。

### 1.3 读者对象

| 读者类型 | 预期收获 |
|---|---|
| 渲染/引擎工程师（Vulkan/D3D） | 崩溃/花屏/性能异常时知道先看哪个日志，不再盲目改 Shader |
| Linux 平台游戏开发者 | 掌握 Mesa/dmesg/合成器日志的联动排查法 |
| 技术支持/QA | 能把用户报告翻译成「疑似某层问题」，附上有价值的日志 |
| 有图形学基础的学习者 | 建立 UMD/KMD/硬件五层模型，理解驱动在管线中的位置 |

### 1.4 学习边界（本系列不做什么）

| 做 | 不做 |
|---|---|
| 建立症状 → 层的映射直觉 | 教你写 DRM/Mesa 驱动代码 |
| 解读关键错误日志的语义 | 逐行分析内核源码 |
| 给出可执行的二分验证流程 | 覆盖 GPU 硬件微架构（见 `移动端GPU架构文档`） |
| 列出每个概念「坏了会怎样」 | 深入编译器后端（见 `Shader工具链文档`） |

## 2. 分层定位直觉：一张图看懂

```
┌─────────────────────────────────────────────────────────────┐
│ 应用 / 引擎      场景逻辑、渲染状态、Shader                  │
│                  坏了：画面错、逻辑 bug                      │  RenderDoc
├─────────────────────────────────────────────────────────────┤
│ 图形 API         Vulkan / OpenGL 调用边界                    │
│                  坏了：参数错误、用法违规                    │  Validation Layers
├─────────────────────────────────────────────────────────────┤
│ 用户态驱动 UMD   命令生成、内存分配、着色器编译              │
│ (Mesa RADV/ANV、  坏了：特定应用崩溃、DEVICE_LOST、编译卡顿  │  RADV_DEBUG
│  NVIDIA libGL)                                              │
├─────────────────────────────────────────────────────────────┤
│ 内核态驱动 KMD   命令提交、GPU 调度、显存管理、显示、电源    │
│ (amdgpu/i915/xe/  坏了：GPU hang、reset、黑屏、花屏、掉帧    │  dmesg
│  NVRM)                                                      │
├─────────────────────────────────────────────────────────────┤
│ 硬件 / 固件      GPU、显存、显示控制器、VBIOS/固件           │
│                  坏了：随机花屏、死机、唤醒失败              │  Xid / 错误寄存器
└─────────────────────────────────────────────────────────────┘
```

**核心心法：dmesg 干净，偏上层；dmesg 有 GPU fault / reset / page fault，偏底层。**

这一条心法能砍掉 80% 的错误排查方向，是本系列第 1 篇的核心。

---

## 3. 最终心法：遇到问题的四句话

排查任何图形问题时，先依次问自己：

```
① 是应用层、UMD、KMD，还是硬件？
        │
        ▼
② dmesg 有没有 GPU fault / reset / page fault？
        │
        ▼
③ 内核、Mesa、Firmware、合成器版本是什么？
        │
        ▼
④ 换内核 / Mesa / 合成器 / API 能不能二分？
```

四个问题的答案凑齐，基本就能写出一份让驱动工程师无法拒绝的 bug report。

## 6. 事实来源与时效说明

- 环境变量与 Mesa 行为：**以 Mesa 官方文档 `docs.mesa3d.org/envvars` 为准（2026-10 核实）**。
- Wayland 显式同步（`linux-drm-syncobj-v1`）落地状态变化快：wlroots 0.19 / Sway 1.11 于 2025 年支持；**以 wayland-protocols 官方与各合成器发行注记为准**。
- 内核错误日志文案随版本演进，文中给出的是**常见代表样式**，具体措辞以你机器上的实际日志为准。
- NVIDIA Xid 错误码语义以 NVIDIA 官方文档《Xid Errors》为准。
