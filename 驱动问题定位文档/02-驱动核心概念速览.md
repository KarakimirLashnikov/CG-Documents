# 驱动核心概念速览

> 本文档是「驱动问题定位」系列文档的第 **2** 篇。挑出 8 个最值得浅学的驱动概念，每个只需掌握三件事：**它负责什么、坏了会怎样、日志里搜什么关键词**。这是把「症状」翻译成「层」所必需的词汇表。

---

## 1. 概念地图

```
        ┌─────────────────────── DRM（内核图形子系统）───────────────────────┐
        │                                                                   │
 显示通路│  ② KMS: CRTC / Plane / Connector / Atomic Commit                 │
        │                                                                   │
 内存通路│  ③ GEM/TTM: BO 分配 / VRAM-GTT 迁移 / reclaim                    │
        │                                                                   │
 执行通路│  ④ Scheduler/Ring → ⑤ Fence/Syncobj → ⑥ CS/VM_BIND（提交+页表）  │
        │                                                                   │
 共享通路│  ⑦ dma-buf / PRIME（跨设备跨进程 buffer 共享）                    │
        │                                                                   │
 基础支撑│  ⑧ Firmware / 电源管理（sclk/mclk、PCIe link）                   │
        └───────────────────────────────────────────────────────────────────┘
 入口： ① /dev/dri/card0（显示+特权操作）  /dev/dri/renderD128（纯渲染）
```

> 编号 ①~⑧ 对应下面 2.1~2.8 节（①设备节点放在最后，因为它是所有概念的入口）。

## 2. 八个概念逐个讲

### 2.1 DRM / KMS —— 显示输出

| 维度 | 内容 |
|---|---|
| 负责 | 显示模式设置（分辨率/刷新率）、多显示器、热插拔、VRR |
| 坏了 | 黑屏（但 SSH 能进）、花屏、分辨率不对、热插拔失败、闪屏 |
| 关键词 | CRTC、Plane、Connector、Atomic Commit、EDID、link training |

四个对象的关系：

```
Connector（接口：HDMI/DP 口，读 EDID 认识显示器）
    │ 绑定
    ▼
CRTC（扫描控制器：决定"哪个时序、哪个分辨率"）
    │ 合成
    ▼
Plane（图层：主图层/光标层/叠加层，合成进同一 CRTC）
```

排查要点：`modetest`（libdrm 自带）可以列出全部 Connector/CRTC/Plane 及其状态；`dmesg` 里搜 `edid`、`link training`、`atomic` 能看到协商失败记录。

> ⚠️ 「开机 logo 之后黑屏」多半是 KMS modeset 阶段失败，可以先用内核参数 `nomodeset` 验证：加上后能亮（走固件 framebuffer，无加速）→ 问题在 KMS 路径；加了还黑 → 更底层。

### 2.2 GEM / TTM —— 显存与系统内存管理

| 维度 | 内容 |
|---|---|
| 负责 | Buffer Object（BO）的分配、在 VRAM 与 GTT（系统内存映射区）之间迁移、内存回收 |
| 坏了 | 分配失败、OOM、卡顿（迁移颠簸）、VRAM 耗尽后性能骤降 |
| 关键词 | VRAM、GTT、reclaim、userptr、`ttm`、`[drm] Cannot allocate memory` |

直觉：**「爆显存」在 Linux 上不是一个干净利落的失败**——TTM 会尝试把 BO 从 VRAM 赶到 GTT/系统内存，表现为「没报错但突然变卡」。性能分析时遇到「帧时间突然阶梯式上升」，记得看一眼 VRAM 用量。

### 2.3 GPU Scheduler / Ring —— 命令队列与提交

| 维度 | 内容 |
|---|---|
| 负责 | 把命令流放进 ring buffer，调度给 GPU 硬件队列执行；超时检测与 GPU reset |
| 坏了 | GPU hang → `ring gfx timeout` → reset；整机短暂卡死 |
| 关键词 | `ring gfx timeout`、`GPU reset begin`、`amdgpu_cs_ioctl` |

这是 **DEVICE_LOST 的头号制造者**。典型日志序列：

```
amdgpu 0000:03:00.0: [drm] *ERROR* ring gfx timeout, signaled seq=N, emitted seq=N+1
amdgpu 0000:03:00.0: [drm] GPU reset begin!
amdgpu 0000:03:00.0: [drm] GPU reset succeeded, trying to resume
```

`signaled` 与 `emitted` 的 seq 差值告诉你「提交了但没执行完」。看到这三连，意味着：应用层接下来会集体收到 DEVICE_LOST，根因在卡死的那条 ring 上。

### 2.4 Fence / Syncobj —— 同步原语

| 维度 | 内容 |
|---|---|
| 负责 | CPU↔GPU、GPU↔GPU 之间的完成通知与等待（dma_fence 是内核统一抽象） |
| 坏了 | DEVICE_LOST、等待超时（帧率掉到个位数）、画面撕裂、死锁 |
| 关键词 | `fence timeout`、`dma_fence`、`syncobj`、`timed out waiting for fence` |

直觉：fence 超时和 ring 超时经常成对出现——**fence 超时是「等的人」的视角，ring 超时是「执行方」的视角**。排查时把两者的日志对齐时间戳，能确定是谁在等谁。

### 2.5 Command Submission / VM_BIND —— 提交与 GPU 页表

| 维度 | 内容 |
|---|---|
| 负责 | 命令流提交（`amdgpu_cs_ioctl` / `i915_gem_execbuffer`），GPU 虚拟地址页表管理（VM_BIND 允许用户态自己管页表） |
| 坏了 | GPU page fault：`VM_L2_PROTECTION_FAULT`（AMD）、`GPU HANG` + fault addr（Intel） |
| 关键词 | `VM_L2_PROTECTION_FAULT`、`page fault`、`walk error`、`VM_BIND` |

直觉：**GPU page fault 之于驱动，相当于段错误之于进程**——GPU 访问了一个没有映射或权限不对的虚拟地址。日志会给出 fault 地址和 ring 信息。常见诱因：应用/UMD 给了悬空指针、VM_BIND 下用户态页表管理出错。

### 2.6 dma-buf / PRIME —— 跨设备跨进程共享

| 维度 | 内容 |
|---|---|
| 负责 | 把一块显存 buffer 以 fd 形式导出，在 GPU↔GPU、GPU↔显示控制器、进程↔进程之间零拷贝共享；Wayland 的 buffer 提交就靠它 |
| 坏了 | Wayland 下闪烁/花屏、多 GPU 笔记本独显不工作、合成器卡顿、录屏黑屏 |
| 关键词 | dma-buf、PRIME、implicit sync、explicit sync、`linux-drm-syncobj-v1` |

同步模型的演进是本概念的核心知识点：

| 模型 | 机制 | 问题 |
|---|---|---|
| 隐式同步（implicit sync） | buffer 自带 fence，消费者自动等生产者完成 | 合成器只能「全等」，过度同步导致卡顿 |
| 显式同步（explicit sync） | 生产/消费双方通过 syncobj timeline 明确传递 acquire/release 点 | 需要全栈（驱动+合成器+应用）支持 |

> 时效（2025 状态，以 wayland-protocols 与各合成器发行注记为准）：显式同步协议 `linux-drm-syncobj-v1` 已在 wlroots 0.19 / Sway 1.11（2025-06）落地，KWin 与 Mutter 也在同期推进；NVIDIA 长期受隐式同步困扰的 Xwayland 闪烁问题由此得到根本解决。**遇到 Wayland 闪烁，先查合成器是否支持显式同步。**

### 2.7 Firmware / 电源管理 —— 初始化、频率与电源

| 维度 | 内容 |
|---|---|
| 负责 | GPU 初始化序列、频率/电压状态（DPM）、PCIe 链路速率、休眠唤醒 |
| 坏了 | 启动黑屏、性能异常低（频率没拉起来）、风扇狂转、休眠唤醒后黑屏/花屏 |
| 关键词 | `firmware`、`pp_dpm_sclk`、`pcie link`、`SMU`、`GUC`（Intel） |

排查入口（AMD 示例）：

```bash
# 看当前频率档位（路径中的 cardN 按实际填）
cat /sys/class/drm/card0/device/pp_dpm_sclk
# 看 PCIe 链路速率与宽度
lspci -vv | grep -A 20 -i vga | grep -i lnksta
# 看固件加载是否有报错
dmesg | grep -i firmware
```

直觉：**「性能突然变低但没有任何报错」优先怀疑电源管理**——频率没升档、PCIe 协商降级（x16 变 x8/x4）、过热降频。这类问题 RenderDoc 完全看不出来，只有 sysfs 和硬件计数器能看到。

### 2.8 Render Node / Card Node —— 设备入口与权限

| 维度 | 内容 |
|---|---|
| 负责 | `/dev/dri/card0`：显示 + 特权操作（modeset）；`/dev/dri/renderD128`：纯渲染（无显示权限），容器/无头计算用它 |
| 坏了 | 应用找不到 GPU、选错设备（独显/核显选反）、`Permission denied` |
| 关键词 | `/dev/dri/renderD128`、`card0`、udev、`DRI_PRIME=1` |

直觉：Vulkan 枚举出**两个物理设备**时，选错的那一半问题就出在这层——`vulkaninfo --summary` 和 `ls -l /dev/dri/` 是第一对检查命令。无显示环境（CI、服务器）务必走 render node。

## 4. 小结

| 要点 | 说明 |
|---|---|
| DRM/KMS | 显示输出；坏了黑屏花屏；用 `modetest` 看对象 |
| GEM/TTM | 显存管理；爆显存常表现为卡顿而非报错 |
| Scheduler/Ring | ring timeout → GPU reset → 应用 DEVICE_LOST |
| Fence/Syncobj | fence 超时是等待方视角，ring 超时是执行方视角 |
| CS/VM_BIND | GPU page fault ≈ 进程的段错误，日志含 fault 地址 |
| dma-buf/PRIME | Wayland 共享缓冲；显式同步（2025 落地中）根治闪烁 |
| Firmware/电源 | 「无报错但性能低」的头号嫌疑人；查 sysfs 频率与 PCIe 链路 |
| 设备节点 | 渲染走 renderD128；多 GPU 先核对选了哪块卡 |
