# 图形栈分层与症状归属

> 本文档是「驱动问题定位」系列文档的第 **1** 篇。把图形栈拆成五层，讲清每层**负责什么、坏了是什么症状、看什么证据**。这是所有排查直觉的地基——先学会把症状归到正确的层，再谈具体怎么查。

---

## 1. 五层模型总表

| 层 | 负责什么 | 坏了的典型症状 | 关键证据 |
|---|---|---|---|
| 应用/引擎 | 场景、渲染逻辑、Shader | 画面错、崩溃、逻辑 bug | RenderDoc 抓帧、应用日志 |
| 图形 API | Vulkan/OpenGL 调用边界 | 验证层报错、参数错误 | Validation Layers |
| 用户态驱动 UMD | 命令生成、内存分配、着色器编译 | 特定游戏崩溃、DEVICE_LOST、编译卡顿 | Mesa 日志、`RADV_DEBUG` |
| 内核态驱动 KMD | 命令提交、调度、显存、显示、电源 | GPU hang、reset、黑屏、花屏、性能异常 | `dmesg`、`journalctl -k` |
| 硬件/固件 | GPU、显存、显示控制器 | 随机花屏、死机、唤醒失败 | GPU 错误寄存器、Xid、firmware 日志 |

> ⚠️ 各层症状有重叠（比如 DEVICE_LOST 可能源于 UMD 提交了非法命令，也可能源于 KMD reset），所以**症状只能给方向，证据才能定层**。

---

## 2. 命令的一生：理解层间边界

一个 `vkCmdDraw` 从你的代码变成屏幕上的像素，要穿过下面这条链路。每一段的负责人不同，挂掉的表现也不同：

```
你的代码: vkCmdDraw(cmd, ...)
   │
   ▼  ┌─ 应用/引擎层 ─────────────────────────────────────┐
   │  │ 记录状态、检查 Vulkan 对象生命周期                 │
   │  └──────────────────────────────────────────────────┘
   ▼  ┌─ 图形 API 层（Loader + Validation，可选）─────────┐
   │  │ 参数校验、分发给 ICD                              │
   │  │ 坏了 → Validation 报 VUID 错误                    │
   │  └──────────────────────────────────────────────────┘
   ▼  ┌─ UMD（Mesa RADV/ANV 或厂商闭源用户态库）──────────┐
   │  │ Shader 编译（SPIR-V → 机器码）                    │
   │  │ 命令缓冲生成（GPU 可执行的指令流）                 │
   │  │ 显存分配、描述符布局                               │
   │  │ 坏了 → vkQueueSubmit 返回 DEVICE_LOST / 编译卡死   │
   │  └──────────────────────────────────────────────────┘
   ▼  ┌─ KMD（amdgpu / i915 / xe / NVRM）─────────────────┐
   │  │ ioctl 提交 → ring buffer → GPU 调度               │
   │  │ 页表管理（GPU VM）、fence 完成通知                 │
   │  │ 显示输出（KMS modeset）、电源管理                  │
   │  │ 坏了 → dmesg: ring timeout / page fault / reset    │
   │  └──────────────────────────────────────────────────┘
   ▼  ┌─ 硬件/固件 ──────────────────────────────────────┐
   │  │ GPU 执行命令流，写显存，扫描输出到显示器           │
   │  │ 坏了 → Xid 错误（NVIDIA）、机器死锁、随机花屏      │
   │  └──────────────────────────────────────────────────┘
```

**定位要诀**：链路是单向委托的。上层看到的错误往往是下层的「二手报告」——例如 `VK_ERROR_DEVICE_LOST` 是 UMD 把 KMD 的 GPU reset 翻译给应用的结果。顺着「谁最先报错」往上追，通常能找到真正的源头。

## 3. 逐层详解：负责什么、坏了会怎样

### 3.1 应用/引擎层

- **负责**：场景管理、渲染状态组织、Shader 编写、资源生命周期、同步逻辑。
- **坏了**：画面错误（错材质、错变换）、逻辑崩溃、Validation 一片红。
- **证据**：RenderDoc 抓帧看 draw 级状态；应用自身日志。
- **直觉**：**只有你自己机器复现、换驱动版本也一样**的渲染错误，优先怀疑这层。

### 3.2 图形 API 层（Loader + Validation）

- **负责**：Vulkan Loader 找到 ICD 并转发调用；Validation Layers 校验用法是否合规。
- **坏了**：参数错误、对象生命周期违规——但注意，这是**最容易被冤枉的一层**：Validation 报错只能说明「调用不合规」，崩溃根因可能在别处。
- **证据**：`VK_LOADER_DEBUG=all` 看加载过程；Validation 输出的 VUID 编号。
- **直觉**：开发期 Validation 必须常开；**Validation 干净但画面错 ≠ 应用无辜**（Validation 查用法不查逻辑）。

### 3.3 用户态驱动 UMD

- **负责**：把 Vulkan 调用翻译成 GPU 命令流；着色器编译（SPIR-V → 机器码）；显存对象分配；descriptor 布局；WSI。
- **坏了**：
  - **特定游戏/特定着色器才崩** → 高度怀疑 UMD 编译器 bug；
  - `vkQueueSubmit` 返回 `VK_ERROR_DEVICE_LOST`；
  - 着色器编译阶段卡死或极慢；
  - Mesa 升级/降级后问题出现或消失。
- **证据**：`RADV_DEBUG=hang`（检测到 GPU hang 时把现场 dump 到 `$HOME/radv_dumps_`）、`MESA_DEBUG=1`、Mesa 版本号。
- **直觉**：**换 Mesa 版本能复现/消失**的问题，大概率在这层。

### 3.4 内核态驱动 KMD

- **负责**：命令提交与 GPU 调度（ring buffer）、GPU 虚拟内存（页表）、fence 完成通知、显示输出（KMS）、电源与频率管理、GPU reset。
- **坏了**：GPU hang → ring timeout → reset；黑屏、花屏；热插拔失灵；性能异常（频率没拉起来）。
- **证据**：`dmesg -T | grep -iE 'drm|amdgpu|i915|xe|nvidia'`、`journalctl -k -b`。
- **直觉**：**dmesg 里有 GPU fault / reset / page fault 字样，问题基本不在你的 Shader。**

### 3.5 硬件/固件层

- **负责**：GPU 硅片、显存颗粒、显示控制器、VBIOS/固件、PCIe 链路。
- **坏了**：**随机性**花屏/死机（与负载、温度相关）、休眠唤醒失败、PCIe 掉链。
- **证据**：NVIDIA `NVRM: Xid` 错误（如 Xid 79 = "GPU has fallen off the bus"，通常是硬件/供电/链路级）；firmware 加载失败日志。
- **直觉**：**跨操作系统、跨驱动版本都能复现的随机故障**，开始怀疑硬件。

## 4. 核心心法：dmesg 定半层

排查的第一刀永远切在 UMD/KMD 边界上，而切口就是 dmesg：

```
┌────────────────────────── 现象 ──────────────────────────┐
│                   游戏崩溃 / 花屏 / 掉帧                  │
└────────────────────────────┬─────────────────────────────┘
                             ▼
                    dmesg 有没有 GPU 相关错误？
                             │
          ┌──────────────────┴───────────────────┐
          │ 干净（无 fault/reset/page fault）     │ 有 ring timeout / reset /
          ▼                                      ▼ page fault / Xid
   偏上层：应用 / API / UMD               偏底层：KMD / 固件 / 硬件
   → RenderDoc + Validation               → 收集 dmesg 全文 + 版本信息
   → 换 Mesa 版本二分                      → 换内核版本二分 / 报上游
```

> ⚠️ 「dmesg 干净」不等于「底层无辜」——有些 UMD bug（如编译器生成错误机器码导致 GPU 执行非法指令）最终也表现为 KMD 报 fault。所以心法的准确读法是：**dmesg 有底层错误 → 先在底层方向收集证据；dmesg 干净 → 底层基本排除，全力查上层。**

---

## 5. 术语表

| 术语 | 全称 | 一句话解释 |
|---|---|---|
| UMD | User Mode Driver | 用户态驱动，Mesa RADV/ANV、NVIDIA libGL 等，跑在应用进程里 |
| KMD | Kernel Mode Driver | 内核态驱动，amdgpu/i915/xe/NVRM，管提交、调度、显存、显示 |
| ICD | Installable Client Driver | Vulkan 的可安装客户端驱动，Loader 通过 JSON 清单找到它 |
| DRM | Direct Rendering Manager | Linux 内核图形子系统总框架 |
| KMS | Kernel Mode Setting | DRM 的显示输出部分，管分辨率/刷新率/多屏 |
| TDR | Timeout Detection & Recovery | Windows 侧的 GPU 超时重置机制（对应 Linux 的 GPU reset） |
| DEVICE_LOST | `VK_ERROR_DEVICE_LOST` | Vulkan 报告「逻辑设备不可用」，绝大多数是 GPU reset 的下游结果 |

---

## 6. 常见误区

| 误区 | 正解 |
|---|---|
| 「DEVICE_LOST 就是驱动 bug」 | 它只是 reset 的翻译。非法命令（应用/UMD 都可能产生）也会触发 reset，先看 dmesg 归因 |
| 「Validation 不报错 = 代码没问题」 | Validation 查用法合规，不查逻辑正确，也不查数值越界后的硬件行为 |
| 「换台机器好了 = 原机器硬件坏」 | 更常见的是驱动/Mesa/内核版本差异，先对齐版本再下结论 |
| 「花屏就是显卡坏了」 | 花屏在 KMS plane 配置错误、显存压缩 bug、VRR 兼容性上都会出现，多数是软件 |
| 「重启好了就不用管了」 | 偶发 GPU hang 往往随负载复现，留下 dmesg 现场比重启有价值得多 |

---

## 7. 小结

| 要点 | 说明 |
|---|---|
| 五层模型 | 应用/引擎 → API → UMD → KMD → 硬件/固件，逐层委托 |
| 错误是二手报告 | 上层看到的错误常是下层事件的翻译，追「谁最先报错」 |
| 第一刀切在哪 | dmesg：干净偏上层，有 fault/reset 偏底层 |
| UMD 特征 | 特定应用/着色器才崩；换 Mesa 版本能复现/消失 |
| KMD 特征 | ring timeout、page fault、GPU reset、黑屏花屏 |
| 硬件特征 | 随机性、温度/负载相关、跨系统复现、Xid 错误 |
| 证据 > 症状 | 症状只给方向，日志证据才能定层 |
