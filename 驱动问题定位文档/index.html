01 LAYER MODEL

图形栈分层与症状归属

  • 五层总表：负责什么 / 坏了什么症状 / 看什么证据
  • 命令的一生：vkCmdDraw 穿过五层的完整链路
  • 上层错误常是下层的二手报告：DEVICE_LOST = reset 的翻译
  • 核心心法：dmesg 干净偏上层，有 fault/reset 偏底层
  • 误区表：DEVICE_LOST ≠ 驱动 bug；Validation 干净 ≠ 无辜

概念

八个概念，每个只记三件事：负责什么、坏了会怎样、搜什么关键词。

02 8 CONCEPTS

驱动核心概念速览

  • DRM/KMS：Connector → CRTC → Plane，黑屏花屏找它
  • GEM/TTM：爆显存常表现为卡顿而非报错
  • Scheduler/Ring：ring timeout → reset → DEVICE_LOST
  • Fence/Syncobj：fence 超时 = 等待方视角
  • CS/VM_BIND：GPU page fault ≈ 进程段错误
  • dma-buf/PRIME：显式同步 linux-drm-syncobj-v1（2025 落地中）根治闪烁
  • Firmware/电源：无报错但性能低的头号嫌疑人
  • 设备节点：渲染走 renderD128，多 GPU 先核对选了哪块卡

04 TOOLS · BISECT

工具与二分定位流程

  • 必会命令：dmesg / journalctl -b -1 / sysfs / modetest
  • 环境变量：RADV_DEBUG=hang 取证 → $HOME/radv_dumps_
  • 工具分工直觉：画面错 RenderDoc、崩溃 dmesg、卡顿 gpu_top
  • 二分六步：内容 → Mesa → 内核 → 合成器 → API → 机器
  • 实验纪律：一次只换一个变量，每步留记录
  • 合格 bug 报告四件套 + Windows WDDM 同构对照

直觉速查

贴在工位上的两张卡。

心法

四句话 + 一刀定位

  • ① 是应用层、UMD、KMD，还是硬件？
  • ② dmesg 有没有 GPU fault / reset / page fault？
  • ③ 内核、Mesa、Firmware、合成器版本是什么？
  • ④ 换内核/Mesa/合成器/API 能不能二分？
  • dmesg 干净 → 偏上层；有 fault/reset → 偏底层
  • 换 Mesa 版本行为变化 → UMD；换内核变化 → KMD
  • 随机 + 温度相关 + 跨系统复现 → 硬件
误区

八个必须纠正的说法

  • 「DEVICE_LOST 就是驱动 bug」→ 它是 reset 的翻译，先看 dmesg 归因
  • 「Validation 不报错 = 没问题」→ 查用法不查逻辑
  • 「爆显存会报错」→ TTM 迁移颠簸，表现为卡顿
  • 「GPU page fault 就改自己的指针」→ 那是 GPU 虚拟地址
  • 「花屏就 RMA 显卡」→ 软件花屏远多于硬件花屏
  • 「nomodeset 能亮 = 修好了」→ 只是绕过 KMS 的验证手段
  • 「重启没日志了」→ journalctl -k -b -1 找上次启动
  • 「fence 超时和 ring 超时是两回事」→ 同一事件的等待方/执行方视角
