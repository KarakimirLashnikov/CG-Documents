2. 实时渲染系统定位

实时渲染系统是引擎中视觉输出的核心子系统，以每帧16.67ms（60fps）或更低的时间预算生成画面。

引擎层（渲染架构选型→材质/光照模型确定） ↓ 渲染核心层（FrameGraph声明式Pass管理） ├─ 资源子系统 (CPU加载 + VMA + Bindless) ├─ 管线子系统 (图形/计算/Mesh/光追缓存) └─ 同步子系统 (屏障推导 + 多队列并行) ↓ 执行层（多线程CB录制→GPU队列提交→Swapchain呈现）

3. 整体架构分层

层级核心职责关键抽象依赖方向
Layer 1 架构选型层确定渲染策略与材质模型渲染路径配置仅依赖引擎高层决策
Layer 2 渲染核心层Vulkan API封装、资源、管线管理虚拟资源句柄、PipelineCache依赖Vulkan API
Layer 3 FrameGraph层Pass依赖管理、自动优化、编排DAG有向无环图依赖Layer 2
Layer 4 执行调度层GPU命令录制、多队列同步CommandPool、Fence、Timeline Semaphore依赖Layer 3
核心设计原则：上层不直接操作Vulkan API对象。Layer 3/4通过虚拟资源句柄与Layer 2交互。

4. 核心设计原则

4.1 声明式优于命令式

Pass声明自己需要什么资源、读写什么附件、依赖什么其他Pass。不硬编码VkImage/VkBuffer。FrameGraph编译器自动推导屏障、布局转换、执行顺序。

4.2 GPU-Driven 优先

尽可能将决策推至GPU：GPU剔除→GPU间接绘制→Bindless全局描述符。减少CPU→GPU同步点。

4.3 数据驱动与零硬编码

渲染路径由场景配置/画质档位动态决定；Shader变体由材质参数驱动；帧图每帧动态构建。

4.4 显存是首要约束

纹理压缩优先于原始格式；资源别名复用；稀疏绑定分页加载。带宽优化优先于计算优化。

5. 术语约定

术语标准含义常见误用
Multi-Draw Indirect (MDI)GPU生成间接绘制命令❌ "Multi-Draw Direct"
FrameGraph行业通用术语，每帧动态构建的渲染DAG❌ 与RDG混为一谈
光追阴影/反射属于主渲染阶段❌ 归类至后处理

2. 预处理阶段标准Pass清单

Pass 1: GPU视锥与遮挡剔除

在GPU上执行视锥剔除和遮挡剔除，过滤不可见物体，生成可见物体的间接绘制命令。

CPU提交: 全场景物体AABB/OBB数据 → GPU Buffer GPU计算: 1. 每个物体执行视锥六面测试 2. 对通过视锥测试的物体执行Hi-Z遮挡测试 3. 写入可见物体索引到Indirect Draw Buffer 输出: VkDrawIndirectCommand Buffer (可见物体数量+偏移)

Pass 2: Depth Only深度预通道

提前渲染场景深度，为遮挡剔除提供Hi-Z深度金字塔，为主渲染Early-Z提供预填深度。

Pass 3: 蒙皮/曲面/海洋几何生成

Mesh Shader是图形管线的新一代替代方案，取代传统VS→GS流程：

输入装配 ──▶ Task着色器 ──▶ Mesh着色器 ──▶ 片段着色器 ──▶ 输出合并 (IA) (Task) (Mesh) (FS) (OM)

核心优势：集群级剔除(Task Shader)、灵活输出、GPU自主调度。

04绘制性能优化
本文档是系列第 4 篇，阐述GPU-Driven绘制优化体系。
⚠️ 术语纠正：正确术语为 Multi-Draw Indirect (MDI)，而非 "Multi-Draw Direct"。Direct需CPU逐物体提交，Indirect由GPU生成命令。

1. GPU-Driven全流程

传统 (CPU-Driven): CPU: 逐物体判断可见→逐物体提交Draw命令→GPU执行 N物体 = N次API调用 GPU-Driven: CPU: 提交全场景数据(1次)→剔除Dispatch(1次)→DrawIndirect(1次) GPU: 自主剔除→生成间接命令→自主绘制 CPU仅3次API调用!

2. Multi-Draw Indirect实现

// Compute Shader: GPU剔除 + 间接命令生成
layout(local_size_x = 256) in;
layout(std430) buffer IndirectCommands {
    VkDrawIndexedIndirectCommand commands[];
};
layout(std430) buffer VisibleCount {
    uint visibleCount;
};

void main() {
    uint objectID = gl_GlobalInvocationID.x;
    if (!isVisible(objectID)) return;

    uint visibleIndex = atomicAdd(visibleCount, 1);
    commands[visibleIndex].indexCount    = meshIndexCounts[objectID];
    commands[visibleIndex].instanceCount = 1;
    commands[visibleIndex].firstIndex    = meshIndexOffsets[objectID];
    commands[visibleIndex].vertexOffset  = meshVertexOffsets[objectID];
}

3. Bindless资源索引

传统逐绑定模式: N物体 = N次描述符绑定切换 = N次GPU状态失效 Bindless模式: 1次描述符绑定 → Shader通过材质索引直接访问全局数组

4. 合批与排序策略

状态切换代价排序（从高到低）：管线切换 > 描述符集切换 > 顶点绑定切换 > Push Constant更新

不透明物体从前到后排序(减少Overdraw)，透明物体从后到前排序(保证混合正确)。

5. Push Constant vs Dynamic UBO

数据大小128~256 bytes无限制
描述符开销无需描述符绑定

06FrameGraph帧图系统
本文档是系列第 6 篇，阐述声明式FrameGraph帧图系统的设计理念与完整生命周期。

1. 设计理念

FrameGraph采用声明式设计：工程师只声明"我要什么"，系统自动推导"如何安排"。

核心抽象：虚拟资源句柄。FrameGraph内部所有资源使用虚拟句柄引用，不硬编码VkImage/VkBuffer。

2. Pass声明五组信息

  1. 绑定管线类型（图形/计算/光追）+ Shader入口
  2. 资源布局（全局Bindless表 + 帧Uniform + 内部临时资源）
  3. 附件信息（色彩/深度 + Load/Store操作 + 清除参数）
  4. 依赖关系（读取哪些Pass的输出、写入哪些资源）
  5. 自动生成（Shader头文件 + PipelineLayout + Bindless索引）

3. 帧图完整生命周期

3.1 构建阶段

收集当前帧所有活跃Pass（根据开关、可见性剔除无效节点），生成DAG有向无环图。

3.2 编译阶段（核心优化）

五项优化：

  1. 无效Pass剔除：输出不被消费的Pass可剔除
  2. 资源别名复用：不同Pass分时共用同一块RT/Buffer物理显存
  3. 自动屏障推导：根据Pass间读写依赖自动生成VkImageMemoryBarrier
  4. Subpass合并：连续Pass合并为同一RenderPass的Subpass（移动端TBDR优化）
  5. 管线缓存查找/动态创建
别名复用效果: 无优化: GBuffer(100MB) + LightingOutput(50MB) + BloomTemp(30MB) = 180MB 有优化: GBuffer→光照后释放→Bloom复用GBuffer显存 = 150MB (节省30MB)

3.3 执行阶段

多线程并行录制CommandBuffer，按拓扑顺序提交队列。配合Timeline信号量、Fence做多队列同步。

3.4 收尾阶段

延迟释放过期资源、重置环形缓冲、重置帧级描述符池、更新历史帧资源。

1. 为什么需要现代图形API？

1.1 传统API的根本瓶颈

OpenGL与Direct3D 11为代表的传统图形API，诞生于GPU架构完全不同的时代。它们的核心问题并非某个单一缺陷，而是整体设计哲学与当代GPU硬件严重脱节：

问题维度传统API (OpenGL/D3D11)症状
驱动隐式同步驱动内部猜测开发者意图，自动插入屏障/等待CPU stall、帧率不稳定、性能不可预测

7. 小结

现代图形API的"现代"不是API本身的语法变革，而是API终于忠实地反映了现代GPU的真实架构：

  • 显式控制——因为GPU需要开发者精确告诉它做什么，而非驱动猜测
  • 多队列并行——因为GPU硬件有独立的图形/计算/传输处理器
  • PSO不可变——因为GPU硬件管线编译是一次性的重操作
  • Bindless全局数组——因为GPU显存足够大、带宽足够高，可以容纳数万纹理同时在线
  • RT/Tensor/Mesh Shader——因为GPU新增了专用硬件核心，需要对应的管线绑定点
  • FrameGraph自动管理——因为显式控制的代码量需要声明式系统来管理复杂性
一句话总结：现代图形API = 现代GPU硬件能力的精确投影 + 开发者对硬件的完全掌控权。

第三阶段：计算着色器与延迟渲染时代（2007–2014）— 通用计算与海量光源

图形API

DirectX 11 (2009)引入计算着色器(Compute Shader)——允许在GPU上运行通用计算程序，不经过图形管线，直接读写缓冲区。这使GPU可用于物理模拟、图像处理、延迟渲染光照计算、全局光照近似算法。曲面细分(Tessellation)让GPU运行时动态细分几何体。

引擎与划时代作品

延迟渲染(Deferred Rendering)的普及：前向渲染逐物体逐像素计算光照，光源数量受限。延迟渲染先将几何属性写入G-Buffer，再用计算着色器并行计算每个光源——光源数量与几何复杂度解耦，同屏数百光源成为可能。Battlefield 3 (2011, Frostbite 2)是延迟渲染在3A游戏中普及的标志。

PBR的崛起：UE4和Frostbite 3率先采用基于物理的渲染(PBR)——基于微面元理论(Burley/Disney BRDF)的着色，确保材质在不同光照条件下表现一致。核心原则是"能量守恒"和"金属-粗糙度工作流"。
