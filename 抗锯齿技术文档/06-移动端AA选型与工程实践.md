# 抗锯齿技术 — 移动端 AA 选型与工程实践

> 本文档是「抗锯齿（AA）技术」系列文档的第 **6** 篇，也是收尾篇。前五篇讲"有哪些技术、各自解决什么"，本篇讲**在移动端该选哪个**：约束来自 TBR/TBDR 与 GMEM，而不是 ALU。⚠️ 阅读本篇前建议先读同工作区的《移动端 GPU 架构文档》，两者的结论直接咬合。

---

## 1. 移动端的约束与人相反

桌面端 AA 选型的核心问题是"ALU 够不够"；移动端的核心问题是"**带宽与片上容量够不够**"。这会得出一些**与桌面直觉相反**的结论。

| 约束 | 说明 | 对 AA 选型的影响 |
|------|------|----------------|
| **TBR / TBDR 架构** | 几何先分箱，再逐 tile 光栅化与着色 | 后处理 AA 是"整屏 pass"，与 tile 局部性无冲突；但任何**跨 pass 的全分辨率纹理读写**都要走主存 |
| **GMEM 容量有限** | 移动端片上内存只有几百 KB 到几 MB（Adreno 615 = 512KB、630 = 1MB、X1 = 3MB；Mali 每核约十几 KB 量级） | **MSAA 让附件尺寸 ×N**，可能把一个 surface 挤到 Direct Mode |
| **MSAA resolve 在片上** | 多样本缓冲留存在 GMEM，resolve 时才写主存 | **MSAA 在移动端相对便宜**（与桌面的普遍认知相反） |
| **带宽是最贵资源** | 主存带宽直接对应功耗与发热 | TAA 的 history 读写、超分的额外输入缓冲都是实打实的成本 |
| **功耗墙 / 温控** | 长时间运行会降频 | 需要评估"持续性能"，而非只测峰值 |
| **无 Tensor Core / XMX** | 桌面级神经网络超分不可用 | 只能用 Arm ASR / NSS、GSR、MetalFX 等移动方案 |
| **FP16 精度友好** | 移动 GPU 对 mediump 友好 | AA 的中间计算尽量用 FP16（但运动矢量的精度要小心） |

### 1.1 两条反直觉结论

```
┌──────────────────────────────────────────────────────────────────────────┐
│  反直觉 1：MSAA 在移动端反而"划算"                                        │
│                                                                          │
│   桌面：MSAA 的多样本缓冲在主存 → 带宽 ×N → 普遍不用                        │
│   移动：多样本缓冲在 GMEM → resolve 时才出主存 → 成本主要是"片上空间"         │
│   → 移动端 4× MSAA 常常是可选项，甚至是首选（前向渲染下）                    │
│                                                                          │
│   ⚠️ 但前提是"塞得进 GMEM"：MSAA 会让附件占用 ×4，                        │
│      一旦溢出就会触发 Direct Mode（见《移动端 GPU 架构文档》第 06 篇）       │
└──────────────────────────────────────────────────────────────────────────┘
```

```
┌──────────────────────────────────────────────────────────────────────────┐
│  反直觉 2：TAA 在移动端"贵"在带宽，不在 ALU                                │
│                                                                          │
│   每帧成本（全分辨率计）：                                                 │
│     · 写运动矢量缓冲           1 次读目标 + 1 次写                         │
│     · 读历史缓冲               1 次读                                     │
│     · 写新历史缓冲             1 次写                                     │
│     · 读当前帧颜色             1 次读                                     │
│     · 写输出                   1 次写                                     │
│   → 相当于每帧多访问 3~5 个全分辨率目标                                     │
│                                                                          │
│   在带宽受限的移动设备上，这个量级足以吃掉一个后处理链的预算                  │
│   → 移动端上 TAA 的"值不值"完全取决于：你的瓶颈是不是填充率                  │
└──────────────────────────────────────────────────────────────────────────┘
```

## 2. 各方案在移动端的代价对照

⚠️ 下表的"成本"是**相对量级**（用于选型排序），不是绝对毫秒数。实际必须实测。

| 方案 | 显存 | 带宽 | ALU | 依赖 | 移动端适配度 |
|------|------|------|-----|------|------------|
| **无 AA** | — | — | — | — | 基线（低端设备兜底） |
| **MSAA 2×/4×** | 附件 ×N（**在 GMEM**） | resolve 时 1 次全屏写 | 光栅化成本增加 | 前向渲染；GMEM 容量 | ⭐⭐⭐⭐ 前向渲染首选 |
| **MSAA 8×** | 附件 ×8 | 同上 | 同上 | 同上 | ⭐⭐ 容易溢出 GMEM |
| **FXAA** | 无 | 1 读 + 1 写（全屏） | 8~12 次采样 | 无 | ⭐⭐⭐⭐⭐ 最省 |
| **SMAA 1x** | 2 张中间图（边缘 + 权重） | 2 读 + 2 写 + 最终 1 读 1 写 | 中等（搜索成本随边缘数变化） | 无 | ⭐⭐⭐ |
| **CMAA2** | 少量中间图 | 略高于 FXAA | 中等 | 无 | ⭐⭐⭐⭐ 低模糊，适合平面风格 |
| **TAA** | history + MV（全分辨率） | **3~5 个全分辨率访问/帧** | 中等 | 运动矢量、深度 | ⭐⭐ 高填充率场景才值 |
| **TAA + MSAA** | 两者叠加 | 叠加 | 叠加 | 两者 | ⭐⭐ 移动端可行（MSAA 便宜），但占 GMEM |
| **FSR 3.1（着色器）** | 多张中间图 | 高（比 TAA 更多输入） | 高（着色器实现） | 运动矢量、深度 | ⭐⭐ 开销大，移动端收益不稳 |
| **Arm ASR** | 多张中间图 | 中（Arm 称约为 FSR 2 的 1/3 开销） | 中 | 运动矢量、深度 | ⭐⭐⭐⭐ 为移动端设计 |
| **Arm NSS** | 依赖神经加速器 | 低带宽（官方称演示中外部内存流量 -70%） | 走 NPU | 神经加速器（2026 年底硬件） | ⭐⭐⭐⭐⭐（未来）当前不可量产 |
| **Snapdragon GSR** | 少 | 低（GSR1 空间路径极低） | 低 | Snapdragon 设备 | ⭐⭐⭐⭐ 平台内首选 |
| **MetalFX** | 中 | 中 | 中 | Apple 平台 | ⭐⭐⭐⭐ iOS/macOS 首选 |
| **A2C** | 复用 MSAA | 无额外 | 无额外 | 需 MSAA | ⭐⭐⭐⭐⭐ 植被场景几乎免费 |
| **SDF 字体（UI）** | 显著省显存 | 低 | 低（fwidth） | 离线烘焙 | ⭐⭐⭐⭐⭐ UI 标准解 |

## 3. 决策树

```
┌──────────────────────────────────────────────────────────────────────────┐
│  移动端 AA 选型决策树                                                      │
│                                                                          │
│  ① 你的瓶颈是 GPU 填充率（fill-rate）吗？                                  │
│     ├─ 否（CPU / 分箱 / 几何受限）→ 先解决瓶颈！AA 换了也没收益             │
│     │      （对照《移动端 GPU 架构文档》第 05 篇的诊断树）                   │
│     └─ 是 ↓                                                              │
│                                                                          │
│  ② 能拿到正确的运动矢量吗（含顶点动画、粒子）？                              │
│     ├─ 不能 → 走空间路线：                                                  │
│     │    ├─ 低端/几何简单        → FXAA                                   │
│     │    ├─ 卡通/平面风格        → SMAA 1x 或 CMAA2                        │
│     │    └─ 前向渲染 + 有空预算  → MSAA 4×（+ A2C 处理植被）                │
│     └─ 能 ↓                                                              │
│                                                                          │
│  ③ 你的基础渲染分辨率低于显示分辨率吗？                                      │
│     ├─ 是（需要上采样）→ 需要"AA + 超分"一体方案：                          │
│     │    ├─ Snapdragon 设备      → Snapdragon GSR                          │
│     │    ├─ Apple 设备           → MetalFX                                 │
│     │    ├─ 跨厂商 / 通用        → Arm ASR（MIT，基于 FSR 2）              │
│     │    ├─ UE5 项目             → TSR                                     │
│     │    ├─ Unity 6 项目         → STP（注意：会覆盖相机 AA 为 TAA，          │
│     │    │                          且不能与动态分辨率同用）                  │
│     │    └─ 有新神经硬件         → Arm NSS（2026 年底起）                    │
│     └─ 否 ↓                                                              │
│                                                                          │
│  ④ 是延迟渲染吗？                                                          │
│     ├─ 是 → 不能上 MSAA（G-Buffer 语义冲突 + GMEM 爆炸）                    │
│     │        → TAA / TSR / 超分方案；或 Mobile Deferred + 移动专用 TAA       │
│     └─ 否（前向）→ MSAA 4× 优先；必要时叠加 TAA 处理时间混叠                  │
│                                                                          │
│  ⑤ 无论如何：UI 永远在最后                                              │
│     UI 以显示分辨率、在 AA 与上采样之后合成（见第 05 篇）                     │
└──────────────────────────────────────────────────────────────────────────┘
```

## 4. 各引擎的移动端设置（⚠️ 以引擎源码/官方文档为准）

### 4.1 UE5

| 设置 | 说明 |
|------|------|
| **项目设置 → Mobile Anti-Aliasing Method** | 可选 None / FXAA / TAA / MSAA |
| **`r.Mobile.AntiAliasing`** | 控制台变量唯一数据源，取值：`0` = off、`1` = FXAA、`2` = TAA（若 `SupportsGen4TAA` 关闭则回退 FXAA）、`3` = MSAA |
| **MSAA 的限制** | 官方 API 文档明确：**MSAA 仅在 forward shading 下支持**；采样数由 `r.MSAACount` 控制 |
| **TAA 的移动端前提** | 需要项目设置里的 **"Supports Desktop Gen4 TAA on Mobile"**，否则会静默回退到 FXAA |
| **Planar Reflection 与 MSAA 互斥** | 官方文档注明：`MobilePPR Exclusive` / `MobilePPR` 模式下 **MobileMSAA 会被禁用** |
| **💡 版本文档的坑** | 存在互相矛盾的二手资料：有平台文档称"`r.Mobile.AntiAliasing=1` 代表 TAA、移动端不支持"，而引擎 cvar 帮助文本明确写 `1: FXAA`、`2: TemporalAA`、`3: MSAA`。**以引擎源码 / 官方 API 文档为准**，遇到黑屏/花屏先核对 cvar 语义 |

| 移动端建议 | 理由 |
|-----------|------|
| 前向渲染项目优先 MSAA | 片上 resolve，成本低，几何边缘精度真实 |
| 延迟渲染项目用 TSR / 移动 TAA | MSAA 与 G-Buffer 语义冲突 |
| 一半以上时间用于检查"是否有意外的后处理链" | 移动端最容易被后处理链吃掉带宽 |

### 4.2 Unity（URP / HDRP）

| 设置 | 说明 |
|------|------|
| **MSAA** | 在 URP Asset 上启用（前向/延迟下的可用性不同，需按版本核对） |
| **相机 Anti-aliasing** | None / FXAA / SMAA / TAA（TAA 需运动矢量，URP 需启用相应支持） |
| **Upscaling Filter**（URP Asset → Quality） | Bilinear / Nearest-Neighbor / FSR / STP / Automatic |
| **STP（Unity 6）** | 时空后处理，**在放大的同时执行 TAA**；官方说明：选择 STP 会**把相机的抗锯齿设置覆盖为 TAA**；**仅支持有 Compute 能力的非 GLES 设备**，不支持时自动回退到 Automatic 选项；**不能与动态分辨率同时使用** |
| **HDRP** | 支持 FSR 2.1、TAAU、CAS、STP（不同平台可用性不同） |
| **Unity 6 Render Graph** | Unity 官方称在移动端可**降低最多 50% 内存带宽** → 对带宽受限的 AA 方案（TAA/超分）是实质性利好 |

### 4.3 自研引擎（Vulkan 路径）

⚠️ 移动端 AA 的 Vulkan 集成，有四个与桌面不同的要点：

| 要点 | 说明 |
|------|------|
| **MSAA 用 lazily allocated 内存** | MSAA 颜色附件在移动端应使用 `VK_MEMORY_PROPERTY_LAZILY_ALLOCATED_BIT`（配 transient/`VK_IMAGE_USAGE_TRANSIENT_ATTACHMENT_BIT`）。**多样本数据只需留在 GMEM，不必真正分配主存** |
| **load/store op 决定成败** | MSAA 附件：`loadOp = CLEAR`（不要 LOAD）、`storeOp = DONT_CARE`（不 resolve 时）；resolve 附件：`loadOp = DONT_CARE`、`storeOp = STORE`。⚠️ 在移动端"跳过 clear"是**反向优化**（驱动会被迫从主存读回 tile buffer） |
| **resolve 的位置** | 用 `VK_RESOLVE_MODE_AVERAGE_BIT` 的 resolve attachment 或 `vkCmdResolveImage`。**优先留在 render pass 内**，让 resolve 在 tile 上完成 |
| **TAA 的 history 是"跨 pass 全屏纹理"** | 它必然走主存，无法留在 GMEM（除非用 `VK_QCOM_tile_memory_heap` 之类的显式片上分配）。这是 TAA 在移动端的结构性成本，plan 预算时要算进去 |
| **VRS 需按设备查询** | 移动端对 `VK_KHR_fragment_shading_rate` 的支持不统一。⚠️ 与 AA 的交互：VRS 降低着色率会放大 `fwidth` 导数 → **破坏 SDF/解析 AA**；UI 与 SDF 渲染阶段应禁用 VRS |

**移动端 MSAA 的配置骨架（要点注释版）**：

```cpp
// ① MSAA 颜色附件：transient + lazily allocated，只在 GMEM 存在
VkAttachmentDescription msaaColor{};
msaaColor.samples     = VK_SAMPLE_COUNT_4_BIT;
msaaColor.loadOp      = VK_ATTACHMENT_LOAD_OP_CLEAR;        // ⚠️ 移动端必须 CLEAR，不要 LOAD
msaaColor.storeOp     = VK_ATTACHMENT_STORE_OP_DONT_CARE;   // ⚠️ 多样本数据不需要写回主存
msaaColor.stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
msaaColor.stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;

// ② resolve 目标：单采样，最终写回主存
VkAttachmentDescription resolve{};
resolve.samples  = VK_SAMPLE_COUNT_1_BIT;
resolve.loadOp   = VK_ATTACHMENT_LOAD_OP_DONT_CARE;          // resolve 会覆盖全部像素
resolve.storeOp  = VK_ATTACHMENT_STORE_OP_STORE;

// ③ resolve 留在 render pass 内 → tile 上完成
VkAttachmentReference msaaRef{ 0, VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL };
VkAttachmentReference resolveRef{ 1, VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL };
subpass.pResolveAttachments = &resolveRef;

// ④ 深度/模板也随 MSAA 尺寸增长 —— GMEM 预算的主要风险点
//    4× MSAA + D24S8 在 1080p 下的片上需求是按 GB/s 带宽无法弥补的，
//    一旦超出驱动预算就会退化到 Direct Mode（见《移动端 GPU 架构文档》第 06 篇）
```

⚠️ **一个必须做的验证**：改完 MSAA 配置后，用 Snapdragon Profiler / Arm Performance Studio 检查是否出现 `Direct Render Mode` / surface 数量异常增长。**MSAA 在移动端最典型的失败模式不是"变慢"，而是"某个 surface 突然掉进 Direct Mode，整条管线退化"**。

## 5. 与《移动端 GPU 架构文档》的联动结论

这两套文档在以下四点上直接咬合，建议对照阅读：

| 本文的 AA 决策 | 对应的移动端 GPU 机制 | 参见 |
|---------------|---------------------|------|
| MSAA 便宜是因为片上 resolve | GMEM 与逐 tile 流水线 | 移动端 03 篇 |
| MSAA ×4 会挤爆 GMEM → Direct Mode | GMEM 容量与 spill | 移动端 03、05 篇 |
| TAA 的 history 无法留在片上 | tile 局部性与 pass 间依赖 | 移动端 03、06 篇 |
| UI 阶段禁用 VRS、禁止降采样 | 导数语义与 VRS | 移动端 05 篇 + 本文第 02 篇 |
| 超分只在填充率受限时有收益 | `% Time ALUs Working` 低 + Stall 高 = 带宽问题 | 移动端 05 篇 |

**一条综合判断规则**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  先判断瓶颈，再选 AA                                                       │
│                                                                          │
│  如果 profiler 显示：                                                    │
│     · ALU 利用率低 + 各种 Stall 高   → 带宽问题                            │
│        → 此时换 AA 方案意义有限，先减 surface / 减后处理 / 减精度            │
│     · 出现 Direct Render Mode       → 附件太大（含 MSAA ×N）               │
│        → 先减 MSAA 或减 G-Buffer，再谈 AA 选型                             │
│     · 分箱时间占比异常高            → 几何/draw call 问题                  │
│        → 与 AA 无关，改几何                                             │
│     · 填充率确实打满（ALU 高、无异常 Stall）→ AA 选型才是真杠杆              │
└──────────────────────────────────────────────────────────────────────────┘
```

## 6. 移动端 AA 检查清单

```
【选型】
□ 确认瓶颈确实是 GPU 填充率（不是一个"以为"）
□ 确认运动矢量可用性（含顶点动画、粒子、UI）
□ 确认渲染分辨率 vs 显示分辨率是否需要上采样
□ 确认渲染路径（前向 / 延迟）—— 决定 MSAA 是否可用
□ 确认目标设备群的 API 能力（Vulkan 版本、是否支持 Compute）

【MSAA 路径】
□ 使用 transient + lazily allocated 颜色附件
□ loadOp = CLEAR（不要 LOAD）
□ storeOp = DONT_CARE（多样本附件）
□ resolve 留在 render pass 内
□ 深度/模板也用了正确的 load/store op
□ 实测确认没有触发 Direct Render Mode
□ 植被/镂空面片考虑 A2C

【TAA / 超分路径】
□ 运动矢量缓冲同分辨率，且已减去 jitter
□ history 带宽已计入预算（3~5 个全分辨率访问/帧）
□ 抖动序列正确（静止画面完全静止）
□ 失败模式已排查（鬼影、UI 拖影、薄几何抹平）
□ 平台超分已按设备分支（GSR / MetalFX / ASR / TSR / STP / NSS）
□ 若用 Unity STP：确认不与动态分辨率同用
□ 若用 UE5 移动 TAA：确认 Supports Desktop Gen4 TAA on Mobile 已开

【UI】
□ UI 在 AA 与上采样之后、以显示分辨率合成
□ UI 阶段禁用 VRS
□ 使用 SDF/MSDF 字体（省显存 + 任意缩放）
□ 预乘 alpha 与混合状态匹配

【持续验证】
□ 峰值帧率与持续帧率都测（温控会改变结论）
□ 在低端与高端设备各测一遍（GMEM 容量差异巨大）
□ 用 profiler 检查 surface 数量与 Direct Mode 警告
```

## 7. 小结

| 要点 | 说明 |
|------|------|
| **移动端瓶颈在带宽与片上容量，不在 ALU** | 所有 AA 选型都应从这个前提出发 |
| **MSAA 在移动端相对便宜** | 多样本缓冲留在 GMEM，resolve 时才出主存；这与桌面直觉相反 |
| **但 MSAA 的代价是 GMEM 空间** | ×4 的附件占用可能触发 Direct Mode——"便宜"的前提是塞得下 |
| **TAA 在移动端贵在带宽** | history 无法留在片上，每帧 3~5 个全分辨率访问 |
| **先判瓶颈，再选 AA** | ALU 低 + Stall 高 = 带宽问题，此时换 AA 没有杠杆 |
| **前向 + MSAA / 延迟 + TAA** | 这是两条最稳的路线，且都由架构语义决定 |
| **超分必须按平台分支** | GSR（高通）/ MetalFX（Apple）/ ASR（跨厂商）/ TSR（UE5）/ STP（Unity） |
| **Arm NSS 是 2026 年底的分水岭** | 神经加速器 + Vulkan ML 扩展（`VK_ARM_tensors` / `VK_ARM_data_graph`），当前只能靠 ASR + 模拟层做原型 |
| **UE5 的 cvar 语义要按源码核对** | `r.Mobile.AntiAliasing` 的取值在二手资料中存在矛盾，且 MSAA 仅前向渲染可用 |
| **Unity STP 有两条硬限制** | 会覆盖相机 AA 为 TAA；不能与动态分辨率同时使用 |
| **UI 永远在最后** | 以显示分辨率、在 AA 与上采样之后合成；UI 阶段禁用 VRS |
| **移动端 MSAA 的最典型失败不是变慢** | 而是某个 surface 掉进 Direct Mode 导致整条管线退化，必须用 profiler 验证 |
