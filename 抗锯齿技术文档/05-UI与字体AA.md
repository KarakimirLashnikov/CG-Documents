# 抗锯齿技术 — UI 与字体 AA

> 本文档是「抗锯齿（AA）技术」系列文档的第 **5** 篇。UI 和字体是独立的一条线：**边缘在纹理/字形内部，不在几何边界上**。这决定了 MSAA 对它无效、TAA 会糊它、而真正管用的是另一套东西（灰度 AA、子像素 AA、SDF、预乘 alpha、A2C）。本篇同时给出管线顺序与分辨率的正确摆放位置。

---

## 1. 为什么 UI / 字体是独立的一条线

```
┌──────────────────────────────────────────────────────────────────────────┐
│  三类边缘的来源完全不同                                                    │
│                                                                          │
│  A. 几何边缘（MSAA 的地盘）                                                │
│                                                                          │
│     场景几何 ──► 三角形边界穿过像素 ──► 0/1 覆盖 ──► 阶梯                  │
│     ▲ 边缘位置在"几何"里，光栅化时才知道                                    │
│                                                                          │
│  B. 纹理/着色内部的高频（mipmap 的地盘）                                    │
│                                                                          │
│     贴图内 ──► 高频信号被欠采样 ──► 摩尔纹/噪点                             │
│     ▲ 边缘位置在"纹理像素"里，几何边界完好无损                              │
│                                                                          │
│  C. UI / 字体边缘（本篇的地盘）                                            │
│                                                                          │
│     字形轮廓/图标矢量 ──► 烘焙进纹理的 alpha ──► 混合时产生软边             │
│     ▲ 边缘位置在"alpha 值"里，几何上就是一个矩形（一个 quad）                │
│        → MSAA 只看到这个 quad 的 4 条边，完全看不到字形笔画！                │
└──────────────────────────────────────────────────────────────────────────┘
```

**这个结论极其重要**：

| 技术 | 对 UI / 字体是否有用 | 原因 |
|------|-------------------|------|
| **MSAA** | ❌ 基本无效 | UI 通常就是一个铺满屏幕的 quad；字形的"边缘"在纹理 alpha 里，MSAA 采样不到 |
| **SSAA** | ✅ 有效 | 每个子像素都完整着色，纹理采样率也随之提高 → 字形边缘被真正多采样 |
| **FXAA / SMAA** | ⚠️ 部分有效，通常有害 | 会把字形当成边缘去"混"，导致字变糊、笔画粘连 |
| **TAA** | ❌ 有害 | 抖动 + 历史累积会让文字抖动、发糊、拖影（除非 UI 在 TAA 之后合成） |
| **A2C** | ✅ 有条件有效 | 若 UI 使用 alpha test（而非 blend），A2C 能把 alpha 转成覆盖率 |
| **灰度 AA（字形烘焙）** | ✅ **正解** | 在字形栅格化时直接计算覆盖率并写入 alpha |
| **子像素 AA（LCD）** | ✅ 正解（有前提） | 利用 RGB 子像素，水平分辨率 ×3，但前提严格 |
| **SDF / MSDF** | ✅ **正解** | 距离场天然支持任意缩放的平滑边缘 |
| **预乘 alpha** | ✅ 必须 | 正确混合的前提，与滤波配合减少边缘伪影 |

## 2. 字体渲染的完整管线

```
┌──────────────────────────────────────────────────────────────────────────┐
│  从矢量轮廓到屏幕像素                                                     │
│                                                                          │
│  ① 字形轮廓（矢量）                                                      │
│     TrueType：二次贝塞尔（quadratic B-spline）                            │
│     OpenType/CFF：三次贝塞尔                                              │
│                                                                          │
│  ② 变换与亚像素定位                                                       │
│     字号缩放 + 位置（可能是非整数像素位置）                                  │
│     ⚠️ 关键决策：                                                   │
│        · 量化到整数像素 → 字距会跳动，但位图可复用                            │
│        · 亚像素定位     → 字距平滑，但每个位置都要重新栅格化                   │
│                                                                          │
│  ③ Hinting（字体微调）                                                   │
│     把笔画边缘对齐到像素网格 → 小字号更清晰                                  │
│     ⚠️ 与 AA 存在张力（见 §2.3）                                          │
│                                                                          │
│  ④ 栅格化（Rasterization）                                              │
│     解析求交 → 计算每个像素的**覆盖面积** → 这就是抗锯齿本身！                 │
│                                                                          │
│  ⑤ 输出                                                                  │
│     · 灰度 AA：1 个 alpha 通道（覆盖率）                                   │
│     · LCD 子像素 AA：3 个通道（R/G/B 各自的覆盖率）                          │
│     · 单色（mono）：1 bit，无 AA                                          │
│                                                                          │
│  ⑥ 合成                                                                  │
│     dst = src × α + dst × (1 − α)      ← ⚠️ 必须在正确的色彩空间做          │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.1 灰度 AA（Grayscale / Coverage AA）

**核心思想**：字形边缘的"锯齿"在栅格化阶段就能解析求解——**直接算这个像素被字形覆盖了百分之多少**，把这个比例当作 alpha。

```
      字形 "A" 的边缘穿过像素网格

      ┌────┬────┬────┐          覆盖率                渲染结果
      │    │ ╱  │    │          ┌────┬────┬────┐    ┌────┬────┬────┐
      ├────┼────┼────┤    →     │ 0  │ 35 │ 0  │ →  │    │▒▒  │    │
      │   ╱│    │    │          ├────┼────┼────┤    ├────┼────┼────┤
      ├──╱─┼────┼────┤          │ 80 │    │ 0  │    │▓▓▓ │    │    │
      │╱   │    │    │          ├────┼────┼────┤    ├────┼────┼────┤
      └────┴────┴────┘          │100 │ 20 │ 0  │    │███ │▒▒  │    │
                                └────┴────┴────┘    └────┴────┴────┘
```

| 优点 | 说明 |
|------|------|
| 分辨率无关的"覆盖率"精度 | 与超采样不同，覆盖率是**解析计算**的，不需要 ×4 采样 |
| 成本低 | 只是 alpha 通道，无额外采样 |
| 与任何合成方式兼容 | 可用于透明背景、旋转文本、视频叠加 |

**这是字体 AA 的默认答案**，也是所有字体渲染引擎（FreeType、DirectWrite、Core Text）的基础。

### 2.2 LCD 子像素 AA（ClearType 家族）

**原理**：LCD 屏幕的每个像素由 R/G/B 三个物理子像素横向排列组成。若能**分别控制三个子像素的亮度**，则水平方向的有效分辨率提升到 3 倍。

```
     逻辑像素              物理子像素
     ┌────────┐           ┌───┬───┬───┐
     │   ●    │    =      │ R │ G │ B │
     └────────┘           └───┴───┴───┘
      1 个 alpha          3 个独立通道（每通道一个覆盖率）

     垂直方向无法利用子像素（RGB 竖条排列），所以：
     → 水平清晰度提升明显，垂直方向提升有限
     → 这也是为什么 LCD AA 的文字"横向更锐利"
```

**代价与前提（这是它逐渐退场的原因）**：

| 前提 | 说明 |
|------|------|
| **已知子像素排列** | RGB stripe（最常见）/ BGR / RGB 竖条…排列不同 → 颜色偏移方向不同。Windows 的 ClearType 有调优向导就是为此 |
| **必须不透明背景** | 透明背景上与背景混合时，子像素的"独立控制"被打乱，彩边无法抵消 |
| **必须在显示分辨率 1:1** | 任何缩放（尤其是非整数缩放）都会破坏子像素对齐 → 彩边变成颜色污染 |
| **需要 gamma 校正** | 子像素亮度与感知亮度非线性，不校正会出现"字重不均" |
| **不能旋转** | 旋转文本时子像素排列与字形笔画不再对齐 |
| **与视频/合成兼容性差** | 视频叠加、屏幕录制、远程桌面都容易出问题 |

**典型伪影**：

| 伪影 | 现象 | 原因 |
|------|------|------|
| **彩边（Color fringing）** | 字形左右边缘出现红/蓝边 | 子像素排列假设错误，或 gamma 未校正 |
| **字重不均** | 同一段文字有的笔画粗有的细 | gamma 校正缺失；不同字形的子像素相位不同 |
| **缩放后变脏** | 缩放 UI 后文字边缘出现彩色噪点 | 子像素对齐被破坏 |

⚠️ **现代趋势**：随着高 DPI 屏（2×/3×）普及，**灰度 AA 已足够清晰**，子像素 AA 的收益下降而风险不变。所以 iOS / macOS 早已默认使用灰度 AA；Windows 也把 ClearType 变成可选开关而非强制。**在移动端和跨平台 UI 里，直接用灰度 AA + 高 DPI 是更稳的选择。**

### 2.3 Hinting 与 AA 的张力

| 手段 | 目的 | 与 AA 的冲突 |
|------|------|-------------|
| **Hinting**（对齐像素网格） | 小字号下笔画不被"半覆盖"而变灰、变模糊 | 会**改变字形形状**（笔画宽度刚性化），大字号下会显得畸形 |
| **AA**（保留覆盖率精度） | 边缘平滑、形状正确 | 小字号下可能让笔画"变灰"，降低可读性 |

**实践分档**：

| 字号 | 建议 |
|------|------|
| 极小（≤ 12px 逻辑） | 强 hinting + 轻 AA（或纯 mono 位图） |
| 常规（14~24px） | 轻 hinting + 灰度 AA |
| 大字号 / 标题 | **关闭 hinting** + SDF 或直接解析 AA |

**共同的前提是"像素对齐"**（见 §4.3）。

### 2.4 色彩空间：为什么字的"胖瘦"取决于混合位置

⚠️ 这是一个真实且容易被忽略的问题：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  alpha 混合发生在哪个空间，会改变文字看起来的"字重"                         │
│                                                                          │
│  在 sRGB（感知）空间混合：                                                │
│     α = 0.5 时，亮度取两端的中值 → 视觉上"正好一半"                         │
│                                                                          │
│  在线性空间混合：                                                         │
│     α = 0.5 时，线性光取中值 → 转换回 sRGB 后比感知中值更亮                  │
│     → 白底黑字会显得**更细**，黑底白字会显得**更粗**                        │
└──────────────────────────────────────────────────────────────────────────┘
```

| 场景 | 常见做法 | 后果 |
|------|---------|------|
| UI 在 sRGB 空间混合 | 传统 UI 框架的默认 | 与设计稿一致，但物理上不"正确" |
| UI 在线性空间混合 | 现代 HDR 管线（含 UI 也在线性空间） | 字重变化，需要美术重新调字号/字重 |
| **最忌混用** | 部分 UI 在 sRGB、部分在线性 | 同一界面上字重不一致，观感很差 |

**结论**：管线可以选任一空间，但**必须全 UI 一致**，并在设计阶段就确定。

## 3. SDF 字体（承第 02 篇）

SDF 在 UI/字体上的地位特殊：它是**唯一能"一次烘焙、任意缩放"而不糊的方案**。

```
┌──────────────────────────────────────────────────────────────────────────┐
│  SDF 字体的工作方式                                                       │
│                                                                          │
│  离线（烘焙）                                                             │
│    字形 → 距离场（每像素存"到最近边界的有符号距离"）                          │
│    → 打包进图集（atlas），通常 8 位单通道或三通道（MSDF）                     │
│                                                                          │
│  运行时（渲染）                                                           │
│    d = texture(atlas, uv).r                                              │
│    w = fwidth(d)              ← 屏幕空间导数：1 像素对应多少距离值          │
│    alpha = smoothstep(-w, +w, d)   ← 得到任意缩放下的覆盖率的近似            │
│                                                                          │
│  关键：因为存的是"距离"而不是"覆盖"，所以能跨越所有字号保持平滑              │
└──────────────────────────────────────────────────────────────────────────┘
```

### 3.1 与位图字体、灰度 AA 的对比

| 方案 | 缩放质量 | 显存 | 可动画 | 备注 |
|------|---------|------|--------|------|
| **灰度 AA 位图（按字号烘）** | 只在烘的档位好，缩放即糊 | 每字号一份，**随字号数量线性增长** | 差 | 传统游戏 UI 做法 |
| **灰度 AA 位图（单档 + 缩放）** | 缩放即糊 | 小 | 一般 | 只在字号少且 1:1 时用 |
| **SDF（单通道）** | 平滑，但**尖角被圆角化** | 一份，**与字号无关** | ✅ 优秀 | 字形/图标通用 |
| **MSDF（多通道）** | 平滑且**保留尖角** | 约 3 倍（三通道） | ✅ 优秀 | 字形首选 |
| **实时轮廓填充** | 完美 | 极小（只存轮廓） | ✅ | 成本高、复杂字形慢 |

### 3.2 SDF 的实用边界

| 项 | 说明 |
|----|------|
| **`pxRange`** | 图集的"距离范围"（如 ±8 像素）。太小 → 放大时平滑区不足、出现硬边；太大 → 精度下降、出现"台阶" |
| **笔画过细时劣化** | 笔画宽度接近图集分辨率极限时，距离场无法表达 → 出现断笔或粗细不均 |
| **极小时号劣化** | `fwidth` 变大，`smoothstep` 跨度过宽 → 字变得灰、发虚 |
| **需要 mip / 多档图集** | 极端缩小时，单个 SDF 的导数跨度过大；大厂做法是按屏幕尺寸选不同 pxRange 的图集 |
| **生成工具** | `msdfgen`（Chlumsky）是 MSDF 的事实标准工具；SDF 生成本身是离线成本 |
| **有效距离截断** | 距离场通常只存有限范围（如 ±8 像素），超出部分饱和 → 决定了放大上限 |

⚠️ **SDF ≠ 无损**：它是"用有限精度的距离信息重建边缘"，因此**放大到很多倍之后依然受原始分辨率限制**。别把它当"无限矢量"用。

### 3.3 与 AA 的关系

SDF 的 AA 是"**在着色器里解析地做**"的：不是靠多采样，也不是靠后处理，而是靠 `fwidth` 把距离转成覆盖率梯度。这带来两个工程要点：

| 要点 | 说明 |
|------|------|
| **导数必须正确** | `fwidth` 在 2×2 quad 内共享，分支发散时会出错（见第 02 篇） |
| **与 VRS 冲突** | VRS 降低着色率会放大导数 → SDF 边缘过度模糊或出现硬边。**UI 阶段不要用 VRS** |

## 4. UI 纹理的 AA 细节

### 4.1 预乘 alpha（Premultiplied Alpha）——不是可选项

```
┌──────────────────────────────────────────────────────────────────────────┐
│  非预乘（straight alpha）                                                 │
│     存储 (R, G, B, A)                                                     │
│     混合：dst = src.rgb × α + dst × (1−α)                                │
│                                                                          │
│  预乘（premultiplied）                                                    │
│     存储 (R×A, G×A, B×A, A)                                              │
│     混合：dst = src.rgb + dst × (1−α)      ← 少一次乘法                   │
└──────────────────────────────────────────────────────────────────────────┘
```

**为什么 UI 必须预乘**——因为预乘让**线性插值（双线性/三线性滤波）在数学上是正确的**：

| 问题 | 非预乘的表现 | 预乘的表现 |
|------|------------|-----------|
| **边缘暗边/亮边** | 透明像素的 RGB 常是"垃圾值"（未定义），插值后与不透明像素混合 → 边缘出现暗边或亮边 | 透明像素的 RGB 已被 α 归零，插值结果正确 |
| **mip 生成** | 相邻 mip 层的颜色平均错误 | 正确 |
| **缩放/旋转** | 边缘出现"脏边" | 干净 |

⚠️ **实践陷阱**：
- 美术导出的 PNG 通常是**非预乘**的，导入引擎时若启用 sRGB 纹理且未做预乘处理，边缘会出问题。
- 预乘会**损失高光数据的精度**（α 很小时 RGB 被压得很小），所以 UI 图集的 RGB 一般是纯色/渐变，问题不大；但**用于 HDR 的叠加层要小心**。
- **同一个混合状态不能同时处理预乘和非预乘纹理**——图集内必须统一。

### 4.2 图集 padding / bleed

```
┌──────────────────────────────────────────────────────────────────────────┐
│  没有 padding（错误）                                                      │
│   ┌────────┬────────┐     双线性采样/生成 mip 时，               │
│   │  图标A  │  图标B │     邻块的像素被"吸"进边缘                 │
│   │ ▓▓▓▓▓▓ │ ▒▒▒▒▒▒ │     → 图标边缘出现邻居的颜色                │
│   └────────┴────────┘                                                   │
│                                                                          │
│  有 padding（正确）                                                        │
│   ┌──┬────────┬──┬────────┬──┐                                          │
│   │P │  图标A  │P │  图标B  │P │   P = 图标边缘像素的"外扩"              │
│   │  │ ▓▓▓▓▓▓ │  │ ▒▒▒▒▒▒ │  │                                          │
│   └──┴────────┴──┴────────┴──┘                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

| 项 | 建议 |
|----|------|
| **padding 宽度** | ≥ 2 像素（若生成 mip，需按最粗 mip 级别放大 padding） |
| **外扩内容** | 复制边缘像素（clamp），不是透明像素 |
| **图集尺寸与 mip** | 若 UI 会缩放，图集尺寸要能被 mip 链整除（避免非 2 的幂造成的对齐问题） |

### 4.3 像素完美（Pixel-perfect）与半像素偏移

⚠️ 这是 UI 最常见的"莫名发虚"来源。

```
┌──────────────────────────────────────────────────────────────────────────┐
│  整数对齐 vs 半像素偏移                                                    │
│                                                                          │
│  纹理像素中心 ≠ 屏幕像素中心，会导致双线性采样落在两个纹素之间                │
│                                                                          │
│  错误：quad 的左边界落在 x = 100.0（纹理像素边界上）                        │
│    → 双线性在 100.0 处采样，实际取到的是"半个左边 + 半个右边" → 整体发虚      │
│                                                                          │
│  正确：quad 覆盖像素中心，边界落在 x = 99.5 或 100.5                        │
│    → 采样点与纹素中心重合 → 1:1 锐利                                       │
└──────────────────────────────────────────────────────────────────────────┘
```

| 对策 | 说明 |
|------|------|
| **UI 坐标取整** | 位置与尺寸在投影到屏幕时取整（round 到像素，或 0.5 偏移） |
| **避免非整数缩放** | UI 缩放系数用整数倍（1×/2×/3×）或用预生成的多档位图 |
| **过滤模式** | 1:1 时用 `NEAREST`（更锐利）或 `LINEAR` + 像素对齐；缩放过则必须 `LINEAR` |
| **D3D/Vulkan 的 0.5 约定** | 不同 API 的像素中心约定不同（D3D 为像素中心，OpenGL 为角点），移植时需测试 |

### 4.4 UI 要不要 mipmap？

| 情况 | 结论 |
|------|------|
| UI 严格 1:1、不缩放 | **不需要 mip**（生成 mip 反而在 1:1 时无收益，增加显存与生成成本） |
| UI 会被缩放到更小（如分辨率适配、缩放动画） | **需要 mip**，否则缩小会出现严重噪点/摩尔纹 |
| UI 会放大 | mip 无用，**需要更高分辨率的源**或 SDF |

## 5. 管线顺序与分辨率（本篇核心结论）

### 5.1 正确的摆放

```
┌──────────────────────────────────────────────────────────────────────────┐
│  UI / 文字在渲染管线中的正确位置                                            │
│                                                                          │
│  ┌─ 场景渲染（渲染分辨率，可能低于显示分辨率）──┐                           │
│  │  几何 → 着色 → 后处理（Bloom/DoF）          │                           │
│  └────────────────────┬────────────────────────┘                          │
│                       ▼                                                  │
│                 Tonemap / 颜色分级                                        │
│                       ▼                                                  │
│           场景 AA（FXAA / SMAA / TAA）                                   │
│                       ▼                                                  │
│        ┌──── 上采样到显示分辨率 ────┐   ← 超分/重建在这里                   │
│        └──────────────┬────────────┘                                     │
│                       ▼                                                  │
│  ┌────────────────────────────────────────────┐                          │
│  │  UI / 文字合成（⚠️ 必须是显示分辨率，        │                          │
│  │  且必须在 AA 与上采样之后）                  │                          │
│  └────────────────────┬───────────────────────┘                          │
│                       ▼                                                  │
│  帧生成（若启用）→ 输出                                                   │
└──────────────────────────────────────────────────────────────────────────┘
```

**三条硬规则**：

| 规则 | 违反后果 |
|------|---------|
| **① UI 在场景 AA 之后** | FXAA/SMAA 会把字形当边缘去混 → 糊字；TAA 会让文字抖动、拖影（静止 HUD 也会因累积而变灰） |
| **② UI 在上采样之后（或原生分辨率层）** | 在低分辨率层画 UI 再放大 → 文字直接糊掉，这是"UI 看起来比游戏画面还差"的唯一原因 |
| **③ UI 在帧生成之前** | 帧生成插值需要 UI 的正确运动矢量；顺序错了会出现 HUD 撕裂/拖影 |

⚠️ **例外：场景内 UI（diegetic UI）**

贴在 3D 物体表面、随场景透视的 UI（如全息屏、招牌）**必须**走场景管线（否则无法正确遮挡与透视）。这类 UI 的处理方式完全不同：

| 项 | 处理 |
|----|------|
| 参与场景 AA | ✅ 会被 TAA/FXAA 处理 |
| 分辨率 | 跟随渲染分辨率（所以会糊） |
| 解决思路 | 提高该 UI 渲染目标的局部分辨率；或用 SDF/矢量 + 解析 AA；或让 UI 由几何（而非纹理）构成 |

### 5.2 各 AA 方案与 UI 的冲突表

| AA 方案 | 与 UI 的关系 | 正确做法 |
|---------|-------------|---------|
| **MSAA** | 对一个铺满屏幕的 quad 无效 | UI 在 MSAA resolve 之后合成（通常顺带做到了） |
| **SSAA** | 有效但成本高 | 不建议为了让 UI 清晰而全局开 SSAA |
| **FXAA** | 糊字、粘连笔画 | UI 在 FXAA 之后 |
| **SMAA** | 比 FXAA 好，但仍会误检字形边缘 | UI 在 SMAA 之后；若必须在之前，关闭 UI 区域的边缘检测 |
| **TAA** | 文字抖动、发灰、拖影 | **UI 必须在 TAA 之后**，且 UI 不应参与抖动 |
| **超分（DLSS/FSR/ASR）** | 若 UI 在低分辨率层，会被重建模型"猜"糊；运动时字体出现闪烁 | UI 应用原生分辨率 overlay 层；或在超分后合成 |
| **帧生成** | HUD 无 MV 或 MV 错误 → 撕裂/拖影 | UI 提供正确 MV 或标注为静止；帧生成放最末端 |
| **VRS** | 降低 UI 着色率 → SDF 边缘劣化、文字发虚 | UI 阶段禁用 VRS |
| **A2C** | 只在 UI 用 alpha test 时有意义 | 见 §6 |

---

## 6. A2C 与 UI 的 alpha 边缘

**A2C（Alpha-to-Coverage）** 把片元的 alpha 值转换成 MSAA 采样覆盖率（承第 01 篇）：

```
   alpha = 0.75  +  MSAA 4x 的 4 个覆盖样本
   ┌─────────┐
   │ ● ● ● ○ │   → 4 个样本中 3 个被写入 → 边缘呈"半软"过渡
   └─────────┘
   → 把 alpha test 的硬边变成 MSAA 能平滑的覆盖率
```

| 适用 | 不适用 |
|------|--------|
| 树叶、栅栏、发丝、草地（大量 alpha test 的小面片） | 用 alpha **blend** 的常规 UI |
| 需要 MSAA 覆盖率的"像素艺术"式 UI | 需要精确子像素控制的字体 |
| 与 MSAA 同用时几乎零额外成本 | 没有 MSAA 时完全无效 |

⚠️ **A2C 的质量上限约等于 N 级灰度（N = MSAA 采样数）**：2× → 3 级，4× → 5 级，8× → 9 级。所以 A2C 适合"边缘粗糙也能接受"的植被，**不适合字形**。

## 7. 移动端的现实约束

| 项 | 说明 |
|----|------|
| **分辨率与带宽** | UI 以显示分辨率合成 → 全屏带宽成本。在全屏 UI 层上用 `LOAD`/`DONT_CARE` 等 load/store op 优化有实际收益（与第 06 篇的 tile 局部性同理） |
| **SDF 显存优势明显** | 一份 SDF 图集替代多档位图 → 显存与下载量下降，对移动端收益很大 |
| **避免子像素 AA** | 移动设备子像素排列多样（RGB/BGR/PenTile 等）、常涉及旋转、且系统 UI 层本身可能已在处理 → 收益低风险高 |
| **UI 与超分管线** | 若项目使用 ASR/NSS/GSR 做超分，UI **必须**在超分之后以设备原生分辨率合成，否则字体被重建模型"猜"糊 |
| **GPU 原生 UI 层** | Android/iOS 的系统 UI（如 HWUI / Impeller 等）在系统合成层处理，游戏内 UI 与系统 UI 之间可能存在**二次采样**（游戏 layer 缩放 + 系统 layer 缩放）→ 这是"背景 UI 清晰、游戏内 UI 发虚"的常见原因，需检查 layer 分辨率与缩放链 |
| **省电模式的影响** | 部分设备在省电模式下会降低合成层分辨率，UI 锐度会随之下降（非渲染问题，无法从引擎侧修复） |

## 8. 工程检查清单

```
【字体/字形】
□ 是否使用灰度 AA（覆盖率）作为默认路径？
□ 大字号是否关闭了 hinting？
□ 是否考虑了亚像素定位（字距平滑 vs 位图复用）？
□ 若使用 LCD 子像素 AA：是否满足"不透明背景 + 1:1 + 已知排列 + gamma 校正"四个前提？
□ 若使用 SDF/MSDF：pxRange 是否合理？极端字号下是否验证过？是否准备了多档图集？
□ 颜色空间是否全 UI 一致（sRGB 或线性，不混用）？

【UI 纹理】
□ 是否预乘 alpha？混合状态是否与预乘匹配？
□ 图集是否留了 ≥2 像素 padding，且 padding 是边缘外扩而非透明？
□ 是否按"会缩放"的实际情况决定是否生成 mip？
□ 缩放系数是否为整数倍？非整数缩放下采样是否正确？

【位置与顺序】
□ UI 坐标是否做了像素对齐（整数或 0.5 偏移）？
□ UI 是否在场景 AA 之后合成？
□ UI 是否在超分/上采样之后、以显示分辨率合成？
□ UI 是否在帧生成之前，且提供了正确的运动矢量（或明确标注静止）？
□ UI 阶段是否禁用了 VRS？
□ 场景内 UI（diegetic）是否被单独处理（不会被 TAA 糊掉）？

【验证】
□ 逐像素对比 UI 截屏与设计稿（1:1 下应几乎完全一致）
□ 快速拖动 HUD，观察是否有拖影/抖动
□ 切换所有 AA 档位与缩放档位，确认 UI 无变化
□ 在多种 DPI/子像素排列的设备上抽查彩边
```

## 9. 小结

| 要点 | 说明 |
|------|------|
| **UI/字体的边缘在 alpha 里，不在几何里** | 所以 MSAA 基本无效，这是这一族技术的分界线 |
| **灰度 AA 是默认答案** | 在栅格化阶段解析计算覆盖率，与任何合成方式兼容 |
| **LCD 子像素 AA 收益在下降** | 需要不透明背景、1:1、已知排列、gamma 校正；高 DPI 时代灰度 AA 已经够 |
| **色彩空间决定字的"胖瘦"** | 线性空间混合会让白底黑字变细；必须全 UI 统一 |
| **Hinting 与 AA 互相拉扯** | 小字号靠 hinting，大字号应关掉；SDF 是"绕开这个矛盾"的方案 |
| **SDF/MSDF 是唯一"一次烘焙、任意缩放"的方案** | 但受距离场精度限制，不是无限矢量；`pxRange`（距离范围）是关键参数 |
| **预乘 alpha 是硬要求** | 否则缩放/mip/旋转都会出脏边；混合状态必须与预乘匹配 |
| **图集必须留 padding** | 否则边缘会"吸"到邻块颜色；有 mip 时 padding 要按最粗级放大 |
| **像素对齐是锐度的前提** | 半像素偏移会让整个 UI 发虚，这是最常见的"莫名模糊" |
| **UI 必须在场景 AA 之后、上采样之后合成** | 顺序错 → 糊字/抖动/拖影；位置错（在低分辨率层）→ 直接糊 |
| **场景内 UI 是另一套问题** | 走场景管线，会被 AA 处理，需要靠局部高分辨率或矢量/几何方式解决 |
| **A2C 适合植被，不适合字形** | 其质量上限约等于 MSAA 采样数对应的灰度级数 |
| **移动端优先 SDF + 原生分辨率合成** | 省显存、避开子像素陷阱、与超分管线兼容 |
