# 抗锯齿技术 — 时间 AA 与超分重建

> 本文档是「抗锯齿（AA）技术」系列文档的第 **4** 篇。本篇覆盖 TAA 的完整链路（抖动、重投影、鬼影抑制、累积）、它的六个伪影与根因，以及 2026 年的超分重建阵营（DLSS 4 / FSR 4 / XeSS 2 / TSR / STP / Arm ASR / NSS）与帧生成的代价结构。

---

## 1. 定位：TAA 不是后处理，是时间采样

先纠正一个普遍误解：

| 说法 | 是否正确 |
|------|---------|
| "TAA 是一种后处理 AA" | ❌ 不准确。它在图像空间执行，但它改变了**采样位置**，属于采样侧技术 |
| "TAA 是每帧抖动 + 历史累积" | ✅ 准确 |
| "TAA 能替代 MSAA" | ⚠️ 部分成立。它覆盖面更广（几何 + 着色 + 纹理 + 时间），但它**不提供真实的几何覆盖率**，边缘几何精度仍不如 MSAA；且它依赖运动矢量，会引入新失败模式 |

一句话概括机制：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  TAA 的核心思想                                                          │
│                                                                          │
│  单帧内：只采 1 个样本（便宜）                                             │
│  跨帧：  每帧把采样位置挪一点点（子像素抖动）                                │
│  累积：  把历史帧的样本重投影到当前帧，与当前帧混合                            │
│                                                                          │
│  → 时间维度上"攒"出 N 倍采样效果，等效于 N× 超采样，但每帧只付 1× 的着色成本    │
│                                                                          │
│    帧 1      帧 2      帧 3      帧 4        累积结果                     │
│   ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐      ┌─────┐                       │
│   │ ·   │  │   · │  │     │  │     │      │ ·· ·│  ← 4 帧的样本被          │
│   │     │  │     │  │ ·   │  │     │      │· ·· │    重投影到同一网格       │
│   │     │  │     │  │     │  │  ·  │      │  ·· │                       │
│   └─────┘  └─────┘  └─────┘  └─────┘      └─────┘                       │
│                                                                          │
│  每帧只做一次着色 ────────────────────► 累积后等效多样本                   │
└──────────────────────────────────────────────────────────────────────────┘
```

**这个"攒样本"的机制同时是它的全部威力和全部麻烦**：只要信息能被正确重投影到当前帧，它就能无限累积；一旦重投影错了（新露出的表面、错误的运动矢量、被遮挡的物体），就会把错误信息"焊"进画面——这就是鬼影。

## 2. TAA 全链路

```
┌──────────────────────────────────────────────────────────────────────────┐
│  TAA 完整数据流                                                           │
│                                                                          │
│  ① 抖动（Jitter）                                                        │
│     在投影矩阵上施加亚像素偏移（Halton(2,3) 序列）                          │
│     ⚠️ 抖动是"投影矩阵层面"的，不是后处理层面的                              │
│         → 所有从这个矩阵产生的颜色/深度/法线/运动矢量都自动带抖动             │
│                                                                          │
│  ② 场景渲染                                                              │
│     ├─ 颜色缓冲（带抖动的采样位置）                                         │
│     ├─ 深度缓冲                                                          │
│     └─ 运动矢量缓冲（⚠️ 必须减去本帧抖动，见 §2.2）                         │
│                                                                          │
│  ③ 重投影（Reprojection）                                                │
│     history_uv = current_uv − motion_vector                              │
│     用 history_uv 采样上一帧的累积结果                                     │
│                                                                          │
│  ④ 校验（Validation）                                                    │
│     · 邻域截断 / 方差截断（把历史颜色限制在当前帧局部色彩范围内）              │
│     · 出屏检测、深度不连续检测、速度异常检测                                 │
│     · 不通过 → 提高当前帧权重 / 直接丢弃历史                                │
│                                                                          │
│  ⑤ 混合（Blend）                                                         │
│     result = lerp(current, history_reprojected, α)                       │
│     α 通常 0.85 ~ 0.95（越大越平滑，越大越容易鬼影）                         │
│                                                                          │
│  ⑥ 锐化（可选）                                                          │
│     补偿混合带来的模糊（unsharp mask / CAS）                              │
│                                                                          │
│  ⑦ 写回 history buffer（与当前帧 ping-pong）                              │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.1 抖动（Jitter）

| 项 | 说明 |
|----|------|
| **序列** | **Halton(2,3)** 是事实标准（低差异序列，分布均匀且周期长，可精确重复） |
| **幅度** | 亚像素单位，范围 `[-0.5, +0.5]²`，映射到裁剪空间：`jitter_ndc = 2 * offset / resolution` |
| **施加位置** | 投影矩阵的 `[2][0]` 与 `[2][1]` 元素（或等价地加到 `gl_Position.xy`） |
| **周期** | Halton(2,3) 的周期长度为 8/9 的 LCM 相关（实用中取 8~16 帧一个循环即可） |
| **必须回传** | TAA pass 需要知道当前帧的抖动值，用于计算正确的重投影 UV |
| **⚠️ 常见 bug** | 忘记把 jitter 从运动矢量里减掉 → 历史采样每次偏移一个亚像素 → 画面缓慢漂移（"画面在爬"），这个 bug 极难定位 |

### 2.2 运动矢量（Motion Vector / Velocity）

**这是 TAA 最脆弱的依赖**。运动矢量必须表达"这个像素上的可见表面，从上一帧到当前帧移动了多少（屏幕空间 UV 单位或像素单位）"。

| 组成部分 | 来源 | 常见错误 |
|---------|------|---------|
| **相机运动** | 用 `prevViewProj × currViewProj⁻¹` 变换当前深度重建的世界坐标 | 忘记透视除法；用错矩阵顺序 |
| **物体运动** | 上一帧与当前帧的模型矩阵差 | 只用当前模型矩阵；忽略了骨骼/顶点动画 |
| **精确上一帧位置** | 应在上一帧**同一个抖动偏移**下计算 | 用未抖动的矩阵导致累积偏差 |
| **抖动补偿** | `MV_final = MV − jitter_delta` | 漏掉 → §2.1 所述的漂移 bug |
| **着色器位移** | 顶点着色器里的风、波浪、地形 LOD morph | **几乎总是被漏掉**，是植被/水面鬼影的头号原因 |
| **粒子/特效** | 通常单独处理或标记 | 用几何 MV → 粒子拖尾变成"鬼影长条" |
| **屏幕空间效果** | SSR、SSAO、体积雾 | 无 MV 可用，需专门设计 |
| **UI / HUD** | 通常 MV = 0（静止） | 若有动画但 MV=0 → 拖影 |

**格式与精度**：

| 方案 | 说明 |
|------|------|
| `RG16F` | 主流选择，支持 `[-64, 64]` 像素位移，精度对多数镜头足够 |
| `RG16_UNORM` + 缩放 | 省带宽，但要小心量化和溢出（高速运动会被截断 → 鬼影） |
| `RGBA16F` | 常见于需要存额外信息（如深度差、物体 ID）的实现 |
| **要求** | 必须与渲染分辨率**同分辨率**（不能降采样后再用，会错位） |

⚠️ **运动矢量的一个根本困难**：它是**屏幕空间**量，而"正确的上一帧位置"需要世界空间的历史。因此所有 TAA 的重投影都是近似的——**遮挡关系变化时必然出错**，只能靠校验机制检测并丢弃历史。

### 2.3 重投影与历史采样

| 采样方式 | 说明 |
|---------|------|
| **双线性** | 最便宜，但会在历史缓冲上引入额外的模糊（历史本身已经是多次累积的） |
| **Catmull-Rom 三次滤波** | Karis 2014 / Jimenez 2016 使用的方案，5 次采样（或按需裁剪），显著更锐利 |
| **⚠️ 关键约束** | 历史采样必须用 **clamp 到边缘** 的寻址，且必须处理越界（越界 = 该像素没有历史 → 直接输出当前帧） |

### 2.4 鬼影抑制：从"邻域截断"到"方差截断"

这是 TAA 工程化的核心。两种主流做法：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  方法 A：邻域截断（Neighborhood Clamp）—— Karis 2014                     │
│                                                                          │
│  取当前帧 3×3 邻域的颜色                                                  │
│  → 得到 AABB：[minColor, maxColor]                                       │
│  → 把重投影得到的历史颜色 clamp 进这个 AABB                                │
│  → 再混合                                                                 │
│                                                                          │
│  问题：3×3 AABB 通常是"过大"的凸包，clamp 后的颜色仍可能远离真实分布         │
│        → 鬼影残留                                                        │
└──────────────────────────────────────────────────────────────────────────┘
```

```
┌──────────────────────────────────────────────────────────────────────────┐
│  方法 B：方差截断（Variance Clipping）—— Salvi 2016（GDC）                │
│                                                                          │
│  同样取 3×3（或 4×4）邻域，但用统计量构造更紧的 AABB：                       │
│                                                                          │
│     m1 = Σ c_i            （一阶矩）                                      │
│     m2 = Σ c_i · c_i      （二阶矩）                                      │
│     μ  = m1 / N           （均值）                                        │
│     σ  = sqrt(m2 / N − μ · μ)     （标准差）                              │
│                                                                          │
│     min_c = μ − γ · σ                                                  │
│     max_c = μ + γ · σ                                                  │
│                                                                          │
│  γ 是缩放因子：                                                           │
│     γ 大 → 更稳定（更靠历史），但鬼影更多                                    │
│     γ 小 → 更快收敛（更靠当前帧），但闪烁增加                                │
│                                                                          │
│  可选：再把 [min_c, max_c] 与原 AABB 求交，进一步收紧                        │
└──────────────────────────────────────────────────────────────────────────┘
```

**两处工程细节（都有明确出处）**：

| 细节 | 说明 | 出处 |
|------|------|------|
| **在 YCoCg 空间做截断** | 直接在 RGB 上截断会在某些表面产生**紫色偏色**（Chrominance 被错误截断） | Karis 2014 第 35 页 |
| **按速度动态调 γ** | 运动越快 γ 越小（更信当前帧）；静止时 γ 大（更信历史，画面稳定） | 常见工程实践 |
| **线性加权代替指数加权** | 用累积样本数 `n` 计数，α = n/(n+1)，收敛更快、鬼影更少 | ReBLUR 2020（自稳定递归模糊） |

**YCoCg 变换**（为了只对亮度做强约束、对色度弱约束）：

```
Y  =  0.25·R + 0.5·G + 0.25·B
Co =  0.5·R             − 0.5·B
Cg = −0.25·R + 0.5·G − 0.25·B
```

### 2.5 废弃历史（Rejection）的判据

| 判据 | 触发条件 | 处理 |
|------|---------|------|
| **出屏** | 重投影 UV 落在 `[0,1]` 之外 | 直接用当前帧（α = 0） |
| **深度不连续** | 当前深度与历史深度差超阈值 | 判定为新露出表面 → 丢弃历史 |
| **速度异常** | 运动矢量突变（如超出画面 1/2） | 丢弃或强降权 |
| **颜色距离过大** | 当前色 vs 截断后历史色的距离超阈值 | 降低历史权重（不要直接丢弃，否则会闪） |
| **薄几何** | 高对比度细节（细栅栏、树叶） | 降低历史权重（否则会被"抹平"） |

⚠️ **调参的本质是一个三选二的权衡**：

```
                   鬼影少
                     ▲
                    ╱ ╲
                   ╱   ╲
                  ╱     ╲
       收敛快 ◄──╱───────╲──► 画面稳定（不闪）
                 ╲       ╱
                  ╲     ╱
                   ╲   ╱
                    ▼
                 模糊少
```

**只能同时优化两个**。所有 TAA 参数调整都是在这个三角形里选位置。

## 3. TAA 伪影图鉴

| 伪影 | 现象 | 根因 | 对策 |
|------|------|------|------|
| **鬼影（Ghosting）** | 运动物体后面跟着残影 | 历史权重过高 / 截断过宽 / MV 错误 | 收紧 γ、按速度降权、修复 MV |
| **拖尾 / 涂抹（Smearing）** | 快速移动时物体被拉长 | MV 缺失（粒子、特效） | 为这些效果提供 MV 或标记为噪声源 |
| **画面爬行（Drift）** | 静止画面缓慢平移 | **忘记从 MV 中减去 jitter** | 减去 jitter delta（§2.1） |
| **闪烁（Fizzle）** | 局部区域噪声化、高频抖动 | 历史被频繁拒绝 / 累积不稳定 | 放宽拒绝阈值，或对高频区域特殊处理 |
| **整体模糊** | 画面发软、纹理细节丢失 | 混合本身是低通；历史双线性采样 | 用 Catmull-Rom、加 sharpen、（更根本地）提高内部渲染分辨率 |
| **消失的细结构** | 栅栏、电线、天线被"抹掉" | 薄几何在累积中被判为噪声并抹平 | 提高渲染分辨率、用 TSR/DLSS 类重建、对薄几何降权 |
| **UI 鬼影** | HUD 拖动时带残影 | UI 被纳入 TAA 但 MV = 0 | **UI 必须在 TAA 之后合成** |
| **去遮挡发灰（Disocclusion Fizzle）** | 相机平移时物体边缘出现"沸腾"的灰边 | 新露出区域没有有效历史，多次拒绝累积出的噪点 | 这些区域用当前帧直接填充 + 更好的校验 |
| **静止画面噪声不收敛** | 放着不动，画面仍有细噪点 | 抖动序列与场景频率共振 / 拒绝阈值过紧 | 检查 Halton 相位，放宽阈值 |

⚠️ 其中"**UI 鬼影**"和"**画面爬行**"是两个"一眼能看出发作者没经验"的 bug，排查优先级最高。

## 4. TAA 的代价账本

| 成本项 | 说明 |
|--------|------|
| **额外渲染目标** | history buffer（全分辨率，`RGB10A2` / `RGBA16F`），可能还需要第二个做 ping-pong |
| **带宽** | 每帧读 history + 写 history = **2 次全分辨率读写**，这是 TAA 最大的成本（尤其在移动端） |
| **运动矢量** | 需要 MV 渲染目标（同分辨率），生产 MV 本身有开销 |
| **ALU** | 3×3 邻域统计、方差计算、YCoCg 变换、Catmull-Rom 采样 |
| **延迟** | TAA 本身不引入额外帧延迟（不是插帧），但 history 依赖上一帧，等于"1 帧的时间耦合" |

**量级参考（仅供量级判断，不同设备差异极大）**：桌面 1080p 下 TAA 通常在 **0.3 ~ 1.0 ms** 区间；4K 下按像素数放大。**关键是带宽而非 ALU**，所以移动端要以"每帧全分辨率读写多少次"来估算。

### 4.1 与 MSAA 的关系

| 问题 | 答案 |
|------|------|
| TAA 能替代 MSAA 吗？ | 覆盖面更广，但**几何边缘精度**不如 MSAA。TAA 是"猜"边缘，MSAA 是"测"边缘 |
| 能叠加吗？ | 原理上可以（MSAA 提供几何样本，TAA 处理时间维度），实践中少见，因为 MSAA 的 resolve 成本和带宽在全分辨率管线上普遍不划算 |
| **移动端例外** | 移动端 TBR/TBDR 的 MSAA resolve 发生在**片上**，成本远低于桌面。所以 **MSAA + TAA 的组合在移动端反而比桌面更可行** |
| 与延迟渲染 | TAA 天然兼容延迟渲染（它工作在 G-Buffer 之后的屏幕空间），这正是 TAA 取代 MSAA 成为主流的直接原因 |

## 5. 超分重建阵营（2026-09 状态）

超分（Upscaling）与 AA 已经合并：现代方案在做"低分辨率渲染 → 高分辨率重建"的同时完成时间 AA。它们都是 **TAA 的强化版**——用更聪明的重建模型替代手工调的截断规则。

```
┌──────────────────────────────────────────────────────────────────────────┐
│  三代的演进                                                                │
│                                                                          │
│  第一代（启发式时间重建）                                                  │
│     TAA → TAAU（Temporal AA Upscaling）→ UE 的 TSR / Unity 的 STP          │
│     特征：手写规则、无模型、跨平台、成本可控                                 │
│                                                                          │
│  第二代（神经网络重建，需要专用推理硬件）                                     │
│     DLSS（Tensor Core）/ XeSS（XMX）/ FSR 4（RDNA 4 AI 加速器）             │
│     特征：质量上限高、需要专用单元、硬件绑定严重                              │
│                                                                          │
│  第三代（移动端专用，模型变小 + 低带宽）                                      │
│     Arm ASR（着色器级，基于 FSR 2）/ Arm NSS（神经网络，2026 年底硬件）        │
│     Snapdragon GSR / MetalFX / MediaTek AI-SR                           │
│     特征：优先降低带宽与功耗，而非追求绝对画质                                │
└──────────────────────────────────────────────────────────────────────────┘
```

### 5.1 桌面阵营对比表（⚠️ 版本与硬件门槛时效性强，请以厂商官方文档为准）

| 方案 | 厂商 | 当前主要版本 | 硬件门槛 | 技术路线 | 开放程度 |
|------|------|------------|---------|---------|---------|
| **DLSS** | NVIDIA | DLSS 4（Transformer 模型） | 超分：RTX 20 系及以上；多帧生成：**仅 RTX 50 系** | 神经网络（Tensor Core）+ 光流 | 闭源 |
| **FSR** | AMD | FSR 4（ML）/ FSR 3.1（非 ML） | FSR 4：**仅 RDNA 4（RX 9000）**；FSR 3.1：几乎任何 GPU | FSR 4 为 ML 模型；3.x 为手工时空算法 | **开源**（FSR 3.1 广泛可用） |
| **XeSS** | Intel | XeSS 2（含 XeSS-FG 帧生成、XeLL 低延迟） | 最佳质量：Arc（XMX）；其他 GPU：DP4a 兼容路径（质量较低） | 神经网络 + DP4a 回退 | SDK 开放，跨厂商 |
| **TSR** | Epic（UE5） | UE5 内建 | 需支持 Compute 的平台（D3D12/SM5 级别） | 高度工程化的时间超分（基于 TAAU 思路） | **引擎内开源** |
| **STP** | Unity | Unity 6（STP 1.0） | 需支持 Compute 的**非 GLES** 设备；不支持时自动回退 | 时空后处理（AA + 上采样一体化） | 引擎内 |

**几个必须记住的边界**：

| 事实 | 说明 |
|------|------|
| **DLSS 不存在于移动端** | 需要 Tensor Core，只有 NVIDIA GPU 有 |
| **DLSS 4 的 Transformer 模型对 RTX 20 系也开放** | 只有**多帧生成（MFG）**限定 RTX 50 系 |
| **FSR 4 锁 RDNA 4** | RX 7000 及更早仍用 FSR 3.1。有报道称 2026 年有将 ML 超分扩展到 RX 7000 的更新（以 AMD 官方发布为准） |
| **XeSS 的 DP4a 路径是降级体验** | 跨厂商可用，但时间稳定性明显弱于 XMX 路径 |
| **TSR 会随分辨率自适应** | TSR 有质量档位，且会根据帧预算动态调整 |
| **STP 会覆盖相机 AA 设置** | Unity 官方说明：选择 STP 会把相机的抗锯齿设置覆盖为 TAA；且**不能与动态分辨率同时使用** |
| **FSR 3.1 是跨平台兜底** | 任何 GPU 都能跑，这是它至今仍被大量集成的唯一理由 |

### 5.2 移动端阵营（与第 06 篇联动）

移动端没有 Tensor Core / XMX，但有自己的路线：**以功耗和带宽为第一目标**。

| 方案 | 厂商 | 类型 | 关键特性 |
|------|------|------|---------|
| **Arm ASR**（Accuracy Super Resolution） | Arm | 空间-时间（着色器） | **基于 AMD FSR 2**，MIT 开源；Arm 称在同等分辨率与缩放比下 GPU 开销约为 FSR 2 的 **1/3**，帧率提升 20%~40%（官方在 Immortalis-G720 + 2800×1260 上实测 2× 放大 +53%，对比 FSR 2 的 +36%）；2× ASR 相比原生 1080p 功耗降低 20%+（天玑 9300 实测） |
| **Arm NSS**（Neural Super Sampling） | Arm | 神经网络 | SIGGRAPH 2025 公布；基于 ASR 构建；需 **Arm 神经加速器**（首批硬件预计 **2026 年底**）；通过 **Vulkan ML 扩展**（`VK_ARM_tensors`、`VK_ARM_data_graph`）运行；提供 UE5 插件 + Vulkan ML 模拟层；含 **NSS**（超分）、**NFRU**（帧率提升/插帧）、**NSSD**（超分 + 降噪）；Arm 称画质接近 **DLSS 2** 级别但模型更小；演示中"魔法城堡"GPU 负载降低 50%，540p→1080p 约 **4 ms** |
| **Snapdragon GSR** | Qualcomm | GSR1 空间 / GSR2 时间 | 仅 Snapdragon 设备；空间路径成本极低 |
| **Adreno Neural Fusion** | Qualcomm | 神经网络 | 已公布，结合神经处理 + 超分 + 帧生成（以 Qualcomm 官方为准） |
| **MetalFX** | Apple | 时间 + 空间 | 仅 Apple 平台；与 FSR 同源思路 |
| **MediaTek Game AI-SR** | MediaTek | 空间 AI | 2022 年推出 |
| **Microsoft Auto SR / DirectSR** | Microsoft | 系统级 | Auto SR 面向 Copilot+ / Arm 设备；**DirectSR** 是跨厂商的统一超分 API |

⚠️ **对移动端的三个提醒**：

1. **所有"提升 X% 帧率"的数字都依赖测试条件**（GPU 型号、分辨率、缩放比、场景）。厂商演示数据不等于你的项目收益。
2. **NSS 的硬件 2026 年底才上市**，当前可用的是 ASR（着色器级）+ 模拟层做原型。
3. **超分只有在 GPU 受限（fill-rate bound）时才有收益**。如果瓶颈在 CPU、分箱（binning）或几何，开超分几乎无收益——这与第 06 篇的诊断树是同一件事。

## 6. 帧生成（Frame Generation）

⚠️ **帧生成不是抗锯齿**。但它是当前超分套件的一部分，且**对延迟的影响机制极易被误解**，所以必须单独讲清。

### 6.1 原理

```
┌──────────────────────────────────────────────────────────────────────────┐
│  帧生成做什么                                                             │
│                                                                          │
│   已渲染帧：  F(n)          F(n+1)          F(n+2)                       │
│                 ●             ●               ●                          │
│                                                                          │
│   插值帧：        ○     ○     ○     ○     ○      ← 用运动矢量/光流合成       │
│                                                                          │
│   显示序列：  F(n) ○ ○ F(n+1) ○ ○ F(n+2)  ...                           │
│                                                                          │
│   输入：已渲染的两帧 + 每像素运动矢量（+ 光流/深度/历史）                     │
│   输出：中间帧（不含新的游戏状态！）                                         │
└──────────────────────────────────────────────────────────────────────────┘
```

**关键事实：插值帧不包含任何新的输入信息。** 它只是把"已有的两帧"在时间上平滑展开。因此：

| 指标 | 帧生成的影响 |
|------|-------------|
| **显示帧率 / 流畅度** | ✅ 显著提升（可到 2×、3×、4×） |
| **输入延迟** | ❌ **不降低**（本质上是略微变差），因为真实输入仍要等下一帧渲染完 |
| **游戏逻辑帧率** | ❌ 不变（逻辑仍按渲染帧率跑） |
| **hitbox / 判定** | ❌ 不变（插值帧不参与逻辑） |

### 6.2 延迟账本（为什么"帧率高了但手感更肉"）

```
┌──────────────────────────────────────────────────────────────────────────┐
│  无帧生成（渲染 60 fps，显示 60 fps）                                      │
│                                                                          │
│   输入 ──► [渲染 16.7ms] ──► 显示                                         │
│   延迟 ≈ 1 帧时间 + 显示延迟 ≈ 16.7ms + ε                                │
│                                                                          │
│  ─────────────────────────────────────────────────────────────────────── │
│  多帧生成（渲染 60 fps，显示 240 fps，插入 3 帧）                           │
│                                                                          │
│   输入 ──► [渲染 16.7ms] ──► [等下一帧渲染完 16.7ms] ──► 插值 ──► 显示     │
│            ↑                              ↑                              │
│         必须等两帧都渲染完才能插值 ────────┘                              │
│                                                                          │
│   延迟 ≈ 2 帧渲染时间 + 插值延迟 + 显示延迟 ≈ 33ms+                      │
│                                                                          │
│   → 帧率数字变漂亮了 4 倍，但手感变差了                                    │
│   → 这就是为什么必须配合 Reflex / XeLL 这类低延迟技术                      │
└──────────────────────────────────────────────────────────────────────────┘
```

| 需要搭配的技术 | 作用 |
|--------------|------|
| **NVIDIA Reflex** | 压缩渲染队列深度，降低基础延迟 |
| **XeLL**（Intel） | XeSS 2 的低延迟模式 |
| **驱动级抗延迟** | AMD 的对应方案 |

### 6.3 帧生成的工程约束

| 约束 | 说明 |
|------|------|
| **必须是管线最末端** | 帧生成之后不能再有依赖游戏状态的 pass |
| **需要正确的运动矢量** | 包括 UI/HUD。UI 若无 MV 或标记错误，会出现 HUD 撕裂/拖影 |
| **不能用于"逻辑帧率"** | 网络同步、物理、判定都必须按渲染帧率走 |
| **静态 UI 是特殊案例** | 完全静止的 HUD 理论上不该被插值；但若整帧一起插值，需要正确的 MV 或后合成 |
| **帧生成的伪影** | 粒子、半透明、快速旋转相机、细几何——都是高发区 |
| **VR / AR 慎用** | 延迟直接决定晕动症，插入帧的延迟放大不可接受 |
| **移动端** | Arm NFRU、Adreno Neural Fusion 都在路上；功耗是主要约束 |

## 7. TAA 及超分的工程集成清单

### 7.1 数据要求（缺一不可）

```
□ 抖动序列（Halton 2,3）并保证当前帧 jitter 值能被 TAA pass 读到
□ 运动矢量缓冲（同分辨率），且已减去本帧 jitter
□ 深度缓冲（用于重建世界坐标 / 遮挡检测）
□ history buffer（格式选定，且与渲染分辨率一致）
□ 上一帧的 View/Proj 矩阵（用于相机 MV）
□ 所有物体的上一帧变换（静态物体也要缓存！）
```

### 7.2 每个渲染特性都要回答的问题

| 特性 | 必答问题 |
|------|---------|
| 顶点动画（风、波浪） | MV 是否包含顶点位移？ |
| 骨骼动画 | 用当前骨骼算的 MV 是否对得上上一帧的骨骼？ |
| 粒子 | MV 用几帧前的？还是标记为不可信的噪声源？ |
| Alpha Test / Dither | 边缘抖动会不会被 TAA 抹平？ |
| 半透明 | 半透明物体通常**在 TAA 之后**合成（避免累积错误） |
| 屏幕空间效果 | SSR/SSAO 的噪声是交给 TAA 还是专用降噪器？ |
| UI | 是否在 TAA 之后合成？是否参与插帧？ |
| 视频播放 / 动态贴图 | 没有合理 MV → 需特殊标记 |

### 7.3 验证方法

| 验证项 | 方法 |
|--------|------|
| **jitter 是否正确** | 关闭所有动画，相机静止 → 画面应**完全静止**。若有缓慢漂移 → jitter 补偿没做对 |
| **MV 是否正确** | 输出 MV 可视化（放大 20~50 倍）→ 静态场景应为纯灰（零位移），旋转相机应为平滑渐变 |
| **鬼影** | 让一个高对比物体快速横穿屏幕 → 观察后方残影长度 |
| **薄几何** | 对着栅栏/铁网/电线缓慢平移 → 看是否被抹断或抹平 |
| **UI 顺序** | 快速拖动 HUD → 是否出现拖影 |
| **收敛性** | 静止时截图对比连续两帧 → 差异应趋近于 0 |
| **A/B 对照** | 与"关闭 TAA 但用 4× 内部超采样"对比，判断模糊是否超出可接受范围 |

## 8. 小结

| 要点 | 说明 |
|------|------|
| **TAA 是时间采样，不是后处理滤波** | 它改变采样位置并跨帧累积信息，因此覆盖面远大于空间 AA |
| **威力与麻烦同源** | "攒样本"能给出 N 倍等效采样，也能把错误信息焊进画面 |
| **抖动必须回传并从 MV 中减去** | 漏掉会产生"画面缓慢爬行"，这是最难定位的 TAA bug |
| **鬼影抑制的两条正解** | 邻域截断（Karis 2014，在 YCoCg 空间做）与方差截断（Salvi 2016，μ ± γσ） |
| **收敛速度与稳定性只能换** | 加"线性加权（n/(n+1)）"是免费提升收敛速度的手段 |
| **MV 是最大的脆弱点** | 顶点动画、粒子、屏幕空间效果、UI 是四个常见缺口 |
| **TAA 的成本是带宽不是 ALU** | 每帧全分辨率读+写 history，移动端要按"每帧全分辨率访问次数"估算 |
| **TAA 天然兼容延迟渲染** | 这是它取代 MSAA 成为桌面主流的结构性原因 |
| **超分 = TAA 的强化版** | DLSS 4 / FSR 4 / XeSS 2 / TSR / STP 都是在做"低分渲染 + 时间重建" |
| **硬件绑定是超分的现实** | DLSS 锁 RTX，FSR 4 锁 RDNA 4，XeSS 最佳质量锁 Arc；跨平台兜底仍是 FSR 3.1 / Arm ASR |
| **移动端的优先级不同** | Arm ASR（MIT，基于 FSR 2，约 1/3 开销）、NSS（2026 年底硬件）、GSR、MetalFX 都以**功耗与带宽**为第一目标 |
| **帧生成不降低延迟** | 它提升的是显示流畅度；多帧生成会把延迟按帧数放大，必须配合 Reflex / XeLL |
| **帧生成必须放在管线最末端** | 且需要 UI/HUD 的正确运动矢量，否则会出现 HUD 伪影 |
| **超分只在 GPU 受限时有收益** | CPU / 分箱 / 几何受限的场合，开超分几乎无用（详见第 06 篇） |
