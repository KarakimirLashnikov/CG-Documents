## 1. 隐患地图

```
                  Mesh Shader 变慢的五个方向
┌────────────────────────────────────────────────────────────┐
│                                                            │
│  ① 分支发散      workgroup/wave 内走不同路径 → 串行执行     │
│  ② 访存不合并    逐字节/随机 gather → 事务数爆炸           │
│  ③ 占有率        输出区/shared memory/payload 吃掉并行度    │
│  ④ 寄存器压力    输出数组 + 属性驻留 → spill 到显存         │
│  ⑤ 共享内存      配额超限 + Bank 冲突 → 串行化             │
│                                                            │
│  外加一条：被别的阶段挤掉（PS 优先于 MS，AMD 明确说明）      │
└────────────────────────────────────────────────────────────┘
```

## 2. 隐患一：分支发散

### 2.1 三种发散，代价不同

| 粒度 | 例子 | 代价 |
|------|------|------|
| **工作组间**（不同 workgroup 走不同分支） | 不同 meshlet 选不同 LOD | ✅ **几乎免费**：不同 wave 本来就独立 |
| **工作组内 / wave 内** | `if (threadId < vertexCount)` 里做重活；逐三角形剔除分支 | ❌ 昂贵：wave 内串行执行所有分支 |
| **wave 模式被切换** | 用 `WavePrefixSum` 等指令使编译器从 wave64 切到 wave32 | ⚠️ 隐蔽：**占用率数字变好看，实际并行工作组数不变**（AMD 明确点出） |

### 2.2 典型发散点

```glsl
// ❌ 差：wave 内一半线程做重活，另一半空转
if (tid < m.y) {
    Vertex v = DecodeAndSkin(vi);          // 重活
    gl_MeshVerticesEXT[tid].gl_Position = viewProj * vec4(v.p, 1.0);
}
// 若 m.y = 33 而线程组 64：只有一个 wave，仍要跑满 64 条通道的时间

// ✅ 好：让"重活"均匀铺满，或用步长循环
for (uint i = tid; i < m.y; i += gl_WorkgroupSize.x) { ... }
```

| 发散点 | 识别 | 对策 |
|--------|------|------|
| LOD/材质分支在 MS 里 | 同一 workgroup 的三角形走不同分支 | **上移到 Task Shader**：让一个 Mesh workgroup 只处理一种 LOD/材质 |
| 逐图元剔除的大分支 | `if (culled) { 复杂计算 }` | 先算好 mask，用 ` compact / ballot` 批量处理 |
| 边界判断 `if (i < n)` | 尾部 wave 半空 | 无解但成本小；**别在 if 体内放大计算** |
| 循环次数不一致 | `while (fanOffset++)`（GTS 解码） | AMD 实测"大多数情况只跑一轮"；用 `firstbithigh` 一次跳 32 位 |
| wave 模式切换 | 占用率异常升高但吞吐没变 | 少用强制 wave32 的指令；必要时显式标注 |

### 2.3 剔除实现方式的发散代价

| 方式 | 发散 | 空间占用 | 适用 |
|------|------|---------|------|
| `gl_MeshPrimitivesEXT[i].gl_CullPrimitiveEXT = true` | 低（写一个 bool） | ⚠️ **仍占**声明配额 | 默认首选（AMD 实验结论） |
| 紧凑化（wave 前缀和重排） | 中（需要 wave-wide scan） | 少占 | `prefersCompactPrimitiveOutput = true`；或顶点属性很宽时 |

⚠️ 紧凑化会破坏"i 号线程写 i 号元素"的最优路径（AMD：*"Need to fix export indices via a wave-wide scan"*）—— 只有在省下的空间确实值钱时才做。

## 3. 隐患二：事务性与合并访存

### 3.1 现象

Mesh Shader 的主要访存是**两次 gather**：

```
meshlets[gid]           → 顺序（workgroup 之间连续，好）
meshlet_vertices[off+i] → 近似顺序（若做了 optimizeMeshlet，更好）
global_vb[vi]           → ⚠️ 随机（vi 是全网格范围内的索引）
meshlet_triangles[...]  → ⚠️ 逐字节（uint8_t）
```

GPU 按**事务**（cache line / sector）取数：一次 32 字节或 128 字节的事务只读到 1 个有用字节，等于浪费 31/127。
指标就是 **overfetch**（meshoptimizer 的 `analyzeVertexFetch`）：读取字节 ÷ 实际需要字节。

### 3.2 六个具体对策

| 问题 | 对策 |
|------|------|
| `uint8_t` 微索引逐字节读 | **按 4 字节打包每个三角形**（3 字节数据 + 1 字节填充），一次对齐读拿到整个三角形 |
| 跨 4 字节边界的位解包 | 离线就对齐好，shader 里不要做 `if (offset & 3)` 判断 |
| 全局 VB 随机 gather | `meshopt_optimizeVertexFetch` 使顶点顺序 = 索引顺序；或改用**每 meshlet 迷你 VB**（连续读） |
| 压缩数据被每个线程各读一遍 | **一次性载入 group shared memory**（AMD GTS 示例：`groupshared uint IndexBufferCache[8+64]`） |
| 依赖式加载（先读 A 才知道 B 的地址） | 预取到 SMEM / 重排数据；AMD 明确列出"避免 dependent memory loads" |
| 同一簇内重复读同一顶点 | 顶点在簇内已去重；确保 `meshlet_vertices` 就是去重后的 |

```glsl
// ✅ 一次协作载入 → SMEM → 各线程从 SMEM 取（合并访存 + 无重复事务）
groupshared uint smemCache[kCacheSize];
void LoadPhase() {
    if (tid < kCacheSize) smemCache[tid] = src[base + tid];   // 连续地址 = 合并
    barrier();                                                 // ⚠️ 工作组同步
}
```

### 3.3 ⚠️ 别把整个 meshlet 塞进共享内存

AMD 明确建议：**不要用 group shared memory 临时存放一个工作组的所有顶点或图元**。
原因：SMEM 配额（`maxMeshSharedMemorySize`）直接决定能同时驻留多少个工作组 → 占用率下降。
SMEM 应该只放"**会被多次复用**的小数据"（压缩索引缓冲、共享的变换矩阵、bounds），不是输出缓冲区。

## 4. 隐患三：占有率（Occupancy）

### 4.1 三个配额共同决定占用率

```
能同时驻留的 Mesh 工作组数 ≈ min(
    shader export 空间     / 每工作组预留的输出,
    共享内存总量           / 每工作组 SMEM,
    payload + 输出合计上限 / 每工作组 payload+输出,
    寄存器文件             / 每工作组寄存器
)
```

| 配额 | 属性名 | 示例值 |
|------|--------|--------|
| 输出内存 | `maxMeshOutputMemorySize` | 32768 |
| payload + 输出 | `maxMeshPayloadAndOutputMemorySize` | 48128 |
| 共享内存 | `maxMeshSharedMemorySize` / `maxMeshPayloadAndSharedMemorySize` | 28672 |
| payload | `maxTaskPayloadSize` | 16384 |

### 4.2 AMD 给出的关键结论

> "Shader export memory size is designed such that regular mesh shaders can reach the rasterizer triangle throughput.
> For **simple mesh shaders, an occupancy of ~25% can be enough** to reach the triangle throughput limit."

推论链：

1. Mesh Shader **不是**"越并行越好"的阶段 —— 它有明确的吞吐上限（光栅器的三角形吞吐）；
2. 简单的 Mesh Shader 只要 ~25% 占用就能打满光栅器 → **不要为了占用率去做无谓优化**；
3. 复杂的 Mesh Shader 会占用更多输出内存 → 反而更容易被输出区卡住；
4. 因此 AMD 的建议是：**Mesh Shader 里只做必需的计算，其余全部预计算**（比如顶点的复用信息）。

### 4.3 占有率被外部因素挤掉

| 现象 | 成因 | 对策 |
|------|------|------|
| MS 占用率周期性塌陷 | 某个 meshlet 覆盖大面积屏幕 → PS 工作塞满 GPU | AMD 说明：**PS 会被优先调度**以缓解光栅器输出压力。这是设计行为，不是 bug |
| 与 pixel shader 并行时 MS 变慢 | 同上 | 若实测明显，可尝试**减小线程组**（AMD：128 → 64 有轻微收益） |
| occupancy 数字变高但帧率没变 | wave64 → wave32 切换（见 §2.1） | 查编译器输出；避免强制 wave32 的指令 |

⚠️ 判读规则：**Mesh Shader 的占用率不是越高越好**，要配合 `MESH_PRIMITIVES_GENERATED` 与帧时间一起看。

## 5. 隐患四：寄存器压力

### 5.1 为什么 Mesh Shader 特别吃寄存器

- 输出数组（`verts[]` / `triangles[]` / `prims[]`）在逻辑上是"每个工作组共享的数组"，实现上要么驻留寄存器、要么落 LDS；
- 每个线程要写多个元素（V=64/T=126，线程 64 → 每线程 1 顶点 + 2 图元），这些元素在导出前都得有地方放；
- 属性越多（position + normal + uv + tangent + …），每个顶点占用的标量数越多。

```
粗略估算每工作组的输出占用：
  per-vertex  attributes: A_v 个标量/顶点  × V
  per-primitive attrs   : A_p 个标量/图元  × T
  索引                  : 3 × T
  → 必须 ≤ maxMeshOutputMemorySize
  （还要按 meshOutputPerVertex/PrimitiveGranularity 向上取整）
```

### 5.2 识别与对策

| 识别手段 | 说明 |
|---------|------|
| 编译器报告 | 用 RGA（AMD）/ NSight / `dxc` 的寄存器统计；看 VGPR 与 spill 字节数 |
| 现象 | 帧时间突然跳变（spill 到显存）、占用率断崖 |
| 公式校验 | 用 `meshOutputPer*Granularity` 手算预留量是否超限 |

| 对策 | 说明 |
|------|------|
| **压低 `layout(max_vertices/max_primitives)`** | 声明上限直接决定预留空间；贴近真实值是最有效的一招 |
| 用 `perprimitiveEXT` 输出平属性 | 平坦着色/Ptex 这类按图元的属性放这里，能减少顶点复制与属性总量（AMD 明确列出） |
| 减少输出属性 | 把部分属性改成"PS 用重心坐标自己插值/采样"（NVIDIA 建议用 barycentrics 替换属性） |
| 量化输出 | 位置/UV 用 half 或 16 位整数输出（视插值精度需求） |
| 提前 `SetMeshOutputsEXT` | AMD：早调用能把几何引擎分配内存的**延迟**藏起来 |
| 拆 pass | 过重的计算移到前置 compute（可见性/bounds/LOD），MS 只做变换+导出 |

⚠️ NVIDIA 的另一条：**减小 payload**。AS（Task）payload 建议 **< 108 字节**，实在不行也要 **< 236 字节**。payload 太大既吃 `maxTaskPayloadSize`，又挤占 `maxMeshPayloadAndOutputMemorySize`。

## 6. 隐患五：共享内存配额与 Bank 冲突

### 6.1 配额

```
maxMeshSharedMemorySize             : SMEM 上限
maxMeshPayloadAndSharedMemorySize   : payload + SMEM 合计上限（⚠️ 两者是共享预算的！）
```

⚠️ 容易被忽略的一点：**Task Shader 的 payload 和 Mesh Shader 的 shared memory 是同一个预算**。
payload 开大了，MS 能用的 SMEM 就少了。

### 6.2 Bank 冲突

```
共享内存被分成 N 个 bank（常见 32 个，按 4 字节交错）。
同一条指令里，若多个线程访问【同一 bank 的不同地址】，就要串行化 → N-way conflict。
```

| 访问模式 | 冲突 |
|---------|------|
| `smem[tid]`（连续 4 字节） | ✅ 无冲突（正好铺满所有 bank） |
| `smem[tid * 2]`（stride 2） | ⚠️ 2-way |
| `smem[tid * 32]`（stride 32） | ❌ 32-way（全部打到一个 bank） |
| `smem[tid * 3]` | ✅ 无冲突（3 与 32 互质） |
| `smemVec4[tid]`（16 字节元素） | ⚠️ 一次访问跨 4 个 bank，某些架构上仍会冲突 |

```glsl
// ❌ 8 位索引缓存按 uint8 存，每线程读 mt[tid] → 逐字节，既冲突又不合并
groupshared uint8_t smemBytes[256];

// ✅ 打包成 uint（4 字节对齐），并按需 padding
groupshared uint smemWords[64];        // 每字装 4 个索引

// ⚠️ 若必须按 (x, y) 二维访问，用 padding 打破同 bank
groupshared float tile[64][33];        // 33 而不是 32 → 行间错开一个 bank
```

| 对策 | 说明 |
|------|------|
| padding | 二维数组行长 +1（经典手段） |
| swizzle | 索引做 XOR 重映射（`idx = tid ^ (tid >> 5)` 一类） |
| 改数据类型 | 尽量按 4 字节/16 字节访问，避免 byte/short 的零散访问 |
| 用 subgroup 替代 SMEM | AMD 建议：**能用 subgroup 操作就不要用共享内存**（`subgroupShuffle`、`WavePrefixSum`） |
| 复用同一块 SMEM | 用 `barrier()` 分段复用，别为每一阶段各开一块 |

### 6.3 barrier 的隐性成本

```glsl
groupshared uint cache[...];
if (tid < N) cache[tid] = src[base + tid];
barrier();                                // ⚠️ 整个工作组等最慢的那个 wave
uint v = cache[idx];
```

- `barrier()` 之后所有线程才能继续 → **长尾的访存延迟会被放大成整个工作组的停顿**；
- 对策：让载入阶段**尽可能短且合并**；或者用 `subgroup` 级操作（无需 barrier）替代工作组级。

## 7. 度量：怎么知道是哪一类问题

| 手段 | 看到什么 | 用于判断 |
|------|---------|---------|
| `VK_QUERY_PIPELINE_STATISTIC_TASK_SHADER_INVOCATIONS_BIT_EXT`（0x800） | Task 调用数 | Task 阶段的放大率是否合理 |
| `VK_QUERY_PIPELINE_STATISTIC_MESH_SHADER_INVOCATIONS_BIT_EXT`（0x1000） | Mesh 调用数 | 线程组大小 × 工作组数 |
| `VK_QUERY_TYPE_MESH_PRIMITIVES_GENERATED_EXT`（1000328000） | **未被固定功能剔除**的实际发射图元数 | 剔除是否生效；与输入三角形数对比得"剔除率" |
| `duplication factor`（自算） | 变换顶点数 ÷ 唯一顶点数 | meshlet 切分质量（第 03 篇） |
| Radeon GPU Profiler / RGA | wave 数、VGPR、LDS、spill、exp 指令数 | 寄存器/SMEM/导出路径 |
| NSight Graphics | SM 占用率、访存吞吐、分支效率 | 发散与访存 |
| `meshopt_analyze*` | ACMR / ATVR / overfetch / overdraw | 离线数据质量（回归用） |

### 7.1 排查顺序（建议）

```
① MESH_PRIMITIVES_GENERATED 是否远小于输入三角形？
   ├─ 否 → 剔除没生效，查 Task Shader 与 bounds
   └─ 是 → ②

② duplication factor 是否接近 1.0？
   ├─ 否（>1.5）→ meshlet 切分/顶点缓存优化有问题（第 03/04 篇）
   └─ 是 → ③

③ 占用率是否异常低？
   ├─ 是 → 查 max_vertices/max_primitives 声明、SMEM 配额、payload
   └─ 否 → ④

④ 编译器报告有 spill？
   ├─ 是 → 减输出属性 / 用 perprimitiveEXT / 上移计算
   └─ 否 → ⑤

⑤ RGP/NSight 里看访存事务数与 LDS bank conflict 计数
   → 打包微索引、optimizeVertexFetch、SMEM padding/swizzle
```

## 8. 优化清单（可直接照着做）

| 优先级 | 动作 | 依据 |
|--------|------|------|
| ★★★ | `layout(max_vertices/max_primitives)` 设为**实际 meshlet 上限**，不要留余量 | 输出区按声明预留 |
| ★★★ | 线程组大小 = V̂；i 号线程写 i 号元素；超出部分用**线程组步长** | RDNA `exp` 导出顺序 = 线程顺序 |
| ★★★ | `SetMeshOutputsEXT` **尽早调用** | 隐藏几何引擎分配延迟 |
| ★★★ | 微索引按 **4 字节/三角形** 打包，离线对齐 | 逐字节读 = 事务爆炸 |
| ★★☆ | 优先 `CullPrimitiveEXT`；只在顶点很宽或 `prefersCompactPrimitiveOutput=true` 时紧凑化 | AMD 实验结论 |
| ★★☆ | 簇剔除频率 < mesh shading 频率（放 Task Shader 或独立 compute） | meshoptimizer 建议 |
| ★★☆ | 压缩数据**一次载入 SMEM**，不要每线程各读一遍 | AMD GTS 案例 |
| ★★☆ | 不要用 SMEM 缓存整个 meshlet 的顶点/图元 | 直接吃掉占用率 |
| ★★☆ | Task payload < 108 B（退而求其次 < 236 B） | NVIDIA 建议 |
| ★★☆ | 平坦属性走 `perprimitiveEXT`，减少顶点复制与属性总量 | AMD 建议 |
| ★☆☆ | 能用 subgroup 就不用 SMEM（免 barrier、免 bank 冲突） | AMD 建议 |
| ★☆☆ | 避免依赖式加载、保持对齐读取 | 通用 compute 优化同样适用 |
| ★☆☆ | 与 PS 并行吃紧时，试把线程组从 128 降到 64 | AMD 实测有轻微收益 |
| ★☆☆ | 逐簇 LOD 加滞回，避免 LOD 抖动 | 工程经验 |
| ★☆☆ | 稀疏拓扑（粒子）与密集拓扑**分开实现** | NVIDIA 建议 |

## 9. 必须纠正的说法

| 说法 | 事实 |
|------|------|
| "占用率越高越好" | 简单 Mesh Shader **~25% 就够打满光栅器**；复杂 shader 反而更容易被输出区卡住 |
| "占有率高了说明优化有效" | 可能是 wave64 → wave32 切换的假象（AMD 明确警告） |
| "剔除了图元就省了空间" | 输出区按**声明上限**预留；`CullPrimitiveEXT` 只让 PA 跳过 |
| "SMEM 用得越多越快" | SMEM 与 payload 共享预算，且直接压低工作组驻留数 |
| "barrier 很便宜" | 它把最慢线程的延迟放大给整个工作组 |
| "bank 冲突是现代 GPU 的古老话题" | 逐字节索引解包这类写法仍会触发；且 LDS 用量直接决定占用率 |
| "Mesh Shader 慢就是顶点变换慢" | 更常见的是：输出区预留过大、微索引逐字节读、payload 过大、被 PS 挤掉 |
| "分析器数字达标就没问题" | `meshopt_analyze*` 是近似模型，只能做回归；真机测才是结论 |

## 10. 小结

| 要点 | 说明 |
|------|------|
| 五类隐患 | 发散 / 访存 / 占有率 / 寄存器 / SMEM（外加被 PS 挤占） |
| 发散 | 工作组间免费、wave 内昂贵；把 LOD/材质分支**上移到 Task Shader** |
| wave 模式 | `WavePrefixSum` 一类指令可能切到 wave32 → 占用率假性升高 |
| 访存 | 微索引按 4 字节打包；`optimizeVertexFetch`；压缩数据一次入 SMEM；避免依赖式加载 |
| 占有率 | 由输出区 / SMEM / payload / 寄存器共同决定；简单 MS ~25% 即够；PS 会被优先调度 |
| 寄存器 | 压低声明上限最有效；用 `perprimitiveEXT` 与 barycentrics 减属性；payload < 108 B |
| SMEM | 与 payload 共享预算；只放"多次复用"的小数据；优先用 subgroup 替代 |
| Bank 冲突 | padding（行长 +1）、swizzle、按 4/16 字节访问、避免 byte 零散读 |
| 度量 | 两个 pipeline statistic 位 + `MESH_PRIMITIVES_GENERATED` + RGP/RGA/NSight + meshopt analyzers |
| 排查顺序 | 剔除率 → 冗余系数 → 占用率 → spill → 访存/LDS |
