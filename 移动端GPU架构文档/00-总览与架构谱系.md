# 移动端 GPU 架构 — 总览与架构谱系

> 本文档是「移动端 GPU 架构」系列文档的第 **0** 篇。本系列从 TBR/TBDR 的第一性原理出发，逐层拆解分箱（Binning）、片上内存（GMEM / Tile Memory）、逐 Tile 流水线的物理执行过程，并对业内流传的常见说法做**准确性审查**，最后落到 Snapdragon Profiler 指标的诊断与优化清单。

---

## 1. 文档目的与读者对象

### 1.1 为什么要单独开一个系列

桌面端的 GPU 心智模型（IMR，立即渲染模式）在移动端**几乎全是错的**。这带来一类很隐蔽的问题：代码在桌面上跑得挺好，一上手机就出现「着色器停顿」「ALU 利用率只有 30%」「Direct Mode 警告」，但开发者照着桌面经验去优化——加大批次、加 MRT、加后处理——反而更糟。

根因是移动端 GPU 用了**完全不同的内存层次结构**：它把「屏幕切成小块、每块的数据不落主存」当成硬件设计的中心思想。不理解这一点，任何优化都是在猜。

### 1.2 核心目标

- **建立正确的心智模型**：分清 IMR / TBR / TBDR / FlexRender 四者的真实差别，不再把它们混为一谈
- **纠正流传的错误说法**：本系列第 1 篇专门做资料勘误，逐条给出「原文 → 判断 → 事实 → 正确表述」
- **讲清物理执行过程**：分箱到底在管线的哪个位置、分的是谁、逐 Tile 流水线如何重叠执行
- **给出可执行的对策**：从 G-Buffer 打包格式到 Vulkan Load/Store Op，落到代码级

### 1.3 读者对象

| 读者类型                            | 预期收获                                                                  |
| ----------------------------------- | ------------------------------------------------------------------------- |
| 从桌面端转向移动端的渲染工程师      | 修正 IMR 惯性思维，建立带宽预算意识                                       |
| 正在调 Snapdragon Profiler 的开发者 | 把警告指标映射回硬件成因，而不是盲目试错                                  |

## 2. 第一性原理：移动端为什么长成这样

### 2.1 带宽与功耗是硬约束

移动设备和桌面主机面对的资源约束根本不同：

| 维度         | 桌面独显（典型）         | 移动 SoC（典型）                      |
| ------------ | ------------------------ | ------------------------------------- |
| 显存类型     | GDDR6 / GDDR6X，独立颗粒 | LPDDR5/LPDDR5X，**与 CPU 共享** |
| 峰值带宽量级 | 400–1000+ GB/s          | 30–70 GB/s                           |
| 显存容量     | 8–24 GB 独占            | 8–16 GB 全系统共享                   |
| 功耗预算     | 150–450 W（整卡）       | 3–8 W（整个 SoC 的 GPU 部分）        |
| 散热         | 主动风冷/水冷            | 被动，靠机身                          |
| 供电         | 外接电源                 | 电池（3–8 Wh 级续航敏感）            |

**带宽消耗直接换算成电**。LPDDR 的 PHY 每传输一个 bit 都要在 PCB 走线上充放电，这是可测量的功耗项。Qualcomm 在 SIGGRAPH 2015 公布的骁龙平台游戏功耗拆解很说明问题：

```
┌──────────────────────────────────────────────┐
│  典型 3D 游戏运行时的整机功耗构成（骁龙平台）  │
├──────────────────────────────────────────────┤
│  CPU          ████████████              ~24% │
│  GPU          ████████                  ~16% │
│  DDR（内存）   ████████                  ~16% │  ← 与 GPU 本身等量级！
│  其他子系统    █████████████████████████  ~50% │
└──────────────────────────────────────────────┘
      数据来源：Qualcomm SIGGRAPH 2015 "Mobile HW and Bandwidth"
```

**结论**：内存访问的功耗和 GPU 自身的功耗**同一量级**。所以移动端 GPU 设计的核心目标不是「算得更快」，而是「**尽量别碰主存**」。

### 2.2 由此推导出的三个设计决策

```
   目标：少碰主存
        │
        ├──▶ 决策一：把屏幕切成小块（Tile / Bin）
        │        → 一块的数据量足够小，小到能塞进片上 SRAM
        │
        ├──▶ 决策二：块内闭环处理（G-Buffer → 光照 → 输出）
        │        → 中间结果从不落主存，只有最终颜色写出
        │
        └──▶ 决策三：只处理真正可见的东西
                 → 隐面剔除（HSR / LRZ / FPK），避免无效着色
```

这三条决策直接导出本系列的三个核心概念：**Binning（分箱）**、**GMEM / Tile Memory（片上内存）**、**HSR（隐藏面消除）**。

### 2.3 关键量化：一次「多写一个附件」值多少钱

以 1080p（1920×1080 ≈ 207 万像素）为例，多增加一张 `RGBA8` 的渲染目标意味着：

```
写入：207 万 × 4 字节 = 8.3 MB
读取：光照 Pass 再读回      = 8.3 MB
                            ─────────
每帧额外主存流量             ≈ 16.6 MB

按 60fps 计 → 约 1.0 GB/s 的持续带宽占用
按 40 GB/s 可用带宽计 → 直接吃掉 2.5% 的总带宽预算
```

单看不多，但移动端游戏常见 15–30 张中间贴图（阴影图、SSAO、泛光各级 mip、Bloom、DOF、透明层……）。**这就是「移动端不要随便加 RT」的算术依据。**

## 3. 架构谱系：四种渲染模式

### 3.1 谱系总览

```
                    几何处理时机 ←───────┬───────→ 像素处理时机
                                          │
   ┌──────────────────────────────────────┴───────────────────────────────────┐
   │                                                                          │
   │  ① IMR（Immediate Mode Rendering）                                       │
   │     桌面独显/主机                                                          │
   │     顶点着色 ─▶ 图元装配 ─▶ 光栅化 ─▶ 片元着色 ─▶ 直接写显存                 │
   │     ✗ 无分箱   ✗ 无片上缓冲   ✓ 任意读写   ✓ 换 RT 几乎免费                  │
   │                                                                          │
   ├──────────────────────────────────────────────────────────────────────────┤
   │                                                                          │
   │  ② TBR（Tile-Based Rendering）                                           │
   │     ARM Mali、Intel iGPU（部分）、Apple GPU                                │
   │     顶点着色 ─▶ 分箱（生成 Tile List）───┐                                  │
   │                                          ▼                                │
   │     逐 Tile：光栅化 ─▶ 片元着色 ─▶ 写入片上 Tile Buffer ─▶ Resolve 到主存    │
   │     ✓ 片上缓冲   ✓ 低带宽   ✗ 换 RT 昂贵（Resolve 成本）                     │
   │                                                                          │
   ├──────────────────────────────────────────────────────────────────────────┤
   │                                                                          │
   │  ③ TBDR（Tile-Based Deferred Rendering）                                 │
   │     Imagination PowerVR                                                   │
   │     顶点着色 ─▶ 分箱 ─▶ 参数缓冲（Parameter Buffer，在主存）                 │
   │                                          ▼                                │
   │     逐 Tile：① HSR 隐面消除（只留可见片元）                                 │
   │              ② 仅对可见片元做纹理取指 + 着色 + 混合 ─▶ 片上 Buffer           │
   │              ③ Resolve 到主存                                              │
   │     ✓ 片上缓冲 + 像素级精确的 HSR   ✓ 提交顺序无关   ✗ 硬件复杂度/面积代价    │
   │                                                                          │
   ├──────────────────────────────────────────────────────────────────────────┤
   │                                                                          │
   │  ④ FlexRender（混合模式）                                                 │
   │     Qualcomm Adreno                                                       │
   │     驱动启发式，**逐 surface** 在以下三档之间动态选择：                      │
   │       Direct Mode        ── 等价 IMR，不生成 bin，直接渲染                   │
   │       Binned Mode        ── 等价 TBR，Binning Pass + 逐 Bin 渲染            │
   │       Binned Direct Mode ── 先跑可见性 Pass 剔除背面，再切 Direct 渲染       │
   │     ✓ 兼容性最好   ✓ 无 binning 开销时可直接过   ✗ 行为不完全可预测           │
   └──────────────────────────────────────────────────────────────────────────┘
```

### 3.2 四种模式的横向对比

| 维度                 | IMR（桌面）             | TBR                          | TBDR                                 | FlexRender                 |
| -------------------- | ----------------------- | ---------------------------- | ------------------------------------ | -------------------------- |
| 代表厂商             | NVIDIA / AMD            | ARM Mali、Apple              | Imagination PowerVR                  | Qualcomm Adreno            |
| 是否有分箱阶段       | ❌ 无                   | ✅ 有（tiling）              | ✅ 有（binning）                     | ⚠️ 视模式而定            |
| 片上缓冲             | ❌（靠 L2 近似）        | ✅ Tile Buffer               | ✅ Tile Buffer + Tag Buffer          | ✅ GMEM                    |
| 隐面剔除             | Early-Z / Hi-Z          | Early-Z + HSR                | **真 HSR**（像素级、顺序无关） | Early-Z + LRZ              |
| 中间结果落主存       | 是（每张 RT）           | 否（同 pass 内）             | 否（同 pass 内）                     | 否（Binned 模式下）        |
| 换 RT / 中途读回代价 | 低                      | **高**（Resolve 成本） | **高**                         | **高**               |
| MSAA 成本            | 中等                    | 相对便宜（片上 resolve）     | 相对便宜                             | 相对便宜（≤2x 近乎免费）  |
| 任意位置纹理采样     | 便宜                    | 贵（破坏局部性）             | 贵                                   | 贵（可能触发 Direct Mode） |
| 提交顺序敏感度       | 高（影响 Early-Z 命中） | 中                           | **低**（HSR 顺序无关）         | 中                         |

### 3.2.1 TBR 与 TBDR：相同点与核心区分

> 上一节的横向对比表里，TBR 与 TBDR 看起来只差一列。本节把这两列单独摊开，明确**哪些是两者共有、哪些是真正的分水岭**。

**① 相同点（两者共有）**

| 维度 | 说明 |
|------|------|
| 基于 Tile 渲染 | 都把屏幕切成块，逐 tile 处理 |
| 片上缓冲 | 中间结果留在 Tile Buffer / GMEM，不每张 RT 落主存 |
| 有分箱阶段 | 都先 binning，再渲染 |
| 都有隐面剔除 | 都做 HSR / Early-Z（只是强度不同） |
| Resolve 成本 | 换 RT / 中途读回代价都高 |
| 任意位置纹理采样都贵 | 都破坏局部性 |

**② 不同点（核心区分）**

| 维度 | TBR（如 Mali / Apple） | TBDR（如 PowerVR） |
|------|----------------------|-------------------|
| HSR 强度 | Early-Z + HSR，**近似、与提交顺序相关** | **真 HSR：像素级精确、顺序无关** |
| 着色与可见性时序 | 着色（含取数）排在可见性判定**之前/之中**，overdraw 片元仍被着色 | 先整 tile 解析可见性，**只为可见片元着色取数** |
| 被遮挡片元的法线/纹理带宽 | 仍被拉取 → overdraw 浪费带宽 | 根本不取 → overdraw 几乎零带宽代价 |
| 提交顺序敏感度 | 中（顺序影响 Early-Z 命中） | **低**（HSR 顺序无关） |
| 带宽优势来源 | 靠 tiling 省 color/depth 往返主存 | tiling + 延迟取数（`02` 篇推导） |
| 典型厂商 | ARM Mali、Apple GPU | Imagination PowerVR |

⚠️ **关键**：区分**不是「有没有分箱 / 片上缓冲 / HSR」**，而是 **HSR 是否 pixel-perfect 且顺序无关、能否在着色前彻底解析可见性**。TBR 也有 HSR（Mali 官方有 hidden surface removal），只是弱于 PowerVR 的真 HSR，所以 overdraw 仍耗带宽。

**③ 流水线结构对比**

TBR：
```
顶点着色 ─▶ 分箱(生成 Tile List)
        ▼
逐 Tile：光栅化 ─▶ 片元着色(拉法线/纹理) ─▶ 隐面剔除(Early-Z/HSR, 近似·顺序相关) ─▶ 片上 Buffer ─▶ Resolve
```
→ overdraw 片元已在着色阶段把法线/纹理拉过一遍，剔除才把它干掉（白取）。

TBDR：
```
顶点着色 ─▶ 分箱 ─▶ 参数缓冲(PB, 主存)
        ▼
逐 Tile：① HSR 隐面消除(像素级·顺序无关, 只留可见片元)
         ② 仅对可见片元做纹理取指 + 着色 + 混合 ─▶ 片上 Buffer ─▶ Resolve
```
→ 被遮挡片元的法线/纹理**从不取**（见 `02` 篇 Imagination 官方注释）。

**④ 使用边界（避免误用）**

1. **「Deferred」≠ 延迟渲染（G-Buffer 那套）**：TBDR 的 Deferred 是硬件上「片元着色推迟到 HSR 之后」，与软件 Deferred Shading 无关（详见下节三重歧义）。
2. **优势只在有 overdraw 时成立**；且 HSR 被 `gl_FragDepth` / `discard` / framebuffer fetch 削弱、或 PB 溢出时，TBDR 优势打折甚至失效。
3. **现实是光谱而非二分**：现代 Apple GPU、Valhall 代 Mali 的 HSR 已很强，边界在模糊化；教科书级 TBDR 指 PowerVR。

### 3.3 「Deferred」这个词的三重歧义 ⚠️

这是极其常见的混淆源，必须先把术语钉死：

```
┌─────────────────────┬──────────────────────────────────────────────────────┐
│ 说法                 │ 真实含义                                              │
├─────────────────────┼──────────────────────────────────────────────────────┤
│ Tile-Based Deferred  │ 建筑学术语。指「片元着色被推迟到隐面消除之后」，          │
│ Rendering (TBDR)     │ 是**硬件架构名**（PowerVR 的 HSR 机制）。               │
│                     │ 与光照算法无关！                                       │
├─────────────────────┼──────────────────────────────────────────────────────┤
│ Deferred Shading /   │ 渲染算法。指「几何先写入 G-Buffer，光照作为第二个        │
│ Deferred Rendering   │ 屏幕空间阶段」。是**软件管线设计**。                     │
│                     │ 与硬件是否为 TBDR 无关（桌面也能做）。                   │
├─────────────────────┼──────────────────────────────────────────────────────┤
│ FlexRender 的         │ 高通文档里的 "deferred mode" 指的是**分箱模式**，       │
│ "Deferred Mode"      │ 即 TBR 行为。也**不是** G-Buffer 那个 deferred。        │
└─────────────────────┴──────────────────────────────────────────────────────┘
```

⚠️ **实战提醒**：在阅读三方资料时，看到 "deferred" 先问一句——说的是硬件架构、渲染算法，还是厂商内部的模式命名？三者含义完全不同，混用会导致推导出完全错误的结论。

## 4. 主流移动 GPU 实现对比

### 4.1 厂商实现对照表

以下数字中，标注「未公开」的表示厂商未在官方文档中给出确切值，社区数字来自逆向分析或 profiler 观测，仅供参考。

| 维度             | Qualcomm Adreno                                                                                                                                                 | ARM Mali                                                                                                                              | Imagination PowerVR                                                                           | Apple GPU                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------- |
| 架构类型         | FlexRender（IMR ⇄ TBR 动态切换）                                                                                                                               | TBR（Bifrost / Valhall / 5th Gen）                                                                                                    | TBDR                                                                                          | TBDR                             |
| Bin / Tile 尺寸  | **可变**，由驱动按 GMEM 容量 + 附件格式决定（含 MSAA 采样数）                                                                                             | 名义**16×16**，tiler 可用更大的 2 的幂尺寸容纳三角形                                                                           | Series 6/7 为**32×32**；SGX5 为 16×16；PCX2 可为 32×32 / 32×16                      | 32×32                           |
| 片上内存         | **GMEM**（图形专用 SRAM）。Adreno 615 ≈ **512 KB**，Adreno 630 ≈ **1 MB**，Adreno X1（PC 端）**3 MB**                                 | Tile Memory，**每 Shader Core 约 16 KB 量级**（低端如 G52 两核共 16 KB；高端更大，官方未系统公布）                              | Tile Buffer（容量未公开）                                                                     | Tile Memory（容量未公开）        |
| 隐面剔除机制     | **LRZ**（Low Resolution Z，Adreno 5xx 起）+ Early-Z                                                                                                       | **HSR** + **FPK**（Forward Pixel Kill，可在像素着色后杀死被遮挡的像素）                                                   | **HSR**（pixel-perfect、与提交顺序无关，是三者中最强的）                                | HSR                              |
| 顶点处理模型     | Binning Pass 跑**position-only VS**，Render Pass 跑完整 VS                                                                                                | **IDVS**（Index-Driven Vertex Shading）：拆成 Position Shader + Varying Shader 两个二进制                                       | Tiling Accelerator 做 clip/project/cull；**仅取位置数据**推进，非位置属性只为可见图元取 | 两段式（类似 IDVS）              |
| 显存压缩         | **UBWC**（Universal Bandwidth Compression）                                                                                                               | **AFBC**（Arm Frame Buffer Compression）                                                                                        | PVR 自有压缩（FB 压缩）                                                                       | 有（私有）                       |
| Tile 写回优化    | Resolve + 压缩                                                                                                                                                  | **Transaction Elimination**（比较 tile CRC，相同则跳过写回）                                                                    | 有                                                                                            | 有                               |
| 并发分箱         | ✅**Concurrent Binning**（分箱硬件与渲染管线并行）                                                                                                        | ✅（tiler 与 shader core 流水重叠）                                                                                                   | ✅                                                                                            | ✅                               |
| 关键 Vulkan 扩展 | `VK_QCOM_tile_properties`、`VK_QCOM_tile_shading`、`VK_QCOM_tile_memory_heap`、`VK_QCOM_render_pass_store_ops`、`VK_QCOM_fragment_density_map_offset` | `VK_EXT_subpass_merge_feedback`、`VK_ARM_rasterization_order_attachment_access`、`VK_EXT_rasterization_order_attachment_access` | `VK_EXT_rasterization_order_attachment_access`                                              | 主要走 Metal，Vulkan 需 MoltenVK |

### 4.2 一个至关重要的架构差异

**Mali 的片上内存比 Adreno 小一到两个数量级。** 这直接导致两者的优化重点不同：

```
┌────────────────────────────────────────────────────────────────────┐
│  Adreno（GMEM 大，如 1 MB）                                         │
│    → Bin 可以开得很大（几十像素见方），bin 数量少                     │
│    → 理论上能容纳「一个 bin 的完整 G-Buffer」                         │
│    → 优化重点：别让驱动切到 Direct Mode；控制 surface 数量            │
│                                                                    │
│  Mali（Tile Memory 小，每核 16 KB 量级）                            │
│    → Tile 固定 16×16，靠 Transaction Elimination 省写回带宽           │
│    → 片上内存装不下胖 G-Buffer，**必须靠格式压缩**                     │
│    → 优化重点：附件数量与精度、避免破坏 HSR 的 shader 写法             │
└────────────────────────────────────────────────────────────────────┘
```

⚠️ **不要把「Adreno 能装下胖 G-Buffer」的经验套到 Mali 上**。这解释了为什么同一个移动端渲染方案在不同机型上表现差异巨大。

## 5. 核心术语表（本系列统一口径）

| 术语             | 英文                       | 准确定义                                                                                             | 常见误用                     |
| ---------------- | -------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------- |
| 分箱             | Binning                    | 几何阶段把图元按屏幕区域归类，生成每块图元列表的过程                                                 | 误以为它是可选优化           |
| 分块             | Tiling                     | 与 binning 同义，Mali/PowerVR 侧更常用                                                               | —                           |
| 块               | Tile / Bin                 | 屏幕划分出的矩形区域。Tile 常指固定尺寸，Bin 常指可变尺寸                                            | 误以为开发者可以设置尺寸     |
| 片上内存         | GMEM / Tile Memory         | GPU 内的高速 SRAM，存放当前块的 color/depth 中间结果。**不是 cache**（不与主存自动保持一致性） | 误以为它和 L2 一样大         |
| 图元列表         | Tile List / Primitive List | 记录「哪些图元落在这一块」的数据结构，**存放于系统内存**                                       | 误以为存在片上               |
| 可见性流         | Visibility Stream          | Adreno Binning Pass 的输出，压缩后约**1 bit / 图元**                                           | 误以为要存完整顶点数据       |
| 参数缓冲         | Parameter Buffer (PB)      | PowerVR 存放顶点数据与图元列表的主存区域                                                             | —                           |
| 解析             | Resolve                    | 把片上块的最终结果搬回主存。**移动端的主要隐形成本**                                           | 误以为只有 MSAA 才有 resolve |
| 直接模式         | Direct Mode                | Adreno 上「不做分箱、直接渲染」的模式，由驱动启发式选择                                              | 误以为它是异常/退化状态      |
| 并发分箱         | Concurrent Binning         | Adreno 上分箱硬件与渲染管线并行工作，分箱时间可被隐藏                                                | 误以为分箱时间总是串行累加   |
| 索引驱动顶点着色 | IDVS                       | Mali Bifrost+ 的两段式顶点处理：Position Shader + Varying Shader                                     | 与普通 VS 混为一谈           |
| 隐面消除         | HSR                        | 硬件级剔除被遮挡片元。PowerVR 的 HSR 是 pixel-perfect 且顺序无关                                     | 误以为等价于 Early-Z         |
| 转发像素杀死     | FPK                        | Mali 的机制，在像素着色执行后根据深度杀死被遮挡的像素结果                                            | 误以为等价于 HSR             |

### 5.1 术语分层图示

```
┌─ 屏幕空间划分 ─────────────────────────────────────────────────────┐
│  Tile（固定尺寸，如 Mali 16×16）  /  Bin（可变尺寸，Adreno）          │
└────────────────────────────────────────────────────────────────────┘
                              │
┌─ 片上存储 ─────────────────▼────────────────────────────────────────┐
│  GMEM / Tile Memory（SRAM，几百 KB ~ 数 MB，寿命 = 一个块的渲染周期）  │
│  ┌──────────────┬──────────────┬──────────────┐                     │
│  │ Color Buffer │ Depth/Stencil │ G-Buffer MRT │                     │
│  └──────────────┴──────────────┴──────────────┘                     │
└────────────────────────────────────────────────────────────────────┘
                              │ Resolve（唯一的必然主存流量）
┌─ 系统内存 / 显存 ────────────▼───────────────────────────────────────┐
│  Tile List / Visibility Stream / Parameter Buffer / 最终帧缓冲        │
└────────────────────────────────────────────────────────────────────┘
```

## 6. 移动端 vs 桌面端：八个关键差异

| # | 维度                | 桌面 IMR 心智模型                     | 移动端 TBR/TBDR 真实情况                                        | 踩坑后果                                     |
| - | ------------------- | ------------------------------------- | --------------------------------------------------------------- | -------------------------------------------- |
| 1 | 中间结果存储        | 每张 RT 都落显存                      | 同 render pass 内保持在片上                                     | 中途切 RT → Resolve 成本翻倍                |
| 2 | 换 RT 的代价        | 几乎免费                              | **昂贵**（每个被写过的 RT 都要 resolve）                  | 每加一个后处理 pass 就加一次全屏带宽         |
| 3 | 任意位置纹理采样    | 便宜                                  | 贵（破坏局部性，可能触发 Direct Mode）                          | 代码写成分离 pass 采样 G-Buffer              |
| 4 | 追加 MRT            | 只花内存和写带宽                      | 可能**撑爆片上内存**，导致整个 pass 退化                  | 从「带宽小增」变成「性能悬崖」               |
| 5 | MSAA                | 成本随采样数近似线性                  | ≤2x 在小屏幕上近乎免费；deferred 下完全不可用                  | 在 G-Buffer 上开 MSAA                        |
| 6 | 顶点处理成本        | 相对便宜                              | 相对昂贵；且 TBR 下可能**跑两次**（position-only + 完整） | 顶点着色器里塞纹理采样                       |
| 7 | 提交顺序            | 强烈建议 front-to-back 以命中 Early-Z | 影响较小（HSR/LRZ 有硬件剔除）                                  | 花大量精力排序却收益微弱                     |
| 8 | Clear 与 Invalidate | 跳过 clear 是优化                     | **必须 clear 或 invalidate**，否则驱动被迫从主存读回      | 沿用桌面的「跳过 clear」习惯，移动端反而变慢 |

⚠️ **差异 #8 值得单独强调**。Carmack 在 Meta 开发者博客里明确指出：移动端「跳过 glClear」是**反向优化**。如果应用不清除也不 invalidate 帧缓冲，驱动保守地认为旧内容需要保留，于是在每个 tile 开始渲染前**从主存把 tile buffer 读回来**。而一次 clear 是纯片上写，永远比一次主存读回快。

对应 Vulkan 的正确做法：

```cpp
// ✅ 正确：明确告诉驱动不需要旧内容
VkRenderingAttachmentInfo color{};
color.loadOp  = VK_ATTACHMENT_LOAD_OP_CLEAR;        // 或 DONT_CARE
color.storeOp = VK_ATTACHMENT_STORE_OP_STORE;       // 最终颜色要留

VkRenderingAttachmentInfo gBufferA{};
gBufferA.loadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE; // 中间结果，不需要旧内容
gBufferA.storeOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;// ⚠️ 关键：用完即弃，不写回主存

VkRenderingAttachmentInfo depth{};
depth.loadOp  = VK_ATTACHMENT_LOAD_OP_CLEAR;
depth.storeOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;   // 深度通常用完就不需要了
```

## 7. 常见误区速查表

| 误区                                        | 真实情况                                                                                                                                                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「移动端一定要分箱，没有例外」              | Adreno 的 FlexRender 支持 Direct / Binned / Binned Direct 三档，由驱动逐 surface 选择。Adreno 上分箱**不是**必然                                                       |
| 「分箱只关心图元，不关心顶点」              | 分箱阶段必须跑**位置着色**（position-only VS）。顶点数量、位置计算复杂度、索引复用率、顶点缓冲布局全都直接决定分箱成本                                                 |
| 「分箱在完整顶点着色器之后」                | 顺序是：**位置着色 → 分箱 → 完整（varying）着色 → 光栅化**。分箱夹在两段着色之间                                                                                    |
| 「分箱阶段零主存访问」                      | 分箱输出的可见性流 / 图元列表**存在系统内存**。Adreno 上压缩到约 1 bit/图元，但不是零                                                                                  |
| 「Tile 尺寸是 16×16 或 32×32，硬件写死」  | Mali 名义 16×16（可用更大的 2 的幂）；**Adreno 的 bin 尺寸可变**，由驱动按 GMEM 与格式决定；且可用 `VK_QCOM_tile_properties` **查询**实际值                   |
| 「跨 Tile 的三角形会被裁剪、拆分」          | **不会**。Qualcomm 官方明确说明：跨 bin 的三角形会在每个覆盖到的 bin 中**完整重复光栅化**，不增加顶点                                                            |
| 「Mali 只有 Early-Z，没有 HSR」             | ARM 官方文档明确提到 Mali 的**hidden surface removal**；late ZS test 会禁用 early ZS **与 HSR**。Mali 还有 FPK                                                   |
| 「延迟渲染是移动端天作之合」                | TBDR 把 deferred 的最大缺陷从「致命」降为「可接受」，所以移动端 deferred**可行**。但 UE 移动端默认仍是 Forward；Oculus 官方明确劝退移动 VR 用 deferred（resolve 成本） |
| 「全屏 draw 一定会破坏 Tile 局部性」        | 判断标准是**访问模式是否 framebuffer-local**，不是是否全屏。用 input attachment 的全屏 draw 完全可以保持片上闭环                                                       |
| 「G-Buffer 撑爆 GMEM 所以触发 Direct Mode」 | 部分对。Qualcomm 官方给出的 Direct Mode 触发条件是：VS 中纹理采样/顶点比高、顶点与 draw 数少、使用 tessellation 或 geometry shader。容量是其中一条但不是唯一                 |
| 「「deferred」就是延迟渲染」                | 该词有三重含义：TBDR 的硬件架构名、Deferred Shading 算法、Adreno FlexRender 的分箱模式。必须按上下文区分                                                                     |

## 9. 小结

| 要点                                       | 说明                                                                                  |
| ------------------------------------------ | ------------------------------------------------------------------------------------- |
| **移动端的设计中心是带宽，不是算力** | 内存功耗与 GPU 功耗同量级，芯片设计围绕「少碰主存」展开                               |
| **三种架构不是同一种东西**           | IMR 没有分箱；TBR 有分箱但用 Early-Z；TBDR 有分箱 + 真 HSR；Adreno 是三者间的动态切换 |
| **「分箱」是手段不是目的**           | 目的是让「一块屏幕的数据」小到能进片上 SRAM（GMEM / Tile Memory）                     |
| **片上内存不是 cache**               | 它是显式管理的暂存器，不会自动与主存保持一致，寿命等于一个块的渲染周期                |
| **Resolve 是移动端最主要的隐形成本** | 每一次「渲染到贴图」都要付一次 resolve；这才是移动端优化真正的把柄                    |
| **架构差异大到不能互相套用**         | Adreno 的大 GMEM ≠ Mali 的小 Tile Memory，优化重点完全不同                           |
| **术语必须钉死**                     | 「deferred」「tile」「bin」在不同上下文里含义不同，混用会推出错误结论                 |
