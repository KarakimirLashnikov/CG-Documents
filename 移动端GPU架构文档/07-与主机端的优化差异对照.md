# 移动端 GPU 架构 — 与主机端的优化差异对照

> 本文档是「移动端 GPU 架构文档」系列的第 **7** 篇（末篇）。前六篇都在讲移动端自身，本篇把移动端与主机 / PC 摆在一起：哪些约束是**两端共有的物理规律**，哪些是**数量级差异导致的策略分野**，以及被广泛流传的几个错误对照。⚠️ 结论是：**优化目标函数不同，不是优化手段对错不同。**

---

## 1. 先修正前提：「移动端 vs 主机端」不是二元的

流传最广的说法是「移动端被动散热、主机主动散热」。这是真的，但它掩盖了一个更重要的事实：**决定性变量是能量预算与散热形式，而不是设备形态**。按这个变量排开，是一条连续的谱系：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  按「持续功耗预算」排列的谱系（对数尺度，量级示意）                          │
│                                                                          │
│  1W ──── 5W ──── 10W ──── 20W ──── 50W ──── 150W ──── 300W ──── 600W+    │
│   │       │        │        │        │         │         │        │      │
│  可穿戴  手机     手机     掌机     轻薄本    主机      桌面GPU   高端     │
│          (轻载)  (重载)  (Switch2/  (核显)   (整机)   (RTX 5080) 工作站   │
│                          SteamDeck)                                     │
│                                                                          │
│  ├────────── 被动散热 ──────────┤├────── 主动散热 ──────┤                │
│  ├─ 电池供电 ─┤                  ├──────── 市电 ────────┤                 │
│                                                                          │
│  ⚠️ 关键：掌机（Switch 2 / Steam Deck）是中间态——                          │
│     既有电池与热约束，也有小风扇与主动降频，还同样用 AI 超分。               │
│     → 它同时具备两端的特征，是检验「哪条规律是普遍的」最好的对照组。          │
└──────────────────────────────────────────────────────────────────────────┘
```

| 档位 | 持续功耗量级 | 散热 | 供电 | 典型内部渲染分辨率 | 降频敏感度 |
|------|------------|------|------|------------------|-----------|
| 手机（重载游戏） | 3~7 W（SoC 持续；标称 TDP 量级 5 W，短时峰值可远高于此） | 被动：VC 均热板 / 石墨 / 导热膜 | 电池 | 通常 < 原生，靠超分合成 | **极高** |
| 掌机（Switch 2 / Steam Deck） | 4~15 W（可配置） | 被动 + 小风扇 | 电池 | 540p → 1080p 级 | 高 |
| 主机（PS5 / Xbox Series X） | 整机 150~250 W | 主动：大风扇 + 热管/均热板 | 市电 | 1080p 内部 → 4K 输出 | 低 |
| 桌面 GPU | 单卡 130~575 W（RTX 50 系实测区间） | 主动：风冷/水冷 | 市电 | 1440p~4K 原生 + 重建 | 极低 |

⚠️ **手机那一格的"3~7 W"是持续值，不要当成能力上限**。旗舰 SoC 的短时峰值功耗可远高于持续值（厂商口径有标称 TDP 与峰值功率两个数字），而持续值是被温控"压"下来的结果——**这正是本篇要解释的核心现象**。

## 2. 三堵墙 vs 三道闸：同一组名词，两种性质

移动端炒作的"三堵墙"与主机/PC 的"三道闸"（功耗墙、温度墙、电压墙）**名字几乎一样，性质完全不同**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  移动端：墙是「外部给定的约束」                                            │
│                                                                          │
│   功耗墙 ─┐                                                              │
│   温度墙 ─┼──► 都源自同一个物理事实：                                     │
│   电池墙 ─┘     被动散热的等效热阻 R_th 很高，且没有市电兜底                │
│                                                                          │
│   → 表现：被迫削峰（throttling），性能随环境温度、握持姿态、充电状态漂移     │
│   → 优化目标是「在给定预算内最大化体验」                                   │
├──────────────────────────────────────────────────────────────────────────┤
│  主机 / PC：闸是「自己设定的包线」                                          │
│                                                                          │
│   TGP/TDP ─┐                                                            │
│   PL1/PL2 ─┼──► 都是设计阶段选定的性能包线，                               │
│   TjMax   ─┘     散热系统按这个包线配（风扇曲线、鳍片面积）                 │
│                                                                          │
│   → 表现：按持续性能设计，性能可预期；散热不足是「设计失误」而非常态        │
│   → 优化目标是「在给定包线内最大化性能/画质」                              │
└──────────────────────────────────────────────────────────────────────────┘
```

| 维度 | 移动端 | 主机 / PC |
|------|--------|----------|
| **墙/闸的来源** | 外部物理环境（环境温度、握持、阳光直射） | 厂商设计决策（TGP、风扇曲线、机箱风道） |
| **是否可预期** | ❌ 同一款机器在不同环境差异巨大 | ✅ 基本固定 |
| **削峰机制** | 多级、面向上百个热区、由内核与厂商策略共同决定 | 简单：频率/功率限制 + 风扇 |
| **削峰后果** | 帧率暴跌、帧时间抖动、可感知 | 通常不可感知（或只是噪音变大） |
| **开发者能做什么** | 可以主动降画质来"换"稳定（见 §9） | 主要靠提高效率与画质 |

⚠️ **纠正「主机极少因温度降频」这个说法**：它基本成立，但需要限定——主机**按持续性能设计 ≠ 没有热管理**。通风不良、积灰、高温环境、竖放遮挡进风口都会触发风扇拉满甚至降频；只是它的热预算固定、可预期，不构成日常优化课题。把它说成"主机不会降频"是过度简化。

## 3. 因果链的真实形态

流传的说法是「高功耗 → 发热 → 温控 → 降频」。方向对，但**漏掉了最关键的一环：为什么功耗会"高"得这么快**。

### 3.1 能效拐点：为什么性能提升 10% 可能让功耗涨 30%

```
┌──────────────────────────────────────────────────────────────────────────┐
│  动态功耗：P_dyn = α · C · V² · f                                        │
│                                                                          │
│  要提高频率 f，必须同时抬高电压 V（否则电路来不及翻转）                      │
│  → P 随 f 的增长是超线性的：在陡区近似 P ∝ f^2.5 ~ f^3                    │
│                                                                          │
│     功耗 P                                                                │
│       ▲                                        ╱  ← 陡区（"能效拐点"之后）  │
│       │                                      ╱                            │
│       │                                   ╱                               │
│       │                            ______╱   ← 拐点：性价比最优处            │
│       │                     ______╱                                       │
│       │          __________╱  ← 缓区（频率低时几乎"免费"）                  │
│       └──────────────────────────────────────────► 性能                    │
│                                                                          │
│  含义：移动端超频/拉满频率的边际收益急剧递减，边际功耗急剧上升               │
│       → 所以"降一点频率，省很多电"往往比"提一点频率"划算得多                 │
│       → 所以移动端的目标函数是「每焦耳的帧数」，不是帧数                     │
└──────────────────────────────────────────────────────────────────────────┘
```

⚠️ `P ∝ f^3` 是**工程经验规律**，不是精确公式（实际指数随工艺、电压区间、漏电占比变化）。但方向可靠：**在陡区，小幅提频换大幅增耗；小幅降频能省大量功耗**。

### 3.2 完整链条（补上被漏掉的环节）

```
负载 ↑
  → 频率/电压 ↑（DVFS 上调）
  → 功耗非线性上升（见 §3.1）
  → 热流密度 ↑，但被动散热的热阻 R_th 固定 → 结温上升快
  → 表面温度上升 → 影响握持（这是最"硬"的约束，用户直接投诉）
  → 系统温控介入（多级、多点位）
  → 频率下降 / 大核限制 / 调度迁移 / 亮度下调 / 充电限流 / 帧率上限
  → 帧率回落 **且帧时间抖动**
  → 体验崩坏（用户感知的不是"帧率低"，而是"忽快忽慢"）
```

**最后一行值得单独强调**：移动端最伤体验的往往不是平均帧率低，而是**帧时间不稳定**。这也是为什么"锁 30 帧 / 锁 40 帧"的策略常比"放任 55~60 帧上下跳"更好（见 §9）。

### 3.3 温控阈值：不存在一个"55℃"

⚠️ **必须纠正的表述**：温控**不是单一阈值**，而是多区域、多级的组合。传闻里的"55℃ 触发降频"既不是主流手机的结温阈值，也不是表面温度阈值，更接近某些"偏重性能释放的游戏手机"允许的表面温度。

| 温度区域 | 典型量级（仅作量级参考） | 触发的行为 |
|---------|----------------------|-----------|
| **SoC 结温（junction）** | 通用电子器件的 CPU 降频点常在 **95~105℃** 量级；手机厂商会设更低的内部限制 | 直接降 CPU/GPU 频率 |
| **机身表面温度（skin）** | 主流旗舰倾向把表面控制在 **~45℃ 以下**（超过就明显烫手）；偏性能释放的机型可放宽到 **50℃+** | 降频、降亮度、限制充电 |
| **电池温度** | 通常 **40~45℃ 量级**即开始限制充放电 | 限流、限充电速度 |
| **显示/其他热区** | 厂商自定义 | 降亮度（最容易被忽略的"隐形降频"） |

**两个推论**：
1. **不同手机的同一颗芯片表现可以完全不同**——因为温控策略、均热板面积、机身材质都不同。这就是设备碎片化的一部分（见 §6.1）。
2. **环境温度直接改变结论**：25℃ 空调房与 38℃ 户外，同一台机器的稳态帧率可以差出一档画质。所以移动端性能测试必须**记录环境温度**，否则数据不可比。

## 4. 量级对照表（修正版）

### 4.1 硬件规格对照（数字均为公开标称值）

| 项 | 移动端旗舰（Snapdragon 8 Elite Gen 5 量级） | 主机（PS5 / Xbox Series X） | 桌面（RTX 50 系） |
|----|------------------------------------------|---------------------------|------------------|
| **持续功耗** | SoC 3~7 W（标称 TDP 量级 5 W；峰值远高于此） | 整机 150~250 W | 单卡 130 W（5050）~575 W（5090） |
| **内存类型** | LPDDR5X（32-bit ×4 = 64-bit） | GDDR6（统一池） | GDDR7（独显专用） |
| **内存带宽** | **84.8 GB/s**（LPDDR5X 5300 MHz，64-bit） | PS5 **448 GB/s**（256-bit）；XSX **560 GB/s**（10GB 快池）/ 336 GB/s（6GB 慢池） | 448 / 672 / 896 / 960 / 1792 GB/s（对应 5060 Ti / 5070 / 5070 Ti / 5080 / 5090） |
| **片上级存储** | GMEM / Tile Memory：几百 KB ~ 几 MB | 大 L2（RDNA2 数 MB 级）+ 高带宽显存 | 大 L2：**24 / 32 / 48 / 64 / 96 MB**（随型号递增） |
| **内存架构** | **UMA**（CPU/GPU 共享，且与 ISP/基带/显示共享） | **也是 UMA**（16 GB GDDR6 统一池） | PC 独显：**分离式**（系统 DDR + 显存，需 PCIe 上传） |
| **散热** | 被动（VC / 石墨 / 导热膜），热阻高 | 主动（大风扇 + 热管/均热板），热阻低 | 主动（风冷/水冷），热阻很低 |
| **硬件光追** | 已有（Arm RTU / Adreno / Xclipse），但能力受限 | 有（RDNA 2 RT 单元，支持 BVH 加速） | 有（RT Core，完整 BVH 加速） |
| **AI 超分** | Arm ASR / NSS、Snapdragon GSR、MetalFX | PS5 Pro：PSSR；Switch 2：**DLSS**；其他：FSR 类 | DLSS 4 / FSR 4 / XeSS 2 |

### 4.2 一个更有意义的指标：每像素可用带宽

**「手机带宽是 PC 的 1/10」这个说法本身没错，但会推出错误的结论**——因为手机的目标分辨率也低得多。把两者除一下：

| 平台 | 目标分辨率 | 像素数 | 带宽 | **每像素可用带宽** | **每帧每像素预算**（@60fps） |
|------|-----------|--------|------|------------------|---------------------------|
| 手机旗舰 | 1080p | 2.07 Mpix | 84.8 GB/s | **40.9 GB/s/Mpix** | **≈ 682 B** |
| 掌机（Steam Deck 量级） | 800p | 1.02 Mpix | 88 GB/s | 85.9 GB/s/Mpix | ≈ 1433 B |
| 主机（PS5） | 4K | 8.29 Mpix | 448 GB/s | **54.0 GB/s/Mpix** | ≈ 900 B |
| 主机（XSX 快池） | 4K | 8.29 Mpix | 560 GB/s | 67.5 GB/s/Mpix | ≈ 1125 B |
| 桌面（RTX 5080） | 4K | 8.29 Mpix | 960 GB/s | **115.7 GB/s/Mpix** | ≈ 1929 B |

```
┌──────────────────────────────────────────────────────────────────────────┐
│  反直觉的结论                                                              │
│                                                                          │
│  手机在 1080p 下的「每像素带宽预算」≈ 主机的 3/4（40.9 vs 54.0）             │
│  → 所以手机的带宽窘境**不是**单纯来自"总量少 1/5"                           │
│                                                                          │
│  真正让移动端难受的是另外三件事：                                            │
│    ① 带宽被**共享**：CPU、ISP、基带、显示 scan-out 都在抢同一个池           │
│       （主机也是 UMA，但带宽是它的 5 倍以上，且没有电池/基带开销）            │
│    ② 带宽的**能耗成本**直接进热预算：搬一次数据的能耗远高于算一次             │
│       → 手机省带宽是为了省**电**，主机省带宽是为了省**时间**                  │
│    ③ 片上容量小：几百 KB 的 GMEM 撑不住稍胖的附件，溢出即退化               │
└──────────────────────────────────────────────────────────────────────────┘
```

⚠️ **这个指标有明确局限**：它忽略了分箱/resolve 的额外流量、DRAM 实际效率（通常只有标称的 50~70%）、以及"系统占用掉的那部分带宽"。**当量级参考用，不要当精确预算。**

## 5. 相同点：两端共享的十条底层规律

这一节是本篇的核心之一——**很多你以为"移动端特有"的做法，主机端其实也在做，只是动因不同**。

| # | 共享规律 | 移动端形态 | 主机/PC 形态 | 共同的优化动作 |
|---|---------|-----------|-------------|--------------|
| 1 | **都做分块光栅化** | TBR / TBDR / FlexRender | NVIDIA 自 Maxwell 起也是 **tile-based immediate-mode 光栅化**（大 tile 分给多个光栅引擎，16×16 Z-Cull，8×8 精光栅，tile buffer 放在 L2） | 减少 overdraw、按屏幕局部性组织绘制顺序 |
| 2 | **都靠片上存储省带宽** | GMEM / Tile Memory（几百 KB~几 MB） | 大 L2（RTX 50 系 24~96 MB）充当 tile buffer | 让数据在片上被消费；减少跨 pass 的全屏往返 |
| 3 | **都用固定功能压缩** | AFBC / UBWC / **AFRC** | DCC、BC7/ASTC 纹理压缩 | 打开压缩、避免禁用压缩的 image 标志 |
| 4 | **都用早期深度剔除** | Early-Z、Mali 的 HSR、Adreno 的 LRZ | Z-Cull（16×16 低分辨率 Z）、Hierarchical Z | 避免破坏 Early-Z 的写法（discard、改深度、片元写深度） |
| 5 | **都在用时间超分** | ASR / NSS / GSR / MetalFX | Switch 2 用 **DLSS**（Tensor Core）、PS5 Pro 用 **PSSR**、其他主机用 FSR 类 | 提供运动矢量 + 深度；低分辨率渲染 → 重建 |
| 6 | **都用动态分辨率（DRS）** | 纹理/分辨率按热预算动态下调 | DRS 保帧率（主机上极常见） | 把分辨率做成可控旋钮，而不是固定值 |
| 7 | **瓶颈都是带宽（而非纯算力）** | 每像素预算 ≈ 41 GB/s/Mpix | 4K 下 54~216 GB/s/Mpix 仍是首要约束 | 用同一条判断规则：ALU 利用率低 + stall 高 = 带宽问题 |
| 8 | **都在做 draw call 合并 / GPU 驱动管线** | MDI、indirect draw、mesh shader、Bindless | 同样（XSX 支持 mesh shader / VRS tier 2 / Sampler Feedback Streaming） | 合批、实例化、indirect、减少 CPU 提交开销 |
| 9 | **都要求帧时间一致性** | 抖动会导致温控介入 → 更抖（正反馈） | 抖动直接被判定为"不合格"（认证会卡） | 锁帧上限、frame pacing、提前降载 |
| 10 | **方法论相同** | Profiler（Snapdragon Profiler / Arm Performance Studio）+ 抓帧（RenderDoc） | 平台专用工具（Razor / PIX）+ Nsight / RenderDoc | 抓帧 → 找瓶颈 → 归因 → 验证，同一条流水线 |

⚠️ **关于第 1 条的重要限定**：NVIDIA 的 tile-based 光栅化与移动端 TBR **不是同一个东西**。据 Realworldtech / David Kanter 的分析与后续讨论，它的分块**只在单个 draw call 内部生效**，draw call 之间仍然严格串行，因此**无法像移动端那样把整帧的中间结果留在片上跨 pass 消费**——它主要改善光栅化阶段的内存局部性。这个差别正是"片上闭环边界不同"，也是为什么 §6 里没有把它归入 UMA 式的"架构同源"。

## 6. 不同点：八个结构性差异

### 6.1 硬件谱系：1~2 个 SKU vs 数千款设备

| | 主机 | 移动端 |
|--|------|--------|
| SKU 数量 | 1~2 个（PS5 / PS5 Pro；XSX / XSS） | 数千款（SoC × 驱动版本 × 散热设计） |
| 驱动 | 随系统统一更新，行为一致 | 多厂商、多版本，同一芯片行为可不同 |
| 策略 | **可以手工调到极致**（针对固定硬件做特化） | **必须保守 + 运行时降级 + 能力查询** |

**驱动成熟度差异的量化例证**：Snapdragon 8 Gen 2 上市后，一次图形驱动/固件更新使某光追基准从 **18.6 fps 提升到 27.1 fps（+45%）**——同一颗芯片、同一个测试。这在主机上几乎不可能发生（驱动行为统一且稳定）。

→ **实践结论**：移动端不能依赖"某条路径在 A 机器上快"就当作通用最优解；必须准备**运行时能力查询 + 降级路径**（与第 06 篇 decision tree 一致）。

### 6.2 持续 vs 峰值：完全不同的设计目标

```
┌──────────────────────────────────────────────────────────────────────────┐
│  同一份工作负载下，两端的"性能曲线"形状不同                                 │
│                                                                          │
│  主机 / PC                                   手机                         │
│   帧率                                        帧率                        │
│    ▲                                          ▲                          │
│    │  ██████████████████   ← 一条直线          │  ██▌                       │
│    │  ██████████████████                     │  ████▌                     │
│    │  ██████████████████                     │  ███████▌                  │
│    │  ██████████████████                     │  ██████████▌               │
│    └──────────────────────► 时间              │  ████████████▌  ← 稳态      │
│       （几乎不变，热预算固定）                 └──────────────────────► 时间  │
│                                                  （前 1~5 分钟是"假象"）    │
│                                                                          │
│  → 手机评测只说"平均帧率"是无意义的                                          │
│  → 必须给出：首分钟 / 第 10 分钟 / 第 30 分钟的帧率与帧时间曲线               │
└──────────────────────────────────────────────────────────────────────────┘
```

**验证方法**：用压力测试模式（如 3DMark 的 20 次连续循环）观察性能衰减曲线。压力测试中，几款旗舰在光追负载下的性能衰减差异明显——有的芯片跑几轮就掉队，而"峰值第一"的芯片未必"稳态第一"。**移动端应选稳态最优的方案，而不是峰值最优的。**

### 6.3 热预算形态：固定 vs 随环境漂移

| | 主机 | 移动端 |
|--|------|--------|
| 环境温度影响 | 小（机内有风道，环境温度波动几个度） | **大**（户外 35℃+ 直射，性能可掉一档画质） |
| 握持影响 | 无 | 有（手部覆盖 → 表面散热被阻断） |
| 充电影响 | 无 | 有（充电 + 游戏 = 双重热源，常触发限流） |
| 结论 | 热预算可当作常数 | **热预算是一个随机变量，必须设计"自适应"** |

### 6.4 CPU 拓扑：异构 vs 同构

| | 主机 | 移动端 |
|--|------|--------|
| 核心构成 | 8 核**同构**（Zen 2，频率固定或小幅动态） | 2 大 + 6 中（或 1+3+4），**异构** |
| 调度 | 简单，可直接吃满 8 核 | EAS 能量感知调度 + 热驱动的迁移 |
| 省电策略 | 主要靠降频率 | 靠"把活赶到小核"（效果大但会影响性能一致性） |
| 优化要点 | 并行度拉满，把 8 核喂饱 | 关键路径别落到小核；避免频繁唤醒（唤醒=功耗）；线程数不是越多越好 |

⚠️ **移动端常见的错误优化**：为了省电而"减少线程数"。这在 CPU 受限时会直接掉帧；正确做法是**让系统的 EAS 去做频率与核心选择**，通过 ADPF 的 PerformanceHint API 把"我这一帧要多少时间"告诉系统（见 §9）。

### 6.5 精度策略：FP16 是默认选择

| | 主机 / PC | 移动端 |
|--|----------|--------|
| 默认精度 | FP32 | **FP16（mediump）优先** |
| 原因 | 算力与精度都充足 | FP16 吞吐通常是 FP32 的 2 倍，且**带宽减半**（省电） |
| 实践 | 直接把桌面 shader 移植过来 | **必须审计精度**：位置、深度、时间、法线编码等需要 FP32 的地方要显式提升 |

⚠️ 把桌面 shader 原样搬到移动端（全程 FP32）是**白白多花一倍电**的典型失误。反过来，在移动端调好的 FP16 shader 搬到主机也没有收益（主机不在乎这点功耗）。

### 6.6 光追：都有硬件，但"加速的层级"不同

| | 主机 / PC | 移动端 |
|--|----------|--------|
| 硬件单元 | RT Core（RDNA 2 RT / NVIDIA RT Core） | Arm **RTU** / Adreno / Samsung Xclipse |
| 加速范围 | 包含 **BVH 遍历** | 加速**盒子与三角形包围盒测试**，但**不加速 BVH 遍历** |
| 面积与功耗 | 大 | 极小（Arm RTU 占 shader core 面积 **< 4%**，Arm 称相对无硬件加速提升 > 300%） |
| 落地方式 | 可以较激进地用 RT 做 GI/反射 | **混合渲染**（光栅化为主 + 局部 RT）+ 低分辨率 + 超分 |
| 现实约束 | 可承受 | 光追负载下**持续性能衰减明显**（压力测试中普遍下滑） |

→ 移动端做光追的正确姿势：**把 RT 用在"最能看出效果、且最便宜"的地方**（反射、阴影接触），并接受"必须靠超分补回分辨率"。

### 6.7 平台约束：认证与 API 矩阵

| | 主机 | 移动端 |
|--|------|--------|
| 认证 | 有强制技术认证（Sony TRC / Microsoft XR / 各家 lotcheck），帧率与稳定性会被卡 | 商店层面通常不强制帧率；但**用户评价与耗电投诉**是硬约束 |
| 图形 API | 固定一套（且版本冻结） | Vulkan / OpenGL ES / Metal 多后端 + 多个 API 版本 |
| 系统版本矩阵 | 系统随机器更新，统一 | Android 版本 × 厂商 ROM × 驱动版本 |
| shader 变体 | 可离线全量编译 | 需要处理变体爆炸与首次编译卡顿 |
| 结论 | 可以"针对固定栈特化" | 必须"面向最小公分母设计 + 向上特化" |

### 6.8 优化目标函数：能效比 vs 性能上限

```
┌──────────────────────────────────────────────────────────────────────────┐
│  同一个"减少 20% 工作量"的优化，在两端意义完全不同                          │
│                                                                          │
│  移动端：省下 20% 的功耗 → 温控来得更晚 → 稳态帧率更高 → 体验更好            │
│          指标：frame / Joule（每焦耳多少帧）                                │
│                                                                          │
│  主机：省下 20% 的 GPU 时间 → 换成更高分辨率/更多特效/更稳的帧率             │
│        指标：frame / second（帧率）或 pixels / second                      │
│        省电只是"风扇安静一点"的副产品                                       │
└──────────────────────────────────────────────────────────────────────────┘
```

**这条差异是整篇文档的落点**：跨平台移植时，很多"优化"在另一端是**没有收益的**（甚至有害，见 §10）。

## 7. ⚠️ 对流传资料的六处勘误

| # | 流传说法 | 准确表述 |
|---|---------|---------|
| 1 | 「UMA 是移动端的特性，主机/PC 用独立显存」 | ❌ **主机也是 UMA**：PS5 与 Xbox Series X 都是 16 GB GDDR6 统一池（CPU/GPU 共享）。真正分离式的是 **PC 独显**。移动端 UMA 的特殊性在于**带宽低一个数量级 + 需与 ISP/基带/显示共享** |
| 2 | 「移动端无专用光追单元，或能力较弱」 | ⚠️ 前半句已过期。Arm（Immortalis-G715 起，RTU）、Adreno、Samsung Xclipse 都已有硬件 RT。准确说法是：**有硬件加速，但不加速 BVH 遍历，因此效率与可承受的光追复杂度远低于主机** |
| 3 | 「移动端普遍采用 TBDR」 | ⚠️ 三种并存：**TBR / TBDR / FlexRender**。Adreno 有 Direct Mode 可选，TBDR 的经典实现是 Imagination（含 pixel-perfect HSR）。术语不能混（见本系列第 00、01 篇） |
| 4 | 「主机极少因温度降频，几乎无此烦恼」 | ⚠️ 基本成立但需限定：主机**按持续性能设计**、热预算固定可预期；通风不良/积灰/高温环境仍会降频。差别是"可预期性"，不是"有没有" |
| 5 | 「降频在 55℃ 触发」 | ⚠️ 不存在单一阈值。真实是**多区域多级**：SoC 结温（95~105℃ 量级）、机身表面温度（主流旗舰控制在 ~45℃ 以下，偏性能机型可放宽到 50℃+）、电池温度（40~45℃ 量级）。且**各家策略差异极大** |
| 6 | 「移动端带宽仅为 PC 的 1/10」 | ⚠️ 取决于对比对象（旗舰手机 84.8 GB/s vs RTX 5080 的 960 GB/s ≈ 1/11；vs RTX 5060 的 448 GB/s ≈ 1/5）。**更该看"每像素可用带宽"**（§4.2），手机 1080p 下约为主机 4K 的 3/4；真正的差距来自"带宽被共享 + 带宽的能耗成本进热预算 + 片上容量小" |

## 8. 优化手段映射表：同一目标，两端做法

| 优化目标 | 移动端做法（动因：省电 + 稳帧） | 主机做法（动因：换画质/帧率） | 共同的底层原理 |
|---------|---------------------------|--------------------------|--------------|
| **降带宽** | AFBC/UBWC/AFRC 压缩、tile 内闭环、FP16、降内部渲染分辨率 | DCC 压缩、靠大 L2、BC7/ASTC、提高压缩率 | 数据尽量在片上被消费 |
| **降填充率** | 降内部渲染分辨率 + 超分、砍后处理链、简化透明排序 | DRS + 时间重建、减少半透明 overdraw | 每像素成本 × 像素数 |
| **降 CPU** | MDI/实例化、减少线程唤醒（省电）、避免小核承接关键路径 | Job 系统拉满 8 核、GPU-driven 管线、减少提交次数 | 提交开销与并行度 |
| **降功耗** | 帧率档位、ADPF 自适应性能、关灯/降亮度、限制 UI 刷新 | 基本不作为首要目标（只影响噪音与电费） | 工作量 ∝ 能耗 |
| **稳帧** | 锁帧上限 + 提前降载 + 热滞回策略 | 锁帧 + frame pacing + DRS | 帧时间一致性比均值重要 |
| **减少 RT 成本** | 局部/混合 RT、低分辨率 + 超分 + 降噪 | 全场景 RT/GI、RT Core 堆叠 | 光线数 × 每条光线成本 |

## 9. 移动端独有的能力：可编程热管理

这是主机端**没有对应物**的一块——因为主机不需要。移动端开发者可以**主动参与热管理**，用"降画质"换取"稳定的帧时间"。

### 9.1 平台提供的接口

| 平台 | 接口 | 说明 |
|------|------|------|
| **Android** | `Window.setSustainedPerformanceMode()` + `PowerManager.isSustainedPerformanceModeSupported()` | **持续性能模式**（Android 7.0 引入）。OEM 通过电源 HAL 的 `POWER_HINT_SUSTAINED_PERFORMANCE` 提示把 CPU/GPU 最高频率**锁在可持续的最高档**。AOSP 文档明确指出：这会**降低帧率**，但由于可持续，在这个模式下仍然是首选 |
| **Android** | `Process.getExclusiveCores()` | CDD 建议为前台应用提供**独占核心**（exclusive core），用于 CPU 密集场景（游戏、相机） |
| **Android（ADPF）** | `PowerManager.getThermalHeadroom()` | **热余量预测**（Android 11 / API 30+）：在过热之前就能提前调整负载，而不是等降频发生 |
| **Android（ADPF）** | `PerformanceHintManager` | **性能提示**（Android 12 / API 31+）：把工作负载与"这一帧实际用了多久"告诉系统，让调度与加速更精准 |
| **Android（ADPF）** | `GameMode` / `GameState` | 用户意图（性能/省电）+ 游戏状态（加载/游玩），系统据此做分辨率缩放与 FPS 覆写 |
| **iOS** | `ProcessInfo.thermalState` | nominal / fair / serious / critical 四档状态 + 低电量模式 |
| **引擎适配** | Unity **Adaptive Performance** Provider（5.0.0+）、Unreal 的 ADPF 插件、Cocos（3.8.3+） | 直接消费上述 API，不必自己写 JNI/OC 桥 |

**厂商侧的自测收益（供参考，非保证）**：UNISOC 集成 ADPF 后，其测试游戏中画质设定下帧率 **+28.1%** 且功耗 **-3.7%**；高画质下帧率 **+50.1%**、功耗仅 **+3.1%**。⚠️ 这是**厂商自测数据**，条件不明，只能说明"主动告知系统负载"这件事本身有可观收益，不能当你的项目预期。

### 9.2 建议的热管理状态机（带滞回）

```
┌──────────────────────────────────────────────────────────────────────────┐
│  按 thermal headroom 分档降画质（示例，阈值需按项目实测调）                  │
│                                                                          │
│  headroom > 0.7   → L0：满档画质、目标帧率上限 = 最高档                     │
│  0.4 ~ 0.7        → L1：降内部渲染分辨率（超分补偿），关高成本后处理          │
│  0.2 ~ 0.4        → L2：降阴影/粒子/局部 RT，帧率上限下调                    │
│  < 0.2            → L3：最低画质档 + 降目标帧率（60→30 往往比"一直 45"更稳）  │
│                                                                          │
│  ⚠️ 三条实现要点                                                          │
│   ① 必须带**滞回**：升级档位需要连续 N 秒高于上一档阈值                       │
│      否则会在档位间反复横跳，比一直低画质更难受                              │
│   ② 降级要**快**，升级要**慢**（降级慢一拍 = 用户先看到掉帧）                 │
│   ③ 档位切换的视觉变化要可控：优先调分辨率（超分能掩盖），                   │
│      最后才动"一眼可见"的东西（阴影、绘制距离、粒子数量）                     │
└──────────────────────────────────────────────────────────────────────────┘
```

## 10. 跨平台移植的两个方向性错误

| 方向 | 错误做法 | 后果 |
|------|---------|------|
| **主机经验 → 移动端** | 全屏后处理链（Bloom+DoF+SSAO+SSR 逐一全屏往返） | 带宽爆炸 → 可能触发 Direct Mode（见第 03、05 篇） |
| | 默认 FP32 的 shader 与高精度 G-Buffer | 白白多花一倍带宽与电，稳态帧率下降 |
| | 大量"渲染到贴图" | 每次都是 Resolve 成本；移动端尤其贵 |
| | 激进的实时光追 | 持续性能快速衰减，长时间游玩崩坏 |
| | 假设性能稳定，不做降级路径 | 温控一来全盘崩，且不同设备差异巨大 |
| **移动端经验 → 主机** | 过度精简 G-Buffer / 材质（怕带宽） | 浪费主机带宽与算力，画面吃亏 |
| | 拒绝 FP32、拒绝 RT | 直接放弃主机的主要画质优势 |
| | 把主机当"省电设备"，为功耗砍效果 | 主机的功耗约束与移动端完全不同量级 |
| | 大量小 draw call 靠"合批"解决 | 主机上更该用 GPU-driven 管线与更激进的剔除 |
| | 用移动端式的保守精度/保守算法 | 白白浪费算力预算 |

**一句话判据**：**同一条优化，先问它省的是"能效"还是"时间"**。省时间的优化两端都受益；纯省能效的优化在主机端基本无收益。

## 11. 工程落地建议：预算驱动，而非平台驱动

### 11.1 建立一份"预算表"，而不是一堆 `if (platform)`

```
┌──────────────────────────────────────────────────────────────────────────┐
│  每帧预算表（建议作为工程规范的一部分，随项目维护）                           │
│                                                                          │
│  · 带宽：MB / frame，以及对应的 GB/s（按目标帧率换算）                       │
│  · 功耗：持续 W（仅移动端有意义，但统一字段便于对比）                          │
│  · GPU：ms / frame（按 pass 拆分）                                         │
│  · CPU：ms / frame（主线程 / 渲染线程 / RHI 提交）                            │
│  · 帧时间：均值 / P95 / P99（⚠️ P99 比均值更能反映体验）                     │
│  · 内部渲染分辨率与超分档位                                                  │
│  · 质量档位表：L0/L1/L2/L3（每档明确列出"动哪些旋钮"）                        │
│  · 热预算：从冷机到稳态的允许性能衰减比例（移动端专属）                        │
└──────────────────────────────────────────────────────────────────────────┘
```

**为什么用预算而不是平台判断**：掌机、低端 PC、云游戏、平板让"平台 → 性能"的映射彻底失效。**用能力与预算驱动质量档位**，代码只需要一条降级阶梯。

### 11.2 三个必须测的场景（移动端）

| 场景 | 目的 | 判据 |
|------|------|------|
| **冷机首分钟** | 峰值性能与"最好看的样子" | 只作参考，不代表体验 |
| **热稳态（第 10~30 分钟）** | 真实体验 | **这才是要达标的目标** |
| **高温环境（35℃+）** | 边界条件 | 是否会掉到不可玩 |

⚠️ **测试必须记录环境温度与设备表面温度**，否则数据不可比（§6.3）。

### 11.3 统一的度量口径

| 指标 | 说明 |
|------|------|
| **frame / Joule** | 移动端最重要的单一指标（能效比） |
| **帧时间 P99** | 反映抖动，比平均帧率更能预测差评 |
| **MB / frame** | 带宽预算的实际占用，可静态估算 + 动态测量 |
| **单位时间内的降档次数** | 反映热管理策略是否稳定（理想是"降到某一档后不再变"） |

## 12. 术语表

| 术语 | 全称 / 含义 | 备注 |
|------|-----------|------|
| **TDP / TGP** | Thermal Design Power / Total Graphics Power | 散热设计功率；CPU 常用 TDP，GPU 常用 TGP |
| **PL1 / PL2** | Power Limit 1 / 2（Intel 平台） | 持续功率墙 / 短时功率墙 |
| **TjMax** | Junction Max Temperature | 结温上限，超过即降频 |
| **DVFS** | Dynamic Voltage and Frequency Scaling | 动态电压频率调节，是所有降频/升频的基础机制 |
| **Skin Temperature** | 机身表面温度 | 移动端最"硬"的约束（用户体感），常比结温更早触发限制 |
| **SEU** | Skin Enable/Threshold 类机制（Android 侧的热区概念） | 各厂商实现不同，以设备实测为准 |
| **EAS** | Energy Aware Scheduling | Linux/Android 的能量感知调度器 |
| **ADPF** | Android Dynamic Performance Framework | Android 的性能提示 + 热 API + 游戏模式框架 |
| **Sustained Performance Mode** | 持续性能模式 | Android 7.0 起，把频率锁在可持续档，牺牲峰值换稳定 |
| **DRS** | Dynamic Resolution Scaling | 动态分辨率，两端都在用 |
| **UMA** | Unified Memory Architecture | 统一内存；**主机也是 UMA**，PC 独显是分离式 |
| **AFBC / UBWC / AFRC** | Arm Frame Buffer Compression / Qualcomm Universal Bandwidth Compression / Arm Fixed Rate Compression | 移动端固定功能帧缓冲压缩 |
| **DCC** | Delta Color Compression（AMD）/ 泛指显存压缩 | 桌面端对应机制 |
| **PSSR** | PlayStation Spectral Super Resolution | PS5 Pro 的 ML 超分 |
| **NSS / NFRU** | Arm Neural Super Sampling / Neural Frame Rate Upscaling | Arm 神经超分 / 神经插帧 |
| **frame / Joule** | 每焦耳帧数 | 移动端能效比的正确度量 |

## 13. 小结

| 要点 | 说明 |
|------|------|
| **决定分类的是能量预算，不是设备形态** | 手机 → 掌机 → 主机 → 桌面是一条连续谱系，掌机是中间态 |
| **移动端的三堵墙源于"被动散热 + 无市电"** | 主机的三道闸是"设计包线"，性质是"被削峰" vs "设定上限" |
| **功耗与性能是超线性的** | 陡区近似 `P ∝ f³`，所以移动端目标函数是**能效比**，不是帧率 |
| **不存在单一降频阈值** | 结温、表面温度、电池温度多区域多级；各家策略差异极大；环境温度直接改变结论 |
| **手机带宽窘境≠总量少** | 每像素预算（1080p 下 40.9 GB/s/Mpix）约为 PS5 4K 的 3/4；真正的痛点是**共享**、**带宽的能耗成本进热预算**、**片上容量小** |
| **十条底层规律两端共享** | 分块光栅化、片上存储、固定功能压缩、早期 Z、时间超分、DRS、带宽瓶颈、GPU-driven、帧时间一致性、同一套方法论 |
| **但"分块"的边界不同** | NVIDIA 自 Maxwell 起是 tile-based **immediate** 光栅化，只在单个 draw call 内生效，**不能跨 pass 保持片上闭环** |
| **八个结构性差异** | SKU 数量/驱动成熟度、持续 vs 峰值、热预算是否漂移、CPU 同构 vs 异构、FP16 策略、RT 加速层级、认证与 API 矩阵、目标函数 |
| **UMA 不是移动端特性** | 主机也是 UMA；PC 独显才是分离式。移动端的特殊性是"低带宽 + 共享对象多" |
| **移动端独有可编程热管理** | Sustained Performance Mode、独占核心、ADPF（热余量 + 性能提示 + 游戏模式）、iOS thermalState；**主机端无对应物** |
| **热管理要带滞回** | 降级快、升级慢；优先调分辨率（可被超分掩盖），最后动一眼可见的效果 |
| **移植错误的判据** | 问"这条优化省的是**能效**还是**时间**"：省时间的两端都受益，纯省能效的主机端无收益 |
| **工程上做成预算驱动** | 用能力与预算决定质量档位，而不是 `if (platform)`；必测冷机/热稳态/高温三个场景 |
