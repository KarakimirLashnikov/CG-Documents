## 2. 结论速览表

### 2.1 A 组：分箱的必然性、粒度与位置

| # | 原文主张 | 判定 | 一句话修正 |
|---|---------|------|-----------|
| A1 | 移动端主流 TBR/TBDR（Adreno/Mali/PowerVR）分箱是硬件固定管线中**不可跳过**的物理步骤 | ❌ | 对 **Adreno 不成立**：FlexRender 支持 Direct / Binned / Binned Direct 三档，驱动逐 surface 动态选择，Direct 是正常模式 |
| A2 | 唯一例外是**驱动强制**进入 Direct Mode，是「退化」 | ❌ | Direct Mode 不是退化，是驱动启发式的正式选项。官方明示触发场景（VS 纹理采样多、顶点少、用 tessellation/GS） |
| A3 | 进入 Direct Mode 意味着几何体仍需被硬件前端处理，但放弃 Tile 优化 | 🟡 | Adreno 还有第三种 **Binned Direct Mode**：先跑可见性 Pass 剔除背面，再切 Direct 渲染 |
| A4 | 驱动「放弃优化策略」，分箱阶段依然存在 | 🟠 | Direct Mode 下**不生成 bin**，Binning Pass 不存在；但顶点/图元前端仍在工作 |
| A5 | 分的是**图元**，不关心顶点本身 | 🟠 | 分类的对象是图元，但分箱阶段**必须运行位置着色（position-only VS）**，因此极度关心顶点 |
| A6 | 硬件为每个三角形算屏幕空间包围盒，看与哪些 Tile 相交 | ✅ | 简化但正确。实际实现常用层次化/更精确的覆盖测试 |
| A7 | 不能分顶点，因为跨 Tile 三角形的顶点会被两个 Tile 共享，分给 A 则 B 找不到几何 | 🟡 | 结论对，理由不准。真因是：光栅化需要完整的图元拓扑与属性，顶点级索引无法表达「这个面覆盖哪些块」 |
| A8 | 分箱发生在**顶点着色器之后**、光栅化之前 | 🟠 | 应为：**位置着色之后**、**完整（varying）着色之前**、光栅化之前 |
| A9 | 资料给出的 7 步流水线顺序 | 🟠 | 基本顺序对，但**漏掉「完整 VS 在分箱之后」这一关键环节** |

### 2.2 B 组：延迟渲染与 GMEM

| # | 原文主张 | 判定 | 一句话修正 |
|---|---------|------|-----------|
| B1 | 延迟渲染在移动端 TBR 下是「**天作之合**」 | 🟠 | 过强。TBDR 把 deferred 的带宽劣势从「致命」降为「可接受」；UE 移动端默认仍是 Forward，Oculus 官方明确劝退移动 VR 用 deferred |
| B2 | G-Buffer 直接写入 GMEM，完全不碰系统内存 | ✅ | 前提是 G-Buffer 总量 + MSAA 未超出片上容量，且 load/store op 设置正确 |
| B3 | 光照 Pass 通过 Input Attachment 从 GMEM 读取 G-Buffer | ✅ | 正确，这是 framebuffer-local 依赖的经典用法 |
| B4 | TBDR（PowerVR）有硬件 HSR；**Adreno/Mali 只在 Tile 内做 Early-Z** | 🟡 | ARM 官方文档明确提到 Mali 有 **hidden surface removal**。三家都有硬件剔除，只是强度不同：PowerVR HSR（pixel-perfect、顺序无关）> Adreno LRZ > Mali FPK |
| B5 | 「只有最终真正可见的像素才会被写入 G-Buffer，才会进行光照计算」 | 🟠 | 只在 **PowerVR 真 TBDR** 上成立。Adreno/Mali 的 LRZ/FPK 是近似剔除，仍有 overdraw |
| B6 | 可「精确剔除掉那些没有光照的 Tile」 | 🟠 | 硬件不会按「有没有光照」筛 tile；光照在 tile 内仍逐像素求值，剔除靠 CPU/Compute 端的光源分簇与包围体 |
| B7 | Vulkan 的 Render Pass / Subpass「简直是为移动端量身定制」 | ✅ | 动机正确（Khronos 明确承认受 tile-based 架构影响）。**但 Vulkan 1.4 起 `VkRenderPass` 已被标记为 deprecated** |
| B8 | 两个 Subpass 同 Render Pass + `VK_DEPENDENCY_BY_REGION_BIT` → 数据在 GMEM 内流转，**绝对不会**触发 Direct Mode | 🟡 | BY_REGION 是必要条件但非充分条件。Direct Mode 是**逐 surface 的驱动决策**，不因 subpass 依赖而免除 |
| B9 | 延迟渲染「大大减轻了 Binning Pass 的压力」 | 🟠 | 存疑。deferred 的材质复杂度下降确实减少 VS 负载，但 G-Buffer 增大了每像素负担；而且 binning 压力主要来自图元数量与 VS 复杂度，与光照阶段无关 |
| B10 | 移动端 GMEM 很小（**通常几百 KB 到几 MB**） | 🟡 | 数字来源需谨慎。已知：Adreno 615 = 512 KB、Adreno 630 = 1 MB、Adreno X1 = 3 MB。**Mali 的 Tile Memory 只有每核 16 KB 量级**，差距达一到两个数量级 |
| B11 | 开 4x MSAA → G-Buffer 数据量 ×4 → 撑爆 GMEM → Direct Mode | 🟠 | 机制不对。MSAA 确实增大片上需求，但真正原因是 **deferred 与 MSAA 语义冲突**（需要逐 sample 着色并 resolve），且 MSAA 增大会让驱动把 bin 调小 |
| B12 | 延迟渲染对 MSAA 天生不友好，应改用 FXAA / TAA | ✅ | 结论正确。UE 官方理由：G-Buffer 空间不足，且光照 Pass 必须逐 sample 着色而非逐像素 |
| B13 | G-Buffer 附件必须设 `storeOp = DONT_CARE` | ✅ | 正确。补充：可用 `VK_ATTACHMENT_STORE_OP_NONE_QCOM` 更精确地表达「绝不写回」 |
| B14 | 最终光照结果与透明物体仍需读写系统内存，带宽依然是死穴 | ✅ | 正确 |

| # | 原文主张 | 判定 | 一句话修正 |

| C1 | 光照 Pass 使用片上 G-Buffer 数据，**完全针对单个 Tile**，不是整个 RT | ✅ | 正确 |

## 3. 关键错误的深度剖析

以下四个问题最容易被错误描述带偏，单独展开。

### 3.1 错误一：分箱在「完整顶点着色器之后」❌

#### 原文说法

```
顶点着色器 → 图元装配与裁剪 → 屏幕映射 → 【分箱】 → 光栅化 → 像素着色
```

这给人的印象是：顶点着色器**只跑一次**，跑完之后才开始分箱。

#### 硬件实际顺序（以 ARM Mali IDVS 官方流水线图为准）

```
Indices ──▶ ┌──────────────────┐
            │ Index Reader     │
            └────────┬─────────┘
                     ▼
            ┌──────────────────┐
            │ Position Cache   │  ← 后变换顶点缓存（复用已算过的位置）
            │ Fetch            │
            └────────┬─────────┘
                     ▼
            ┌──────────────────┐
            │ Position Shading │  ← 只算 gl_Position（clip space）
            └────────┬─────────┘
                     ▼
            ┌──────────────────┐
            │ Primitive        │
            │ Assembly         │
            └────────┬─────────┘
                     ▼
            ┌──────────────────┐
            │ Culling          │  ← 背面剔除 / 视锥剔除 / 微三角形剔除
            └────────┬─────────┘
                     ▼
            ┌──────────────────┐
            │ Culling and      │  ← ★ 这就是分箱（Binning / Tiling）
            │ Tiling           │     产出 Tile List
            └────────┬─────────┘
                     ▼
                 Tile List ──────────┐
                                     ▼
                        ┌────────────────────┐
                        │ Varying Shading    │  ← ★ 完整顶点着色器在这里！
                        │ (if visible)       │     只对存活下来的可见图元执行
                        └────────────────────┘
```

**关键结论**：

| 阶段 | 跑什么着色器 | 服务对象 |
|------|------------|---------|
| 分箱之前 | **Position Shader**（只算 `gl_Position`） | 全场景所有顶点 |
| 分箱之后 | **Varying Shader**（算 UV、法线、世界坐标……） | **只对通过剔除的可见图元** |

ARM 官方文档原文（Mali Offline Compiler User Guide, §2.7.4）：

> "In the IDVS pipeline, vertex shaders are compiled into two binaries: A **position shader**, which computes only the position output. A **varying shader**, which computes the remaining non-position outputs. The position shader runs for every vertex, but the varying shader **only runs for vertices that are part of a visible primitive that survives culling**."

#### 为什么这个区别至关重要

这个顺序**直接决定了移动端最重要的一条优化**：

```
┌────────────────────────────────────────────────────────────────────┐
│  优化 1：把位置属性与非位置属性拆成两个独立的顶点缓冲（Split Stream）  │
│                                                                    │
│  ❌ 交错布局（Interleaved）                                         │
│     [X Y Z | U V | Nx Ny Nz][X Y Z | U V | Nx Ny Nz]...            │
│     → 分箱阶段只需 Position，却要为每个顶点拉入整条 32 字节           │
│     → 无效带宽被浪费                                                │
│                                                                    │
│  ✅ 分离布局（Split / Non-interleaved）                             │
│     Stream 0: [X Y Z][X Y Z][X Y Z]...       ← 分箱阶段只读这条      │
│     Stream 1: [U V Nx Ny Nz][U V Nx Ny Nz]... ← 只有可见顶点才读     │
└────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────┐
│  优化 2：绝不在计算 gl_Position 的路径上做纹理采样                    │
│                                                                    │
│  ❌ position = Texture2D(displacementMap, uv) * ...                │
│     → 顶点位移贴图的采样会被拖进 Position Shader                     │
│     → 分箱阶段被迫做纹理访问，Snapdragon Profiler 里直接体现为        │
│       「Excessive Binning Pass Time」                               │
│                                                                    │
│  ✅ 把与位置无关的重计算（复杂法线变换、动画混合）放到 varying 路径    │
└────────────────────────────────────────────────────────────────────┘
```

⚠️ **这正是 Snapdragon Profiler 建议里「简化顶点着色器」的真实含义**——它指的不是笼统地"让 VS 更快"，而是精确地指**降低 Position Shader 的复杂度**。

### 3.2 错误二：「Adreno 的 bin 是 16×16 或 32×32」❌

#### 事实

| 厂商 | Bin / Tile 尺寸 | 是否固定 |
|------|----------------|---------|
| ARM Mali | 名义 16×16，tiler 可用更大的 2 的幂尺寸容纳三角形 | 基本固定（可上调） |
| Imagination PowerVR | Series 6/7 = 32×32，SGX5 = 16×16 | 固定（按系列） |
| **Qualcomm Adreno** | **可变**，由驱动按 GMEM 容量 + 渲染目标格式（含 MSAA 采样数、附件精度）动态决定 | **不固定** |

Carmack 在 Meta 开发者博客中对此有明确表述：

> "Mali uses small, **fixed-size** tiles, and Adreno uses larger, **variable-sized** bins."

#### 为什么 Adreno 要可变

Adreno 的设计哲学是「**核心少、GMEM 巨大**」。既然 GMEM 能到 1 MB，那就没必要死守 16×16——驱动可以算出一块「刚好塞满 GMEM」的矩形区域，把 bin 开大，从而**减少 bin 总数、降低分箱元数据开销**。

但反过来，如果渲染目标是 HDR（`RGBA16F`）+ 4x MSAA，每像素成本翻好几倍，同一个 GMEM 就只能装下更小的 bin：

```
                          GMEM 容量固定（例如 1 MB）
                                    │
        ┌───────────────────────────┴───────────────────────────┐
        ▼                                                       ▼
  轻量 RT（RGBA8，无 MSAA）                            重量 RT（RGBA16F × 4 + 4x MSAA）
  每像素 ~8 字节                                       每像素 ~40+ 字节
        │                                                       │
        ▼                                                       ▼
  bin 可以开得很大                                       bin 被迫缩到很小
  （bin 总数少，分箱开销低）                             （bin 总数多，分箱开销高、Resolve 更碎）
```

#### 这对你的项目意味着什么

1. **不能用「先算出 bin 是多少、再推算 G-Buffer 预算」的思路**。bin 尺寸是驱动的**输出**，不是输入。
2. **降低 RT 格式开销会同时带来两重收益**：省带宽 + 让驱动能开更大的 bin。
3. 想查实际 bin 尺寸，用 `VK_QCOM_tile_properties`（见下）。

#### 查询实际 tile 尺寸的 Vulkan 路径

```cpp
// VK_QCOM_tile_properties（2022-07-11 注册，revision 1）
// ⚠️ 只能查询，不能设置

// 方式 A：使用 render pass 时，从 framebuffer 查询
uint32_t propCount = subpassCount;
std::vector<VkTilePropertiesQCOM> props(propCount,
    { VK_STRUCTURE_TYPE_TILE_PROPERTIES_QCOM });
vkGetFramebufferTilePropertiesQCOM(device, framebuffer, &propCount, props.data());
// props[i].tileSize.width / .height → 实际 tile 尺寸（像素）
// props[i].tileSize.depth         → tile 跨越的 slice 数
// props[i].apronSize              → apron 尺寸（配合 VK_QCOM_tile_shading）
// props[i].origin                 → 第一个 tile 的左上角

// 方式 B：使用 dynamic rendering 时
VkTilePropertiesQCOM props{ VK_STRUCTURE_TYPE_TILE_PROPERTIES_QCOM };
vkGetDynamicRenderingTilePropertiesQCOM(device, &renderingInfo, &props);
```

⚠️ **重要**：`VK_QCOM_tile_memory_heap` 引入后，tile 尺寸**不再是静态的**——同一应用的不同 render pass 可能因分配的 tile memory 不同而得到不同的 tile 属性。查询 tile 属性时必须通过 `VkTileMemorySizeInfoQCOM` 声明该 render pass 使用的 tile memory 字节数。

### 3.3 错误三：「分箱阶段绝对没有系统内存的读写」❌

#### 真实的主存流量账本

```
┌────────────────────────────────────────────────────────────────────────┐
│  移动端一帧的必然主存流量（按来源分）                                     │
├────────────────────────────────────────────────────────────────────────┤
│  ① 顶点数据读取        ← 分箱阶段读 Position Stream，渲染阶段读 Varying  │
│  ② Tile List /         ← ★ 分箱阶段的输出，写在系统内存                  │
│     Visibility Stream      Adreno 压缩后约 1 bit / 图元                  │
│     Parameter Buffer       PowerVR 存顶点数据 + 图元列表                 │
│  ③ 索引缓冲读取                                                         │
│  ④ 纹理采样                                                            │
│  ⑤ 最终 Resolve       ← 每个被写过的 RT 各一次（★ 移动端最大一项）        │
│  ⑥ 跨 Pass 的 RT 读写   ← 应尽力消除                                    │
└────────────────────────────────────────────────────────────────────────┘
```

Qualcomm 在 SIGGRAPH 2015 的架构演讲中明确说明了 Binning Pass 的产物：

> "The only output of Binning Pass is a **compressed 1 bit/primitive 'visibility stream'**. Avoids write bandwidth for transformed positions and overflow/management of transformed VBO."

**为什么这个纠正很重要**：

- 它解释了「**图元数量**为什么直接决定分箱成本」——每多一个图元，就要多写 1 bit 的可见性流 + 多一遍包围盒计算
- 它也说明了为什么 Adreno 选择「压缩可见性流」而不是「存变换后的顶点」——后者会带来巨大的写带宽
- 它暗示了一条优化路径：**减少图元数量**（LOD、合并网格、剔除、GPU-Driven 的间接绘制）

#### 关于「分箱阶段跑顶点着色器」的连带影响

分箱阶段的主存读流量 = **Position Stream 的读取量**。因此：

| 顶点缓冲布局 | 分箱阶段每顶点的读取量 | 评价 |
|-------------|---------------------|------|
| 交错：`[P(12) N(12) UV(8) T(8)]` = 40 字节 | 40 字节（cache line 拉入） | ❌ 60% 是浪费 |
| 分离：Stream0 = `[P(12)]` | 12 字节 | ✅ 最优 |
| 分离 + 量化：`[P as short4 @ 8 字节]` | 8 字节 | ✅✅ 移动端常见做法 |

### 3.4 错误四：「分箱是移动端的必然步骤」❌

#### FlexRender 的三种模式

Qualcomm 官方在 Snapdragon X Elite 架构深度拆解中给出 FlexRender 的完整定义：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Qualcomm® FlexRender™ Technology                                        │
│  "Dynamic switching between rendering modes for each surface"            │
│  "Managed by graphics driver using intelligent heuristics"               │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  ① Direct Mode（直接模式）                                                │
│     - PC GPU 的标准渲染范式，兼容性最好                                     │
│     - 【不生成 bin】、不做 Binning Pass                                    │
│                                                                          │
│  ② Binned Mode（分箱模式）                                                │
│     - 帧被划分为多个 bin，每个 bin 渲染进 GMEM                              │
│     - 数据移动最小化，能效最优                                              │
│                                                                          │
│  ③ Binned Direct Mode（分箱直接模式）                                      │
│     - 在与前一个渲染任务并行的情况下，先跑一个「分箱可见性 Pass」             │
│     - 目的：作为一次"免费的深度预通道"，剔除所有背面图元，                      │
│       使它们不进入光栅化                                                   │
│     - 剔除完成后切到 Direct Mode，此时负载已经减小                            │
│     - 兼具 Direct 与 Binned 两种模式的好处                                  │
└──────────────────────────────────────────────────────────────────────────┘
```

#### 官方明示的 Direct Mode 触发条件

Qualcomm《Adreno GPU on Mobile: Best Practices》原文：

> "The driver heuristics that determine when to run binned or direct mode are **not exposed to the developer**, but generally these scenarios trigger direct mode:
> - **High ratio of texture samples in vertex shaders to vertices**
> - **Small number of vertices and/or draws**
> - **Use of tessellation or geometry shaders**"

这直接修正了资料中「唯一例外是驱动强制」的说法——**Direct Mode 是三条明文启发式规则的正常结果**，而且规则 1 恰好就是「顶点着色器里的纹理采样太多」，也就是上一节讲的那个坑。

#### 对 Adreno 的准确表述

| 平台 | 分箱是否必然 |
|------|------------|
| **Qualcomm Adreno** | ❌ 不必然。逐 surface 由驱动在 Direct / Binned / Binned Direct 之间选择 |
| **ARM Mali** | ✅ 基本必然（TBR 是核心架构）。但 tiler 阶段会做筛选，且 tiler 与 shader core 流水重叠 |
| **Imagination PowerVR** | ✅ 必然（真 TBDR，HSR 依赖分箱产物） |
| **Apple GPU** | ✅ 必然（TBDR） |

⚠️ **实践含义**：在 Adreno 设备上调优时，「看到 Binning Pass 时间是 0」**不一定**说明优化成功——也可能是驱动根本没走分箱路径（因为你的 draw 太少）。反之，「Binning 时间占比高」也不能一概归因于「图元太多」，还要检查是否命中上述三条启发式。

## 4. 资料遗漏的重要内容（➕）

以下是原文未提及、但对移动端优化至关重要的事实。

### 4.1 并发分箱（Concurrent Binning）

```
┌───────────────────────────────────────────────────────────────────────┐
│  Adreno 的 GPU 前端同时存在两条管线：                                    │
│                                                                       │
│   ┌─────────────────────┐          ┌─────────────────────┐            │
│   │  Binning 专用前端    │  ←并行→  │  渲染前端 / Raster   │            │
│   │  （与渲染任务同步）   │          │  + Shader Cores     │            │
│   └─────────────────────┘          └─────────────────────┘            │
│                                                                       │
│  含义：Surface N+1 的分箱可以与 Surface N 的渲染并行进行                 │
│        → 分箱时间在理想情况下被「隐藏」，不累加到总帧时间                  │
└───────────────────────────────────────────────────────────────────────┘
```

Qualcomm 官方文档中关于 concurrent binning 的关键要点：

| 要点 | 说明 |
|------|------|
| 激活方式 | 无需额外步骤，但需注意不要主动破坏它 |
| 破坏条件 1 | 顺序 render pass 之间存在依赖，迫使分箱同步执行 |
| 破坏条件 2 | **在帧内对同一个 Z-buffer 反复 clear** —— clear 定义了依赖，从而阻止所有使用该 Z-buffer 的 pass 的并发分箱 |
| 最佳实践 | 跨多个 render pass 复用同一个 Z-buffer，不做 clear 也不做 invalidate |
| 备选方案 | 如果做不到复用，给每个 render pass 分配独立的 Z-buffer 也能允许并发分箱，但会增加内存和带宽开销 |
| VSYNC 相关 | 若应用受 VSYNC 限制且第一个 surface 承担了所有几何负载，可考虑在该 pass 之前安排一些独立工作，让它们并行 |

⚠️ **这一条极其重要且反直觉**：桌面端的经验是「Z-buffer 要 clear」，移动端却是「跨 pass 复用 Z-buffer 且不 clear 更有利于并发分箱」。但注意与「必须 clear/invalidate」的规则区分——那一条针对的是**颜色附件与最终需要写回的附件**。两条规则并不矛盾，只是作用对象不同。

### 4.2 显存压缩：UBWC / AFBC

| 厂商 | 技术 | 作用 |
|------|------|------|
| Qualcomm | **UBWC**（Universal Bandwidth Compression） | 无损/近无损压缩渲染目标与纹理，减少主存流量 |
| ARM | **AFBC**（Arm Frame Buffer Compression） | 同上，Mali 侧 |
| Imagination | PVR Frame Buffer Compression | 同上 |

⚠️ **实战坑点**：Qualcomm 官方明确指出 `VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT` 会「降低性能，且通常会**削弱或禁用 UBWC**」。类似地，不恰当的 image 创建标志、非对齐的分辨率、非常规格式都会关掉压缩。

**含义**：一张被禁用压缩的 1080p `RGBA8` 贴图，其真实带宽成本可能是启用压缩时的 2–4 倍。这类问题在 profiler 里表现为「带宽莫名很高」，但代码看起来完全正常。

### 4.3 Transaction Elimination（Mali）

Mali 的 tile 写回优化：计算当前 tile 的 CRC，与上一帧同位置 tile 的 CRC 比较，**相同则整个 tile 不写回主存**。

**收益场景**：UI 层、静态背景、静态阴影图——大面积帧间不变的区域。
**含义**：在 Mali 上，「减少帧间变化」本身就是一个带宽优化手段。

### 4.4 Load/Store Op 与「必须 clear」规则

资料完全没提这一条，但它是移动端**最容易踩、代价最大**的坑。

```
❌ 桌面惯性思维：跳过 clear 是优化
   → 因为我确定会把每个像素都画到，clear 是浪费

✅ 移动端事实：跳过 clear 是反向优化
   → 驱动不知道你会涂满，只能保守地把旧内容从主存读回 tile buffer
   → 一次主存读 ≫ 一次片上 clear

⚠️ 更糟的是不清除也不 invalidate：
   → 颜色附件要读回 + 深度附件也要读回 → 两项主存流量
```

Carmack 在 Meta 博客中的表述：

> "If you don't explicitly clear or invalidate all the render buffers you use, the driver has to be pessimistic and assume that you're expecting whatever you last drew to the buffer to remain there. ... **The clear will always be faster than the forced read from main memory.** The even-better solution is to use `glInvalidateFramebuffer()`, which does nothing but tell the driver that it can safely skip the read."

Vulkan 对应表：

| 场景 | 正确设置 |
|------|---------|
| 最终颜色附件，会全部覆盖 | `loadOp = DONT_CARE`，`storeOp = STORE` |
| 最终颜色附件，有部分未覆盖（如 UI 叠加） | `loadOp = LOAD` 或 `CLEAR`（不要留默认 LOAD） |
| G-Buffer / 深度 | `loadOp = DONT_CARE`，`storeOp = DONT_CARE` |
| 深度，本帧内后续 pass 还要读 | `loadOp = LOAD`，`storeOp = STORE`（此时应尽量合并 pass） |
| 明确不写回（Qualcomm） | `storeOp = VK_ATTACHMENT_STORE_OP_NONE_QCOM`（`VK_QCOM_render_pass_store_ops`） |

### 4.5 破坏 HSR / Early-Z 的 Shader 写法（Mali 官方检查清单）

ARM 官方 Mali Offline Compiler 会显式报告以下项目，它们**会直接削弱移动端的隐面剔除**：

| 检查项 | 后果 | 对策 |
|--------|------|------|
| `Uses late ZS test`（例如写入 `gl_FragDepth`） | **禁用 early ZS 测试与 HSR** | 避免写 `gl_FragDepth`；必要时用 `layout(early_fragment_tests)` |
| `Modifies coverage`（例如使用 `discard`） | 必须使用 late ZS update，降低同坐标后续片元的 early ZS 效率 | 减少 `discard`；用 alpha-to-coverage 或预乘 alpha 替代 |
| `Reads color buffer`（例如 `gl_LastFragColorARM` / framebuffer fetch） | 该 shader 被当作**透明**处理，**不能作为 HSR 的遮挡体** | 只在确实需要的材质上用 framebuffer fetch |
| `Has slow shading rate`（VRS 块尺寸 > 2×2） | 某些 Mali 上 VRS 会比预期更慢 | 用 `min()` 把 shading rate 限制在 2 以内（配合 per-draw 常量提供上界保证） |

⚠️ **这说明一件事**：在移动端，「着色器写得"正确"」和「着色器对硬件友好」是两码事。编译器能报出来的这些检查项，是免费的优化提示，应该纳入 CI。

### 4.6 Per-Tile Draw 的真实陷阱（Qualcomm 官方）

`VK_QCOM_tile_shading` 允许在 tile 内部执行 draw/dispatch，但官方有明确的适用边界：

| 规则 | 说明 |
|------|------|
| 适用场景 | **仅** GPU-Driven 渲染：per-tile compute 写间接缓冲 → per-tile `vkCmdDrawIndirect` 消费该缓冲 |
| CPU-Driven 场景 | **不推荐**。常规 draw 放进 per-tile block 很可能性能下降 |
| ⚠️ 关键陷阱 | **per-tile draw 不受 visibility pass 影响**——无论该 draw 在 tile 内是否光栅化，都会执行 |
| 必须做的事 | 每个 per-tile draw 只能包含覆盖当前 tile 的图元 |
| 必须用 BY_REGION | 漏掉 `VK_DEPENDENCY_BY_REGION_BIT` 很可能**禁用 tile_shading 并移除所有相关收益** |
| 配套要求 | 应同时启用 `VK_QCOM_tile_memory_heap` 与 `VK_QCOM_tile_shading`；只启用后者不被推荐 |

### 4.7 GMEM 可以被显式分配（2025 新能力）

`VK_QCOM_tile_memory_heap`（2025-03 首个 revision）允许把 `VkImage` / `VkBuffer` **直接分配到 tile memory heap**，并在多个 render pass 之间常驻：

```cpp
// 创建可放入 tile memory 的 image
VkImageCreateInfo ici{};
// ... 常规字段 ...
ici.usage |= VK_IMAGE_USAGE_TILE_MEMORY_BIT_QCOM;   // ★ 新增标志
vkCreateImage(device, &ici, nullptr, &img);

// 查询它需要多少 tile memory
VkTileMemoryRequirementsQCOM tmReqs{ VK_STRUCTURE_TYPE_TILE_MEMORY_REQUIREMENTS_QCOM };
VkMemoryRequirements2 mr2{ VK_STRUCTURE_TYPE_MEMORY_REQUIREMENTS_2 };
mr2.pNext = &tmReqs;
vkGetImageMemoryRequirements2(device, &mri2, &mr2);

if (tmReqs.size > 0) {
    // ✅ 支持，从 tile memory heap 分配并绑定
    VkMemoryAllocateInfo mai{ VK_STRUCTURE_TYPE_MEMORY_ALLOCATE_INFO };
    mai.allocationSize  = tmReqs.size;
    mai.memoryTypeIndex = FindTileMemoryType();   // heap 带 MEMORY_HEAP_TILE_MEMORY_BIT_QCOM
    vkAllocateMemory(device, &mai, nullptr, &tileMem);
    vkBindImageMemory(device, img, tileMem, 0);
} else {
    // ❌ 该格式不支持放入 tile memory，走回退路径
}

// 在命令缓冲中绑定 tile memory
VkTileMemoryBindInfoQCOM bindInfo{ VK_STRUCTURE_TYPE_TILE_MEMORY_BIND_INFO_QCOM };
bindInfo.memory = tileMem;
vkCmdBindTileMemoryQCOM(cmd, &bindInfo);
```

**为什么这条重要**：这正是「移动端延迟渲染」在当前 Vulkan 上的**最新正解**——用 `tile_memory_heap` 把 G-Buffer 显式钉在 GMEM 上并跨 pass 常驻，比依赖驱动的隐式优化更可控。

⚠️ 注意限制：**resolve attachment 不得绑定到 tile memory**；tile memory 内容只在命令缓冲提交批次的边界内保持（可通过队列属性查询是否扩展到提交边界）。

### 4.8 移动端的其他「不要做」

Qualcomm 官方明确列出的性能避坑项：

| 项 | 原因 |
|----|------|
| `primitiveRestartEnable` | 多次 draw 几乎总是优于图元重启 |
| Tessellation（hull / tessellator / domain shader） | 移动端为软件模拟，且是 Direct Mode 的触发条件之一 |
| Geometry Shader | 同上 |
| Client-side vertex arrays | 无缓存友好的访问模式 |
| `VK_EXT_vertex_input_dynamic_state` | 应尽量少用，静态管线严格更快 |
| User clip planes | 硬件不支持良好 |
| `VK_EXT_conditional_rendering` | 除非跳过大量工作，否则开销显著 |
| `VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT` | 削弱或禁用 UBWC |

### 4.9 最佳颜色格式（Qualcomm 官方）

| 格式 | 定位 |
|------|------|
| **`R10G10B10A2`** | **硬件优化得最好的格式**，应作为默认选择 |
| `R11G11B10A0`（`R11G11B10_UFLOAT`） | 需要更高色深且不需要 alpha 透明时 |
| `RGBA16` / `RGBA16F` | 需要渐变透明，或上述格式色深实在不够时 |

```
│                                                                            │
│  约束：电池供电 + LPDDR 共享带宽（30~70 GB/s）                                │
│        且内存访问功耗 ≈ GPU 计算功耗                                          │
│                              │                                             │
│                              ▼                                             │

└────────────────────────────────────────────────────────────────────────────┘
```

## 6. 小结

| 要点 | 说明 |
|------|------|
| **四类错误，各有特征** | ❌ 结论错（分箱必然、Adreno bin 固定、零主存访问）；🟡 结论对但机制错（最危险）；🟠 论断过强（延迟渲染天作之合）；➕ 遗漏（clear/invalidate、并发分箱、压缩、HSR 破坏项） |
| **最重要的单点纠正** | 分箱在 **position-only VS 之后、完整 VS 之前**。这一条直接决定「拆分顶点流」与「简化 VS」两条核心优化 |
| **第二重要的单点纠正** | Adreno 的 bin **尺寸可变**，是驱动的输出，不是可以预设的常数。「缩小 tile」不是可操作的优化手段 |
| **第三重要的单点纠正** | 分箱阶段**有**主存流量（Visibility Stream）。图元数量本身就是成本，这给了「减面」一个额外的理由 |
| **资料整体缺失的主线** | 「**Resolve 成本**」——移动端每一次「渲染到贴图」都要付一次主存往返。资料把注意力全放在 GMEM 容量上，但实际项目里最大的带宽浪费通常来自 pass 切分过碎 |
| **不要把桌面经验平移** | 不清除、跳 invalidate、频繁换 RT、给 G-Buffer 开 MSAA——这四条在桌面无害，在移动端全是反向优化 |
| **善用厂商给的免费信号** | Mali Offline Compiler 的检查项、Qualcomm 的最佳实践列表、`VK_EXT_subpass_merge_feedback`，都是可以直接接进 CI 的确定性提示 |
