# 移动端 GPU 架构 — 性能诊断与优化清单

> 本文档是「移动端 GPU 架构」系列文档的第 **5** 篇。本篇把前四篇的硬件原理，翻译成「Profiler 上的指标 → 硬件成因 → 可执行对策」的直接映射，并给出可接进 CI 的检查清单。

---

## 1. 诊断的基本原则

### 1.1 三步法

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  第 1 步：先确定「驱动选了哪种渲染模式」                                         │
│    · 是不是 Direct Mode？如果是，所有基于 GMEM 的优化都不成立                    │
│    · 分箱是否真的在跑？                                                       │
│    ⚠️ 跳过这一步去调 G-Buffer 格式是常见的时间浪费                               │
├──────────────────────────────────────────────────────────────────────────────┤
│  第 2 步：确定「瓶颈类型」                                                     │
│    · CPU-bound？  → draw call 数、RHI 线程耗时                                 │
│    · GPU 几何受限？→ 分箱占比高、顶点数、图元数                                 │
│    · GPU 带宽受限？→ 停滞指标（Texture Fetch Stall / Shaders Stalled）         │
│    · GPU ALU 受限？→ % Time ALUs Working 高                                   │
├──────────────────────────────────────────────────────────────────────────────┤
│  第 3 步：按「成本量级」排序优化项                                              │
│    推荐顺序（移动端经验）：                                                     │
│      ① 消除跨 pass 的 RT 往返（Resolve + LOAD）    ← 通常收益最大            │
│      ② 消除触发 Direct Mode 的条件                  ← 收益是「倍数级」        │
│      ③ 压缩 G-Buffer / 减少活跃 RT 数               ← 收益 20–50%            │
│      ④ 减少图元数与顶点数                            ← 收益 10–40%            │
│      ⑤ 微调 shader 指令数                            ← 收益 5–15%             │
│    ⚠️ 大多数人从 ⑤ 开始，应该从 ① 开始                                         │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 GPU 耗时构成的正确理解

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  一帧的 GPU 时间线（移动端典型）                                                │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  Surface 0   ████░░░░░░░░░░░███████████████████████████████████████████████ │
│              └┬─┘└────┬─────┘└──────────────────┬──────────────────────────┘ │
│               │       │                        │                            │
│            GPU 空闲  分箱（可能被并发隐藏）      实际的逐 tile 渲染             │
│                      （若并发分箱生效）                                        │
│                                                                              │
│  要点：                                                                      │
│    · "GPU 空闲"（Idle）通常意味着 CPU 提交没跟上 → 是 CPU-bound 的信号          │
│    · 分箱时间在并发分箱生效时不一定出现在关键路径上                              │
│    · 逐 tile 渲染段里，真正受限的可能是：几何、纹理带宽、ROP、ALU               │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 2. Snapdragon Profiler 指标语义表

⚠️ **注意**：指标的确切定义随 profiler 版本与 GPU 世代变化。下表的语义解释是通用口径，具体阈值应通过**基线对比法**（同一场景改一处、看变化方向）来确定，而不是硬套绝对数字。

| 指标 | 大致含义 | 偏高意味着 | 偏低意味着 |
|------|---------|-----------|-----------|
| `% Time ALUs Working` | ALU（算术逻辑单元）活跃周期占比 | ALU-bound：计算量过大，可能需要降 LOD / 简化 shader | 被其他资源拖住（带宽、纹理、几何），ALU 在等数据 |
| `% Time Shaders Busy` | 着色器单元有工作可做的占比 | 着色阶段压力大 | 存在大量等待 |
| `Shaders Stalled` | 着色器因资源等待而停顿的时间占比 | 见 §5 停滞分类 | — |
| `Texture Fetch Stall` | 因纹理取指而停顿的占比 | 纹理带宽不足 / cache 命中率低 / 纹理未压缩 | — |
| `Vertex Fetch Stall` | 因顶点数据读取而停顿 | 顶点缓冲布局差（交错）、顶点数过多、cache 命中率低 | — |
| `ALU Stall` | 因依赖链、分歧导致的 ALU 停顿 | shader 有长依赖链或严重分歧 | — |
| `Excessive Binning Pass Time` | 分箱阶段耗时占比异常 | 见 §3 | — |
| `Direct Render Mode` | 该 surface 走了 Direct Mode | 见 §4 | — |
| `Large Surface Using Direct Render Mode` | 大 surface 走了 Direct Mode | 见 §4 | — |
| `Surface Count` | 一帧内被渲染到的 surface 总数 | 见 §6 | — |
| `GPU Utilization` | GPU 忙碌占比 | GPU-bound | 若同时 GPU idle 高 → CPU-bound |
| `GPU Idle` | GPU 空闲占比 | CPU-bound（提交跟不上） | — |

## 3. 诊断树：`Excessive Binning Pass Time`

### 3.1 先弄清指标语义

这个指标表达的是「分箱阶段的耗时占比异常地高」。但**它未必是瓶颈**——因为并发分箱的存在，分箱通常在独立硬件上与渲染并行。

```
⚠️ 前提判断：并发分箱是否生效？
      │
      ├─ 生效  → 分箱时间被隐藏 → 即使占比高也不一定是瓶颈
      │          → 此时应继续看几何/带宽/ALU 指标找真正的瓶颈
      │
      └─ 失效  → 分箱确实在关键路径上 → 进入下面的排查
```

### 3.2 排查顺序

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  ① 图元数量是否爆炸？                                                          │
│     检查：提交到分箱的图元总数                                                 │
│     对策：GPU-Driven 剔除（compute culling + indirect draw）、LOD、HLOD、      │
│           合并静态网格、减少子网格数量                                         │
├──────────────────────────────────────────────────────────────────────────────┤
│  ② 是否有大量「远大于 bin 尺寸」的三角形？                                      │
│     检查：地形、水面、天空盒、大型建筑的三角形屏幕尺寸                            │
│     原理：Qualcomm 官方——跨 bin 的三角形会在每个覆盖的 bin 中完整重复光栅化      │
│     对策：在资产侧做镶嵌；避免单个巨型三角形；把大面切成与 tile 同量级的网格       │
├──────────────────────────────────────────────────────────────────────────────┤
│  ③ 是否有海量微三角形（亚像素）？                                              │
│     检查：植被、粒子、远距离密集物件                                            │
│     对策：LOD 激进降级；微三角形剔除；用 impostor / billboard 替代              │
├──────────────────────────────────────────────────────────────────────────────┤
│  ④ Position Shader 复杂度是否过高？                                            │
│     检查：gl_Position 的计算路径上是否有：                                      │
│       · 纹理采样（顶点位移贴图、烘焙动画、流体 UV）                              │
│       · 复杂的骨骼矩阵链                                                       │
│       · 长依赖链的数学运算                                                     │
│     原理：Position Shader 对**所有**顶点执行，含最终被剔除的                     │
│     对策：把顶点动画改到 compute shader 预计算到 SSBO；                           │
│           骨骼矩阵放 UBO/SSBO 而非纹理；分离 position 顶点流                     │
├──────────────────────────────────────────────────────────────────────────────┤
│  ⑤ 顶点复用率是否过低？                                                        │
│     检查：Mali 上跑 Mali Offline Compiler，看                                │
│           Position threads per input primitive                               │
│     目标：< 1.5 次/三角形（优秀）；≥ 3 说明几乎无复用                          │
│     对策：meshoptimizer 顶点缓存优化；确保索引区间无空洞                         │
├──────────────────────────────────────────────────────────────────────────────┤
│  ⑥ 顶点缓冲是否交错布局？                                                      │
│     检查：position 与非 position 属性是否在同一个 packed buffer 里              │
│     对策：拆成两个 stream；position 单独一个 binding                            │
├──────────────────────────────────────────────────────────────────────────────┤
│  ⑦ bin 数量是否过多？                                                          │
│     检查：分辨率、MSAA 采样数、同帧活跃 RT 数量、附件格式复杂度                    │
│     对策：降分辨率 / VRS / MSAA 降到 2x / 减少同帧 RT 数 / 压缩附件格式          │
├──────────────────────────────────────────────────────────────────────────────┤
│  ⑧ 并发分箱是否被破坏？                                                        │
│     检查三项：                                                                 │
│       (a) 顺序 render pass 之间是否有依赖（尤其 pass N+1 的顶点着色器           │
│           依赖 pass N 的输出）                                                 │
│       (b) 帧内是否对同一个 Z-buffer 反复 clear                                 │
│       (c) 是否受 VSYNC 限制且首个 surface 承担了全部几何负载                     │
│     对策：(a) 重审 render pass 设置与 barrier，切断顶点输入依赖；               │
│           (b) 跨 pass 复用同一深度缓冲且不 clear；                             │
│           (c) 在几何密集 pass 前安排独立工作，或让 CPU 多提交一帧（可接受 1 帧延迟）│
├──────────────────────────────────────────────────────────────────────────────┤
│  ⑨ 是否使用了 tessellation / geometry shader？                                  │
│     原理：几何放大发生在分箱阶段之后，binning 难做静态规划                        │
│     对策：移动端避免；改用 mesh shader 或 compute 侧镶嵌                        │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 3.3 快速定位表

| 观察到的伴随现象 | 最可能的根因 |
|----------------|------------|
| Vertex Fetch Stall 也高 | 顶点缓冲交错布局 / 顶点数过多（④⑤⑥） |
| 图元数很高但像素填充很低 | 微三角形海量（③） |
| 只有少数大物体时也高 | 超大三角形（②） |
| 加了后处理/换了格式后恶化 | bin 数量增加（⑦） |
| 帧内多 pass 结构时高 | 并发分箱被破坏（⑧） |
| 一加位移贴图就恶化 | Position Shader 有纹理采样（④） |

## 4. 诊断树：`Large Surface Using Direct Render Mode`

### 4.1 官方触发条件优先

⚠️ **不要一上来就怀疑 G-Buffer 太大。** Qualcomm 官方给出的 Direct Mode 触发条件优先排查：

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  Qualcomm 官方原文：                                                          │
│  "generally these scenarios trigger direct mode:                             │
│     · High ratio of texture samples in vertex shaders to vertices            │
│     · Small number of vertices and/or draws                                  │
│     · Use of tessellation or geometry shaders"                               │
└──────────────────────────────────────────────────────────────────────────────┘

① 【最高优先级】顶点着色器里是否有纹理采样？
   · 查：gl_Position 计算路径（位移贴图、烘焙动画、流体 UV、顶点拾取）
   · 对策：改用 compute shader 预计算到 SSBO

② 【高优先级】是否使用了 tessellation 或 geometry shader？
   · 移动端 tessellation 是软件模拟，且是 Direct Mode 触发条件
   · 对策：改用 mesh shader（VK_EXT_mesh_shader）或 compute 侧镶嵌

③ 【中优先级】该 surface 的顶点数 / draw 数是否过少？
   · 小 surface（如仅画一个全屏 quad 的后处理）走 Direct Mode 是**合理的**，
     不是问题
   · 只有几何密集型 surface 走 Direct Mode 才是问题

④ 【中优先级】surface 分辨率是否过大？
   · 原理：bin 数量与分辨率正相关；大 surface 让 binning 的固定开销摊不薄
   · 对策：降分辨率、VRS、分段渲染

⑤ 【中优先级】附件格式是否过重？
   · 原理：重格式让可用的 bin 变小；bin 太小则 binning 收益不抵开销
   · 对策：压缩格式、减少 MRT 数、禁用 MSAA
```

### 4.2 Direct Mode 的代价量化

一旦某个 surface 走了 Direct Mode：

| 失去的收益 | 后果 |
|-----------|------|
| G-Buffer 无法留在片上 | 每个 G-Buffer 附件都要写主存 + 读回 |
| 深度无法留在片上 | 深度读写走主存 |
| 混合/深度测试的 ROP 流量 | 全部走主存 |
| 显存压缩（UBWC/AFBC）可能失效 | 带宽进一步放大 |

**含义**：一个 1080p 的 Deferred surface 走 Direct Mode，主存流量可能从 ~8 MB/帧涨到 40+ MB/帧。这直接解释了为什么 `% Time ALUs Working` 会暴跌——ALU 在等数据。

### 4.3 修复优先级

```
优先级 1：消除顶点着色器中的纹理采样   ← 通常改动最小、收益最大
优先级 2：移除 tessellation / geometry shader
优先级 3：压缩附件格式、减少 MRT
优先级 4：降低 surface 分辨率 / 使用 VRS
优先级 5：拆分过大的 surface
```

## 5. 停滞（Stall）指标解读

### 5.1 因果链

当一个 surface 走了 Direct Mode 或 G-Buffer 溢出到主存时，会形成这样一条因果链：

```
     G-Buffer 落主存（或 Direct Mode 退化）
              │
              ▼
     主存带宽压力上升
              │
              ▼
   ┌──────────────────────┬──────────────────────┐
   ▼                      ▼                      ▼
Texture Fetch Stall   Shaders Stalled     ROP 受限
（纹理取指等不到数据）  （着色器整体停等）    （混合/深度测试排队）
   │                      │
   └──────────┬───────────┘
              ▼
       ALU 没有数据可算
              │
              ▼
   % Time ALUs Working 下跌（例如 31%）
              │
              ▼
      GPU 时间被拉长，帧率下降
              │
              ▼
   开发者误判为「ALU 算力不足」，去优化 shader 指令数（无效方向）
```

⚠️ **这就是「ALU 利用率低 ≠ ALU 算力不足」的含义。** 低 ALU 利用率 + 高 Stall 指标 = **带宽问题**，优化方向是减少内存流量，不是简化 shader。

### 5.2 停滞指标的定位表

| 停滞指标高 | 定位方向 | 具体检查 |
|-----------|---------|---------|
| Texture Fetch Stall | 纹理带宽 | ① 纹理是否启用压缩（UBWC/AFBC）② 采样地址是否连贯（cache 命中）③ mip 是否开启 ④ 各向异性过滤是否必要 ⑤ 是否在顶点着色器里采样 |
| Vertex Fetch Stall | 顶点数据带宽 | ① 顶点缓冲是否交错 ② 顶点数 ③ 顶点复用率 |
| ALU Stall | 依赖链 / 分歧 | ① shader 里的长依赖链 ② `if` 分支是否导致 warp 分歧 ③ 是否使用了低效的内建函数（pow/sin） |
| Shaders Stalled（笼统） | 先看上面三项细分 | — |
| GPU Idle 高 | CPU 侧 | ① draw call 数 ② RHI 线程耗时 ③ 同步点是否过多 ④ 是否每条指令都在等上一帧 |

### 5.3 一个诊断口诀

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                                                                              │
│   ALU 利用率低 + 停滞高  →  带宽问题，去减内存流量                              │
│   ALU 利用率高 + 停滞低  →  计算问题，去简 shader / 降 LOD                     │
│   ALU 利用率低 + 停滞低  →  GPU 空闲，是 CPU-bound 或同步问题                  │
│   分箱占比高 + 其他都正常 →  可能并发分箱生效，不必管                           │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 6. Surface 数量：被忽视的头号指标

### 6.1 为什么 surface 数量至关重要

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  每个 surface = 一次完整的「分箱 + 逐 tile 渲染 + Resolve」                    │
│  其中 Resolve 是固定成本，与 surface 大小基本无关                                │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  理想情况（移动端）：                                                          │
│    2 个 surface（VR 双目）或 1 个（单屏）                                       │
│                                                                              │
│  现实情况（典型问题项目）：                                                     │
│    阴影图 × 4（CSM 级）                                                        │
│    + 反射探针 × 6                                                             │
│    + SSAO 中间 × 2                                                            │
│    + Bloom 各 mip × 5                                                         │
│    + DOF 中间 × 3                                                             │
│    + 运动模糊 × 2                                                             │
│    + 半透明层 × 3                                                             │
│    + ...                                                                      │
│    = 数十到数百个 surface                                                      │
│                                                                              │
│  ⚠️ 每个 surface 都可能有：                                                   │
│     · 自己的分箱 Pass（破坏并发分箱、增加 bin 元数据）                            │
│     · 前一个 surface 的 Resolve + 后一个 surface 的 LOAD                       │
│     · 深度的额外读写                                                          │
│                                                                              │
│  参考数据点：Oculus 官方实测，每个 eye buffer 的 Resolve 约 0.5 ms              │
│  → 若有 100 个 surface，Resolve 累计成本是数量级问题                             │
└──────────────────────────────────────────────────────────────────────────────┘
```

Carmack 在 Meta 博客中对类似现象的评述（Pinball FX2 VR）：

> "There are a lot of surfaces, which is concerning. **Ideally, you just want to see two surfaces**—one for each VR eye."

### 6.2 Surface 数量膨胀的排查表

| 来源 | 检查点 | 削减手段 |
|------|--------|---------|
| 阴影图 | CSM 级数、每级分辨率、是否需要每帧更新 | 降到 2 级 CSM；静态阴影缓存（不每帧更新）；降低分辨率 |
| 反射探针 | 是否每帧重新烘、是否有必要 | 烘焙 / 预计算；降低更新频率（每 N 帧） |
| 后处理中间贴图 | 每一级是否必要、分辨率是否可降 | 合并 pass（用 input attachment）；Bloom 用低分辨率 + 少量 mip；SSAO 用半分辨率 |
| 半透明分层 | 是否真的分了多层 | 用 OIT 的廉价近似；减少分层 |
| 帧内切换 framebuffer 渲染"副产品" | 是否把临时的 RT 绘制插在场景渲染中间 | 把副产品集中到帧的独立阶段（帧首或帧尾） |
| UI / 视频 / 相机预览 | 是否在移动端启用 | 移动端降级或禁用 |
| 多相机（后视镜、小地图、狙击镜） | 每增加一个相机 = 一整套 surface | 降低更新频率、降分辨率、仅在可见时渲染 |

### 6.3 「中途切换 framebuffer」为什么是移动端反模式

Carmack 的原文描述：

> "This is an anti-pattern for mobile graphics: Start drawing stuff to your scene. Switch to another framebuffer to render some effect. Switch back to your scene to use that texture."

```
❌ 反模式：A → B → A
   Surface A：▐████████▌  ▐███▌       ← 被切成两段
   Surface B：          ▐███▌
              └─切换──┘     └─切回─┘

   代价：A 被渲染两次（两次分箱 + 两次 Resolve + 中间态要落盘）
        → 而且 A 的第一段与第二段之间，A 的内容必须**完整的写回主存**，
          因为 B 是独立 surface，无法与 A 共享片上的 tile 局部性

✅ 正确：把所有 A 的渲染做完，再渲染 B
   Surface A：▐███████████████▌
   Surface B：               ▐███▌
```

## 7. 全量优化清单

### 7.1 A 组：附件与内存（收益最大）

```
□ A01. G-Buffer 每个 MRT：loadOp = DONT_CARE，storeOp = DONT_CARE
□ A02. 深度（后续不用）：storeOp = DONT_CARE
□ A03. 深度（跨 pass 复用）：LOAD 一次，跨 pass 复用不重复 clear
□ A04. 最终颜色：loadOp = CLEAR 或 DONT_CARE，不用默认 LOAD
□ A05. 减少同帧活跃的渲染目标数量
□ A06. G-Buffer 无 MSAA
□ A07. 每个 G-Buffer 字段都能说清"为什么必须存"；能重建的就不存
□ A08. 不存 world position（由深度重建）
□ A09. 法线用 Octahedron 编码 + RG16F / RGB10A2，不用 RGBA16F
□ A10. 颜色格式优先 R10G10B10A2
□ A11. 检查是否误用 MUTABLE_FORMAT_BIT 等禁用显存压缩的标志
□ A12. 分辨率对齐（避免非对齐尺寸破坏压缩与 tile 网格）
□ A13. 若支持，考虑 VK_QCOM_tile_memory_heap 让中间贴图常驻 GMEM
```

### 7.2 B 组：Pass 结构（收益第二大）

```
□ B01. G-Buffer 渲染与光照在同一 render pass（subpass）或同一组 local read scope
□ B02. 所有 subpass 依赖 / barrier 带 VK_DEPENDENCY_BY_REGION_BIT
□ B03. 用 VK_EXT_subpass_merge_feedback 断言 subpass 真的被合并（接入 CI）
□ B04. 不在帧内中途切换 framebuffer 渲染副产品
□ B05. 统计整帧 surface 数量，设定上限目标并逐项削减
□ B06. 合并后处理 pass（用 input attachment 替代中间纹理）
□ B07. 降低阴影图 CSM 级数与分辨率；静态阴影考虑缓存
□ B08. 减少反射探针数量与更新频率
□ B09. Bloom 用低分辨率 + 少量 mip
□ B10. SSAO / DOF / 运动模糊逐项评估性价比，移动端优先砍掉
□ B11. 跨 render pass 复用同一个深度缓冲且不重复 clear（允许并发分箱）
□ B12. 切断「Pass N+1 的顶点着色器依赖 Pass N 输出」的依赖链
□ B13. 新项目走 dynamic rendering + VK_KHR_dynamic_rendering_local_read
```

### 7.3 C 组：几何与分箱

```
□ C01. 顶点缓冲分离：position 单独一个 stream / binding
□ C02. 用 meshoptimizer 做顶点缓存优化，目标每三角形顶点着色 < 1.5 次
□ C03. 确保索引区间无空洞
□ C04. 顶点位置属性量化（short4 / 归一化）
□ C05. 绝不在 gl_Position 计算路径上做纹理采样
□ C06. 顶点动画（骨骼/烘焙）改到 compute 预计算到 SSBO
□ C07. 避免单个超大三角形（地形/水面/天空盒）→ 做镶嵌
□ C08. 亚像素微三角形 → 激进 LOD / 剔除 / impostor
□ C09. 用 GPU-Driven（compute culling + indirect draw）压低提交图元数
□ C10. 用 MDI / 合并绘制压低 draw call 数
□ C11. 避免 primitiveRestartEnable（用多次 draw）
□ C12. 避免 tessellation / geometry shader
□ C13. 控制 varying 数量与精度（能用 mediump 就用）
```

### 7.4 D 组：着色器

```
□ D01. 避免写 gl_FragDepth（会禁用 early ZS 与 HSR）
□ D02. 必要时用 layout(early_fragment_tests) 强制 early ZS
□ D03. 减少 discard（会强制 late ZS update）
□ D04. 谨慎使用 framebuffer fetch / gl_LastFragColorARM
        （会让 shader 不能作为 HSR 遮挡体）
□ D05. 不在片元着色器里采样当前 pass 的深度附件（Mali 上禁用 HSR）
        → 把线性深度写进 G-Buffer 通道
□ D06. 光照 Pass 用 subpassInput / subpassLoad，不用 sampler2D
□ D07. 纹理开启 mip，采样地址尽量连贯
□ D08. 评估是否真的需要各向异性过滤
□ D09. VRS 的 shading rate 控制在 2×2 以内（某些 Mali 上更慢）
□ D10. 简化 shader 里的长依赖链
□ D11. 避免无必要的 `pow` / `sin` / `cos`（用查表或直接乘方）
□ D12. 静态管线优于动态状态（避免 VK_EXT_vertex_input_dynamic_state）
```

### 7.5 E 组：CPU 侧

```
□ E01. 统计 draw call 数，与同类型项目横向对比
□ E02. 检查 RHI 线程耗时（state 绑定、描述符更新）
□ E03. 减少同步点（避免每帧多次等待）
□ E04. 用 ring buffer / 多帧飞行减少 CPU-GPU 耦合
□ E05. 描述符更新用 bindless 或预先打包，避免逐 draw 更新
□ E06. 若 CPU-bound，可接受最多 1 帧额外延迟来换取分箱并行
```

## 8. 跨平台工具与验证手段对照表

| 平台 | 几何/分箱侧 | 带宽侧 | 片上闭环验证 | Shader 侧 |
|------|-----------|-------|-------------|----------|
| Qualcomm Adreno | Snapdragon Profiler（分箱指标、surface 模式） | Snapdragon Profiler（带宽、停滞） | 观察 surface 模式 + 带宽实测 | Snapdragon Profiler 的 shader 指令统计 |
| ARM Mali | Mali Offline Compiler（Position/Varying shader 分开统计） | Streamline / Mali 性能计数器 | `VK_EXT_subpass_merge_feedback` | Mali Offline Compiler 的检查项（late ZS / coverage / color buffer read / slow shading rate） |
| Imagination PowerVR | PVRTune / PVRCarbon | PVRTune | 同上 | PVRTune |
| Apple GPU | Xcode Metal Debugger / GPU Capture | Xcode GPU 计数器 | — | Xcode Shader Profiler |
| 跨平台 | RenderDoc（管线结构可视化） | RenderDoc | `VK_EXT_subpass_merge_feedback` | RenderDoc SPIR-V 反汇编 |

### 8.1 可以接进 CI 的确定性检查

```
□ 1. Mali Offline Compiler 输出解析
     · Position shader / Varying shader 周期数
     · 是否报告 "Uses late ZS test" / "Modifies coverage" /
       "Reads color buffer" / "Has slow shading rate"
     · Position threads per input primitive（目标 < 1.5）

□ 2. VK_EXT_subpass_merge_feedback
     · 断言所有应当合并的 subpass 的 subpassMergeStatus == MERGED
     · 未合并时读取 notMergedReason 定位原因

□ 3. SPIR-V 静态检查
     · 断言没有 shader 在位置计算路径上出现 OpImageSample*
     · 断言没有 gl_FragDepth 写入（除非白名单材质）

□ 4. 附件配置断言
     · G-Buffer 附件的 storeOp 必须是 DONT_CARE 或 NONE_QCOM
     · 所有 subpass 依赖必须带 BY_REGION
     · G-Buffer 附件的 sampleCount 必须是 1

□ 5. Surface 数量统计
     · 每帧统计被渲染到的 image 数量，设阈值告警
```

## 9. 一页速查

```
╔══════════════════════════════════════════════════════════════════════════════╗
║  移动端 GPU 性能速查                                                          ║
╠══════════════════════════════════════════════════════════════════════════════╣
║                                                                              ║
║  【硬件心智模型】                                                              ║
║    屏幕 → 切成 Tile/Bin（Mali 16×16 固定；Adreno 可变）                       ║
║    几何 → Position Shading → Culling → Binning → Varying Shading → 光栅         ║
║    片元 → 全在片上 SRAM 完成 → 块末 Resolve 到主存                             ║
║    Adreno 可能不做分箱（FlexRender 三档，驱动启发式）                            ║
║                                                                              ║
║  【三条铁律】                                                                  ║
║    ① 每个"渲染到贴图"都有 Resolve 成本 → 减少 pass 数量、合并 pass             ║
║    ② 中间结果要留在片上 → BY_REGION + input attachment + DONT_CARE           ║
║    ③ 清空/丢弃要显式声明 → CLEAR / DONT_CARE，绝不依赖 LOAD 默认值            ║
║                                                                              ║
║  【头号杀手清单】                                                              ║
║    ✗ 顶点着色器里采样纹理（触发 Direct Mode）                                   ║
║    ✗ 用 tessellation / geometry shader（触发 Direct Mode）                    ║
║    ✗ G-Buffer 拆成两个独立 render pass                                         ║
║    ✗ subpass 依赖漏掉 BY_REGION                                               ║
║    ✗ G-Buffer 开 MSAA                                                         ║
║    ✗ G-Buffer 存 world position / 用 RGBA16F 存法线                            ║
║    ✗ 附件用 LOAD 但实际不需要旧内容                                             ║
║    ✗ 帧内中途切换 framebuffer 渲染副产品                                        ║
║    ✗ 写 gl_FragDepth / 大量 discard（禁用早期剔除）                             ║
║    ✗ 交错顶点缓冲 + 索引有空洞                                                  ║
║                                                                              ║
║  【诊断口诀】                                                                  ║
║    ALU 利用率低 + 停滞高   → 带宽问题                                          ║
║    ALU 利用率高 + 停滞低   → 计算问题                                          ║
║    ALU 利用率低 + 停滞低   → CPU-bound / 同步问题                              ║
║    分箱占比高 + 其他正常   → 可能并发分箱生效，不必管                            ║
║                                                                              ║
║  【优化顺序】                                                                  ║
║    ① 消除跨 pass RT 往返 → ② 消除 Direct Mode 触发条件                         ║
║    → ③ 压缩 G-Buffer / 减 RT 数 → ④ 减图元顶点 → ⑤ 微调 shader               ║
║                                                                              ║
╚══════════════════════════════════════════════════════════════════════════════╝
```

## 10. 小结

| 要点 | 说明 |
|------|------|
| **先确定渲染模式，再谈优化** | 是否 Direct Mode 决定了整套优化逻辑是否成立。跳过这步是最大的时间浪费 |
| **分箱占比高 ≠ 分箱是瓶颈** | 并发分箱生效时它被隐藏在独立硬件管线上。先确认三条破坏条件 |
| **Direct Mode 的首要排查项不是 G-Buffer 大小** | 是「VS 里的纹理采样」和「tessellation / GS」，这是官方明示的触发条件 |
| **ALU 利用率低是症状，不是病因** | 低 ALU + 高 Stall = 带宽问题。此时简化 shader 是无效方向 |
| **Surface 数量是头号被忽视指标** | 每个 surface 都有分箱 + Resolve 的固定成本。理想值是 1–2 个，现实常是几十到几百 |
| **「帧内中途切 RT」是移动端定义级反模式** | 会让被切碎的 surface 承担两次完整生命周期 |
| **优化的正确顺序** | 先消除跨 pass 往返，再消除 Direct Mode 触发条件，再压 G-Buffer，最后才微调 shader |
| **把确定性检查接进 CI** | Mali Offline Compiler 的检查项、`VK_EXT_subpass_merge_feedback` 的合并状态、附件配置断言，都不依赖人工观察 |
