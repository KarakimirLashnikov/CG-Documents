# 反射方案对比与选型

> 系列第 **3** 篇。反射不只是 SPIRV-Reflect 一家：SPIRV-Cross、glslang、Slang、D3D12/Metal 官方反射，甚至"不反射"都是合法选项。本文给出横向对比矩阵、决策树，以及在真实引擎里最稳的**混合方案**。

---

## 1. 候选方案概览

```
                    ┌─────────────────────────────────────┐
                    │         需要 shader 接口元数据         │
                    └──────────────┬──────────────────────┘
                                   │
      ┌────────────────┬───────────┴────────┬──────────────────┐
      ▼                ▼                    ▼                  ▼
  读 SPIR-V 二进制   读 SPIR-V 但顺带转译   读自家 IR        读目标平台格式
  ┌────────────┐   ┌────────────────┐  ┌──────────┐   ┌──────────────┐
  │SPIRV-Reflect│   │  SPIRV-Cross   │  │  Slang   │   │D3D12 Reflect │
  │  自建解析器  │   │(get_shader_    │  │ Slang IR │   │Metal Reflect │
  │SPIRV-Tools  │   │  resources)    │  │ Reflection│   └──────────────┘

```

## 2. 方案逐一剖析

### 2.1 SPIRV-Reflect

| 维度 | 评价 |
|------|------|
| 定位 | 纯只读反射 + 有限原地改写 |
| 依赖 | 无（C99 单文件） |
| 信息丰富度 | ⭐⭐⭐ 覆盖描述符/块布局/接口/PC/特化常量 |
| 改写能力 | ⭐⭐ 仅能改 `Binding`/`Set`/`Location` 字面量 |
| 跨平台 | 只服务 Vulkan（SPIR-V 原生） |
| 稳定性 | Khronos 维护，API 稳定 |

**适合**：Vulkan 引擎的**运行时管线构建**（本系列主推）。

---

### 2.2 SPIRV-Cross

| 维度 | 评价 |
|------|------|
| 定位 | SPIR-V → GLSL / HLSL / MSL / C++ **反编译器**，反射是其副产品 |
| 依赖 | 较大（完整 SPIR-V 解析 + 各语言后端） |
| 信息丰富度 | ⭐⭐⭐⭐ 额外提供活跃变量分析（`get_active_interface_variables`）、声明大小 |
| 改写能力 | ⭐⭐⭐ 可改后再重新发射源码 |
| 跨平台 | ⭐⭐⭐⭐⭐ 多目标语言 |
| 稳定性 | Khronos 维护 |

核心 API 形态（C++）：

```cpp
#include "spirv_cross.hpp"

spirv_cross::CompilerGLSL compiler(spv);
auto resources = compiler.get_shader_resources();

for (auto& ubo : resources.uniform_buffers) {
    uint32_t set     = compiler.get_decoration(ubo.id, spv::DecorationDescriptorSet);
    uint32_t binding = compiler.get_decoration(ubo.id, spv::DecorationBinding);

    auto& type = compiler.get_type(ubo.base_type_id);
    // 结构体大小、成员偏移
    size_t size = compiler.get_declared_struct_size(type);
    for (uint32_t i = 0; i < type.member_types.size(); ++i)
        size_t off = compiler.type_struct_member_offset(type, i);
}

// ⭐ SPIRV-Cross 独有的"活跃变量"分析
auto active = compiler.get_active_interface_variables();
compiler.set_enabled_interface_variables(active);
```

**SPIRV-Cross 独有的杀手锏**：

1. **活跃变量分析** —— 精确判断哪些变量真的被入口点用到（比 `OpEntryPoint` interface 列表更靠谱，因为它自己做了可达性分析）
2. **声明结构大小** —— `get_declared_struct_size` 与 `get_declared_struct_member_size`，处理 std140 边界情况经验更足
3. **跨语言发射** —— 一份 SPIR-V 转出 Metal / GL / D3D

**代价**：
- 库体积与编译时间显著大于 SPIRV-Reflect
- 反射 API 是"顺手做的"，某些 Vulkan 细节（如 `uav_counter_binding`）没有直接对应
- 每次反射都要构造完整的 `Compiler` 对象，比 SPIRV-Reflect 重

**适合**：需要**多后端**（Metal / GL / D3D）的跨平台引擎；或需要活跃变量分析做激进裁剪的引擎。

---

### 2.3 glslang 内建反射（`glslang::TReflection`）

| 维度 | 评价 |
|------|------|
| 定位 | 编译期反射——在 AST/中间表示层拿到信息，**不需要先产出 SPIR-V** |
| 依赖 | glslang（大） |
| 信息丰富度 | ⭐⭐⭐ 类型信息比 SPIR-V 更全（保留更多源码级信息） |
| 改写能力 | 可以在生成 SPIR-V 之前调整 |
| 跨平台 | Vulkan |

用法形态：

```cpp
glslang::TShader shader(EShLangFragment);
// ... parse ...
glslang::TProgram program;
program.addShader(&shader);
program.link(EShMsgDefault);
program.buildReflection();          // ★ 构建反射

int blockCount = program.getNumUniformBlocks();
for (int i = 0; i < blockCount; ++i) {
    const glslang::TObjectReflection& r = program.getUniformBlock(i);
    // r.name, r.getBinding(), r.size ...
}
program.getNumUniformVariables();   // 单独的 uniform
program.getUniform(i);
```

**优势**：能拿到 SPIR-V 里丢失的东西（如未优化掉的变量、更完整的类型名）。

**劣势**：
- 与 glslang 强绑定 —— 换 DXC / slangc 就失效，**违反"SPIR-V 是唯一契约"原则**
- 反射的是"编译前"状态，与实际产出的 SPIR-V 可能有偏差（优化后某些绑定消失）

**适合**：只用 glslang、且需要在编译期做工具（如 shader 校验器、文档生成器）的场景。**不建议作为运行时反射方案**。

---

### 2.4 SPIRV-Tools IR（`spvtools::opt::IRContext`）

| 维度 | 评价 |
|------|------|
| 定位 | 完整的 SPIR-V 中间表示 + Pass 框架 |
| 依赖 | SPIRV-Tools（大） |
| 信息丰富度 | ⭐⭐⭐⭐⭐ 想拿什么都能拿 |
| 改写能力 | ⭐⭐⭐⭐⭐ 任意改写 + 优化 Pass |
| 稳定性 | Khronos 维护，但内部 API 变动较多 |

```cpp
spvtools::SpirvTools tools(SPV_ENV_VULKAN_1_3);
std::unique_ptr<spvtools::opt::IRContext> ctx =
    spvtools::BuildModule(SPV_ENV_VULKAN_1_3, nullptr, spv.data(), spv.size());

spvtools::opt::analysis::DefUseManager* du = ctx->get_def_use_mgr();
for (auto& inst : ctx->module()->annotations()) {
    if (inst.opcode() == spv::Op::OpDecorate) {
        auto target = inst.GetSingleWordInOperand(0);
        auto deco   = static_cast<spv::Decoration>(inst.GetSingleWordInOperand(1));
        // ...
    }
}
```

**适合**：要做**自定义 SPIR-V 变换**（见 [04](04-LLVM前端与着色器编译器架构.md)/[05](05-可编程着色器元编程.md) 篇的 IR 级元编程）。单纯做反射是杀鸡用牛刀。

---

### 2.5 Slang 反射 API

| 维度 | 评价 |
|------|------|
| 定位 | 现代着色器语言的"一等公民反射" |
| 依赖 | Slang 编译器（大，但可预编译成 `.slang-module`） |
| 信息丰富度 | ⭐⭐⭐⭐⭐ 最丰富：**参数类别**模型天然支持 Vulkan/D3D/Metal/CUDA 多目标 |
| 改写能力 | 通过编译器选项与特化 |
| 跨平台 | ⭐⭐⭐⭐⭐ |

Slang 的反射模型与 SPIR-V 反射**范式不同**：它把每个参数按"类别（category）"给偏移，而不是给一个扁平的 set/binding：

```cpp
slang::IComponentType* program = ...;
slang::ProgramLayout* layout = program->getLayout();

// 全局参数（cbuffer、纹理、采样器……统一为"参数"）
slang::VariableLayoutReflection* var = layout->getParameterByIndex(0);

// 按类别取偏移 —— 这正是多目标的优雅之处
size_t uniformOffset = var->getOffset(SLANG_PARAMETER_CATEGORY_UNIFORM);       // UBO 内偏移
size_t cbvSlot       = var->getOffset(SLANG_PARAMETER_CATEGORY_CONSTANT_BUFFER); // D3D 的 b#
size_t descriptorSlot= var->getOffset(SLANG_PARAMETER_CATEGORY_DESCRIPTOR_TABLE_SLOT); // Vulkan 的 binding
size_t space         = var->getOffset(SLANG_PARAMETER_CATEGORY_SUB_ELEMENT_REGISTER_SPACE); // set/space

// 类型布局递归
slang::TypeLayoutReflection* tl = var->getTypeLayout();
for (unsigned r = 0; r < tl->getBindingRangeCount(); ++r) {
    slang::BindingType bt = tl->getBindingRangeType(r);
}
```

**优势**：

- 泛型特化后的**精确布局**（SPIR-V 反射看到的是特化后的结果，Slang 能给出参数化视图）
- 一套反射喂给 Vulkan / D3D12 / Metal / CUDA
- 支持 bindless 的一等抽象

**代价**：引入 Slang 编译器 = 引入一整套工具链依赖；团队要接受一门新语言。

**适合**：新项目、多平台、愿意用现代着色器语言的团队。

---

### 2.6 平台原生反射（对照参考）

| 平台 | API | 关键类型 |
|------|-----|---------|
| **D3D12**（FXC/DXBC） | `ID3D12ShaderReflection` | `GetResourceBindingDesc()` → `D3D12_SHADER_INPUT_BIND_DESC{BindPoint, BindCount, Space, Type}` |
| **D3D12**（DXC/DXIL） | `IDxcContainerReflection` → `ID3D12ShaderReflection` | 同上；`GetBindingDescByName()` |
| **Metal** | `MTLRenderPipelineReflection` | `vertexArguments` / `fragmentArguments` → `MTLArgument{index, type, access}`；`MTLStructType.members` |
| **CUDA** | `cuModuleGetGlobal` / `nvrtc` | 弱反射，基本靠手写 |

D3D12 的对照写法（帮助理解 Vulkan 反射的差异）：

```cpp
ID3D12ShaderReflection* refl = nullptr;
D3DReflect(bytecode, sizeof(bytecode), IID_PPV_ARGS(&refl));

D3D12_SHADER_INPUT_BIND_DESC desc{};
refl->GetResourceBindingDescByName("PerFrame", &desc);
// desc.BindPoint → register(bN) 中的 N
// desc.Space     → register(bN, spaceM) 中的 M   ← 对应 Vulkan 的 set
// desc.Type      → D3D_SIT_CBUFFER / D3D_SIT_TEXTURE / D3D_SIT_SAMPLER / D3D_SIT_UAV_RWTYPED ...
```

> **概念映射**：D3D 的 `Space` ≈ Vulkan 的 `set`；D3D 的 `BindPoint` ≈ Vulkan 的 `binding`。但 D3D12 **没有**"描述符集布局"这个显式对象——根签名（Root Signature）是另一种抽象。这也解释了为什么 Vulkan 更依赖反射自动化。

---

### 2.7 "不反射"：约定驱动的手写布局

相当多引擎选择**不解析 SPIR-V**，而是在源码里用**注释/宏约定**声明接口，由构建脚本解析文本：

```hlsl
// bgfx 风格
$input v_position, v_normal, v_texcoord0

// Filament 风格（C++ 侧声明绑定点）
constexpr uint8_t SamplerBindingPoints::PerView = 0;
constexpr uint8_t SamplerBindingPoints::PerMaterial = 1;

// Unity 风格（ShaderLab 属性块）
Properties {
    _AlbedoTex ("Albedo", 2D) = "white" {}
}
```

| 优点 | 缺点 |
|------|------|
| 零依赖、构建快 | 双重维护（又回到起点） |
| 完全可控 | 无法自动发现不一致 |
| 对简单引擎够用 | 不支持 bindless 自动化、不支持热重载 |

**适用**：小型引擎、固定管线、或者**作为反射的补充**（用于提供"语义"——见 [06 篇](06-实战-反射驱动的布局与描述符生成.md)）。

## 4. 决策树

```
                        起点
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
   只做 Vulkan?      要多平台?          要做编译器/工具?
        │                 │                  │
    ┌───┴───┐        ┌────┴────┐        ┌────┴────┐
    ▼       ▼        ▼         ▼        ▼         ▼
  要改写  只要读   已有SPIR-V  用Slang  要变换SPIR-V 要写前端
  绑定?   取元数据  做唯一输入?  语言?                      
    │       │        │         │        │         │
    ▼       ▼        ▼         ▼        ▼         ▼
SPIRV-  SPIRV-   SPIRV-    Slang     SPIRV-    LLVM
Reflect Reflect  Cross     Reflect   Tools IR  (见04篇)
(Change*)        (+ 转译)             
```

### 4.1 推荐结论

| 场景 | 推荐方案 |
|------|---------|
| **自研 Vulkan 引擎（本系列目标）** | **SPIRV-Reflect**（运行时）+ `spirv-val/opt`（构建期） |
| Vulkan + Metal + D3D 跨平台 | SPIRV-Reflect 做 Vulkan 路径，SPIRV-Cross 转译其他后端；或直接用 Slang |
| 需要激进裁剪 uber shader | SPIRV-Reflect + SPIRV-Cross 的活跃变量分析 |
| 需要自定义 SPIR-V 注入 | SPIRV-Reflect（改绑定）+ SPIRV-Tools（自定义 Pass） |
| 新项目、追求开发效率 | Slang（自带反射 + 泛型 + 多目标） |
| 小引擎 / 固定管线 | 约定驱动 + 手写布局，够用即止 |

## 5. 混合方案（真实引擎的做法）

**不要把所有赌注压在一个库上。** 推荐分层：

```
┌────────────────────────────────────────────────────────┐
│ Layer A：构建期工具链（离线，可重）                        │
│   spirv-val（校验）→ spirv-opt（优化/剥离）               │
│   → SPIRV-Cross（可选：转译 Metal/HLSL）                 │
│   → 生成 .spv.refl（序列化元数据）                        │
│   → 生成 .h（C++ 参数结构体 + static_assert）             │
└─────────────────────────┬──────────────────────────────┘
                          ▼
┌────────────────────────────────────────────────────────┐
│ Layer B：抽象层（引擎自己的 POD，与任何库解耦）             │
│   ShaderReflectionData {                                │
│     stage, bindings[], pushConstants[], attributes[],   │
│     specConstants[], entryPoints[]                      │
│   }                                                     │
└─────────────────────────┬──────────────────────────────┘
                          ▼
┌────────────────────────────────────────────────────────┐
│ Layer C：实现层（可替换）                                 │
│   SPIRVReflectBackend  ─┐                              │
│   SPIRVCrossBackend    ─┼─ 都产出 Layer B 的结构          │
│   SlangBackend         ─┘                              │
└────────────────────────────────────────────────────────┘
```

**接口设计**：

```cpp
// ShaderReflection.h —— 引擎唯一依赖的头文件（不含任何第三方库）
struct BindingInfo {
    uint32_t          set      = 0;
    uint32_t          binding  = 0;
    uint32_t          count    = 1;
    VkDescriptorType  type     = VK_DESCRIPTOR_TYPE_MAX_ENUM;
    VkShaderStageFlags stages  = 0;
    std::string       name;
    bool              runtimeSized = false;
    std::string       semanticGroup;   // "PerFrame" / "PerMaterial"（由命名约定推导）
};

struct ShaderReflectionData {
    VkShaderStageFlags           stage;
    std::vector<BindingInfo>     bindings;
    std::vector<PushConstantInfo> pushConstants;
    std::vector<VertexAttribute> attributes;
    std::vector<SpecConstantInfo> specConstants;
    std::vector<std::string>     entryPoints;
};

// 抽象后端
struct IReflectionBackend {
    virtual ~IReflectionBackend() = default;
    virtual ShaderReflectionData Reflect(std::span<const uint32_t> spirv) = 0;
};
```

**收益**：

| 收益 | 说明 |
|------|------|
| 换库成本 = 一个 .cpp | 从 SPIRV-Reflect 迁到 Slang 只需新写一个后端 |
| 可离线烘焙 | 构建期就序列化成 `.refl`，运行时不用解析 |
| 可测试 | 用假后端做单元测试，无需真实 SPIR-V |
| 可渐进迁移 | 新旧后端共存，逐 shader 切换 |

## 6. 组合拳：三个库的职责边界

| 工具 | 什么时候用 | 不要用它做什么 |
|------|-----------|--------------|
| **SPIRV-Reflect** | 运行时/构建期：生成 DescriptorSetLayout、PushConstantRange、绑定代码 | 转译语言、深度优化 |
| **SPIRV-Cross** | 构建期：转 Metal/HLSL/GL；活跃变量分析用于裁剪 | 每次管线创建都调（太重） |
| **SPIRV-Tools** | 构建期：`spirv-val` 校验、`spirv-opt` 优化/剥离、自定义 Pass 注入 | 运行时反射 |
| **glslang / DXC / slangc** | 编译期：源码 → SPIR-V | 反射（与编译器强耦合） |
| **Slang** | 若采用：一体化（编译 + 反射 + 多目标） | 只为了反射而引入 |

---

## 7. 常见误区

| 误区 | 事实 |
|------|------|
| "SPIRV-Cross 能替代 SPIRV-Reflect" | 能，但重得多；且它缺一些 Vulkan 专有细节（`uav_counter_binding` 等） |
| "反射一次就一直有效" | shader 改一行，布局可能全变；必须有哈希/校验机制 |
| "有反射就不需要命名约定" | 反射给的是**事实**（set 0 binding 3），不是**语义**（这是 PerFrame）。语义必须额外约定 |
| "Slang 反射可以完全取代 SPIR-V 反射" | 若你已全量采用 Slang 编译，是的；若混用 glslang/DXC，仍需 SPIR-V 反射 |
| "反射能保证 shader 正确" | 不能。反射只描述接口，`spirv-val` 才做规则校验 |
| "描述符布局可以每次创建" | 可以但很慢。应按哈希缓存（见 [06 篇](06-实战-反射驱动的布局与描述符生成.md)） |

---

## 8. 小结

| 结论 | 内容 |
|------|------|
| 主推 | **SPIRV-Reflect**：Vulkan 反射的性价比之王 |
| 补充 | SPIRV-Cross（多目标 + 活跃变量）、SPIRV-Tools（校验/优化/变换） |
| 未来 | Slang（若接受新语言，反射体验最好） |
| 架构关键 | 用**自己的 POD 抽象层**隔离反射库，换库只改一个文件 |
| 认知关键 | 反射给事实，语义靠约定；反射前先校验 |
