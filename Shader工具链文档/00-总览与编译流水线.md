# Shader 工具链 — 总览与编译流水线

> 本文档是「Shader 工具链」系列的第 **0** 篇，给出整个系列的坐标系：着色器从源码文本到 GPU 可执行的完整链路、工具链的三层切分、以及本系列要解决的核心问题。

---

## 1. 为什么需要一篇"Shader 工具链"

在实时渲染系统（见 [实时渲染系统文档](../实时渲染系统文档/00-总览与架构概览.md)）中，我们讨论的是**帧内**发生的事情：Pass 如何声明资源、FrameGraph 如何推导屏障、GPU 如何执行。但有一个前提问题被默认跳过了：

> **CPU 侧的 C++ 代码，凭什么知道一个 shader 需要哪些参数？**

传统写法是"两边手写、靠人保证一致"：

```cpp
// C++ 侧：人肉声明
struct PerFrame {
    glm::mat4 viewProj;   // offset 0
    glm::vec4 cameraPos;  // offset 64
};
static_assert(sizeof(PerFrame) == 80);

// HLSL 侧：再人肉写一遍
cbuffer PerFrame : register(b0) {
    float4x4 viewProj;
    float4   cameraPos;
};
```

这套做法在 5 个 shader 时可用，在 500 个 shader 时是灾难：

| 问题 | 表现 |
|------|------|
| **双重维护** | 改一个 uniform 要改两处，忘了就是静默的错位数据 |
| **绑定号靠约定** | `b3` 到底是 PerView 还是 PerMaterial？没有机器可校验的真相 |
| **变体爆炸** | `#ifdef` 组合数指数增长，编译时间从秒级变成小时级 |
| **无法自动化** | 描述符集布局手写 → 无法做 Bindless、无法做自动池化 |
| **热重载不可能** | 改一行 shader 要重编 C++ |

**Shader 工具链的本质目标**：让**编译产物（SPIR-V）成为唯一的真相来源**，C++ 侧的一切（布局、描述符、绑定代码、参数结构体）都由它**派生**出来。

```
        ┌─────────────┐
        │  .hlsl/.slang│  ← 人写的源码
        └──────┬──────┘
               │ 编译器（前端）
               ▼
        ┌─────────────┐
        │   SPIR-V    │  ← ★ 唯一真相来源（二进制 IR + 元数据）
        └──────┬──────┘
               │ 反射（Reflection）
               ▼
   ┌───────────────────────────────┐
   │ DescriptorSetLayout / Pipeline│
   │ Layout / PushConstantRange /  │
   │ VertexInputLayout / C++ 绑定头│  ← 机器生成的胶水代码
   └───────────────────────────────┘
```

## 2. 全景流水线

一条完整的现代着色器工具链，从源码到 GPU 指令经过 **4 个阶段、8 个可选环节**：

```
 ┌──────────────────────────────────────────────────────────────────────┐
 │ STAGE A：源码准备（Source Preparation）                                │
 │                                                                       │
 │  .hlsl / .glsl / .slang / .cl / .metal                                │
 │        │                                                              │
 │        ├─(A1)─ 元编程展开：宏 / 模板 / 代码生成 / permutation 展开       │
 │        ├─(A2)─ #include 展开（自定义 include handler）                 │
 │        └─(A3)─ 源码哈希 → 缓存查询（命中则直接跳到 E）                  │
 └───────────────────────────────┬──────────────────────────────────────┘
                                 ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ STAGE B：编译到 SPIR-V（Frontend → SPIR-V）                            │
 │                                                                       │
 │  ① glslangValidator   GLSL/HLSL → AST → SPIR-V        （无 LLVM）      │
 │  ② dxc                HLSL → AST → SPIR-V 或 DXIL    （LLVM 血统）     │
 │  ③ clang + LLVM SPIR-V backend                                         │
 │                       C/C++/OpenCL → LLVM IR → SPIR-V                 │
 │  ④ slangc             Slang → Slang IR → SPIR-V / HLSL / MSL / ...    │
 └───────────────────────────────┬──────────────────────────────────────┘
                                 ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ STAGE C：SPIR-V 后处理（IR-level Toolchain）                           │
 │                                                                       │
 │  ⑤ spirv-val     合法性校验（Vulkan 环境规则）                          │
 │  ⑥ spirv-opt     优化：死代码消除 / 内联 / 特化常量折叠 / 绑定重编号     │
 │  ⑦ spirv-link    多模块链接（库化 shader、跨模块库函数）                │
 │  ⑧ strip         剥调试信息 / 剥 NonSemantic（发布包）                 │
 └───────────────────────────────┬──────────────────────────────────────┘
                                 ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ STAGE D：反射（Reflection）                                            │
 │                                                                       │
 │  SPIRV-Reflect / SPIRV-Cross / Slang Reflection API                    │
 │  → 描述符绑定表、PushConstant 布局、输入输出变量、入口点、特化常量        │
 └───────────────────────────────┬──────────────────────────────────────┘
                                 ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ STAGE E：代码生成 & 运行时构建（Codegen + Runtime）                     │
 │                                                                       │
 │  ⑨ 生成 C++ 绑定头（结构体 + offset 静态断言）                          │
 │  ⑩ 生成 VkDescriptorSetLayout / VkPipelineLayout                       │
 │  ⑪ 描述符池定额计算、DescriptorWriter、UpdateTemplate                   │
 │  ⑫ Pipeline Cache / PSO 预热 / 热重载                                  │
 └──────────────────────────────────────────────────────────────────────┘
```

> **关键观察**：反射（D）是整条链路的**枢纽**。向前它消费编译产物，向后它是所有自动化（E）的输入。本系列的 01/02/03 讲反射本身，06 讲如何用它驱动 E。

## 3. 工具链的三层切分

按"谁负责什么"把工具链切成三层，有利于定位问题和分工：

| 层级 | 组成 | 输入 → 输出 | 变化频率 | 本系列对应 |
|------|------|------------|---------|-----------|
| **L1 前端层** | glslang / DXC / Clang / slangc | 源码文本 → SPIR-V | 随 shader 改 | 04（LLVM 前端）、05（元编程） |
| **L2 IR 层** | SPIRV-Tools（val/opt/link/dis）、SPIRV-Cross | SPIR-V → SPIR-V / 目标语言 | 构建期固定 | 01、07 |
| **L3 反射层** | SPIRV-Reflect、自定义解析器、Slang API | SPIR-V → 结构化元数据 | 随引擎演进 | 02、03、06 |

**依赖关系（单向）**：

```
L1 前端层  ──产生──▶  SPIR-V  ──消费──▶ L2 IR 层 ──▶ L3 反射层 ──▶ 引擎运行时
   ▲                                                                    │
   └──────────────────── 元编程 / permutation 驱动 ◀────────────────────┘
                        （运行时需求反向驱动变体生成）
```

> **设计原则**：L3 绝不应该反向依赖 L1 的具体编译器。SPIR-V 是稳定的契约，换了编译器（glslang → DXC → slangc），反射层和运行时代码应**零改动**（或只改少量兼容分支）。这是本系列反复强调的架构主张。

## 4. 核心概念速查

### 4.1 SPIR-V

Khronos 定义的**二进制中间表示**，是 Vulkan / OpenCL / SYCL 的官方着色器格式。特点：

- **SSA 形式 + 显式控制流图（CFG）**
- **逻辑寻址模式**（Vulkan 使用）：变量是"句柄"，不能做指针算术（除非启用 `VariablePointers`）
- **强类型 + ID 引用**：每条指令结果分配一个 `<id>`，后续指令按 ID 引用，形成 DAG
- **Decoration 与指令分离**：`OpDecorate` 挂在 ID 上，不侵入类型定义 → 反射库可以只读 Decoration 拿到绑定号

### 4.2 反射（Reflection）

从**已编译的产物**中反向提取**源码级语义信息**的过程。反射能拿到的信息层次：

| 层次 | 信息 | 来源 Op |
|------|------|---------|
| 模块级 | 入口点名、执行模型、着色器阶段、能力集、扩展、源语言 | `OpEntryPoint`、`OpCapability`、`OpSource` |
| 资源级 | set/binding、描述符类型、资源维度/格式、数组长度 | `OpDecorate` `DescriptorSet`/`Binding`、`OpTypeImage` |
| 内存布局级 | Uniform Block 的成员名、offset、size、数组 stride、矩阵主序 | `OpTypeStruct` + `MemberDecorate Offset` |
| 接口级 | 输入/输出变量的 location、component、内建量、格式 | `OpDecorate Location`/`Location`/`BuiltIn` |
| 常量级 | 特化常量 ID、默认值 | `OpSpecConstant*` |

**反射拿不到的**（这是常见误解）：

- ❌ 源码语法结构（if/for/函数）—— SPIR-V 是 SSA + CFG，不是语法树
- ❌ 宏定义的名字 —— `#define` 在前端就消失了
- ❌ 未被调用的静态函数 —— 可能被 DCE 掉
- ❌ 注释 —— 除非编译成 `OpString` / NonSemantic 调试信息
- ❌ "用户意图"（这个 buffer 是 PerFrame 还是 PerMaterial？）—— **需要命名约定或额外元数据**

最后一条是本系列 06 篇要重点解决的：**反射给的是事实，语义靠约定**。

### 4.3 元编程（Metaprogramming）

"写生成代码的代码"。在 shader 语境下分五个层次，本系列 05 篇展开：

| 层次 | 手段 | 时机 | 典型用途 |
|------|------|------|---------|
| L0 文本 | C 预处理器宏、字符串拼接 | 预处理 | 简单开关 |
| L1 模板代码生成 | Jinja2 / Mako / 自研生成器输出源码 | 构建前 | permutation、重复代码 |
| L2 语言内模板/泛型 | HLSL 2021 `template`、Slang `generic` | 前端语义分析 | 类型安全的复用 |
| L3 IR 变换 | LLVM Pass、Slang IR pass、SPIR-V opt pass | 编译中 | 跨编译器统一注入 |
| L4 运行时 | 特化常量（`VkSpecializationInfo`） | 管线创建 | 消除变体的杀手锏 |

### 4.4 描述符集与绑定（Vulkan）

- `DescriptorSetLayout` 描述"一个 set 里每个 binding 是什么类型、几个"
- `PipelineLayout` 描述"这个管线用到哪些 set + push constant 范围"
- **反射的价值**：这两者 100% 可以从 SPIR-V 推导，不需要手写

## 7. 术语约定

本系列统一使用以下术语，避免歧义：

| 术语 | 标准含义 | 常见误用 |
|------|---------|---------|
| **SPIR-V** | Khronos 二进制 IR 标准，Vulkan/OpenCL/SYCL 通用 | ❌ 当成"SPIR 的 V 版本"（SPIR 是另一套基于 LLVM IR 的旧格式） |
| **反射（Reflection）** | 从编译产物反向提取接口元数据 | ❌ 当作"运行时反射/自省"（shader 反射全在 CPU 构建期） |
| **Descriptor Set** | Vulkan 的一组绑定集合，编号 0..N | ❌ 与 binding 混为一谈（set 是抽屉，binding 是格子） |
| **变体（Variant / Permutation）** | 同一 shader 源码按不同宏组合编译出的多个产物 | ❌ 与"Shader 程序"混用（一个程序 = 多个阶段的变体组合） |
| **特化常量（Spec Constant）** | SPIR-V 中延迟到管线创建才定值的常量 | ❌ 当成普通 uniform（它会被编译器内联优化掉分支） |
| **Bindless** | 用大数组描述符 + Shader 内索引访问资源 | ❌ "没有描述符"（实际是超大描述符数组 + 部分绑定标志） |
| **前端（Frontend）** | 源码 → IR 的编译器部分 | ❌ 指 Web 前端 |
| **Uber Shader** | 单个包含全部分支、靠常量裁剪的巨 shader | ❌ 与"多 variant"等价（两者是治理爆炸的两种相反路线） |
