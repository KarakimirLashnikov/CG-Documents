# 可编程着色器元编程

> 系列第 **5** 篇。反射解决的是"编译后我知道了什么"，元编程解决的是"编译前我该生成什么"。本文建立**五层元编程模型**，逐层给出手段与代码，并重点回答工程上最痛的问题：**shader 变体爆炸怎么治**。

---

## 1. 五层元编程模型

"元编程"在 shader 语境下不是单一技术，而是**五个层次**的叠加。选错层次会让问题复杂十倍。

```
┌──────────────────────────────────────────────────────────────┐
│ L4 运行时特化    特化常量（VkSpecializationInfo）                │
│                  时机：管线创建时   手段：常量内联 + 分支消除      │
├──────────────────────────────────────────────────────────────┤
│ L3 IR 变换       LLVM Pass / Slang IR / SPIR-V 自定义 Pass      │
│                  时机：编译中       手段：遍历 IR 注入/改写        │
├──────────────────────────────────────────────────────────────┤
│ L2 语言内泛型    HLSL 2021 template / Slang generic+interface   │
│                  时机：语义分析     手段：类型参数化              │
├──────────────────────────────────────────────────────────────┤
│ L1 模板代码生成  Jinja2 / Mako / 自研生成器输出源码               │
│                  时机：构建前       手段：字符串模板              │
├──────────────────────────────────────────────────────────────┤
│ L0 文本宏        #define / #ifdef / #include                    │
│                  时机：预处理       手段：C 预处理器              │
└──────────────────────────────────────────────────────────────┘
        越往上：越晚生效、越接近语义、越难调试、越强表达力
        越往下：越早生效、越简单、越容易"字符串拼错"
```

### 1.1 层次选择决策表

| 你想做的事 | 该用哪层 |
|-----------|---------|
| 开/关一个功能分支 | L0（宏）或 **L4（特化常量，更优）** |
| 同一算法处理 float / half / double | **L2（模板/泛型）** |
| 生成 20 个结构相似但参数不同的 shader | **L1（模板生成器）** |
| 给所有 shader 统一注入一段公共代码 | **L1（include）或 L3（IR 注入）** |
| 运行时才知道的参数（分辨率、TAA 开关） | **L4（特化常量）或 uniform** |
| 批量改绑定号 | **L3（SPIR-V 层）+ 反射 `Change*`** |
| 按材质自动选择光照模型 | L2（泛型）/ L4（特化）/ 数据驱动分支 |

## 2. L0：文本宏层

### 2.1 基本形态

```hlsl
#define SHADING_MODEL_DEFAULT   0
#define SHADING_MODEL_CLEARCOAT 1
#define SHADING_MODEL_CLOTH     2

#ifndef SHADING_MODEL
#define SHADING_MODEL SHADING_MODEL_DEFAULT
#endif

float3 Shade(Surface s) {
#if SHADING_MODEL == SHADING_MODEL_CLEARCOAT
    return ShadeClearcoat(s);
#elif SHADING_MODEL == SHADING_MODEL_CLOTH
    return ShadeCloth(s);
#else
    return ShadeDefault(s);
#endif
}
```

### 2.2 宏的实用技巧

```hlsl
// ① 函数式宏：消除重复声明
#define DECLARE_TEX_SLOT(name, slot)  Texture2D name : register(t##slot)

DECLARE_TEX_SLOT(g_Albedo, 0);
DECLARE_TEX_SLOT(g_Normal, 1);
DECLARE_TEX_SLOT(g_Metal,  2);

// ② X-macro：一份清单，多处展开（可与 C++ 侧共用同一份定义）
#define UNIFORM_LIST(X)        \
    X(float4x4, viewProj)      \
    X(float4,   cameraPos)     \
    X(float,    time)

#define DECLARE_MEMBER(type, name)  type name;
struct PerFrame { UNIFORM_LIST(DECLARE_MEMBER) };
#undef DECLARE_MEMBER
```

### 2.3 宏的陷阱

| 陷阱 | 说明 | 对策 |
|------|------|------|
| **没有类型** | 宏在预处理期就被替换，编译器看不到 | 优先用 L2 泛型 |
| **调试困难** | 报错行号指向展开后 | 保留中间产物（`-E` 输出） |
| **组合爆炸** | N 个开关 → 2^N | 见 §7 |
| **宏名污染** | 全局作用域 | 统一前缀 + `#undef` |
| **拼接歧义** | `t##slot` 与 `##` 优先级 | 加括号、用中间宏 |

> **黄金法则**：宏只用于"**开关**"和"**片段拼接**"，不要用于"**类型参数化**"。后者是 L2 的地盘。

## 3. L1：模板代码生成

### 3.1 适用场景

- 一批 shader 结构相同、只有少量参数不同（后处理链、不同数据类型的 reduce kernel）
- permutation 展开（见 §7）
- 生成"胶水"：C++ 绑定头、shader 注册表

### 3.2 Jinja2 模板示例

```jinja
{# templates/gbuffer.frag.hlsl.j2 #}
// ⚠ GENERATED FILE — DO NOT EDIT
// Source: {{ template_name }}   Keywords: {{ keywords | join(', ') }}
{% for k in keywords %}
#define {{ k }}
{% endfor %}

#include "Common.hlsl"
#include "Surface.hlsl"

cbuffer PerMaterial : register(b{{ slots.per_material }}) {
    float4 baseColor;
    {% if 'USE_EMISSIVE' in keywords %}
    float3 emissive;
    float  emissiveIntensity;
    {% endif %}
};

struct PSOut {
    float4 gbuffer0 : SV_Target0;
    float4 gbuffer1 : SV_Target1;
    {% if 'USE_VELOCITY' in keywords %}
    float2 velocity : SV_Target2;
    {% endif %}
};

PSOut PSMain(VSOut i) {
    PSOut o;
    Surface s = DecodeSurface(i);
    o.gbuffer0 = float4(s.albedo, s.roughness);
    o.gbuffer1 = float4(s.normal * 0.5 + 0.5, s.metallic);
    {% if 'USE_VELOCITY' in keywords %}
    o.velocity = ComputeVelocity(i);
    {% endif %}
    return o;
}
```

### 3.3 生成器（Python）

```python
#!/usr/bin/env python3
"""shader_cooker.py — 变体展开 + 编译 + 缓存"""
import itertools, hashlib, subprocess, pathlib, json, sys
from jinja2 import Environment, FileSystemLoader

TEMPLATES = pathlib.Path("templates")
OUT       = pathlib.Path("generated")
CACHE     = pathlib.Path(".shadercache")

env = Environment(loader=FileSystemLoader(TEMPLATES),
                  trim_blocks=True, lstrip_blocks=True)

def variant_key(name: str, keywords: list[str]) -> str:
    """变体的稳定标识：名字 + 排序后的关键字集合"""
    return f"{name}|{'|'.join(sorted(keywords))}"

def content_hash(text: str) -> str:
    return hashlib.blake2b(text.encode(), digest_size=16).hexdigest()

def expand(name: str, keywords: list[str], slots: dict) -> pathlib.Path:
    """按关键字集合渲染一份 HLSL（内容哈希命名 → 天然去重）"""
    tmpl = env.get_template(f"{name}.hlsl.j2")
    src  = tmpl.render(keywords=keywords, slots=slots, template_name=name)
    h    = content_hash(src)
    out  = OUT / f"{name}.{h[:12]}.hlsl"
    OUT.mkdir(parents=True, exist_ok=True)
    out.write_text(src, encoding="utf-8")
    return out

def compile_spirv(src: pathlib.Path, entry: str, stage: str,
                  defines: list[str]) -> pathlib.Path:
    """DXC → spirv-val → spirv-opt（带内容哈希缓存）"""
    h   = content_hash(src.read_text() + "|" + entry + "|" + stage + "|".join(defines))
    spv = CACHE / f"{src.stem}.{h[:12]}.spv"
    if spv.exists():
        return spv                                    # 缓存命中

    CACHE.mkdir(parents=True, exist_ok=True)
    tmp = CACHE / f"{src.stem}.{h[:12]}.raw.spv"

    cmd = ["dxc", "-spirv", "-fspv-target-env=vulkan1.3",
           "-T", f"{stage}_6_6", "-E", entry]
    for d in defines:
        cmd += ["-D", d]
    cmd += ["-Fo", str(tmp), str(src)]

    r = subprocess.run(cmd, capture_output=True, text=True)
    if r.returncode != 0:
        print(f"[FAIL] {src}\n{r.stdout}\n{r.stderr}")
        sys.exit(1)

    subprocess.run(["spirv-val", "--target-env", "vulkan1.3", str(tmp)], check=True)
    # 注意：不要整体 strip debug —— 反射依赖 OpName
    subprocess.run(["spirv-opt", "-O", "--strip-nonsemantic",
                    "-o", str(spv), str(tmp)], check=True)
    tmp.unlink()
    return spv

def main():
    targets = [
        ("gbuffer.frag", ["USE_EMISSIVE", "USE_VELOCITY"]),
        ("gbuffer.frag", ["USE_VELOCITY"]),
        ("gbuffer.frag", []),
        ("depthonly.vert", []),
    ]
    slots    = {"per_material": 2}
    manifest = {}

    for name, kws in targets:
        key  = variant_key(name, kws)
        base = name.rsplit(".", 1)[0]
        src  = expand(base, kws, slots)
        if name.endswith(".frag"):
            stage, entry = "ps", "PSMain"
        else:
            stage, entry = "vs", "VSMain"
        manifest[key] = str(compile_spirv(src, entry, stage, kws))

    (OUT / "manifest.json").write_text(json.dumps(manifest, indent=2))
    print(f"[OK] cooked {len(manifest)} variants")

if __name__ == "__main__":
    main()
```

### 3.4 生成器的工程要点

| 要点 | 说明 |
|------|------|
| **幂等** | 相同输入 → 相同输出。不嵌时间戳、绝对路径 |
| **内容哈希命名** | `name.<hash>.hlsl`，天然去重 |
| **缓存** | hash 命中就跳过编译（CCache 思想） |
| **保留中间产物** | 编译失败时能拿到展开后的源码 |
| **头部警告注释** | `⚠ GENERATED — DO NOT EDIT` |
| **并行** | 变体之间无依赖，用 `multiprocessing` / `xargs -P` |
| **不要提交生成物** | 提交 `manifest.json` 即可（或按需提交以加速 CI） |

## 4. L2：语言内泛型（模板）

### 4.1 HLSL 2021 模板

需要 **Shader Model 6.6+** 与 DXC 的 HLSL 2021 模式（`-HV 2021`）。

```hlsl
// 类型参数化：一份代码，多种精度
template<typename T>
T Lerp3(T a, T b, T t) { return a + (b - a) * t; }

// 非类型模板参数：编译期常量参与代码生成
template<uint SampleCount>
float4 ResolveMSAA(Texture2DMS<float4, SampleCount> tex, uint2 uv) {
    float4 acc = 0;
    for (uint i = 0; i < SampleCount; ++i)
        acc += tex.Load(uv, i);
    return acc / SampleCount;
}

float4 PSMain(VSOut i) : SV_Target {
    if (g_MsaaCount == 4) return ResolveMSAA<4>(g_Msaa4, i.pos.xy);
    if (g_MsaaCount == 8) return ResolveMSAA<8>(g_Msaa8, i.pos.xy);
    return ResolveMSAA<1>(g_Msaa1, i.pos.xy);
}
```

```bash
dxc -HV 2021 -T ps_6_6 -E PSMain -spirv -fspv-target-env=vulkan1.3 -Fo out.spv in.hlsl
```

**HLSL 2021 模板的能力边界**：

| 能力 | 支持 |
|------|------|
| 函数模板（类型 + 非类型参数） | ✅ |
| 显式特化 / 重载决议 | ✅ |
| 结构体模板 | ✅（有限） |
| 变参模板（parameter pack） | ⚠️ 有限 |
| SFINAE / concepts / 约束 | ❌ |
| `if constexpr` | ❌（用 `if` + 编译期常量，编译器会折叠） |

### 4.2 Slang 泛型 + 接口（表达力最强）

Slang 把 Rust/C# 风格的泛型与接口带进了着色器语言：

```slang
// ---- 接口：约束"光照模型必须实现什么" ----
interface ILight {
    float3 Evaluate(float3 P, float3 N, float3 V);
}

// ---- 实现一 ----
struct PointLight : ILight {
    float3 position; float3 color; float radius;
    float3 Evaluate(float3 P, float3 N, float3 V) {
        float3 L = position - P;
        float  d = length(L);
        float  atten = saturate(1.0 - d / radius);
        return color * saturate(dot(N, L / d)) * atten;
    }
}

// ---- 实现二 ----
struct DirectionalLight : ILight {
    float3 direction; float3 color;
    float3 Evaluate(float3 P, float3 N, float3 V) {
        return color * saturate(dot(N, -direction));
    }
}

// ---- 泛型函数：一次编写，按 T 特化 ----
float3 ShadeAll<T : ILight>(T light, Surface s) {
    return light.Evaluate(s.P, s.N, s.V) * s.albedo;
}

[shader("fragment")]
float4 PSMain(VSOut i) : SV_Target {
    Surface s = DecodeSurface(i);
    float3 c  = ShadeAll(PointLight(g_LightPos, g_LightColor, g_LightRadius), s);
    c        += ShadeAll(DirectionalLight(g_SunDir, g_SunColor), s);
    return float4(c, 1);
}
```

| Slang 额外能力 | 说明 |
|---------------|------|
| 泛型 + 接口约束 | 类型安全的编译期多态 |
| `extension` | 给已有类型加方法（类似 Rust trait） |
| 自动微分 `bwd_diff` | 可微渲染、材质参数反解 |
| `__target_switch` | 一份源码按目标展开不同实现 |
| 存在类型（existential） | 运行期动态分派（有开销） |
| 一等反射 API | 见 [03 篇](03-反射方案对比与选型.md) |

### 4.3 GLSL 的处境

GLSL **没有模板**。可选手段：宏（L0）、`const` 常量折叠、SPIR-V 特化常量（L4），或者换 Slang / HLSL。

## 5. L3：IR 级变换

这一层"在编译中间做手脚"，最强也最容易出事。

### 5.1 三种落点

```
源码 ─[前端]─▶ AST ─▶ IR ─▶ SPIR-V ─▶ GPU
                 │      │       │
                 │      │       └─ ③ SPIR-V Pass（SPIRV-Tools）
                 │      └─ ② LLVM Pass（见 04 篇）/ Slang IR Pass
                 └─ ① AST 变换（Clang LibTooling / Slang）
```

| 落点 | 工具 | 能看到什么 | 适合做什么 |
|------|------|-----------|-----------|
| ① AST | Clang LibTooling、Slang | 完整源码语义 | 代码生成、语义标注、跨阶段校验 |
| ② LLVM IR | LLVM Pass 插件 | 优化过的 IR | 通用优化、插桩 |
| ③ SPIR-V | SPIRV-Tools 自定义 Pass、反射 `Change*` | 最终产物 | 改绑定、注入资源、裁剪 |

### 5.2 SPIR-V 层注入（示意）

```cpp
// 用 SPIRV-Tools 的 IR 层给模块注入一个全局 UBO
#include "source/opt/ir_context.h"
#include "source/opt/instruction.h"

void InjectGlobalUBO(spvtools::opt::IRContext* ctx,
                     uint32_t ptrTypeId, uint32_t varId) {
    auto* module = ctx->module();

    // 1) 追加 OpVariable 到全局变量区
    module->AddGlobalValue(
        std::make_unique<spvtools::opt::Instruction>(
            ctx, spv::Op::OpVariable, ptrTypeId, varId,
            std::initializer_list<spvtools::opt::Operand>{
                { SPV_OPERAND_TYPE_STORAGE_CLASS,
                  { uint32_t(spv::StorageClass::Uniform) } } }));

    // 2) 追加 DescriptorSet / Binding 装饰
    ctx->AddDecoration(spv::Op::OpDecorate, varId,
                       spv::Decoration::DescriptorSet, 0);
    // 3) 把 varId 加进每个 OpEntryPoint 的 interface 列表
    // 4) 更新 module header 的 bound
    // 5) ctx->InvalidateAnalyses(...)
}
```

> ⚠️ **SPIR-V 注入的合规清单**（漏一条就 `spirv-val` 报错）：
> 1. 新全局变量必须加入 `OpEntryPoint` 的 interface 列表（SPIR-V ≥ 1.4）
> 2. 所需 Capability / Extension 必须声明
> 3. ID 必须小于 module header 的 `bound`（记得同步更新）
> 4. 指令顺序必须符合模块逻辑分段（见 [01 篇](01-SPIR-V模块结构与反射原理.md)）
> 5. 装饰必须位于注解段（在类型/变量声明之前）

**更省事的替代**：注册自定义 Pass 到 `spvtools::Optimizer`，让它处理杂务：

```cpp
spvtools::Optimizer opt(SPV_ENV_VULKAN_1_3);
opt.RegisterPass(spvtools::MakeUnique<MyInjectPass>());
opt.Run(spv.data(), spv.size(), &outSpv);
```

### 5.3 反射驱动的"后处理元编程"

别忘了 [02 篇](02-SPIRV-Reflect库详解与实战.md) §11 的 `Change*` 系列——它本质是**最轻量的 SPIR-V 层元编程**：

```cpp
// 编译后统一把所有资源重排到引擎约定的 set 布局
for (auto* b : bindings) {
    uint32_t newSet = DecideSetByConvention(b->name, b->descriptor_type);
    spvReflectChangeDescriptorBindingNumbers(&m, b, b->binding, newSet);
}
```

成本远低于写 SPIR-V Pass，**优先用它**。

## 6. L4：运行时特化常量（性价比之王）

### 6.1 原理

```hlsl
[[vk::constant_id(0)]] const bool  ENABLE_TAA = true;
[[vk::constant_id(1)]] const int   SAMPLE_COUNT = 4;
[[vk::constant_id(2)]] const float TAA_BLEND = 0.1;

float4 PSMain(VSOut i) : SV_Target {
    float4 c = g_Scene.Sample(g_Sampler, i.uv);
    if (ENABLE_TAA)                       // ← 常量 → 分支被折叠
        c = lerp(c, g_History.Sample(g_Sampler, i.uv), TAA_BLEND);
    return c;
}
```

```
┌──────────────────────────────────────────────────────┐
│  一份 SPIR-V ──[VkSpecializationInfo]──▶ N 份机器码    │
│                                                       │
│  驱动在创建管线时内联常量 → 常量传播 → 死代码消除        │
│  → 效果≈每个值一个变体，但你只存了一份 SPIR-V            │
└──────────────────────────────────────────────────────┘
```

### 6.2 Vulkan 侧

```cpp
struct SpecValue { uint32_t id; std::vector<std::byte> bytes; };

// entries / data 必须在 vkCreateGraphicsPipelines() 返回后才可释放
struct SpecInfoStorage {
    std::vector<VkSpecializationMapEntry> entries;
    std::vector<std::byte>                data;
    VkSpecializationInfo                  info{};

    void Build(std::span<const SpecValue> values) {
        for (auto& v : values) {
            uint32_t off = (uint32_t)data.size();
            data.insert(data.end(), v.bytes.begin(), v.bytes.end());
            entries.push_back({ .constantID = v.id,
                                .offset     = off,
                                .size       = (uint32_t)v.bytes.size() });
        }
        info = { .mapEntryCount = (uint32_t)entries.size(),
                 .pMapEntries   = entries.data(),
                 .dataSize      = data.size(),
                 .pData         = data.data() };
    }
};

VkPipelineShaderStageCreateInfo stageCI{
    .sType               = VK_STRUCTURE_TYPE_PIPELINE_SHADER_STAGE_CREATE_INFO,
    .stage               = VK_SHADER_STAGE_FRAGMENT_BIT,
    .module              = shaderModule,
    .pName               = "PSMain",
    .pSpecializationInfo = &specStorage.info,
};
```

> ⚠️ **生命周期陷阱**：`VkSpecializationInfo` 及其数组必须在管线创建**返回之后**才能释放。用 RAII 容器持有，别用栈上临时对象接引用。

### 6.3 特化常量的边界

| ✅ 能用于 | ❌ 不能用于 |
|---------|-----------|
| 开关分支 `if (ENABLE_X)` | 改变资源绑定（set/binding 编译期固定） |
| 循环次数（会被展开） | 改变结构体成员布局 |
| 数组长度（UBO 内数组、局部数组） | 改变描述符数组元素数（Vulkan 要求布局兼容） |
| 数值参数（阈值、混合系数） | 改变输入输出变量的存在与否（会破坏 VS/PS 匹配） |

> **与反射的配合**：用 `spvReflectEnumerateSpecializationConstants()` 拿 `constant_id`，**不要手写**。手写 ID 一旦与 shader 漂移，行为静默错误。

### 6.4 L0 vs L4

| 维度 | 宏 `#define`（L0） | 特化常量（L4） |
|------|------------------|---------------|
| 产物数量 | N 个 SPIR-V | **1 个 SPIR-V** |
| 编译时间 | O(N) | O(1) |
| 磁盘/内存 | O(N) | O(1) |
| PSO 数量 | N | N（每套常量一个 PSO） |
| 能否改变资源绑定 | ✅ | ❌ |
| 能否改变结构体布局 | ✅ | ❌ |

**结论**：**能用特化常量解决的，绝不用变体**。只有"改变资源/布局"的需求才必须走变体。

## 7. 变体爆炸：问题与治理

### 7.1 数学

```
N 个独立 bool 关键字 → 2^N 个理论组合

N=5   →      32
N=10  →    1024
N=16  →   65536   ← 真实项目常见量级
N=20  → 1048576   ← 不可行
```

一个真实 PBR shader 的关键字示例：

```
USE_NORMAL_MAP, USE_ROUGHNESS_MAP, USE_METALLIC_MAP, USE_AO_MAP,
USE_EMISSIVE, USE_EMISSIVE_MAP, USE_ALPHA_TEST, USE_DOUBLE_SIDED,
USE_CLEARCOAT, USE_CLOTH, USE_SHEEN, USE_ANISOTROPY,
USE_VERTEX_COLOR, USE_INSTANCING, USE_MORPH_TARGET,
SHADING_MODEL_*, BLEND_MODE_*, ...
```

### 7.2 危害

| 危害 | 表现 |
|------|------|
| 编译时间 | 从秒级到小时级；CI 阻塞 |
| 包体 | GB 级 SPIR-V |
| 运行时 PSO | 每个 PSO 创建耗时毫秒级 → 卡顿 |
| 内存 | 数千个 PSO 常驻 |
| 首帧卡顿 | 首次用到某变体时才编译 |
| 维护 | 没人知道哪些变体真的被用到 |

### 7.3 五条治理策略

#### 策略 A：按需收集（Demand-driven）——**必做**

不要生成笛卡尔积。从**材质资产**反查实际用到的组合：

```cpp
std::set<KeywordSet> CollectFromAssets(const MaterialDB& db) {
    std::set<KeywordSet> unique;
    for (const Material& m : db.materials)
        unique.insert(m.ComputeKeywords());   // 由材质参数推导
    return unique;   // 例如 16 个关键字 → 实际只有 200 种组合
}
```

**效果**：理论 65536 → 实际 200。投入产出比最高的一步。

#### 策略 B：二进制去重（Content dedup）——**必做**

不同关键字组合可能产出**完全相同**的 SPIR-V（比如某宏只影响未被使用的代码路径）：

```cpp
std::unordered_map<std::string /*sha of spv*/, VariantId> dedup;
for (auto& [key, spvBytes] : cooked) {
    auto h = blake3(spvBytes);
    if (auto it = dedup.find(h); it != dedup.end())
        alias[key] = it->second;      // 指向同一份产物
    else
        dedup[h] = Store(spvBytes);
}
```

> ⚠️ **去重要在 strip 之后**。SPIR-V 若残留 `OpSource` 的**源码文件路径**，会导致相同代码产出不同字节。先统一路径或 `--strip-nonsemantic`，再算哈希。

#### 策略 C：特化常量替代宏（见 §6）——**强烈推荐**

#### 策略 D：Uber Shader + 动态分支——**谨慎**

```hlsl
if (g_Flags & FLAG_NORMAL_MAP)
    normal = DecodeNormal(g_NormalMap.Sample(g_Sampler, i.uv));
```

| 优点 | 缺点 |
|------|------|
| 产物数 = 1 | **寄存器压力上升**（所有分支的资源都按上限占用） |
| 编译极快 | 分支发散（wave 内不一致 → 两边都执行） |
| 热更新友好 | 占用率（occupancy）下降 |

> **适用**：分支短、分支间资源开销相近、目标平台寄存器充裕。
> **不适用**：分支里各自用了大量纹理采样器。

#### 策略 E：Bindless + 数据驱动——**未来方向**

```hlsl
// 不再用 #ifdef 决定"用不用法线贴图"
uint normalIdx = material.normalMapIdx;      // 0 = 无
if (normalIdx != 0)
    normal = DecodeNormal(g_BindlessTex[normalIdx].Sample(g_Sampler, uv));
```

分支仍在（性能同策略 D），但**彻底消除了变体维度的资源差异**，配合 GPU-Driven 效果最好。

### 7.4 策略决策链

```
        所有关键字
             │
             ▼
   ① 能改成特化常量吗？ ──是──▶ 特化常量（1 份 SPIR-V）
             │ 否
             ▼
   ② 是否改变资源/布局？ ──否──▶ 特化常量 或 动态分支
             │ 是
             ▼
   ③ 必须走变体 ──▶ 按需收集组合 + 二进制去重 + 哈希缓存
```

## 8. Permutation 系统设计

### 8.1 Key 的设计

```cpp
struct ShaderKey {
    std::string              source;      // 相对路径（绝不含绝对路径）
    std::string              entryPoint;
    VkShaderStageFlags       stage;
    std::vector<std::string> keywords;    // ★ 必须排序：{A,B} == {B,A}
    std::vector<uint32_t>    specValues;  // 若参与 PSO 缓存

    auto operator<=>(const ShaderKey&) const = default;
};

uint64_t HashShaderKey(const ShaderKey& k) {
    uint64_t h = 14695981039346656037ull;          // FNV-1a
    auto mix = [&](std::string_view s) {
        for (char c : s) { h ^= (unsigned char)c; h *= 1099511628211ull; }
    };
    mix(k.source);
    mix(k.entryPoint);
    uint64_t st = k.stage;
    mix({ reinterpret_cast<const char*>(&st), sizeof(st) });
    for (auto& kw : k.keywords) { h ^= 0x9e; mix(kw); }  // ★ 分隔符防拼接歧义
    return h;
}
```

> ⚠️ **分隔符很重要**：`{"AB"}` 与 `{"A","B"}` 直接拼接会产生相同字符串。加分隔符或逐元素哈希。

### 8.2 Cooker 流水线

```
┌──────────────────────────────────────────────────────────┐
│ ① 扫描     遍历 shaders/ 与 templates/                     │
│            提取 #pragma keyword(NAME)、模板清单              │
├──────────────────────────────────────────────────────────┤
│ ② 收集     从材质/场景资产收集真实组合 + 强制变体清单          │
├──────────────────────────────────────────────────────────┤
│ ③ 去重     关键字集合规范化（排序）                           │
├──────────────────────────────────────────────────────────┤
│ ④ 展开     L1 模板 → 中间 .hlsl（内容哈希命名）              │
├──────────────────────────────────────────────────────────┤
│ ⑤ 编译     并行：dxc/glslang → spirv-val → spirv-opt        │
├──────────────────────────────────────────────────────────┤
│ ⑥ 反射     SPIRV-Reflect → .refl + .h（绑定头）             │
├──────────────────────────────────────────────────────────┤
│ ⑦ 二进制去重 相同 SPIR-V 合并，写别名表                       │
├──────────────────────────────────────────────────────────┤
│ ⑧ 清单     manifest.json  {key → {spv, refl, header, hash}}│
├──────────────────────────────────────────────────────────┤
│ ⑨ PSO 预热 离线预编译 / 在线异步 + VkPipelineCache           │
└──────────────────────────────────────────────────────────┘
```

### 8.3 并行编译

```cpp
void CookAll(std::span<VariantJob> jobs) {
    std::atomic<int> failed{0};
    std::for_each(std::execution::par, jobs.begin(), jobs.end(), [&](VariantJob& j) {
        if (TryLoadFromCache(j)) return;                 // ① 内容哈希缓存
        auto src = ExpandTemplate(j);                    // ② 展开
        if (!RunCompilerSubprocess(j, src)) { ++failed; return; }  // ③ 编译
        auto refl = Reflect(j.spvPath);                  // ④ 反射
        WriteHeader(j, refl);                            // ⑤ 生成绑定头
    });
    if (failed) throw std::runtime_error(std::format("{} variants failed", failed.load()));
}
```

> **建议**：用**子进程**调编译器而非链接编译器库。好处：崩溃隔离、易并行、升级只换 exe。

### 8.4 PSO 预热

```cpp
class PipelineWarmer {
public:
    void WarmAsync(std::vector<ShaderKey> keys) {
        worker_ = std::jthread([this, ks = std::move(keys)] {
            for (auto& k : ks) {
                auto pso = CreatePipeline(k);       // 写入共享 VkPipelineCache
                std::lock_guard lk(mu_);
                cache_[k] = pso;
            }
        });
    }

    VkPipeline Acquire(const ShaderKey& k) {
        {
            std::shared_lock lk(mu_);
            if (auto it = cache_.find(k); it != cache_.end()) return it->second;
        }
        LogWarn("PSO cache miss (not warmed): {}", k.source);
        return CreatePipeline(k);                   // 同步创建 → 可能卡顿
    }
private:
    std::shared_mutex mu_;
    std::unordered_map<ShaderKey, VkPipeline> cache_;
    std::jthread worker_;
};
```

`VkPipelineCache` 应**持久化到磁盘**（`vkGetPipelineCacheData`），下次启动直接复用驱动编译结果。

## 9. 最佳实践清单

### 9.1 该做 ✅

| # | 实践 | 理由 |
|---|------|------|
| 1 | 关键字统一前缀（`USE_` / `ENABLE_`） | 便于工具扫描 |
| 2 | 变体 key 用**排序后**的关键字集合 | 保证稳定一致 |
| 3 | 编译产物用**内容哈希**命名 | 天然去重与缓存 |
| 4 | 先 `spirv-val` 再反射 | 反射不校验合法性 |
| 5 | 优先特化常量，其次变体 | 大幅降低产物数量 |
| 6 | 从资产反查真实组合 | 避免笛卡尔积 |
| 7 | 生成物头部写 `⚠ GENERATED` | 防止手改 |
| 8 | 保留中间 `.hlsl` | 编译失败时能调试 |
| 9 | 用子进程调编译器 | 崩溃隔离 + 易并行 |
| 10 | 持久化 `VkPipelineCache` | 消除首帧卡顿 |
| 11 | CI 里 diff `.refl` 输出 | 意外改布局立刻暴露 |
| 12 | `constant_id` 从 SPIR-V 读 | 防止手写 ID 漂移 |

### 9.2 不该做 ❌

| # | 反模式 | 后果 |
|---|--------|------|
| 1 | 生成笛卡尔积式全变体 | 编译小时级 |
| 2 | 用宏做类型参数化 | 类型不安全、难调试 |
| 3 | 用特化常量改资源绑定 | 布局不兼容，行为未定义 |
| 4 | 生成物提交 Git 且允许手改 | 下次生成被覆盖 |
| 5 | 哈希里混入绝对路径 | 构建不可重现 |
| 6 | 栈上临时 `VkSpecializationInfo` | 悬垂引用 |
| 7 | `spirv-opt -O` 后仍依赖变量名 | `name` 被 strip |
| 8 | 变体 key 未排序 | 同一组合产出两份 |
| 9 | 运行时同步创建 PSO | 卡顿 |
| 10 | 把"语义"（PerFrame/PerMaterial）藏进宏名 | 反射读不到，见 [06 篇](06-实战-反射驱动的布局与描述符生成.md) |

## 10. 小结

| 层次 | 手段 | 关键价值 |
|------|------|---------|
| L0 宏 | `#define` / `#ifdef` | 简单开关、片段拼接 |
| L1 模板生成 | Jinja2 / 自研 | permutation 展开、胶水代码 |
| L2 泛型 | HLSL 2021 template / Slang generic | 类型参数化，类型安全 |
| L3 IR 变换 | LLVM Pass / SPIR-V Pass / 反射 `Change*` | 统一注入、批量改写 |
| L4 特化常量 | `VkSpecializationInfo` | ⭐ 一份 SPIR-V，N 种行为 |

**一句话决策链**：

> 能 uniform 就别特化常量 → 能特化常量就别变体 → 必须变体就按需生成 + 去重 + 缓存。
