# UE渲染源码导读 — 延迟渲染路径主线

> 本文档是「UE渲染源码导读」系列文档的第 **5** 篇。把分散在十几个文件里的可见性、剔除、绘制、光照环节，收敛成**一条主干 + 三个旁路入口**，回答：是否存在统一入口？各环节什么时机执行？先后逻辑是什么？基于 UE 5.8.2 源码实测，行号可直接下断点验证。

## 1. 有没有统一入口？——有，且只有一个

```
游戏线程                              渲染线程
────────                             ────────
BeginRenderingViewFamily
(SceneRendering.cpp:5354)
  │ SendAllEndOfFrameUpdates  ← 保证 proxy 数据最新
  │ FSceneRenderProcessor::CreateSceneRenderers
  │   (SceneRenderBuilder.cpp:475 → new FDeferredShadingSceneRenderer :516)
  │ Execute → ENQUEUE_RENDER_COMMAND ──────► RenderViewFamily_RenderThread
                                              (SceneRendering.cpp:5215)
                                                │
                                                ▼
                          ★ FDeferredShadingSceneRenderer::Render ★
                            (DeferredShadingRenderer.cpp:1822, 约2600行)
                                                │
                                                ▼
                                   CleanupViewFamilies_RenderThread
                                   (SceneRendering.cpp:5235)
```

**结论**：延迟路径的一切都在 `Render()` 这一个函数体内按顺序展开（任务化部分用 Begin/End 对夹持）。你不需要「猜入口」——从 :1822 开始顺序读，遇到函数调用先查本篇 §3 的主线表，属于主线就继续，属于分支就查 06 篇决定跳不跳。

⚠️ 它确实长（约 2600 行），但**结构是线性的**：可见性 → 几何 → 光照 → 半透明 → 后处理。真正让它显得乱的是内嵌的分支判断与 lambda，不是流程本身。

## 4. 三个旁路入口（主线之外的「暗门」）

主线函数不是唯一会执行渲染代码的地方。看到「不知道谁调的」渲染逻辑时，查这三个机制：

| 旁路 | 接口 | 挂接点 | 典型用户 |
|------|------|--------|---------|
| **SceneViewExtension** | `ISceneViewExtension`（BeginRenderViewFamily / PrePostProcessPass_RenderThread 等回调） | CreateSceneRenderers（SceneRenderBuilder.cpp:475 附近）、:4268 | 插件、后处理扩展、XR |
| **SceneExtension** | `ISceneExtension` / `GetSceneExtensionsRenderers()` | Render() 内 `PreInitViews`（:2007）等 | 5.x 新扩展机制，RenderCurve（发丝曲线）等 |
| **MeshPassProcessor 家族** | `FPassProcessorManager::CreateMeshPassProcessor` | 任何 Pass 需要把 FMeshBatch 翻译成命令时 | 39 个 EMeshPass 各自的处理类 |

**「想画哪就画哪」的真相**：并不是任何地方都能画——所有绘制最终都要么走 EMeshPass 的 MDC 管线，要么走 RDG 全屏/compute Pass 挂在 `Render()` 的某个锚点上。感到「迷宫」通常是因为从某个 Pass 内部往外读；改成从 `Render()` 锚点往里读，迷宫就变成树。

## 5. 时序上的三个「反直觉」点

| 反直觉点 | 真相 |
|---------|------|
| 遮挡剔除在可见性阶段就用，HZB 却在 BasePass 后才建 | 可见性用的是**上帧**的遮挡数据（OcclusionCullTask）；本帧 `RenderOcclusion` 产出给**下帧**用——跨帧流水线 |
| 阴影深度在 BasePass 之后 (:3291) | 5.8 主线把阴影渲染排在 BasePass 后、光照前（任务化后时序重排过）；前向路径才提前到 :2925 |
| 动态网格收集的「开始」和「汇合」隔了几百行 | LaunchVisibilityTasks 里启动并行任务，:2218 Finish 汇合——中间的主线程代码与收集是并发的，不是顺序依赖 |

## 6. 小结

| 要点 | 说明 |
|------|------|
| 唯一主干 | `FDeferredShadingSceneRenderer::Render`（:1822），线性五段：可见性→几何→光照→透明→后处理 |
| 阅读方向 | 从锚点表往里读，不要从 Pass 内部往外读 |
| 旁路三暗门 | SceneViewExtension / SceneExtension / MeshPassProcessor 家族 |
| 反直觉时序 | 遮挡跨帧复用；阴影在 BasePass 后；动态收集是异步任务 |
| 验证方法 | :1822 下断点 + 锚点表逐行 F10 + cvar 关分支瘦身 |
